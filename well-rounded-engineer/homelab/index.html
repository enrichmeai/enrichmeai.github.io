Home lab: learn by doing

Reading builds vocabulary; running things builds judgement. These labs each start from a real, public repository you clone and run on a laptop or a small cloud budget. Do them in order or pick the ones for the area you are going deep in. Each has a "done when" so you know you finished, and each ends with you writing up what broke.

Set up once

  • Machine: a laptop with 16 GB RAM is enough for most labs; an old PC or mini PC running Linux makes a good always-on lab server.
  • Tools: Git, Docker (or Podman), kubectl, kind or k3d, Helm, Python 3.12+, a JDK 21, and the gcloud CLI.
  • Cloud, carefully: new Google Cloud accounts get free-trial credit, and BigQuery has a free sandbox. Set a budget alert on day one and delete what you are not using.
  • Your lab journal: one Git repository with a folder per lab and a README in each: goal, steps, numbers you measured, what broke and why. This becomes your portfolio.
mkdir -p ~/lab && cd ~/lab && git init
kind create cluster --name lab        # a Kubernetes cluster in Docker
kubectl get nodes

Lab 1: microservices on Kubernetes

Repo: GoogleCloudPlatform/microservices-demo (Online Boutique: about ten services in several languages).

kubectl apply -f https://raw.githubusercontent.com/GoogleCloudPlatform/microservices-demo/main/release/kubernetes-manifests.yaml
kubectl get pods -w
kubectl port-forward deploy/frontend 8080:8080     # open http://localhost:8080

Then: delete a pod and watch it come back; scale a deployment; set a memory limit too low and read the OOMKilled event; break a readiness probe.

Done when: you can explain, from kubectl describe and events alone, why each thing you broke failed. Tabs: Kubernetes, Microservices.

Lab 2: observability stack

Repo: prometheus-community/helm-charts (kube-prometheus-stack) on the Lab 1 cluster; or open-telemetry/opentelemetry-demo with Docker Compose.

helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm install monitoring prometheus-community/kube-prometheus-stack -n monitoring --create-namespace
kubectl port-forward -n monitoring svc/monitoring-grafana 3000:80

# or the OpenTelemetry demo (traces, metrics, logs across many services)
git clone https://github.com/open-telemetry/opentelemetry-demo
cd opentelemetry-demo && docker compose up -d

Then: write one PromQL alert for an error ratio, make it fire on purpose, and find the failing span in a trace.

Done when: an alert you wrote fires for a failure you caused, and you traced it to the line of code. Tabs: Observability, Ops Tooling.

Lab 3: service mesh

Repo: istio/istio (its samples/bookinfo application) on a kind cluster.

# after downloading an Istio release and adding istioctl to PATH
istioctl install --set profile=default -y
kubectl label namespace default istio-injection=enabled
kubectl apply -f samples/bookinfo/platform/kube/bookinfo.yaml
istioctl analyze

Then: turn on STRICT mTLS, split traffic 90/10 between review versions, inject a delay, and write an AuthorizationPolicy that denies one service.

Done when: you can produce, then explain, a 403 and a 503 from proxy logs. Tab: Service Mesh.

Lab 4: GitOps and Helm

Repo: argoproj/argocd-example-apps, with Argo CD installed on your cluster.

kubectl create namespace argocd
kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
kubectl port-forward -n argocd svc/argocd-server 8443:443

Then: fork the example repo, point an Argo CD application at its Helm example, change a value in Git and watch it roll out; change something by hand in the cluster and watch Argo CD report the drift.

Done when: every change reaches the cluster only through a Git commit. Tabs: Helm Charts, DevOps.

Lab 5: a data pipeline on your laptop

Repo: dbt-labs/jaffle_shop_duckdb (dbt's demo project, running on DuckDB, no cloud account).

git clone https://github.com/dbt-labs/jaffle_shop_duckdb
cd jaffle_shop_duckdb
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
dbt build                       # seeds, models and tests
dbt docs generate && dbt docs serve

Then: add an incremental model, a unit test and a test that fails on purpose; load a public dataset of your own (BigQuery public datasets or the Registry of Open Data on AWS) into DuckDB and model it in layers.

Done when: running the pipeline twice gives identical results, and a bad row is rejected and counted, not silently nulled. Tabs: Data Engineering, dbt, Data Libraries.

Lab 6: orchestrate it

Repo: apache/airflow, using the official Docker Compose quick start from the Airflow documentation.

Then: write a DAG that runs Lab 5's dbt build daily, uses data intervals, retries, and records a run summary; backfill a week; make one day fail and rerun just that day.

Done when: a rerun of any single day changes nothing else, and a missing run raises an alert. Tab: Airflow DAGs.

Lab 7: Culvert against emulators

Repo: enrichmeai/culvert. Its stack runs against local emulators, so no cloud account is needed.

git clone https://github.com/enrichmeai/culvert
pip install 'culvert[gcp]'
# then follow the repository's docs to start the emulators and run a pipeline

Then: write a small pipeline against the BlobStore and Warehouse contracts, run it on the emulators, then read the conformance suite to see what every adapter must guarantee.

Done when: your pipeline code imports no cloud SDK. Tabs: Culvert, Frameworks vs AI.

Lab 8: events with Kafka

Repo: the official apache/kafka Docker image, plus a producer and consumer you write.

docker run -d --name kafka -p 9092:9092 apache/kafka:latest   # pin a version once it works
docker exec -it kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --create --topic judgment.landed --partitions 3

Then: write a consumer that is idempotent, kill it mid-batch, restart it and prove no event was applied twice; add a dead-letter topic for a poison message.

Done when: you can show consumer lag rising and recovering, and duplicates handled. Tab: Kafka.

Lab 9: RAG and an MCP server

Repos: anthropics/anthropic-quickstarts for starting points, modelcontextprotocol/python-sdk for the server, and the pgvector/pgvector Docker image for search.

docker run -d --name pg -e POSTGRES_PASSWORD=pw -p 5432:5432 pgvector/pgvector:pg17
pip install "mcp[cli]" anthropic psycopg

Then: chunk and embed a small document set, build hybrid search, answer questions with citations, write 30 golden questions and measure recall; wrap Lab 5's run records in a read-only MCP server and use it from Claude Code.

Done when: your eval score is written down, and the MCP tool says "could not read" when the database is stopped. Tabs: RAG, MCP.

Lab 10: infrastructure as code

Start: HashiCorp's "Get started with Docker" Terraform tutorial (local, free), then a small Google Cloud project behind a budget alert.

Then: declare a bucket, a dataset and a Cloud Run job in Terraform; rename a resource with a moved block; import something created by hand; destroy everything at the end.

Done when: terraform plan shows no changes after apply, and nothing you made is left running. Tabs: Terraform, Cloud Run.

Lab 11: payments in test mode

Start: a Stripe or Razorpay test account. Stripe's CLI forwards test webhooks to your laptop.

stripe login
stripe listen --forward-to localhost:8080/webhooks/stripe
stripe trigger payment_intent.succeeded

Then: build order → checkout → signature check → webhook; replay the same webhook twice; simulate a timeout and reconcile.

Done when: no replay or retry can mark an order paid twice. Tab: Payment Gateways.

Lab 12: game day

Repo: chaos-mesh/chaos-mesh on your kind cluster, or just kubectl delete and tc by hand.

Then: with a friend, one person breaks something on the Lab 1–3 stack without saying what; the other detects, mitigates and writes a blameless postmortem using the template on the SRE tab.

Done when: the postmortem has at least one action that adds a guard (an alert, a test, a limit). Tab: SRE.

Rules for lab work

  • Predict, then run: write down what you expect before each experiment; the gap is the lesson.
  • Break it on purpose: every lab includes a failure you cause and explain.
  • Measure: record latency, cost, row counts or recovery time, not impressions.
  • Use AI as the bulldozer, not the driver: let it scaffold and explain, then verify everything it claims by running it.
  • Pin versions once something works, and note them in the README so the lab is repeatable.
  • Clean up: kind delete cluster, docker compose down -v, terraform destroy, and check the cloud billing page.
  • Write it up: a short post or README per lab. Teaching what you learned is the final test that you learned it.

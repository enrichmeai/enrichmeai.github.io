Culvert

enrichme.ai's open-source, cloud-agnostic data pipeline framework for Java and Python. Pipeline code depends on a set of contracts, and adapters implement them for each cloud. Every fact on this tab is taken from the Culvert page on enrichmeai.com, which is checked daily against Maven Central and PyPI; read it there for the current release.

The idea

Pipelines are defined once against a language-neutral contract set (sixteen contracts plus a metrics record: BlobStore, Warehouse, Source, Sink, JobControlRepository and eleven more), realised as Java interfaces and Python Protocols. Adapters implement the contracts for each cloud, and every adapter must pass the same conformance suite, or it is not an adapter. Swap the cloud, keep the logic.

LayerIs
Your business logicWritten once; depends only on the contracts, never on a cloud SDK
The contractsJava interfaces and Python Protocols from one spec
Cloud adaptersSwappable implementations that pass the shared conformance suite

This is the "framework, not generated boilerplate" argument from the Frameworks vs AI tab made concrete: one contract and one test suite instead of a hand-written cloud integration in every pipeline.

Design choices

  • Java owns Beam: the Dataflow/Beam execution layer is Java; legacy Python Beam is not carried forward. The two languages deliberately do different jobs.
  • dbt, reused: transformation is SQL and macros, packaged once; there is deliberately no Java transform module.
  • Local-first: the whole stack runs against emulators, so you can develop and test without a cloud account.
  • No silent defaults: Warehouse.loadFromUri requires a LoadOptions, because a defaulted write disposition let a re-run silently double its data.
  • Honest failure: reconciliation runs before the target is written, so a failed load cannot be reported as succeeded.
  • Not a replacement for Beam, Airflow or dbt: they are engines, and Culvert is a framework around them.

Install (Python)

# core contracts only, no cloud SDKs
pip install culvert
# + BigQuery, GCS, Pub/Sub, Secret Manager, observability
pip install 'culvert[gcp]'
# + Airflow-side DAG factory / operators / sensors, or dbt
pip install 'culvert[orchestration]'
pip install 'culvert[transform]'
# + StageClaim on PostgreSQL
pip install 'culvert[postgres]'
# test fixtures, and the conformance suite for your own adapters
pip install 'culvert[tester]'
pip install 'culvert[contract-tests]'
# gcp + orchestration + transform
pip install 'culvert[all]'
# adapters are discovered through entry points
from data_pipeline_core import autoconfig
blob_store = autoconfig.discover().first("blob_store")
# -> GcsBlobStore, when culvert[gcp] is installed

Python 3.10 or newer.

Features worth knowing

  • Job control: run state through JobControlRepository on BigQuery, DynamoDB, Athena or PostgreSQL; a read-only culvert command line (runs, run, entities, failures, adapters).
  • StageClaim (PostgreSQL): one stage of one unit for one period cannot start twice.
  • InputReadiness (PostgreSQL): names each expected input that is missing, failed or still running, rather than counting rows.
  • Orchestration: a cloud-neutral DAG model rendered to Airflow/Composer or Cloud Run jobs, with stage gates and a concurrency ceiling.
  • Schema files: an entity's columns, types, required flags, classification, masking, ranges and allowed values in YAML or JSON, loaded with the same rules in Java and Python.
  • BlobStore.head(uri): size, version token and metadata without reading the object, for loaders that must be idempotent by object version.
  • BigQueryWarehouse.merge(): upserts with one MERGE and refuses a key that is not a target column.

Status, stated plainly

  • Released in both languages on Maven Central and PyPI, under Apache 2.0 (the earliest releases were MIT).
  • Ran end to end on a real GCP project (Cloud Run to BigQuery, event-driven) before release; that run caught eight production-only bugs every local test had passed.
  • Culvert is pre-1.0: read the changelog's upgrade notes before moving between versions.
  • A book on its design is in progress.

Pin a version in your build, and verify any API against that version's sources, not against main.

Levels: what to expect

1 Foundation

  • Explain contracts, adapters and the conformance suite
  • Install culvert with the right extras or add the Maven artifacts
  • Use an adapter through auto-discovery instead of a cloud SDK

2 Practitioner

  • Write pipeline code against BlobStore, Warehouse and job control
  • Use LoadOptions, head() and merge() for idempotent loads
  • Run and test against emulators locally

3 Senior

  • Design pipelines whose logic is cloud-neutral
  • Add an adapter that passes the conformance suite
  • Use StageClaim, InputReadiness and orchestration gates

4 Expert

  • Shape the contract spec and its evolution
  • Lead adoption across teams and clouds
  • Contribute adapters for new clouds (Azure)

Each level includes the ones before it. See Start here for what the levels mean.

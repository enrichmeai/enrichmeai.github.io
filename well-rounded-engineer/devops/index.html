DevOps

Getting a change from a laptop to production safely and keeping it running: Git, CI/CD, releases, observability, incidents and supply-chain security.

Git you will use daily

git switch -c feat/123-short-name origin/main
git add -p                         # stage hunk by hunk
git commit -m "fix: reject unparseable order dates"
git fetch origin && git rebase origin/main
git push -u origin feat/123-short-name
git push --force-with-lease        # after a rebase; never plain --force

git log --oneline --graph -20
git log -S "parse_date" --oneline  # commits that added/removed a string
git blame -L 40,60 file.py
git diff origin/main...HEAD        # what my branch changes
git show <sha>:path/file           # a file at a revision
git stash push -m wip; git stash pop
git restore file                   # discard local edits
git revert <sha>                   # undo a merged commit safely
git bisect start BAD GOOD          # binary-search a regression
git worktree add ../wt2 -b other origin/main   # second checkout
git reflog                         # find "lost" commits

Branching & PR habits

  • Trunk-based: short-lived branches off main, merged within a day, behind feature flags if unfinished.
  • One concern per PR. If the title needs "and", split it.
  • Protect main: PR required, checks required, no force pushes.
  • Commit messages say why, not only what. Conventional prefixes (feat:, fix:, chore:) help changelogs.
  • Review for behaviour: tests that would fail without the change, error paths, what happens when a dependency is down.
  • Promote artefacts, not branches: build once, tag the image with the commit SHA, deploy that same image to each environment.

GitHub Actions → GCP (no keys)

name: deploy
on:
  push: { branches: [main] }
permissions:
  contents: read
  id-token: write              # needed for Workload Identity Federation
concurrency: { group: deploy-${{ github.ref }}, cancel-in-progress: false }
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-java@v6
        with: { distribution: temurin, java-version: 21, cache: gradle }
      - run: ./gradlew test
  deploy:
    needs: test
    runs-on: ubuntu-latest
    environment: prod          # environment secrets, protection rules
    steps:
      - uses: actions/checkout@v7
      - uses: google-github-actions/auth@v3
        with:
          workload_identity_provider: ${{ vars.WIF_PROVIDER }}
          service_account: ${{ vars.DEPLOY_SA }}
      - uses: google-github-actions/setup-gcloud@v3
      - run: |
          IMG=asia-south1-docker.pkg.dev/${{ vars.GCP_PROJECT }}/apps/api:${GITHUB_SHA::12}
          gcloud auth configure-docker asia-south1-docker.pkg.dev --quiet
          docker build -t "$IMG" . && docker push "$IMG"
          echo "IMG=$IMG" >> "$GITHUB_ENV"
      - uses: google-github-actions/deploy-cloudrun@v3
        with: { service: api, region: asia-south1, image: "${{ env.IMG }}" }

The major versions shown were current in November 2026; check each action's latest release. For security, pin third-party actions to a full commit SHA rather than a tag. A workflow-level paths: filter on a required check can leave a PR waiting forever; skip inside the job instead.

Release strategies

StrategyHowWhen
RollingReplace instances a few at a timeDefault for stateless services
Blue/greenRun old and new side by side, switch traffic at onceFast rollback, needs double capacity
CanarySend a small % to the new version, watch metrics, increaseRisky changes with good metrics
Feature flagShip code dark, turn it on per user or percentageSeparating deploy from release
Expand / contractAdd the new schema, migrate, remove the old in a later releaseDatabase changes with zero downtime

Every release needs a rollback you have practised. A database migration that cannot be rolled back makes the whole release one-way.

Blue-green, in plain words

Think of a theatre with two stages. The audience watches the blue stage while the crew builds the next show on the green one. When green is ready and rehearsed, you swing the audience over in one move. If something goes wrong, you swing them straight back: blue is still standing.

  • Before the switch: green gets the same checks real users would give it, through a private URL or a test route.
  • The switch is all at once, so a fault reaches every user, but only until you switch back, which takes seconds.
  • Keep blue running until you trust green. Pulling it down early leaves you with no way back.
# Kubernetes: a Deployment per colour,
# labelled version: blue / version: green.
# The Service's selector picks the live one.
kubectl patch service shop-api \
  -p '{"spec":{"selector":{"version":"green"}}}'
# Roll back: patch it back to "blue".

# Cloud Run: deploy green with no traffic
gcloud run deploy api --image=…:4b1c2d0 \
  --no-traffic --tag=green
# test https://green---api-xxxxx.a.run.app
gcloud run services update-traffic api \
  --to-tags=green=100

The price: for a while you run two full copies, so you pay for twice the capacity. Read Martin Fowler's BlueGreenDeployment.

Canary, in plain words

Miners once took a canary underground: if the air turned bad, the bird showed it first. A canary release works the same way. A small share of real users gets the new version, you watch closely, and only when it looks healthy do you send more.

  • Go in steps: for example 1%, then 5%, 25%, 50%, 100%, pausing at each step long enough to learn something.
  • Compare the canary with the old version running at the same time, not with yesterday: error rate, p95 and p99 latency, saturation, and one number the business cares about.
  • Decide the stop rule before you start. "Roll back if errors rise above 1% for five minutes" is a rule; "keep an eye on it" is not.
# Kubernetes Gateway API:
# weights on an HTTPRoute
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: shop-api
spec:
  parentRefs:
    - name: public-gw
  rules:
    - backendRefs:
        - name: shop-api-stable
          port: 8080
          weight: 95
        - name: shop-api-canary
          port: 8080
          weight: 5

# Cloud Run: move traffic by revision
gcloud run services update-traffic api \
  --to-revisions=api-00042-xyz=5,api-00041-abc=95

With Istio, the same weights live on a VirtualService (see Service Mesh). Read the Gateway API guide to HTTP traffic splitting and Fowler's CanaryRelease.

Choosing between them, and the hard parts

  • Pick blue-green when you need an instant, whole switch and an instant way back, and you can afford two copies for a while. It suits releases you can test fully before users arrive.
  • Pick canary when you have enough traffic and good metrics to learn from a small slice. At 1% of 100 requests an hour you learn almost nothing, so a quiet service is better served by blue-green and a thorough test.
  • The database is the hard part of both. Old and new versions run at the same time against the same data, so every schema change has to work for both: add first, move the data, remove the old shape in a later release (expand and contract).
  • Sessions and caches: a user who bounces between versions may see two behaviours, so keep a user on one version where that matters, and make sure caches and queues can be read by both.
  • Feature flags are a separate tool. A deploy puts code on servers; a flag decides who sees the feature. Used together, a canary checks the code is healthy and a flag controls the release to users.
  • Automate it once you understand it. Argo Rollouts and Flagger run blue-green and canary steps on Kubernetes with automatic analysis, and Harness has both built in. Do it by hand a few times first, so you know what the tool is deciding for you.

Whichever you pick, rehearse the rollback before you need it. The way back is the part of a release that matters most when things go wrong, and it is usually the part nobody practised.

Observability

  • Logs say what happened (structured JSON, with a request or run ID). Metrics say how much and how often. Traces say where the time went across services.
  • Golden signals: latency, traffic, errors, saturation. RED for services (rate, errors, duration); USE for resources (utilisation, saturation, errors).
  • SLI: a measured ratio, e.g. requests under 500 ms ÷ all requests. SLO: the target, e.g. 99.5% over 30 days. Error budget: the 0.5% you may spend on releases and incidents.
  • Alert on symptoms users feel (SLO burn rate), not on every CPU spike. Every alert needs an owner and a runbook.
  • Know "nothing there" from "cannot see": a check whose data source is down must report unknown, not zero or green.

Incident response

  1. Declare it early and name an incident lead. One channel, one timeline.
  2. Mitigate before you diagnose: roll back, fail over, scale up, turn the flag off.
  3. Communicate status on a schedule, even "no change".
  4. Write down what you saw and did, with timestamps, as you go.
  5. Review blamelessly afterwards: what happened, why the system allowed it, which guard would have caught it. Track the follow-ups to done.

Supply-chain & secrets

  • No long-lived keys: Workload Identity Federation for CI, service accounts for workloads.
  • Secrets in a secret manager, injected at runtime. Never in Git, images, logs or CI output.
  • Least privilege: one service account per workload, with only the roles it uses.
  • Dependency updates automated (Dependabot or Renovate), with tests gating them.
  • Scan code (SAST), dependencies (SCA), images (Trivy) and committed secrets (gitleaks, GitHub secret scanning).
  • Know what you ship: SBOMs and signed images (cosign) make "are we affected by CVE-X?" a query, not a hunt.

Measuring delivery

DORA metricQuestion
Deployment frequencyHow often do we ship to production?
Lead time for changesCommit to production: how long?
Change failure rateWhat share of deploys cause a failure?
Failed deployment recovery time (formerly time to restore)How fast do we recover from a failed deploy?
Deployment rework rateWhat share of deploys are unplanned fixes for a production incident?

Speed and stability rise together when changes are small, tested and easy to roll back.

Twelve-factor, short version

  • One codebase, many deploys; config in the environment, not the code.
  • Dependencies declared and pinned; backing services (DB, queue) attached by URL.
  • Build, release and run are separate steps; the same build goes to every environment.
  • Processes are stateless and disposable: fast start, graceful shutdown on SIGTERM.
  • Logs are an event stream to stdout; the platform collects them.
  • Admin tasks (migrations, backfills) run as one-off processes from the same release.
  • Dev and prod as similar as possible: same images, same database engine.

Levels: what to expect

1 Foundation

  • Use Git daily: branch, commit, rebase, PR
  • Read a CI run and find why it failed
  • Roll back a deploy

2 Practitioner

  • Write CI/CD workflows with caching and keyless cloud auth
  • Add structured logs, metrics and alerts
  • Take part in incident response

3 Senior

  • Design release strategies (canary, blue/green, flags)
  • Define SLOs and alerting on symptoms
  • Improve DORA metrics; lead post-incident reviews

4 Expert

  • Build an internal developer platform and golden paths
  • Set delivery and reliability standards for the organisation
  • Lead culture change toward small, safe, frequent releases

What data engineering is

The concepts behind the tools: what data engineers build, the shape of every pipeline, and the properties that make data trustworthy. Read this before the dbt, DAG and BigQuery tabs.

In one paragraph

Data engineering is building and running the systems that move data from where it is produced to where it is used, and making it correct, current, documented and affordable on the way. Source systems (apps, files, APIs, sensors, public datasets) produce data in their own shapes and at their own pace. Analysts, dashboards, machine-learning models, AI features and products need it in a shape they can query and trust. The data engineer owns the path between them: getting it in, keeping a faithful copy, reshaping it, checking it, delivering it, and knowing at any moment whether it is right.

A pipeline that runs is not the goal. The goal is data that people can rely on without asking the data engineer first.

Running underneath every stage: orchestration (DAGs), data quality and observability, security and access, data management (catalog, lineage, retention), infrastructure as code (Terraform), and ordinary software engineering (tests, CI, reviews).

This stage model follows Fundamentals of Data Engineering by Joe Reis and Matt Housley, a good first book on the subject.

Batch vs streaming

  • Batch: process a bounded chunk (yesterday, one file, one partition) on a schedule. Simple, cheap, easy to rerun. Latency of minutes to a day.
  • Streaming: process events continuously as they arrive. Latency of seconds, but harder: ordering, late events, state, exactly-once.
  • Micro-batch: small batches every few minutes. Often the practical middle.
  • Choose by the consumer's need, not by fashion. Most reporting and legal research is fine with daily or hourly batch.

ETL vs ELT

  • ETL: extract, transform in a separate engine, then load the result. Common when the warehouse was expensive or small.
  • ELT: extract, load the raw data into the warehouse, transform there with SQL (dbt). The modern default on BigQuery and similar.
  • Why ELT wins today: you keep the raw data, so a bug in a transform is fixed by rerunning it, not by re-ingesting from a source that may have changed or gone.
  • Heavy non-SQL work (parsing PDFs, images, large joins outside the warehouse) still goes to an engine built for it, such as Dataflow or Spark.

File formats: CSV and JSON are easy but untyped and slow to scan. Parquet and ORC are columnar, compressed and typed, best for analytics. Avro suits row-by-row streams with schema evolution.

Layers: each one has one job

LayerAlso calledRule
Raw / landingbronze, RAWByte-for-byte copy of what the source published. Never edited. Lets you replay everything.
Operational / stagingODP, stagingThe raw data as typed tables, as published. Renamed and cast, not reinterpreted.
Foundation / conformedsilver, FDP, intermediateCleaned, deduplicated, keyed, versioned, joined to reference data. Structure added once, reused by many.
Consumable / martsgold, CDP, martsShaped for one named use: a dashboard, an API, a model's features.

Derivation runs one way: each layer reads only the layer below. A product that reads from a downstream serving database creates a cycle and should be refused.

Modelling basics

  • Grain: what one row means ("one judgment", "one order line per day"). State it for every table; most bugs are grain confusion.
  • Keys: a natural key from the source and, where needed, a surrogate key you generate. Never reuse or renumber a key that others store.
  • Normalised (many narrow tables, no repetition) suits OLTP. Dimensional (facts plus dimensions, a star schema) suits analytics. One big table is fine on BigQuery for a single use.
  • Facts are events with measures (a decision, a payment). Dimensions describe them (court, judge, date).
  • Slowly changing dimensions: type 1 overwrites; type 2 keeps history with valid-from/valid-to rows (dbt snapshots).

Properties of a good pipeline

  • Idempotent: running it twice for the same input gives the same result. Overwrite a partition or MERGE on a key; never blindly append.
  • Incremental: processes only what is new or changed, decided from evidence (a watermark, ETag or ledger), not "we visited it".
  • Backfillable: any past period can be rerun on purpose.
  • Late data aware: records can arrive after their period; reprocess a lookback window.
  • Schema-change safe: a new or renamed source column fails loudly or is handled deliberately, never silently dropped.
  • Observable: every run records what it read, wrote, skipped and failed, with counts.
  • Resumable: a failure midway restarts from where it stopped, not from zero.

Data quality

DimensionExample check
CompletenessRow count matches the source; no unexpected NULLs
ValidityDates parse; codes are in the allowed set
UniquenessOne row per key at the stated grain
ConsistencyEvery court code exists in the court table
FreshnessNewest record is within the expected age
AccuracyValues match the source on a sample

The worst quality failure is a silent one: a parse that turns bad dates into NULL, or a monitor that reports 0 when its source was unreachable. Reject or count what you cannot read, and report "unknown" rather than a confident zero.

Ingestion patterns

  • Full snapshot: copy everything each time. Simple; fine for small tables.
  • Incremental by watermark: fetch rows changed since the last updated_at or ID.
  • Change data capture (CDC): read the source database's change log for inserts, updates and deletes (Datastream, Debezium).
  • File drops: compare source and destination listings (names, sizes, ETags) and copy only the difference.
  • Events: producers publish to a queue (Pub/Sub, Kafka); consumers process at-least-once, so handle duplicates.
  • APIs: paginate, respect rate limits, keep the raw response, and record the error body when a call fails.

Governance & responsibility

  • Ownership: every table has a named owner and a description.
  • Lineage: you can say which sources feed a column and which products a change will affect.
  • Access: least privilege per dataset; serving systems get read-only access.
  • Personal and sensitive data: know where it is, mask or restrict it, honour deletion and suppression orders.
  • Licences: respect source terms; carry attribution (for example CC-BY) into every published output.
  • Retention and cost: decide how long each layer is kept and who pays for scans.
  • Contracts: agree the schema and meaning of anything another team reads, and change it on purpose.

A worked example, end to end

Indian court judgments published as open data, served to lawyers through a search API.

  1. Source: two public mirrors publish judgment metadata as Parquet and JSON archives, partitioned by year, under CC-BY-4.0. Partitions are sometimes republished in place.
  2. Ingest (LAND): a Cloud Run job compares the mirror's listing with the GCS landing bucket and copies only new or changed objects. It records examined, copied, already-current and failed counts.
  3. Raw: the bucket keeps the originals byte for byte, so anything later can be replayed.
  4. Load (ODP): each landed file becomes rows in BigQuery tables, with run ID and load time, exactly as published.
  5. Transform (FDP): dbt cleans and conforms: parses two date formats (and rejects what does not parse), computes a stable judgment key, deduplicates republished rows, joins court reference data, and runs tests.
  6. Consumable (CDP): a dbt model shapes exactly what the search API needs, with a contract on its columns.
  7. Serve: a loader upserts that table into Postgres on the stable key, without renumbering existing IDs that links and legal records depend on. The API reads Postgres read-only.
  8. Orchestrate and observe: a scheduler ticks daily; an orchestrator runs each stage when its input is ready and appends every state change to a ledger, so "what happened on 2026-09-19?" has an answer.

Every tab in this guide appears somewhere in that path. That is why a data engineer needs breadth.

Questions a data engineer always asks

  • What does one row mean, and what is its key?
  • What happens if this runs twice? If it fails halfway?
  • What does this return when the source is down, and can anyone tell that apart from "no data"?
  • How will I know it is late or wrong before a user does?
  • Who reads this table, and what breaks for them if I change it?
  • How much does a run cost, and what makes it grow?
  • Can I rebuild it from raw if I have to?

Glossary

  • Partition: a slice of a table (by date or year) that queries can skip.
  • Watermark: the point up to which data is known to be processed.
  • Backfill: deliberately reprocessing a past period.
  • Upsert / MERGE: insert new rows, update existing ones, by key.
  • Lineage: the graph of which data feeds which.
  • Data contract: an agreed schema and meaning between producer and consumer.
  • Freshness: how old the newest data is.
  • SCD: slowly changing dimension, how history of descriptive attributes is kept.
  • CDC: change data capture, streaming a database's changes.
  • DAG: directed acyclic graph, the dependency order of tasks.
  • Ledger: an append-only record of every run and state change.

Levels: what to expect

1 Foundation

  • Explain the lifecycle and the layers
  • Load a file into a warehouse and query it
  • Write a simple, idempotent transformation

2 Practitioner

  • Build incremental, tested pipelines end to end
  • Choose batch vs streaming and ingestion patterns
  • Model data at a stated grain with keys and tests

3 Senior

  • Design a data platform: layers, contracts, orchestration, observability
  • Own data quality and reconciliation across sources
  • Plan cost, retention and governance

4 Expert

  • Set data architecture and standards across the organisation
  • Lead migrations between platforms without losing trust
  • Shape data products and their contracts with consumers

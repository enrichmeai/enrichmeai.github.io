Service mesh and Istio

A service mesh moves service-to-service concerns (encryption, identity, retries, traffic splitting, telemetry, access policy) out of application code and into the platform. What a mesh does, when it is worth it, how Istio works in sidecar and ambient modes, the resources you will write, and how to debug it. Background on Microservices and Kubernetes.

What a mesh gives you

CapabilityWhat it meansWithout a mesh
Mutual TLSEvery call between services encrypted and authenticated with workload certificates, rotated automaticallyTLS and certificates managed in each service
Workload identity and authorisationPolicies such as "only the frontend's service account may call GET /api/*"Network policies (IP-based) and code checks
Traffic managementCanary weights, header-based routing, mirroring, timeouts, retriesLoad balancer rules or code
ResilienceCircuit breaking, outlier detection, connection limitsLibraries such as Resilience4j in each service
ObservabilityUniform request metrics, access logs and trace spans for every hopInstrumentation in every service
Egress controlOnly allow-listed external hosts reachableFirewall and proxy rules

North-south traffic (clients into the platform) is the gateway's job; east-west traffic (services to each other) is the mesh's. Business logic belongs in neither.

When it is worth it

Good reasons

  • Many services on Kubernetes, often in several languages.
  • A requirement for encrypted, authenticated traffic between all services (zero trust, compliance).
  • Frequent canary or progressive releases.
  • Uniform telemetry without changing every service.

Reasons to wait

  • A handful of services, or a modular monolith.
  • Serverless platforms such as Cloud Run, which already give service identity (IAM) and TLS.
  • No one to own and upgrade the mesh: it is a critical system in every request path.

Istio architecture

  • Control plane, istiod: turns your configuration into proxy configuration, issues workload certificates, and pushes both to the data plane.
  • Data plane, sidecar mode: an Envoy proxy injected into every pod intercepts its inbound and outbound traffic. Full L7 features per pod, at the cost of a proxy per pod.
  • Data plane, ambient mode: a per-node ztunnel provides L4 mTLS and identity for all pods without sidecars; optional waypoint proxies add L7 features (routing, L7 authorisation) only where needed. Lower overhead and no pod restarts to join.
  • Gateways: Envoy deployments at the edge for ingress and egress, configured with the Kubernetes Gateway API or Istio's own Gateway resource.

On Google Cloud, Cloud Service Mesh offers a managed, Istio-based mesh for GKE and other environments.

Install and enrol workloads

# sidecar mode
istioctl install --set profile=default -y
kubectl label namespace legal istio-injection=enabled
kubectl rollout restart deploy -n legal        # pods get sidecars on restart

# ambient mode
istioctl install --set profile=ambient -y
kubectl label namespace legal istio.io/dataplane-mode=ambient   # no restart needed
istioctl waypoint apply -n legal --enroll-namespace             # add L7 where needed

istioctl analyze -n legal                      # check configuration for problems

In production, install and upgrade Istio through Helm charts or your platform's managed offering, from Git, with canary upgrades of the control plane (revisions).

The resources you will write

ResourcePurpose
Gateway + HTTPRoute (Kubernetes Gateway API)Ingress and routing; the recommended API for new setups
VirtualServiceIstio routing rules: matches, weights, retries, timeouts, fault injection
DestinationRulePolicies for a destination: subsets (versions), load balancing, connection pools, outlier detection, TLS
PeerAuthenticationmTLS mode for workloads: STRICT or PERMISSIVE
AuthorizationPolicyWho may call what: by service account, namespace, path, method, JWT claims
RequestAuthenticationValidate end-user JWTs at the proxy
ServiceEntryRegister external services so they can be reached and controlled
SidecarLimit which services a sidecar knows about, to reduce memory and config size
TelemetryTune metrics, access logs and tracing

Security: mTLS and authorisation

# mesh-wide strict mTLS (after a PERMISSIVE migration period)
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata: { name: default, namespace: istio-system }
spec:
  mtls: { mode: STRICT }
---
# only the frontend may call the API, and only GET on /api/*
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata: { name: legal-api-allow, namespace: legal }
spec:
  selector: { matchLabels: { app: legal-api } }
  action: ALLOW
  rules:
    - from:
        - source: { principals: ["cluster.local/ns/web/sa/frontend"] }
      to:
        - operation: { methods: ["GET"], paths: ["/api/*"] }
---
# validate end-user JWTs at the proxy
apiVersion: security.istio.io/v1
kind: RequestAuthentication
metadata: { name: jwt, namespace: legal }
spec:
  selector: { matchLabels: { app: legal-api } }
  jwtRules:
    - issuer: "https://auth.example.com/"
      jwksUri: "https://auth.example.com/.well-known/jwks.json"

Once any ALLOW policy selects a workload, everything not allowed is denied. Roll out in a test namespace first. The service still checks object-level permissions: the mesh knows which service is calling, not whether this user owns this case.

Traffic: canary, retries, timeouts

apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata: { name: legal-api, namespace: legal }
spec:
  host: legal-api
  subsets:
    - { name: v1, labels: { version: v1 } }
    - { name: v2, labels: { version: v2 } }
  trafficPolicy:
    connectionPool: { http: { http1MaxPendingRequests: 100 } }
    outlierDetection:                     # eject failing pods for a while
      consecutive5xxErrors: 5
      interval: 10s
      baseEjectionTime: 30s
---
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata: { name: legal-api, namespace: legal }
spec:
  hosts: [legal-api]
  http:
    - timeout: 3s
      retries: { attempts: 2, perTryTimeout: 1s, retryOn: "5xx,connect-failure" }
      route:
        - { destination: { host: legal-api, subset: v1 }, weight: 90 }
        - { destination: { host: legal-api, subset: v2 }, weight: 10 }
# the same split with the Gateway API
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: legal-api, namespace: legal }
spec:
  parentRefs: [{ name: legal-gateway }]
  hostnames: ["api.example.com"]
  rules:
    - backendRefs:
        - { name: legal-api-v1, port: 8080, weight: 90 }
        - { name: legal-api-v2, port: 8080, weight: 10 }

Put retries in one place, mesh or application, not both: retries multiplied at every layer turn a slowdown into a retry storm. Retry only idempotent requests.

Egress control

# with outbound traffic policy REGISTRY_ONLY, only registered hosts are reachable
apiVersion: networking.istio.io/v1
kind: ServiceEntry
metadata: { name: indian-kanoon-mirror, namespace: legal }
spec:
  hosts: ["api.example-mirror.org"]
  ports: [{ number: 443, name: https, protocol: TLS }]
  resolution: DNS
  location: MESH_EXTERNAL

Route egress through an egress gateway when you need a fixed exit point, central logging, or to combine with Cloud NAT and firewall rules.

Observability with a mesh

  • Metrics for every request, such as istio_requests_total and request duration histograms, labelled by source, destination and response code.
  • Kiali draws the live service graph with health and traffic.
  • Tracing: proxies create spans, but your application must forward the trace headers (traceparent) from incoming to outgoing requests, or traces break at every service.
  • Access logs per proxy, tunable with the Telemetry resource.
# 5xx rate per destination service
sum by (destination_service) (rate(istio_requests_total{response_code=~"5.."}[5m]))
  / sum by (destination_service) (rate(istio_requests_total[5m]))

Debugging

istioctl analyze -A                                # config problems across namespaces
istioctl proxy-status                              # is every proxy in sync with istiod?
istioctl proxy-config routes   deploy/legal-api -n legal
istioctl proxy-config clusters deploy/legal-api -n legal
istioctl x describe pod <pod> -n legal             # which policies apply to this pod
kubectl logs <pod> -c istio-proxy -n legal         # sidecar access log
SymptomUsually
503 with UF / URX flagsUpstream failing or refusing; check the app and outlier ejection
503 NRNo route: VirtualService or HTTPRoute mismatch
Connection reset after enabling STRICTA client outside the mesh still sends plain text
403 RBAC: access deniedAn AuthorizationPolicy denies it (or no ALLOW rule matches)
App fails at startup calling a dependencySidecar not ready yet; hold the app until the proxy starts
Jobs never completeSidecar keeps the pod alive; use native sidecars or ambient mode
Pod has no sidecarNamespace not labelled, or pod created before the label

Meshes compared

MeshNotes
IstioMost features; sidecar or ambient; large community; more to learn and operate
Cloud Service MeshGoogle-managed, Istio-based, integrated with GKE and Cloud Monitoring
LinkerdSimpler and lightweight, with its own Rust proxy; fewer features
Cilium service mesheBPF-based networking with mesh features, often without sidecars
ConsulSpans Kubernetes and VMs, with service discovery

Adopting a mesh safely

  1. Install in a non-production cluster; enrol one namespace.
  2. Start with PERMISSIVE mTLS and observe traffic in Kiali and metrics.
  3. Move namespaces to STRICT once every client is in the mesh.
  4. Add AuthorizationPolicies service by service, tested in CI against a cluster.
  5. Move retries, timeouts and canaries into the mesh deliberately, removing duplicates from code.
  6. Keep all mesh config in Git, delivered by GitOps, with istioctl analyze in CI.
  7. Plan control-plane upgrades with revisions and canary them like any critical release.

Levels: what to expect

1 Foundation

  • Explain mTLS, workload identity and east-west vs north-south traffic
  • Read VirtualService, DestinationRule and AuthorizationPolicy resources
  • Find a pod's sidecar logs and proxy status

2 Practitioner

  • Enrol namespaces and roll out STRICT mTLS safely
  • Write authorisation policies and canary routes
  • Debug 503s and RBAC denials with istioctl

3 Senior

  • Decide whether a mesh is worth it, and sidecar vs ambient
  • Design zero-trust service-to-service security
  • Run mesh upgrades with revisions; keep config in GitOps

4 Expert

  • Own the mesh platform across clusters and environments
  • Design multi-cluster and multi-network meshes
  • Set network security strategy combining mesh, gateway and cloud controls

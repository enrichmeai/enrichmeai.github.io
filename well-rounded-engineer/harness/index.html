Harness CI/CD

Harness is a software delivery platform: CI, continuous delivery with verification and rollback, GitOps, feature flags, and more, organised as pipelines. This tab walks through Harness CI and Harness CD in depth, an end-to-end pipeline to Google Cloud, troubleshooting, and how to use Harness as a blueprint for every team.

Building blocks

  • Account → organisation → project: the hierarchy for access control and shared resources.
  • Pipeline: stages run in order or parallel; each stage has steps.
  • Stage types: Build (CI), Deploy (CD), Approval, Custom.
  • Service: what you deploy (manifests, artefact).
  • Environment and infrastructure definition: where you deploy (dev, prod; a cluster or project).
  • Connector: a stored, permissioned link to GitHub, GCP, a registry or a cluster.
  • Delegate: an agent running in your infrastructure that executes tasks, so Harness never needs inbound access.
  • Secrets: stored in Harness or referenced from Google Secret Manager or Vault.
  • Templates: versioned step, stage and pipeline templates teams reuse.
  • Triggers: start pipelines on Git events, artefact pushes or schedules.

Pipeline as code (shape)

pipeline:
  name: shop-api
  identifier: shop_api
  orgIdentifier: default
  projectIdentifier: shop
  stages:
    - stage:
        name: Build
        identifier: build
        type: CI
        spec:
          cloneCodebase: true
          execution:
            steps:
              - step:
                  type: Run
                  name: Test
                  identifier: test
                  spec:
                    shell: Sh
                    command: ./gradlew test
    - stage:
        name: Approve prod
        identifier: approve
        type: Approval
        spec:
          execution:
            steps:
              - step:
                  type: HarnessApproval
                  name: Founder approval
                  identifier: founder
                  timeout: 1d
                  spec:
                    approvers:
                      userGroups: [prod_approvers]
                      minimumCount: 1
    - stage:
        name: Deploy prod
        identifier: deploy_prod
        type: Deployment
        spec:
          # service, environment, infrastructure and strategy
          # (rolling / canary / blue-green) go here
          ...

This shows the structure only. Build pipelines in the Harness editor first and copy its YAML into Git, since exact step specs vary by module and version.

Deploying safely

  • Strategies: rolling, canary and blue-green built in, with automatic rollback steps.
  • Continuous verification: compares metrics and logs (from Prometheus, Datadog, Cloud Monitoring and others) of the new version against the old, and fails the stage when they degrade.
  • Approvals: Harness user groups, or Jira/ServiceNow tickets.
  • Freeze windows: block deployments during set periods.
  • Policy as code: OPA policies on pipelines (e.g. "prod deploys must have an approval stage and a verification step").
  • Audit trail: who ran what, with which inputs, when.

Harness vs GitHub Actions

GitHub ActionsHarness
StrengthCI next to the code; huge action marketplaceCD: strategies, verification, approvals, governance at scale

GovernanceEnvironments, rulesets, required reviewersOPA policies, templates, RBAC, freeze windows, audit
FitsSmall and medium teams; code-centric workflowsMany teams and services needing a standard, governed path to production

A common split: GitHub Actions builds and tests on every PR; Harness promotes the built artefact through environments.

End to end: commit to production on Google Cloud

  1. Trigger: a push or merged pull request on GitHub starts the pipeline (webhook trigger on main; PR trigger runs CI only).
  2. CI stage: clone, restore cache, compile and run tests (with test intelligence), run scanners, then build the image once and push it to Artifact Registry tagged with the commit SHA.
  3. Deploy to dev: a CD stage deploys that exact image to the dev environment (GKE or Cloud Run) with a rolling strategy.
  4. Verify dev: smoke tests and continuous verification against dev metrics and logs.
  5. Approval: a named group approves prod (or a policy auto-approves outside freeze windows).
  6. Deploy to prod: canary or blue-green with the same artefact; verification watches error rate and latency; automatic rollback on degradation.
  7. Notify and record: Slack/email notification, deployment recorded with who, what, which commit, and the verification result.

Build once, promote the same artefact. Rebuilding per environment means prod runs something that was never tested.

Harness CI in depth

  • Build infrastructure: Harness Cloud (hosted machines), your Kubernetes cluster (pods per build), your own VMs, or a local runner. Choose by network access, cost and isolation.
  • Codebase: the repo connector and clone settings for the pipeline; each CI stage can clone automatically.
  • Run step: any shell command in a container image you choose (eclipse-temurin:21, python:3.12).
  • Test step with test intelligence: selects only tests affected by the change, and reports results in the UI (JUnit XML).
  • Background step: a service the build needs, such as Postgres or a Kafka broker, running beside the steps.
  • Build and push steps: build an image and push it to Artifact Registry, Docker Hub or another registry.
  • Caching: Cache Intelligence for common build tools, or explicit save/restore cache steps to GCS or S3.
  • Plugins: Drone plugins and many GitHub Actions can run as steps.
  • Outputs: steps export variables for later steps and stages, e.g. the image tag.

A CI stage (shape)

- stage:
    name: Build
    identifier: build
    type: CI
    spec:
      cloneCodebase: true
      platform: { os: Linux, arch: Amd64 }
      runtime: { type: Cloud, spec: {} }       # Harness Cloud machines
      execution:
        steps:
          - step:
              type: Run
              name: Unit tests
              identifier: unit_tests
              spec:
                image: eclipse-temurin:21
                shell: Sh
                command: ./gradlew test
                reports:
                  type: JUnit
                  spec:
                    paths: ["**/build/test-results/test/*.xml"]
          - step:
              type: BuildAndPushGAR
              name: Image
              identifier: image
              spec:
                connectorRef: gcp_bld
                host: asia-south1-docker.pkg.dev
                projectID: my-proj
                imageName: apps/shop-api
                tags: [<+codebase.shortCommitSha>]

Field names follow Harness's YAML at the time of writing; generate the stage in the editor and compare before committing.

Harness CD in depth

  • Service: what you deploy: the artefact source (Artifact Registry image), manifests (Kubernetes YAML, Helm chart, Kustomize) and variables.
  • Environment: dev or prod, marked pre-production or production, with environment-level overrides (replicas, URLs, secrets).
  • Infrastructure definition: the exact target: a GKE cluster and namespace, or a GCP project and region for serverless.
  • Deployment types: Kubernetes, Native Helm, serverless targets, VMs over SSH/WinRM, Tanzu, ECS, and custom deployments for anything else. Check Harness's current list for Google Cloud targets such as Cloud Run and Cloud Functions.
  • Execution: generated from the chosen strategy, editable step by step; failure strategies say what to do on each kind of error (retry, rollback, manual intervention).
  • Rollback: a rollback section per stage, run automatically on failure or on a failed verification.
  • Input sets and overlays: saved sets of runtime inputs (which service, which tag) so one pipeline serves many services.
  • Multi-service and multi-environment deployments from a single stage.

Deployment strategies in Harness

StrategyHow Harness runs itUse when
RollingReplaces pods or instances gradually; rollback restores the previous releaseDefault for stateless services
CanaryDeploys a small canary set, verifies, then rolls out fully and deletes the canaryRisky changes with good metrics
Blue-greenDeploys the new version as a stage set, tests it, then swaps trafficInstant switch and rollback; capacity for two copies
Basic / customYour own steps (shell, HTTP, Terraform, approvals)Targets without a built-in type

Connecting Harness to Google Cloud

  • GCP connector with OIDC (workload identity federation) where your plan supports it, so no service account key is stored. Otherwise inherit credentials from a delegate running in GKE with Workload Identity.
  • One service account per environment with only the roles deploys need (Artifact Registry reader/writer, GKE developer or Cloud Run developer, and service account user on the runtime account).
  • Delegates run inside your network (for example a GKE namespace), so private clusters and services are reachable without opening inbound access. Run at least two for availability.
  • Secrets referenced from Google Secret Manager through a secret manager connector.
  • GitHub connector with a GitHub App for cloning, PR status checks and webhooks.

Troubleshooting

SymptomCheck

Connector test failsDelegate network egress, credentials, or the account's IAM roles
Image pull error in deployCluster or runtime identity lacks Artifact Registry read; wrong tag expression
Deployment times outReadiness probes failing; check pod events and logs in the step output
Verification fails unexpectedlyBaseline too short, wrong metric query, or too few data points; read the analysis detail
Expression resolves to nullWrong scope or step identifier; use the expression picker in the editor
Pipeline in Git differs from UIRemote pipeline branch selection; check which branch the run used

Good practice

  • Keep pipelines, templates and input sets in Git, reviewed like code.
  • One pipeline template per deployment shape; services pass only inputs.
  • Run unit and integration tests in CI on every PR; deploy only from main.
  • Promote by artefact tag or digest; never rebuild per environment.
  • Every prod stage has verification and an automatic rollback.
  • Enforce with OPA: prod needs approval, verification, and an artefact from the trusted registry.
  • Watch delegate health and versions; alert when none are connected.
  • Track DORA metrics from Harness deployment data.

Harness as a blueprint

  • Publish account-level templates for "build a JVM service", "deploy to Cloud Run", "deploy to GKE".
  • Teams reference the template version; a fix to the template reaches every pipeline that uses it.
  • Enforce the template with OPA policies rather than reviews.
  • Keep pipelines in Git (remote pipelines) so changes are reviewed like code.
  • This is the same idea as the AI tab's blueprints card: decide once, reuse everywhere.

Levels: what to expect

1 Foundation

  • Run a pipeline and read its logs
  • Understand stages, steps, services and environments
  • Approve or roll back a deployment

2 Practitioner

  • Build CI and CD pipelines with connectors, secrets and triggers
  • Use canary or blue-green with verification
  • Keep pipelines in Git and use templates

3 Senior

  • Design org-wide templates and OPA policies
  • Set up delegates, RBAC and environments securely
  • Integrate verification with monitoring and feature flags

4 Expert

  • Own the delivery platform strategy and its governance
  • Lead migrations from other CI/CD tools
  • Measure and improve delivery (DORA) across teams

Each level includes the ones before it. See Start here for what the levels mean.

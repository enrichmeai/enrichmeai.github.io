Observability

Being able to answer new questions about a running system from the outside: what happened, where, why, and to whom. Logs, metrics, traces and profiles; OpenTelemetry; Google Cloud's tools; dashboards and alerts; and observability for data pipelines and AI features.

Signals and what each answers

SignalIsAnswersCost driver
LogsTimestamped records of events, ideally structured JSONWhat exactly happened in this request or run?Volume and retention
MetricsNumbers aggregated over time (counts, gauges, histograms)How much, how often, how fast, trending where?Number of time series (label cardinality)
TracesA request's path across services as a tree of timed spansWhere did the time go? Which dependency failed?Sampling rate
ProfilesWhere CPU and memory go inside the codeWhich function is slow or allocating?Usually low (continuous sampling)
Events / run recordsBusiness or pipeline facts (deploys, run outcomes)What changed, and did the job do its work?Low

Monitoring tells you that something is wrong from questions you planned. Observability lets you find out why, including for failures nobody predicted. You need both.

Structured logging

{"timestamp":"2026-11-12T06:15:04.120Z",
 "severity":"ERROR",
 "message":"load failed",
 "service":"odp-load", "version":"3f2a9c1", "env":"prod",
 "run_id":"r-2026-11-12", "stage":"ODP_LOAD",
 "object":"gs://landing/data/year=2024/part-3.parquet",
 "error":"400 Bad Request", "error_body":"InvalidArgument: …",
 "logging.googleapis.com/trace":"projects/p/traces/4bf92f…"}
  • One JSON object per line; a severity field so levels work.
  • Always include service, version, environment, and a request or run ID.
  • Log the evidence: the upstream error body, the input that failed, counts. A log that says only "failed" helps no one.
  • Never log secrets, tokens or unnecessary personal data.
  • Levels: ERROR needs attention; WARN is unusual but handled; INFO is a business event; DEBUG is off in production.

Metrics that matter

  • Counter: only goes up (requests, errors, rows loaded). Graph its rate.
  • Gauge: current value (queue depth, connections, lag).
  • Histogram: distribution of values (latency); gives percentiles.
  • RED for services: rate, errors, duration.
  • USE for resources: utilisation, saturation, errors.
  • Golden signals: latency, traffic, errors, saturation.
  • Cardinality: each unique label combination is a separate series. Never use user IDs, request IDs or URLs with IDs as labels.
  • Percentiles, not averages: p50 for typical, p95/p99 for the users having a bad time.

Distributed tracing

  • A trace is one request end to end; a span is one operation in it (an HTTP call, a query), with start, duration, attributes and status.
  • Context propagation: the trace ID travels in the W3C traceparent header and in message attributes across queues.
  • Sampling: keep a percentage of traces (head sampling), or keep all errors and slow ones (tail sampling in a collector).
  • Link logs to traces by writing the trace ID into every log line.
  • Batch jobs: one trace per run, a span per stage or partition.

OpenTelemetry

The vendor-neutral standard for producing logs, metrics and traces: one API in your code, an SDK that processes and exports, the OTLP protocol, and an optional Collector that receives, filters, samples and forwards to any backend.

# Java: zero-code instrumentation with the agent (HTTP, JDBC, Kafka, gRPC …)
java -javaagent:/otel/opentelemetry-javaagent.jar -jar app.jar
#   OTEL_SERVICE_NAME=legal-api
#   OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4318
#   OTEL_TRACES_SAMPLER=parentbased_traceidratio  OTEL_TRACES_SAMPLER_ARG=0.1

# Python: auto-instrumentation
pip install opentelemetry-distro opentelemetry-exporter-otlp
opentelemetry-bootstrap -a install
OTEL_SERVICE_NAME=odp-load opentelemetry-instrument python -m loader
# manual span around meaningful work (Python)
from opentelemetry import trace
tracer = trace.get_tracer("odp-load")

with tracer.start_as_current_span("load_object") as span:
    span.set_attribute("object.uri", uri)
    rows = load(uri)
    span.set_attribute("rows.loaded", rows)
# Collector: receive OTLP, batch, send to Google Cloud

@Component
class LoadMetrics {
  private final Counter loaded, failed;
  private final Timer duration;
  LoadMetrics(MeterRegistry r) {
    loaded   = Counter.builder("odp.objects").tag("outcome", "loaded").register(r);
    failed   = Counter.builder("odp.objects").tag("outcome", "failed").register(r);
    duration = Timer.builder("odp.load.duration").publishPercentileHistogram().register(r);
  }
}

Dashboards that get used

  • One overview per service: traffic, errors, latency percentiles, saturation, last deploy marker.
  • Top-down: user-facing SLOs first, then dependencies, then resources.
  • Same layout for every service (a dashboard template is a blueprint).
  • Show the denominator: "12 errors" means nothing without "of 1.2 million requests".
  • Annotate deploys and incidents so changes line up with effects.
  • Delete dashboards nobody opens.

Alerting

  • Page on symptoms users feel (SLO burn rate, failed runs, stale data), not on causes (CPU at 80%).
  • Every page is actionable and links to a runbook. If nobody needs to act, it is a ticket or a dashboard, not a page.
  • Alert when the signal is missing: a job that did not run, a metric that stopped reporting. Silence is not health.
  • Match on fields you control (a marker in the message, a structured field), not on a severity that may not be set.
  • Prove each alert fires once in a test environment before trusting it.
  • Review noisy alerts monthly: tune, fix the cause, or delete.

Observing data pipelines

DimensionCheck
Run outcomeEvery scheduled run recorded SUCCEEDED, FAILED or UNKNOWN; missing runs alert
FreshnessNewest data per source within its expected age
VolumeRow and object counts within expected ranges; reconciliation in = out + rejected
SchemaUnexpected new, missing or retyped columns detected
QualityTest results (nulls, keys, parse failures) tracked over time
Cost and durationBytes, slot time and runtime per run, trended

The most important rule: a check whose source is unreachable reports UNKNOWN, never zero and never green.

Observing AI features

  • Log model ID, input and output tokens, latency, stop reason and cost per call.
  • Trace each tool call and retrieval step as a span.
  • Track refusals, empty retrievals, citation failures and "not found" rates.
  • Sample real conversations for quality review and feed them into evals (with privacy controls).

Keeping observability affordable

  • Exclude noisy, low-value logs at the router (exclusion filters) or lower their level.
  • Sample traces; keep 100% of errors and slow requests with tail sampling.
  • Watch metric cardinality; drop unused labels.
  • Route long-term logs to BigQuery or GCS with retention rules instead of keeping everything hot.
  • Label resources so observability cost can be attributed to teams.

Following a journey across services

  • Give every request an ID, and pass it on to every service the request touches. Log it with every line.
  • Give every user journey an ID too, when several requests belong together, such as a multi-step form or a checkout. Then you can follow the whole journey, not just one request.
  • Use the standard for tracing: the W3C Trace Context traceparent header carries a trace ID and the caller's span ID between services, so tools from different vendors can join the pieces up. OpenTelemetry propagates it for you.
  • An audit trail makes rollback safe. If a journey fails halfway, you can only undo the steps you know were taken. Record each step and why, then compensate in reverse order (see Architecture on sagas).

Levels: what to expect

1 Foundation

  • Find a request's or run's logs and errors in Cloud Logging
  • Read a service dashboard: traffic, errors, latency
  • Write structured logs with IDs and evidence

2 Practitioner

  • Instrument a service with OpenTelemetry and custom metrics
  • Write log queries, log-based metrics and PromQL
  • Build dashboards and actionable alerts with runbooks

3 Senior

  • Design observability for a system: signals, sampling, cardinality, cost
  • Trace problems across services, queues and pipelines
  • Set dashboard and alert templates for teams

4 Expert

  • Own the observability platform and its standards
  • Lead cost and data-governance strategy for telemetry
  • Drive observability-led reliability across the organisation

Each level includes the ones before it. See Start here for what the levels mean.

What an API is

An API (application programming interface) is a contract: the operations a system offers, the inputs they take, the outputs and errors they return, and the rules for calling them. The contract is what other teams build against; the implementation behind it can change freely as long as the contract holds.

  • Public / partner / internal: who may call it, and so how strict versioning, security and documentation must be.
  • Synchronous: the caller waits (REST, gRPC, GraphQL).
  • Asynchronous: the caller sends and moves on; the result arrives later (queues, events, webhooks).
  • Spec first: write the contract (OpenAPI, protobuf, AsyncAPI) before the code; generate clients and docs from it.

REST in practice

  • Resources are nouns with URLs: /judgments, /judgments/{id}, /courts/{code}/judgments.
  • HTTP methods are the verbs: GET reads, POST creates, PUT replaces, PATCH updates part, DELETE removes.
  • Stateless: each request carries everything needed (including auth); no server session required.
  • Status codes carry meaning: 200, 201 Created (+ Location), 204, 400, 401, 403, 404, 409 Conflict, 422, 429, 500, 503.
  • Errors as Problem Details (RFC 9457): type, title, status, detail.
  • Pagination with a cursor (?cursor=…&limit=50) rather than deep offsets.
  • Filtering and sorting by query parameters: ?court=2_5&from=2024-01-01&sort=-decision_date.
  • Caching with ETag/If-None-Match and Cache-Control.

  /v1/judgments/{id}:
    get:
      operationId: getJudgment
      parameters:
        - { name: id, in: path, required: true, schema: { type: string } }
      responses:
        "200":
          description: The judgment
          content:
            application/json:
              schema: { $ref: "#/components/schemas/Judgment" }
        "404":
          description: Not found
          content:
            application/problem+json:
              schema: { $ref: "#/components/schemas/Problem" }
components:
  schemas:
    Judgment:
      type: object
      required: [id, cnr, court]
      properties:
        id: { type: string }

        court: { type: string }
        decisionDate: { type: [string, "null"], format: date }
  securitySchemes:
    bearer: { type: http, scheme: bearer, bearerFormat: JWT }

gRPC contract

syntax = "proto3";
package legal.v1;

service JudgmentService {
  rpc GetJudgment(GetJudgmentRequest) returns (Judgment);
  rpc StreamNew(StreamNewRequest) returns (stream Judgment);   // server streaming
}

message GetJudgmentRequest { string id = 1; }
message StreamNewRequest  { string court = 1; }
message Judgment {
  string id = 1;
  string cnr = 2;
  string court = 3;
  string decision_date = 4;      // ISO date; field numbers never reused
}

Compatibility rules: add fields with new numbers; never change or reuse a field number; reserve removed ones.

North-south traffic (clients into your platform) goes through the gateway; east-west traffic (services to each other) is the mesh's job. Keep business logic out of both.

API versioning and evolution

  • Additive changes are safe: new endpoints, new optional fields, new enum values clients are told to tolerate.
  • Breaking changes (removing or renaming fields, changing types or meaning) need a new version.
  • Where to version: in the path (/v1/) is the most visible and the easiest to route at a gateway; headers are cleaner but harder to test.
  • Deprecate politely: announce, add Deprecation and Sunset headers, measure who still calls, then remove.
  • Meaning can break without a schema change: a field whose values change meaning is a breaking change even if its type is the same.
  • Contract tests in CI catch accidental breaks.

Reliable integration

  • Timeouts on every call; retries only for idempotent operations, with backoff and jitter.
  • Idempotency keys for POSTs that create or charge.
  • Long-running work: return 202 Accepted with a status URL, or emit an event when done.
  • Webhooks you send: sign the payload (HMAC), retry with backoff, let clients replay.
  • Webhooks you receive: verify the signature, respond fast, process asynchronously, dedupe by event ID.
  • Rate limits with 429 and Retry-After.
  • Correlation IDs (traceparent) passed through every hop.

Integration styles (oldest to newest)

  1. File transfer: one system writes files, another reads them. Simple and still common for bulk data.
  2. Shared database: several systems read and write the same tables. Avoid: no system owns the schema.
  3. Remote procedure call: one system calls another's API (REST, gRPC). Simple; couples availability.
  4. Messaging: systems exchange messages through a broker. Decoupled in time; more moving parts.

Levels: what to expect

1 Foundation

  • Explain REST resources, methods and status codes
  • Call an API with curl and read its OpenAPI spec
  • Tell sync from async integration

2 Practitioner

  • Design a REST API with pagination, errors and versioning
  • Write and publish an OpenAPI contract
  • Add timeouts, retries and idempotency keys

3 Senior

  • Choose REST, gRPC, GraphQL or events for a context
  • Design gateway, mesh and BFF responsibilities
  • Run API evolution: deprecation and contract tests

4 Expert

  • Set API standards and governance across the organisation
  • Design a partner and public API programme
  • Lead integration architecture across many systems

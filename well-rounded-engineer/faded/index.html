Faded? Ruby on Rails, Adobe Flex and Grails

Some technologies that many teams once built on are mentioned less today. This page looks at three, what each introduced, and where each stands now, from their own repositories and histories. The answer differs: one runtime was switched off, while the other two are still releasing. The browser side of the story is on UI History; today’s JVM frameworks are on Spring and Quarkus.

The short answer

Flex has gone with the Flash runtime it ran on. Rails and Grails have not: both were still tagging new versions in 2026. Our view: “faded” describes how often they are talked about more than whether they work, and many of their ideas now live in other frameworks.

Then and now

Ruby on Rails

A server-side model–view–controller web framework in Ruby, under the MIT licence. David Heinemeier Hansson extracted it from the project management tool Basecamp at 37signals and released it as open source in July 2004.

What it introduced: it emphasises convention over configuration, a term Hansson used to describe Rails’ philosophy, and don’t repeat yourself. A model class User maps by default to a table users; database migrations and scaffolding of views made it quick to build an application. Wikipedia lists Django, Laravel, CakePHP and Grails among the frameworks it influenced.

Now: Rails 8.0 was released in November 2024 and 8.1 in October 2025; the repository tagged v8.1.4 in September 2026. Sites that use it include GitHub and Shopify.

Grails

An open-source web framework for the Java platform in the Groovy language, following the same coding by convention idea. It was first called “Groovy on Rails” and dropped that name in March 2006 at Hansson’s request. Version 0.1 came out in March 2006 and 1.0 in February 2008.

What it brought: Rails-style productivity on the JVM, re-using existing Java technologies, Hibernate and Spring, under one interface.

Now: it is Apache Grails, developed at the Apache Software Foundation; its repository tagged v8.0.0 in October 2026. Groovy itself lives on in Gradle build files and Jenkins pipelines (see Build Tools and Harness).

Adobe Flex

A software development kit for cross-platform rich web applications on the Adobe Flash platform, first developed by Macromedia. User interfaces were laid out in MXML, with ActionScript for behaviour, and applications needed Flash Player or Adobe AIR to run. Adobe gave Flex to the Apache Software Foundation in 2011.

Why it ended: it depended on one runtime. The iPhone and iPad did not support Flash Player; Adobe stopped developing Flash Player for mobile, deprecated Flash in July 2017, ended support at the end of 2020, and began blocking Flash content on 12 January 2021. Apache Flex’s latest release listed on Wikipedia is 4.16.1, in November 2017. Its successor project, Apache Royale (formerly FlexJS), compiles ActionScript to JavaScript instead.

Analysis: the declarative idea survived, describing a user interface as nested components in a markup language, as JSX does today (see Front-end Toolchain); the dependence on one vendor’s runtime did not.

Why technologies fade (analysis)

CauseSeen here
The runtime goes awayFlex could not outlive Flash Player
The platform shiftsPhones and tablets without Flash; HTML5 took over video and interactive content
The ideas are absorbedConvention over configuration, migrations and scaffolding spread to frameworks in other languages, so choosing Rails for them alone became less necessary
Attention moves onA framework can keep releasing while fewer people write about it; being discussed less is not the same as being unsupported

Choose by requirement: you maintain one of these

If this is true for youIt leans towards (analysis)
The application runs in Flash PlayerReplace it: the runtime has had no general support since 2020, and browsers block Flash content
A Rails or Grails application on a version that still gets fixesKeep it, and upgrade on the project’s schedule; check each project’s own maintenance policy
An old major version that no longer gets security fixesUpgrade in steps, one major version at a time, with tests around the behaviour first (see Testing)
You cannot hire or keep people who know the stackWeigh a gradual move, piece by piece behind the same interface (see Solution Architecture: A to B)
Your team knows the stack well and it meets the requirementsStay: a rewrite has its own cost and risk

Our view, and the other view

Our view: judge a framework by whether it is maintained and whether it fits your requirements, not by how often it is in the news. The ideas these three introduced are worth learning even if you never use them.

The other view: attention matters in practice: fewer new tutorials, libraries and people to hire make a stack harder to staff and extend, so choosing what most teams use lowers that risk, even if an older framework still works well.

Levels: what to expect

1 Foundation

  • Say what convention over configuration means
  • Name what each of Rails, Grails and Flex introduced
  • Check whether a framework is still releasing

2 Practitioner

  • Read a framework's maintenance policy before upgrading
  • Upgrade a framework one major version at a time
  • Recognise a dependency on a runtime one vendor controls

3 Senior

  • Decide whether to keep, upgrade or replace an older application
  • Plan a gradual migration behind the same interface
  • Weigh staffing risk against rewrite risk

4 Expert

  • Set an organisation's policy for ageing stacks
  • Spot single-vendor runtime risk early
  • Carry good ideas from older frameworks into new ones

Each level includes the ones before it. See Start here for what the levels mean.

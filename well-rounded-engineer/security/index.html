Security

The risks every engineer must recognise, and the habits that prevent most of them: in application code, APIs, data, cloud and the supply chain.

Principles

  • Least privilege: every person, service and token gets only the access it needs, for only as long as it needs it.
  • Defence in depth: several independent layers (network, identity, application, data), so one failure is not a breach.
  • Secure by default: private unless opened, denied unless allowed, encrypted unless there is a reason not to be.
  • Never trust input: anything from a user, another service, a file, a web page or a model's output is validated before use.
  • No secrets in code, images, logs or chat. They live in a secret manager and are injected at runtime.
  • Fail closed: when an auth or permission check cannot run, deny. A gate that opens on error is not a gate.
  • Assume breach: log and alert so that a compromise is noticed and contained quickly.

A 2025 edition of the list has been published; compare it at owasp.org. The categories below remain a sound checklist.

Injection: always parameterise

// Java JDBC
// WRONG: "SELECT * FROM judgment WHERE cnr = '" + cnr + "'"
PreparedStatement ps = conn.prepareStatement(
    "SELECT * FROM judgment WHERE cnr = ?");
ps.setString(1, cnr);

// Spring JdbcClient
jdbc.sql("SELECT * FROM judgment WHERE cnr = :cnr").param("cnr", cnr)...

# Python psycopg
cur.execute("SELECT * FROM judgment WHERE cnr = %s", (cnr,))   # never f-strings

# BigQuery
bigquery.QueryJobConfig(query_parameters=[
    bigquery.ScalarQueryParameter("cnr", "STRING", cnr)])      # WHERE cnr = @cnr
  • Identifiers (table and column names) cannot be parameters: pick them from an allow-list.
  • Never pass user input to a shell. Use the library call, or an argument list without a shell.
  • Escape output for its context (HTML, JSON, URLs) to prevent XSS. Use the framework's templating, not string building.

Authentication & authorisation

  • Authentication is who you are; authorisation is what you may do. Most breaches are authorisation bugs.
  • Use OIDC / OAuth 2.0 with a proven provider rather than building login yourself. For browser apps, the authorisation code flow with PKCE.
  • JWTs: verify the signature, issuer, audience and expiry on every request; keep them short-lived; never accept alg: none; never put secrets in them (they are only encoded).
  • Refresh tokens rotate on use and are revocable; in browsers keep them in HttpOnly; Secure; SameSite cookies.
  • Check permissions on the server for every request and every object: "is this user allowed this case?", not just "is the user logged in?".
  • Load roles from the source of truth on each authentication; do not trust roles a client sends.
  • Passwords: argon2id or bcrypt, rate-limited login, breached-password checks, MFA for admins.

Spring Security: a stateless API

@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
  return http
    .authorizeHttpRequests(a -> a
        .requestMatchers("/actuator/health/**").permitAll()
        .requestMatchers("/api/admin/**").hasRole("ADMIN")
        .anyRequest().authenticated())            // deny by default
    .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
    .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
    .csrf(c -> c.disable())   // only safe when auth is a bearer header, not a cookie
    .build();
}

// object-level check in the service, not only the URL rule
if (!caseFile.ownerId().equals(currentUserId)) throw new AccessDeniedException("not yours");

Web & API hardening

  • HTTPS only, with HSTS (Strict-Transport-Security).
  • Content-Security-Policy to limit where scripts load from; X-Content-Type-Options: nosniff; frame-ancestors against clickjacking.
  • CORS: list exact origins; never reflect any origin with credentials allowed.
  • CSRF: needed when the browser sends cookies automatically; use tokens or SameSite cookies.
  • Rate limits on login, signup, password reset and expensive endpoints.
  • Validate request bodies (types, lengths, ranges) and reject unknown fields where it matters.
  • Errors: generic messages to the client, details to the logs. No stack traces in responses.
  • Uploads: check type and size, store outside the web root, scan if users share them.

Secrets

# store
echo -n "$VALUE" | gcloud secrets create db-password --data-file=-
# grant one workload access to one secret
gcloud secrets add-iam-policy-binding db-password \
  --member=serviceAccount:api@p.iam.gserviceaccount.com \
  --role=roles/secretmanager.secretAccessor
# rotate: add a version, roll the workload, then disable and destroy the old one
gcloud secrets versions add db-password --data-file=new.txt
gcloud secrets versions destroy 1 --secret=db-password
  • No service account JSON keys: Workload Identity Federation for CI, attached service accounts for workloads.
  • A rotation is not finished until old versions are destroyed.
  • Scan commits for secrets (gitleaks, GitHub secret scanning). A leaked secret is rotated, not just deleted from Git: history and forks keep it.
  • Never print secrets in logs, CI output, error messages or AI prompts.

Cloud security on GCP

  • IAM: one service account per workload; predefined narrow roles; no Owner or Editor for services; grant to groups, not individuals.
  • Organisation policies: block public buckets, service account key creation, and external IPs where not needed.
  • Network: private IPs for databases; ingress limited to the load balancer; Cloud Armor in front of public apps.
  • Data: encryption at rest is on by default; CMEK when you must control keys; VPC Service Controls around sensitive datasets.
  • Audit logs: Admin Activity is always on; enable Data Access logs for sensitive services so reads are attributable.
  • Security Command Center surfaces misconfigurations and threats across the project.
  • Separate projects for dev and prod; nobody's laptop has standing prod write access.

Threat modelling in 30 minutes

  1. Draw the data flow: users, services, stores, and the trust boundaries between them.
  2. For each boundary, ask STRIDE questions.
  3. List the threats, rate likelihood and impact, and pick mitigations.
  4. Turn mitigations into tickets and tests.
STRIDEQuestion
SpoofingCan someone pretend to be another user or service?
TamperingCan data be changed in transit or at rest?
RepudiationCan someone deny an action because nothing recorded it?
Information disclosureCan data leak to someone not entitled to it?
Denial of serviceCan someone exhaust a resource or the budget?
Elevation of privilegeCan someone gain rights they should not have?

Data protection & privacy

  • Know where personal data is: tag columns and datasets; keep an inventory.
  • Collect less, keep less: only what the purpose needs, with a retention period.
  • Mask or tokenise personal data in non-production environments and analytics.
  • Honour legal obligations: deletion requests, court suppression orders, consent. Apply them on every read path, not only in one table.
  • Know the law that applies: for India, the Digital Personal Data Protection Act, 2023; GDPR for EU residents.
  • Logs are data too: no personal data or tokens in log lines unless necessary and protected.

Supply chain & CI

  • Pin dependencies with lockfiles; review what new dependencies bring.
  • Automated updates (Dependabot, Renovate) gated by tests.
  • Scan: SAST (CodeQL, Semgrep), SCA (Dependabot alerts, OSV), images (Trivy), secrets (gitleaks).
  • Pin third-party GitHub Actions to a commit SHA; give workflows the minimum permissions:.
  • Protect main and deploy tags; require reviews and checks; restrict who can push release tags.
  • Sign images and generate SBOMs so you can prove what is running.

Security testing

  • Unit and integration tests for access control: user A cannot read user B's object; an expired token is refused; a missing role gets 403.
  • SAST reads code for dangerous patterns; DAST (OWASP ZAP) probes the running app.
  • Dependency and image scans on every build.
  • Fuzzing parsers and file handlers with malformed input.
  • Penetration test before launch and after major changes, by someone independent.
  • Prove each guard red: try the forbidden action in a test and watch it fail.

Security checklist for a pull request

  • Is every new endpoint authenticated, and does it check ownership of each object?
  • Is all input validated, and every query parameterised?
  • Any new secret? Is it in the secret manager, not in code or config?
  • Any new permission or IAM role? Is it the narrowest that works?
  • Does anything new get logged that should not be (tokens, personal data)?
  • New dependency: maintained, licensed acceptably, no known CVEs?
  • What happens on error: does it fail closed?
  • Is there a test that proves the forbidden case is refused?

When something goes wrong

  1. Contain: revoke the leaked key, disable the account, block the IP, take the endpoint down.
  2. Preserve evidence: keep logs and snapshots before cleaning up.
  3. Assess: what was accessed, since when, whose data.
  4. Notify: security lead, then customers and regulators as the law requires and within its deadlines.
  5. Fix the cause and add a guard (test, policy, alert) so it cannot recur.

Levels: what to expect

1 Foundation

  • Parameterise every query; never commit secrets
  • Check that users can only reach their own data
  • Apply the PR security checklist

2 Practitioner

  • Implement OAuth 2.0 / OIDC with a provider and validate tokens properly
  • Use least-privilege IAM and a secret manager
  • Fix findings from SAST, SCA and image scans

3 Senior

  • Threat-model a system and turn threats into tests
  • Design authentication, authorisation and audit for a product
  • Respond to and contain a security incident

4 Expert

  • Own the security architecture and policies across teams
  • Lead compliance (DPDP, GDPR, SOC 2) and external testing
  • Build a security culture and secure-by-default platforms

Each level includes the ones before it. See Start here for what the levels mean.

GraphQL

A query language for APIs: one typed schema, and clients ask for exactly the fields they need. How it works, when it beats REST, the performance and security traps, and servers in Spring, Quarkus and Python. API styles in general are on APIs & Integration.

The idea in one paragraph

A GraphQL server publishes a schema: the types, their fields and how they connect. Clients send a query to a single endpoint (usually POST /graphql) describing the shape of data they want, and get back JSON in exactly that shape. Reads are queries, writes are mutations, live updates are subscriptions. Each field is filled by a resolver function on the server, which can read from a database, another service or a cache.

RESTGraphQL
EndpointsMany, one per resourceOne
Response shapeFixed by the serverChosen by the client
Nested dataSeveral round trips or custom endpointsOne request
ContractOpenAPI (optional)The schema (built in, introspectable)
HTTP cachingNatural for GETHarder: needs persisted queries or client caches
ErrorsHTTP status codesUsually 200 with an errors array; partial data possible
Versioning/v1, /v2Evolve one schema; deprecate fields
Best forPublic APIs, simple resources, cachingUIs combining many related entities; many client types

Schema (SDL)

type Query {
  judgment(id: ID!): Judgment
  searchJudgments(q: String!, court: String, first: Int = 20, after: String): JudgmentConnection!
}

type Mutation {
  saveToCase(caseId: ID!, judgmentId: ID!): CaseFile!
}

type Subscription {
  judgmentAdded(court: String!): Judgment!
}

type Judgment {
  id: ID!
  cnr: String!
  decisionDate: Date          # custom scalar
  court: Court!
  judges: [String!]!
  citedBy(first: Int = 10): [Judgment!]!
}

type Court { code: ID!  name: String!  state: String }

scalar Date

! means non-null. [String!]! is a non-null list of non-null strings.

Queries, variables, fragments

query Search($q: String!, $court: String, $after: String) {
  searchJudgments(q: $q, court: $court, first: 10, after: $after) {
    edges {
      node { ...JudgmentCard }
    }
    pageInfo { hasNextPage endCursor }
  }
}

fragment JudgmentCard on Judgment {
  id
  cnr
  decisionDate
  court { name }
}

# variables (sent separately as JSON):
# { "q": "land acquisition", "court": "2_5" }
curl -s https://api.example.com/graphql \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"query":"query($id:ID!){judgment(id:$id){cnr court{name}}}","variables":{"id":"123"}}'

Always use variables, never string interpolation into the query: it enables caching of the parsed query and avoids injection.

Resolvers and the N+1 problem

Asking for 20 judgments, each with its court, naively runs 1 query for the list and 20 more for courts: N+1 queries.

  • Batch loading (DataLoader pattern): collect all the court IDs requested in one execution step, fetch them in one query, and hand each judgment its court.
  • Per-request cache: the same court requested twice in one query is loaded once.
  • Spring: @BatchMapping. Quarkus: a resolver taking @Source List<…>. Python Strawberry: DataLoader.
  • Measure: log query counts per GraphQL request in tests.

Spring for GraphQL

// schema files: src/main/resources/graphql/*.graphqls
@Controller
class JudgmentGraphQl {
  private final JudgmentService judgments;
  private final CourtService courts;
  JudgmentGraphQl(JudgmentService j, CourtService c) { judgments = j; courts = c; }

  @QueryMapping
  Judgment judgment(@Argument String id) {
    return judgments.find(id).orElse(null);       // null → field is null, no error
  }

  @MutationMapping
  CaseFile saveToCase(@Argument String caseId, @Argument String judgmentId) {
    return judgments.saveToCase(caseId, judgmentId);   // check ownership inside
  }

  @BatchMapping                                    // one query for all courts
  Map<Judgment, Court> court(List<Judgment> list) {
    Map<String, Court> byCode = courts.byCodes(
        list.stream().map(Judgment::courtCode).collect(Collectors.toSet()));
    return list.stream().collect(Collectors.toMap(j -> j, j -> byCode.get(j.courtCode())));
  }
}

// test
@GraphQlTest(JudgmentGraphQl.class)
class JudgmentGraphQlTest {
  @Autowired GraphQlTester tester;
  @MockitoBean JudgmentService judgments;  @MockitoBean CourtService courts;
  @Test void returnsNullForUnknownId() {
    tester.document("{ judgment(id: \"x\") { cnr } }")
          .execute().path("judgment").valueIsNull();
  }
}

Quarkus (SmallRye GraphQL)

// quarkus ext add smallrye-graphql   → schema generated from code
@GraphQLApi
public class JudgmentApi {
  @Inject JudgmentService judgments;
  @Inject CourtService courts;

  @Query
  public Judgment judgment(@NonNull String id) { return judgments.find(id).orElse(null); }

  @Mutation
  public CaseFile saveToCase(@NonNull String caseId, @NonNull String judgmentId) {
    return judgments.saveToCase(caseId, judgmentId);
  }

  // batched field resolver: adds Judgment.court, one call for all judgments
  public List<Court> court(@Source List<Judgment> list) {
    return courts.inOrderFor(list);
  }
}
// GraphQL UI in dev mode: http://localhost:8080/q/graphql-ui

Spring for GraphQL is schema-first (you write SDL); SmallRye GraphQL is code-first (the schema comes from your classes).

Python (Strawberry)

import strawberry
from strawberry.dataloader import DataLoader

async def load_courts(codes: list[str]) -> list["Court"]:
    rows = await db.courts_by_codes(codes)              # one query
    by = {r.code: r for r in rows}
    return [by.get(c) for c in codes]                   # same order as input

@strawberry.type
class Court:
    code: strawberry.ID
    name: str

@strawberry.type
class Judgment:
    id: strawberry.ID
    cnr: str
    court_code: strawberry.Private[str]
    @strawberry.field
    async def court(self, info: strawberry.Info) -> Court:
        return await info.context["court_loader"].load(self.court_code)

@strawberry.type
class Query:
    @strawberry.field
    async def judgment(self, id: strawberry.ID) -> Judgment | None:
        return await db.judgment(id)

schema = strawberry.Schema(query=Query)
# context per request: {"court_loader": DataLoader(load_fn=load_courts)}

Pagination: connections

type JudgmentConnection {
  edges: [JudgmentEdge!]!
  pageInfo: PageInfo!
  totalCount: Int            # optional; can be expensive
}
type JudgmentEdge { cursor: String!  node: Judgment! }
type PageInfo { hasNextPage: Boolean!  endCursor: String }
  • Cursor-based (the Relay connection convention): stable under inserts, works with keyset queries in the database.
  • Cap first on the server (e.g. max 100).
  • Make cursors opaque (base64 of the sort key and ID).

Errors

{
  "data": { "judgment": null },
  "errors": [{
    "message": "Not authorised to view this judgment",
    "path": ["judgment"],
    "extensions": { "code": "FORBIDDEN" }
  }]
}
  • A response can hold partial data plus errors; clients must check errors even on HTTP 200.
  • Put a stable machine-readable extensions.code on every error.
  • Expected business outcomes (validation failed, not found) can also be modelled in the schema as result types (union SaveResult = CaseFile | ValidationError).
  • Never leak stack traces or SQL in message.

Security

  • Authorise per field and per object in resolvers or the service layer; one endpoint means URL-based rules cannot protect anything.
  • Limit query depth and complexity so a client cannot request citedBy { citedBy { citedBy … } } a thousand levels deep.
  • Cap list sizes and set timeouts per request.
  • Persisted queries (allow-list of known query hashes) for first-party clients: blocks arbitrary queries and enables GET caching.
  • Introspection: consider disabling it in production for private APIs; it is not a security boundary, just less help to attackers.
  • Rate limit by cost, not by request count, since one request can be cheap or enormous.
  • Batching attacks: limit the number of operations or aliases per request (aliases can repeat a login mutation hundreds of times).

Performance and caching

  • Batch loaders everywhere a field fetches by key.
  • Select only needed columns: look at the requested fields (selection set) before querying.
  • Client caches (Apollo Client, Relay, urql) normalise results by type and ID; give every object a stable id.
  • HTTP caching needs GET with persisted queries; otherwise cache in resolvers or the data layer.
  • Trace per resolver (OpenTelemetry) to find slow fields.

Schema evolution and scale

  • Add freely: new types, new fields, new optional arguments.
  • Deprecate before removing: oldField: String @deprecated(reason: "Use newField"), then watch usage and remove.
  • Never change a field's type or meaning in place.
  • Schema checks in CI compare against the published schema and fail on breaking changes.
  • Federation: several teams own subgraphs (judgments, users, billing) composed by a router into one supergraph (Apollo Federation, GraphQL Mesh).
  • Behind a gateway: Apigee or another gateway can still handle authentication and rate limits in front of /graphql.

Levels: what to expect

1 Foundation

  • Read a schema and write queries with variables and fragments
  • Explain queries, mutations, subscriptions and resolvers
  • Tell when GraphQL fits better than REST

2 Practitioner

  • Build a server with Spring for GraphQL, SmallRye or Strawberry
  • Avoid N+1 with batch loaders; paginate with connections
  • Return useful errors and test resolvers

3 Senior

  • Secure a GraphQL API: field authorisation, depth and cost limits, persisted queries
  • Evolve a schema without breaking clients; schema checks in CI
  • Tune performance with tracing and caching

4 Expert

  • Design a federated graph across teams
  • Set GraphQL governance and standards for the organisation
  • Decide GraphQL vs REST vs gRPC strategy across products

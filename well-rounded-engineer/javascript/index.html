Guide / Languages / JavaScript

JavaScript: learn the language, then any framework

New developers meet React, Angular, Vue, Svelte, Solid and more, and ask which one to learn. Every one of them is JavaScript underneath, and every one is built from the same handful of language patterns. Learn the language and those patterns first, and a framework becomes a few weeks of reading rather than a new career. The language is standardised as ECMAScript by the TC39 committee at Ecma International; each claim here links to TC39 or MDN.

Which version should I learn?

Short answer: none in particular. Learn modern JavaScript, meaning everything from ECMAScript 2015 onward, and use what your target browsers or Node.js support.

  • ECMAScript 2015 (also called ES6) is the line that matters (our view; it is where most of today’s syntax begins). It added let and const, arrow functions, classes, modules (import/export), promises, iterators and for…of, template literals and destructuring. Much older code you meet was written without these.
  • Since then there has been one edition a year, named by year: ES2016, ES2017, up to ES2026. Each one is small: the proposals that reached Stage 4 before that year’s spec was branched, in March.
  • To reach Stage 4, a feature needs, among other things, two compatible implementations that pass the Test262 conformance tests and real experience with shipping implementations, so by the time it is in an edition it is already running in at least two JavaScript engines.
  • Do not ask "which ES version". Ask "is this feature available where my code runs?" For browsers, MDN marks each feature with Baseline: widely available means it has worked for at least 2.5 years in Chrome, Edge, Firefox and Safari on desktop, and in Chrome, Firefox and Safari on mobile.
  • TypeScript is JavaScript with types, checked before the code runs. Learn it after the language, not instead of it.

The patterns underneath every framework

  • Functions are values. You pass them, return them and store them. Event handlers, callbacks, React components and hooks are all functions.
  • Closures: a function keeps access to the variables around it when it was created. MDN: closures are created every time a function is created. Private state and callbacks that remember values rely on this.
  • The event loop: one thread runs one job at a time, each to completion. Slow work (network, timers, files) finishes later and queues a job. Block that thread and nothing else runs until you finish, including the page’s response to the user.
  • Promises and async/await: a promise is a value that arrives later. await pauses your function, not the thread.
  • Modules: import and export. Modules always run in strict mode.
  • Objects and prototypes: class is a cleaner way to write prototype-based inheritance, not a different model.
  • Immutability: make a new object or array instead of changing the old one ({...obj}, toSorted). Some frameworks compare old and new values to decide what to redraw; a new object makes that comparison cheap and reliable (analysis).
  • Iterators and generators: anything you can for…of over.

Try it: the patterns in plain JavaScript

Save as patterns.mjs and run node patterns.mjs, or paste into a browser console. No framework, no install.

// 1. Closure: count keeps its own private state
function counter() {
  let n = 0;
  return () => ++n;
}
const next = counter();
next(); next();
console.log("closure:", next());            // 3

// 2. Observer: the core of every "reactive" framework
function signal(value) {
  const subs = new Set();
  return {
    get: () => value,
    set: (v) => { value = v; subs.forEach((f) => f(v)); },
    subscribe: (f) => { subs.add(f); return () => subs.delete(f); },
  };
}
const price = signal(10);
const stop = price.subscribe((v) => console.log("render price:", v));
price.set(12);                             // render price: 12
stop();

// 3. Immutability: new array, old one untouched
const items = [3, 1, 2];
const sorted = items.toSorted();
console.log(items, sorted);                // [ 3, 1, 2 ] [ 1, 2, 3 ]

// 4. The event loop: synchronous code finishes first
setTimeout(() => console.log("timer job"), 0);
Promise.resolve().then(() => console.log("promise job"));
console.log("sync code");
// sync code, promise job, timer job

// 5. async/await: pauses the function, not the thread
const wait = (ms) => new Promise((r) => setTimeout(r, ms));
async function load() {
  await wait(100);
  return { user: "ada", roles: ["admin"] };
}
const { user, roles: [first] } = await load();   // top-level await, destructuring
console.log(user, first, user?.length ?? 0);

A learning order that works

  1. Values, types, let/const, functions, arrays and objects
  2. Closures and scope
  3. The DOM and events: change a page with no framework
  4. The event loop, promises, async/await, fetch
  5. Modules, then a build tool (see Build Tools)
  6. Classes, prototypes, iterators
  7. TypeScript
  8. Then one framework, the one your team or your target job uses

Our view: the framework you learn second takes a fraction of the time of the first, because you now see the patterns rather than the syntax. The other view: many people learn a framework first because jobs ask for it, and pick up the language as they go; that works too, as long as you go back and fill in the patterns above. See UI History for how the frameworks came and went.

Choosing a framework: start from the requirement

Comparisons of frameworks usually turn into preference. Instead, write down what your product and your team need, and ask each candidate the same questions. Check every answer in the framework’s own documentation, at the version you would use.

If you needAsk each candidate
Fast first load and search-engine indexing (public sites, shops)Does it render on the server or generate static pages, and how much JavaScript does a page ship?
A rich app behind a login (dashboards, tools)How does it manage state, forms and data loading at scale?
Mostly static content with a few interactive partsCould plain HTML, a little JavaScript, or Web Components do it with no framework at all?
Mobile apps from the same codeIs there a supported way to build native or cross-platform apps? (See Apps.)
A product that must live for many yearsWhat is its release and support policy, who funds it, and how hard were its past major upgrades?
Hiring and a team that can keep it runningDo your current team and your local job market know it?
Accessibility from the startDo its components and docs follow WCAG patterns? (See Accessibility.)
An existing codebaseCan it be added page by page, or does it need a rewrite?

Two rules of thumb (our view): the requirement you cannot change later (hosting, long-term support, team skills) outweighs the one you can; and a choice you can explain in one sentence of requirements is better than one you explain by popularity.

Common traps

  • == converts types; use ===.
  • || replaces 0 and "" too; use ?? when only null or undefined should fall back.
  • Numbers are 64-bit floating point (IEEE 754): 0.1 + 0.2 === 0.3 is false. Keep money in integer minor units (pence, paise, cents) or a decimal library.
  • sort() changes the array it is called on; toSorted() returns a new one.
  • A forgotten await gives you a promise, not the value.
  • Long work on the main thread blocks the UI; a Web Worker runs it on a background thread instead.

Levels: what to expect

1 Foundation

  • Use let, const, functions, arrays and objects
  • Explain closures and the event loop
  • Change a page with the DOM and events, no framework

2 Practitioner

  • Write async code with promises and async/await
  • Organise code in modules and build it
  • Check feature support with Baseline

3 Senior

  • Design state and reactivity without leaning on a framework
  • Keep the main thread free; use Web Workers
  • Adopt TypeScript and write typed APIs

4 Expert

  • Choose and migrate frameworks on evidence
  • Set JavaScript and TypeScript standards across teams
  • Follow and evaluate TC39 proposals

Each level includes the ones before it. See Start here for what the levels mean.

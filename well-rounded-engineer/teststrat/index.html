Guide / Quality / Test Strategy for Cloud Systems

Test strategy when you cannot run it all locally

A system that runs on Kubernetes in the cloud also leans on managed services: queues, databases, identity, storage, networking. Kubernetes runs on a laptop, but the cloud around it does not, and (analysis) mocking everything can leave gaps at the boundaries between your code and managed services. This page is about deciding what to test where: on your machine, in CI, in a short-lived cloud environment, and in production. The kinds of test and the tools are on Testing.

The short answer

Our view: stop aiming for one environment that runs everything. Test logic locally and fast; test each boundary with contracts and real dependencies in containers; run a small number of end-to-end checks in a short-lived cloud environment built the way production is; and treat production itself as a place you test, carefully, with canaries and monitoring. The other view is in the last card on this page.

Where each kind of check runs

Why “everything end to end” breaks down

  • The test pyramid, from Mike Cohn’s Succeeding with Agile: many small, fast unit tests, some coarser tests, and very few high-level tests, because the higher you go, the fewer you should have.
  • End-to-end tests are notoriously flaky, fail for unexpected reasons, need a lot of maintenance and run slowly, as Ham Vocke puts it in The Practical Test Pyramid.
  • Vocke also cautions that the pyramid is overly simplistic and works best as a rule of thumb.
  • Microservices add network boundaries, so the testing strategies of a single in-process application need to be reconsidered (Toby Clemson, Testing Strategies in a Microservice Architecture).

Contracts instead of a full stack

  • Contract tests (Martin Fowler): keep testing against a test double for speed and reliability, and separately run contract tests to catch the real service changing underneath you. Fowler notes they can run on their own rhythm, often once a day, and a failure need not break the build.
  • Consumer-driven contracts (Ian Robinson, 2006): each consumer states what it needs from a provider, and the provider tests against all its consumers’ expectations.
  • In practice (Vocke): consuming teams send their Pact contract files to the provider team, which uses them in its provider tests. He calls consumer-driven contract tests “a real game changer” for autonomous teams that move fast and with confidence.

Analysis: two services can then be tested apart, which is what makes a team independent of a shared environment.

Local stand-ins for cloud services, and their limits

Stand-inWhat it gives youIts own caveat
TestcontainersThrowaway instances of databases, browsers or anything that runs in a Docker container, inside your testsAnalysis: only for what ships as a container image
kindA local Kubernetes cluster whose “nodes” are Docker containers; usable for local development or CIDesigned first for testing Kubernetes itself; it is not your cloud’s managed cluster
Google Pub/Sub and Firestore emulatorsLocal versions for development and testsThe Pub/Sub emulator itself warns its implementation may be incomplete or differ from the real system; Google’s known limitations include no IAM operations. Firestore’s emulator has “notable limitations”, for example it does not mirror production’s transaction concurrency modes
AzuriteA free local emulator for Azure StorageMicrosoft says it supports only Blob, Queue and Table storage, and has functional differences from an Azure Storage account in the cloud
LocalStackA framework to develop and test AWS applications locallyIts open-source repository is archived and read-only as LocalStack consolidates into a single unified image; the company offers a free Hobby plan for non-commercial use, and paid plans

Analysis: an emulator passing is evidence about your code, not about the cloud service. Pub/Sub’s emulator lists IAM operations as unsupported, and none of the stand-ins above claims to reproduce your cloud’s identity, networking or quotas, so check those in a real environment.

Short-lived cloud environments

  • Create an environment per pull request or per test run, built by the same Helm charts and Terraform as production (see Helm and Terraform), and delete it afterwards.
  • In Kubernetes, a namespace isolates a group of resources within one cluster, and resource quotas divide the cluster between users, so many such environments can share one cluster.
  • Point them at real managed services, using separate small instances or test projects.

This card is analysis built on the Kubernetes namespace documentation, which says namespaces are intended for clusters with many users across teams. The cost is real: cloud spend and setup time per environment.

Production is part of the strategy

  • QA in production (Rouan Wilsenach): watch the behaviour of production closely, with the right monitoring and a good continuous delivery pipeline, so issues are found as they happen and fixed quickly.
  • Canarying (Google SRE Workbook): a partial and time-limited deployment of a change, evaluated against the rest, usually on a much smaller part of production or of the users.
  • Feature flags let you ship code switched off and turn it on for a few users first (analysis; see DevOps).

How much of each: choose by requirement

If this is true for the part you are testingIt leans towards (analysis)
Business logic, calculations, validationUnit tests on your machine, lots of them
Your code talking to a database, cache or broker that ships as a containerIntegration tests with Testcontainers, on your machine and in CI
A call to another team’s serviceConsumer-driven contract tests, verified in the provider’s CI
A managed cloud service whose emulator’s listed limitations do not touch what you useThe emulator for fast feedback, plus a few tests against the real service
Identity, IAM permissions, network policies, quotasA short-lived cloud environment: there is no faithful local copy
A critical user journey (sign in, pay, place an order)A handful of end-to-end tests in a cloud environment, plus synthetic checks in production
A risky change you cannot fully rehearseA canary or a feature flag, with monitoring and a fast rollback
Your team already has a shared test environment that worksKeep it, and add contracts to reduce how much depends on it: switching has a cost

Our view, and the other view

Our view: fast local tests and contracts catch most mistakes cheaply, and a few real-environment checks plus careful releases catch what they cannot. Chasing a perfect local copy of the cloud costs more than it saves.

The other view: some teams, for example in regulated or high-risk settings, judge a full pre-production environment that mirrors production worth its cost and flakiness, and run large end-to-end suites there for the assurance it gives.

Levels: what to expect

1 Foundation

  • Say which tests run locally and which need a real environment
  • Explain a contract test
  • Run a dependency in a container for a test

2 Practitioner

  • Write consumer contract tests and verify them in the provider's CI
  • Use an emulator and know its listed limitations
  • Add smoke tests to a deployment

3 Senior

  • Design a per-pull-request cloud environment
  • Plan canary releases with automatic evaluation
  • Decide test depth per component by risk

4 Expert

  • Set an organisation's test strategy across teams and environments
  • Balance test-environment cost against risk
  • Make production observability part of quality

Each level includes the ones before it. See Start here for what the levels mean.

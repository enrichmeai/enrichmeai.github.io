IO, NIO and web servers

How Java I/O went from blocking streams to NIO, NIO.2 and virtual threads, and how web servers evolved alongside it, from CGI and Apache to nginx, Netty and Tomcat.

The short answer

Every web server answers the same question: when ten thousand clients are connected and most of them are idle or slow, who waits for them? Over thirty years the answer moved from a process, to a thread, to an event loop, and now back to a thread that costs almost nothing. The same story from the thread’s side is on How Java Threads Evolved; the network underneath is on Networking.

Thirty years in one line

1. A process per request

1993–1995

The early web ran programs through CGI, specified by the NCSA team in 1993: for every request, the web server started a new process, passed the request in environment variables and standard input, and sent back whatever the program printed. It was simple and fully isolated, but starting a process per request is slow.

Apache httpd (April 1995) kept processes around instead. Its pre-forking model (later the “prefork” module) held a pool of worker processes, each answering one request at a time.

The cost: one process per connection. Memory, not CPU, set the number of users a server could hold.

2. java.io: a thread per connection

Java 1.0 (1996) · Servlets (1997) · Tomcat (1999)

Java’s original I/O, java.io, is stream-based and blocking: InputStream.read() blocks until data is available. A server built on it accepts a socket and gives it a thread:

ServerSocket server = new ServerSocket(8080);
while (true) {
    Socket socket = server.accept();               // blocks until a client connects
    pool.submit(() -> handle(socket));             // that thread blocks on every read and write
}

The Servlet API (1.0 in 1996–97) put a standard interface over this model, and Tomcat, first released at the Apache Software Foundation in 1999, became a widely used container, alongside Jetty. Threads were lighter than processes, and the code was easy to read: read the request, call the database, write the response, top to bottom.

The cost: an idle keep-alive connection still holds a whole thread. In 1999 Dan Kegel named the problem C10K: how do you serve ten thousand clients at once?

3. Readiness and event loops: NIO

kqueue (2000) · Java 1.4 NIO (2002) · epoll (2002) · nginx (2004)

Operating systems answered C10K with efficient readiness notification: kqueue in FreeBSD 4.1 (July 2000) and epoll in Linux 2.5.45 (October 2002), replacing the older select and poll, whose cost grows with the number of sockets watched. Instead of one thread waiting on each socket, one thread asks the kernel which sockets are ready and services only those.

Java got the same ability in Java 1.4 (February 2002) through NIO (JSR 51): channels, buffers, and a Selector that watches many channels at once.

Selector selector = Selector.open();
serverChannel.configureBlocking(false);
serverChannel.register(selector, SelectionKey.OP_ACCEPT);
while (true) {
    selector.select();                             // one thread waits for any socket to be ready
    for (SelectionKey key : selector.selectedKeys()) {
        if (key.isAcceptable()) accept(key);
        if (key.isReadable())   read(key);         // never blocks: the data is already there
    }
    selector.selectedKeys().clear();
}

Outside Java, nginx (October 2004) was built on this model: a master process and a few worker processes, each handling many connections with an asynchronous, event-driven approach rather than a thread each. It became a widely used front door for web applications, often in front of Java servers.

The cost: raw NIO is hard. Partial reads, buffer flipping, back-pressure and threading rules are all yours to get right.

4. Frameworks on NIO

Netty and Apache MINA (mid-2000s) · Tomcat 6 NIO connector (2006–07) · NIO.2 in Java 7 (2011)

Libraries took on that difficulty. Apache MINA and then Netty, created by Trustin Lee, wrapped NIO in event loops, pipelines of handlers and pooled buffers. Netty became the networking layer under much of the Java world: gRPC for Java, Cassandra, Elasticsearch, Vert.x and, later, Spring Boot’s default server for WebFlux.

Servlet containers moved their connectors to NIO too. Tomcat 6.0 (betas in 2006, stable in 2007) shipped an NIO connector, so an idle keep-alive connection no longer held a thread; the old blocking connector was removed in Tomcat 8.5 and 9. Request processing itself still used a thread per request.

NIO.2 in Java 7 (2011, JSR 203) added asynchronous channels and the java.nio.file API (Path, Files) that replaced most uses of java.io.File.

5. Asynchronous all the way through

Servlet 3.0 (2009) · Node.js (2009) · Servlet 3.1 (2013) · Spring WebFlux (2017)

The next step was to free the thread during the request, not only between requests. Servlet 3.0 (December 2009) let a request be suspended and resumed later on another thread, and Servlet 3.1 (May 2013) added non-blocking reads and writes.

Node.js (2009) showed a whole application could live on one event loop, with every I/O call asynchronous. In Java, Vert.x (2011), Undertow (first released 2013, 1.0 in 2014) and Spring WebFlux (2017, on Reactor, running on Netty by default) followed. A handful of event-loop threads serve everything, as long as nobody blocks one of them.

The cost: every library in the request path must be non-blocking, down to the database driver. One blocking call on an event-loop thread stalls every connection that thread serves.

6. Virtual threads: blocking I/O becomes cheap

Socket rewrites in Java 13 and 15 · virtual threads final in Java 21 (2023)

Project Loom took a different route. Java first reimplemented its classic blocking socket classes (JEP 353 in Java 13, JEP 373 in Java 15) so they could work with a new kind of thread, then called fibers. Then virtual threads (final in Java 21, JEP 444) made threads cheap. When a virtual thread blocks on a socket, the JVM unmounts it and resubmits it when the operation can complete; on Linux, the JDK’s poller underneath uses epoll.

try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    while (true) {
        Socket socket = server.accept();
        executor.submit(() -> handle(socket));     // the 1996 code, now one cheap thread per connection
    }
}

The code from step 2 is back, and it scales like step 3. Spring Boot runs request handling on virtual threads with one property (spring.threads.virtual.enabled=true), and Helidon 4 introduced a web server (Helidon Nima) built from the ground up on virtual threads.

The same problem, four answers

ModelWho waits for a slow clientExamples
Process per connectionA whole OS processCGI, Apache prefork
Thread per connectionA platform thread (the JVM’s default stack is 1 MB on 64-bit x86 Linux)java.io servers, classic Tomcat
Event loopNobody: the kernel reports when the socket is readynginx, Node.js, Netty, WebFlux
Virtual threadA parked virtual thread, with an event loop underneathSpring Boot 3.2 and later on Java 21, Helidon 4

The protocols kept moving too: HTTP/2 (RFC 7540, May 2015, since replaced by RFC 9113) put many requests on one connection, and HTTP/3 (RFC 9114, June 2022) runs over QUIC on UDP. Each step raised the number of conversations a server holds at once.

Our view, and the other view

Our view: underneath, it is now the same machinery: the kernel’s readiness API (epoll, kqueue) does the waiting. What changed is how much of it the programmer has to see. NIO and event loops exposed it; virtual threads hide it again behind plain, blocking-looking code, which suits most services.

The other view: hiding the machinery has a price. Event-loop code makes concurrency and back-pressure visible in the program, and some teams prefer that explicitness, especially for streaming or very high connection counts, where it is easier to reason about than many parked threads.

Choose by requirement

If this is true for youIt leans towards (analysis)
Request/response service that mostly waits on databases and APIs, on Java 21 or laterThread per request on virtual threads
Streaming, server-sent events, many long-lived idle connectionsAn event-loop server (Netty, WebFlux, Vert.x)
Serving static files and terminating TLS in front of applicationsA dedicated event-loop proxy such as nginx
Your team already runs one model wellStay with it unless a row above forces a change: switching has a cost

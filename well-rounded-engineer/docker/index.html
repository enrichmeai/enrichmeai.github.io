Docker

Build small, reproducible images, run and debug containers, and compose a local stack. See Cloud Run and Kubernetes for where the images go.

Mental model

  • Image: a read-only stack of layers plus metadata (entrypoint, env, user). Built from a Dockerfile, named registry/repo:tag, pinned exactly by @sha256:digest.
  • Container: a running process from an image, with its own filesystem layer, network and process namespace. Not a VM: it shares the host kernel.
  • Layer cache: each instruction is a layer. A change invalidates that layer and every one after it, so put what changes least first.
  • Volume: storage that outlives the container. Anything written elsewhere disappears with it.
  • Tag vs digest: a tag can be moved to a new image; a digest cannot. Deploy by digest or by an immutable tag such as the commit SHA.

Everyday commands

docker run --rm -p 8080:8080 -e APP_PROFILE=local api:dev

docker ps -a

docker exec -it db psql -U postgres

A good Dockerfile

# syntax=docker/dockerfile:1
FROM python:3.12-slim AS base
ENV PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1
WORKDIR /app

# dependencies first: cached until requirements change
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements.txt

# then the code, which changes often
COPY src/ ./src/

RUN useradd --uid 1001 --no-create-home app
USER 1001
EXPOSE 8080
ENTRYPOINT ["python", "-m", "src.main"]
# .dockerignore: keeps the build context small and secrets out
.git
.venv
__pycache__/
*.pyc
.env
node_modules/
target/
build/

Multi-stage builds

# Build with the full toolchain, ship only the result
FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY gradle/ gradle/
COPY gradlew settings.gradle.kts build.gradle.kts ./
RUN ./gradlew dependencies --no-daemon          # cache dependencies
COPY src/ src/
RUN ./gradlew bootJar --no-daemon -x test

FROM gcr.io/distroless/java21-debian12          # no shell, no package manager
COPY --from=build /src/build/libs/app.jar /app.jar
USER nonroot
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "/app.jar"]

# build one stage only
docker build --target build -t api:build .

Distroless images have no shell, which makes them smaller and safer but harder to debug. Keep a -debug variant or use an ephemeral debug container.

Instructions that trip people up

  • ENTRYPOINT vs CMD: ENTRYPOINT is the program; CMD supplies default arguments that docker run image … replaces.
  • Exec form ["java","-jar","app.jar"] runs your process as PID 1 so it receives SIGTERM. Shell form java -jar app.jar wraps it in /bin/sh, which may not forward signals.
  • COPY over ADD: ADD also unpacks archives and fetches URLs, which surprises people.
  • ARG vs ENV: ARG exists only at build time; ENV persists into the running container. Neither is a safe place for secrets: use RUN --mount=type=secret.
  • One RUN per logical step, cleaning up in the same command: apt-get update && apt-get install -y --no-install-recommends curl && rm -rf /var/lib/apt/lists/*.
  • Pin base images to a version (python:3.12-slim) or a digest, never latest.

Docker Compose for local stacks

# compose.yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: pw
      POSTGRES_DB: corpus
    ports: ["${DB_PORT:-5433}:5432"]
    volumes: [dbdata:/var/lib/postgresql/data]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 10
  api:
    build: .
    ports: ["${APP_PORT:-8080}:8080"]
    environment:
      DB_HOST: db                      # service name is the hostname
    depends_on:
      db: { condition: service_healthy }
volumes:
  dbdata:
docker compose up -d --build
docker compose logs -f api
docker compose exec db psql -U postgres corpus
docker compose down            # keep volumes
docker compose down -v         # also delete volumes (data gone)
docker compose -p wt2 up -d    # second copy with its own project name

Multi-platform & build secrets

# Apple Silicon builds arm64 by default; Cloud Run and most servers need amd64
docker buildx build --platform linux/amd64 -t REGISTRY/api:3f2a9c1 --push .
docker buildx build --platform linux/amd64,linux/arm64 -t REGISTRY/api:3f2a9c1 --push .
docker image inspect api:dev --format '{{.Os}}/{{.Architecture}}'

# secret available during one RUN, never stored in a layer
docker build --secret id=pip_token,env=PIP_TOKEN .
RUN --mount=type=secret,id=pip_token \
    PIP_INDEX_URL="https://__token__:$(cat /run/secrets/pip_token)@pypi.example.com/simple" \
    pip install -r requirements.txt

Image security

  • Run as a non-root user (USER 1001).
  • Start from a minimal base (slim, distroless, or Alpine where musl is fine). Fewer packages, fewer CVEs.
  • Scan images in CI: trivy image REGISTRY/api:tag, or Artifact Registry's built-in scanning.
  • Never bake secrets into an image or a layer; anyone who can pull it can read them with docker history or by unpacking layers.
  • Rebuild regularly so base-image security fixes reach you.
  • Generate an SBOM (docker buildx build --sbom=true or syft) so you can answer "are we affected?" quickly.

Levels: what to expect

1 Foundation

  • Build, run, stop and inspect containers
  • Read a Dockerfile and explain each instruction
  • Use docker compose for a local stack

2 Practitioner

  • Write small multi-stage Dockerfiles with good layer caching
  • Run as non-root; keep secrets out of layers
  • Build for linux/amd64; debug exit codes and OOM kills

3 Senior

  • Set image standards: base images, scanning, SBOMs, signing
  • Optimise image size and startup time for Cloud Run or Kubernetes
  • Design local development environments for a team

4 Expert

  • Own the organisation's container supply chain
  • Understand the OCI image and runtime specs
  • Choose and govern registries, build systems and policies

Each level includes the ones before it. See Start here for what the levels mean.

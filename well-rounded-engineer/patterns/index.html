Guide / Architecture & design / SOLID & Design Patterns

SOLID principles and design patterns

Architecture decides how systems fit together; these decide how one codebase stays easy to change. SOLID is five principles for classes and modules. Design patterns are named, reusable answers to problems that keep coming back. Both give a team a shared vocabulary, and both can be overdone. Not to be confused with Solid, the personal data pods.

The five principles

PrincipleWhat it saysThe smell it fixes (analysis)Overdone, it becomes (analysis)
SSingle responsibilityA class should have only one reason to changeOne class that prices, saves and emails; every change risks the other twoDozens of one-method classes that are hard to follow
OOpen–closedSoftware entities should be open for extension but closed for modification: behaviour can be extended without editing their sourceA growing if/switch that every new case editsExtension points for variations that never come
LLiskov substitutionA property provable about objects of a type should hold for objects of any of its subtypesA subclass that throws, or quietly changes behaviour, where the parent workedRarely overdone; the usual fix is less inheritance
IInterface segregationNo code should be forced to depend on methods it does not useA huge interface that every implementer half-fills with stubsInterfaces so small that a simple idea is spread across many
DDependency inversionHigh-level modules should not depend on low-level ones; both depend on abstractions, and abstractions do not depend on detailsBusiness logic that cannot be tested without a real databaseAn interface for every class, each with one implementation forever

Where they come from: Robert C. Martin introduced the principles in his 2000 paper Design Principles and Design Patterns; Michael Feathers coined the acronym SOLID around 2004. The open–closed principle is Bertrand Meyer’s, and the substitution principle is Barbara Liskov’s, from 1987, formalised with Jeannette Wing in 1994 (see A brief history).

Four of them in one small example

// Before: one class prices, applies every rule and saves.
// A new discount means editing this method again.
class OrderService {
  long totalPence(Order o) {
    long t = o.subtotalPence();
    if (o.customer().isStaff()) t = t * 80 / 100;
    if (o.coupon() != null)     t = t - o.coupon().valuePence();
    repository.save(o);
    return t;
  }
}

// After: a new rule is a new class, not an edit (O).
interface Discount {                          // one method; nothing to stub (I)
  long apply(Order o, long totalPence);
}
record StaffDiscount() implements Discount {
  public long apply(Order o, long t) { return o.customer().isStaff() ? t * 80 / 100 : t; }
}
record CouponDiscount() implements Discount {
  public long apply(Order o, long t) { return o.coupon() == null ? t : Math.max(0, t - o.coupon().valuePence()); }
}

class Pricing {                               // pricing only; saving lives elsewhere (S)
  private final List<Discount> discounts;    // depends on an abstraction, not on concrete rules (D)
  Pricing(List<Discount> discounts) { this.discounts = discounts; }

  long totalPence(Order o) {
    long t = o.subtotalPence();
    for (Discount d : discounts) t = d.apply(o, t);
    return t;
  }
}

Money is kept in integer pence, as on Payment Gateways. Pricing no longer saves, so it can be tested with no database (S), and with a list of fake discounts (O, D). The order the discounts run in is now the order of the list, and it changes the answer: staff then coupon turns 1000 into 700, coupon then staff into 720. The “before” version fixed that order in code; now it is a decision to make, and test, on purpose.

Liskov, the classic trap

A classic textbook example. A square is a rectangle in geometry, so it is tempting to make Square extends Rectangle. But code that sets a rectangle’s width and then its height expects the area to be width × height. A square that keeps its sides equal breaks that expectation, so it cannot stand in for a rectangle: the subtype fails the property the caller relied on.

Analysis: the usual way out is fewer inheritance links, not cleverer ones: make both immutable values, or give them a shared interface with no setters.

Two rules from the Gang of Four

  • “Program to an interface, not an implementation.”
  • “Favor object composition over class inheritance.”

Both are from Design Patterns (Gamma, Helm, Johnson and Vlissides). Dependency injection is a common way to meet them: an object receives what it depends on rather than creating it, often from a framework container. Martin Fowler’s article of January 2004 described it, and settled on the name after discussion with other advocates of inversion of control.

Patterns by the problem they solve

Design Patterns describes 23 patterns in three groups: creational, structural and behavioural. Below is a selection of the 23. The last column is analysis.

If your problem is…Pattern (group)In modern Java or Kotlin
Choosing an algorithm at runtimeStrategy (behavioural)Often just a functional interface and a lambda
Telling many objects when one changesObserver (behavioural)Listeners, events and reactive streams (see JavaScript for the same idea in the browser)
A fixed sequence of steps where some steps varyTemplate method (behavioural)An abstract class with hooks, or a method that takes the varying steps as functions
Requests as objects you can queue, log or undoCommand (behavioural)A record per command, handled in one place
Behaviour that depends on the object’s stateState (behavioural)A sealed type per state and a switch over it
Walking a collection without exposing its structureIterator (behavioural)Built in: Iterable and the for-each loop
Adding behaviour around an object without subclassingDecorator (structural)Java’s I/O streams are built this way
Making an interface you cannot change fit the one you needAdapter (structural)A small wrapper class at the edge of your code
Offering one simple entry point to a complicated subsystemFacade (structural)A service class in front of several clients
Standing in for another object (access checks, remote calls, added behaviour)Proxy (structural)Generated by frameworks more often than written by hand
Treating a tree of parts the same way as a single partComposite (structural)Menus, file trees, expression trees
Building an object with many optional partsBuilder (creational)Kotlin’s named and default arguments, or a builder for Java
Letting a subclass or caller decide which class to createFactory method (creational)A static factory method, or a function that returns an implementation
Exactly one instance of somethingSingleton (creational)Some consider it an anti-pattern: global state that hides dependencies and makes unit testing harder. One instance managed by a dependency-injection container avoids both

When principles and patterns hurt

  • Presumptive features: Fowler’s word for code built for a feature that is not needed yet. YAGNI, “you aren’t gonna need it”, is the counter.
  • Kent Beck’s rules of simple design, as Fowler states them, in priority order: passes the tests, reveals intention, no duplication, fewest elements.
  • Anti-patterns: common but counterproductive solutions; Andrew Koenig coined the term in 1995, inspired by Design Patterns.

Our view, and the other view

Our view: learn the principles and the common patterns well enough to name them in a review, then use one when its problem is in front of you, not to make code look professional. Refactor into a pattern when the second or third variation arrives.

The other view: in a large codebase shared by many teams, agreeing on patterns early keeps code consistent and saves later rewrites. And in functional styles, many patterns become plain functions and modules, so some argue SOLID matters less outside object-oriented code.

Test yourself

A class formats invoices and also sends them by email. Which principle does that strain?

Single responsibility: it has two reasons to change, the invoice layout and the way it is delivered.

Every new payment method means editing the same switch. Which principle, and which pattern helps?

Open–closed; the Strategy pattern, with one implementation per payment method.

A ReadOnlyList extends List and throws on add. What is wrong?

It breaks Liskov substitution: code written for List that calls add fails when handed the subtype.

Your business logic news up a database client directly. Which principle would let you test it without the database?

Dependency inversion: depend on an interface, and pass in a real client in production and a fake in tests.

Which pattern are Java’s I/O streams built on?

Decorator: each stream wraps another and adds behaviour, such as buffering.

Levels: what to expect

1 Foundation

  • Name the five SOLID principles and the smell each one fixes
  • Recognise Strategy, Observer, Decorator, Adapter and Builder in code you read
  • Explain why a subclass must keep its parent's promises

2 Practitioner

  • Refactor a growing switch into a strategy or a sealed type
  • Inject dependencies so logic is testable without infrastructure
  • Name a pattern in a code review, and say why it fits

3 Senior

  • Decide when a pattern earns its place and when it is speculative
  • Design module boundaries with dependency inversion
  • Keep an inheritance hierarchy honest, or replace it with composition

4 Expert

  • Set design standards a whole organisation can review against
  • Teach patterns as answers to problems, not as goals
  • Judge which principles change shape in functional code

Each level includes the ones before it. See Start here for what the levels mean.

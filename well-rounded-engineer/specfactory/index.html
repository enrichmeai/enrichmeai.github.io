Guide / AI / A Spec-Driven AI Factory

A spec-driven AI factory in a human team

Agents can now write a lot of the code. What they cannot do is decide what is worth building, or be accountable for it. A spec-driven “factory” puts people where judgement is needed and agents everywhere else. What it is, where people stay and why, how roles and rituals change, what goes wrong, and a Spring Boot microservice built this way, compiled and tested.

The short answer

Write down what you want and how you will know it works (the spec) before any code. Let agents turn the spec into a plan, small tasks and code. Run gates that answer pass or fail: tests, a check that every requirement has a test, and a review by an agent that did not write the code. Keep people at three points: approving the spec, approving the plan, and merging.

That is the “factory”: a line of stations, each with an input, an output and a check. It is not a new team; it is a new way for an existing team to spend its time. Our view: the team ends up writing and checking more specs and less boilerplate.

What “spec-driven” means

The term is young. Birgitta Böckeler of Thoughtworks looked at three tools that use it (Kiro, GitHub’s Spec Kit and Tessl) and found three levels:

  • Spec-first: write a careful spec, then use it for the task in hand.
  • Spec-anchored: keep the spec after the task and evolve it with the feature.
  • Spec-as-source: people edit only the spec; the code is generated and never touched by hand.

Every approach she found was spec-first; only some aim higher. She also separates a spec (about one change) from the memory bank: the rules that apply to every session. Spec Kit calls those rules a constitution, Kiro calls them steering, and Claude Code reads them from CLAUDE.md.

Sources: Birgitta Böckeler (Thoughtworks), “Understanding Spec-Driven-Development: Kiro, spec-kit, and Tessl”, 15 October 2025; for CLAUDE.md, Claude Code: Best practices.

Why it suits agents

An agent stops when the work looks done. Anthropic’s Claude Code guide says to give it “something it can run that comes back pass or fail”, otherwise, in its words, that “makes you the test suite”. A spec with numbered acceptance criteria turns into exactly that: one test per criterion.

Spec Kit’s templates add two habits that help: keep the spec on what and why, never how; and mark every gap as [NEEDS CLARIFICATION: …] instead of guessing. GitHub’s announcement puts the person’s job plainly: “your role isn’t just to steer. It’s to verify.”

Sources: Claude Code: Best practices; Spec Kit: spec-driven.md; The GitHub Blog: Spec-driven development with AI, 2 September 2025.

Where people stay, and why

  • Deciding what is worth building. DORA’s 2025 research found that a user-centric focus is “a prerequisite for AI success”: AI helps most when it is pointed at a clear problem. Our view: choosing the problem stays with the product manager, not the agent.
  • Answering the open questions. Every [NEEDS CLARIFICATION] is a decision someone must own. An agent that guesses turns an assumption into code nobody chose.
  • Approving the plan. The plan fixes the database, the boundaries and the contracts: the decisions that are expensive to undo. A person reads it before any code exists, when changing it costs a paragraph.
  • Merging. Someone is accountable for what reaches users. DORA found 30% of respondents report little or no trust in AI-generated code. The answer is not blind trust but evidence: the merge is where a person reads the test output and the review, and signs.
  • Feeding back. When production surprises you, a person decides whether the spec was wrong, the plan was wrong or the code was. Spec Kit describes this as “bidirectional feedback”: incidents and metrics update the spec.

Sources: Google Cloud: Announcing the 2025 DORA Report, 23 September 2025; Spec Kit: spec-driven.md. More on briefing and freedom levels: Humans & Agents.

Analysis: our view of how roles shift, with the platform finding from Google Cloud: Announcing the 2025 DORA Report, 23 September 2025.

Embedding it in a team: rituals

  • Refinement becomes spec review. The team reads draft specs together and kills vague criteria (“fast”, “robust”) before agents meet them.
  • Planning includes plan review. The tech lead walks through each agent plan; disagreements are settled before code.
  • Stand-up looks at the board of waiting work. What is blocked on a human answer, a plan approval or a merge?
  • Retros produce rules. Each mistake an agent made becomes a constitution line, a hook or a test, so it cannot recur. A note in a chat does not count.

Analysis: our practice; the last point is how this site’s own pipeline works (below). The other view: Böckeler argues that small, iterative steps keep a team in control better than a lot of up-front spec work, so a team might keep its rituals as they are and add only the gates.

Rolling it out

  1. Fix the foundations first. DORA’s 2025 report calls AI an amplifier: it found AI adoption linked to higher throughput but lower delivery stability, and says that without “strong automated testing, mature version control practices, and fast feedback loops” more change means more instability.
  2. One team, one kind of work. Pick small backend features with clear rules. Leave big, unclear product bets for later.
  3. Measure before and after. Lead time, change failure rate and time to restore, plus how long work waits on people.
  4. Widen only when the gates hold. If reviewers wave things through, the factory is running faster than the team can check.

Sources: Google Cloud: Announcing the 2025 DORA Report, 23 September 2025; DORA: State of AI-assisted Software Development 2025.

Example: a Spring Boot microservice from a spec

A stock reservation service: checkout calls it to hold stock for an order line, so the last unit is never sold twice. Everything below is in one Maven project on Spring Boot 4.2.0 and Java 21, compiled and tested on 24 November 2026 against an in-memory H2 database in one JVM. Running several instances against Postgres was not tested. It starts where a team would: with the spec, approved by product and the tech lead.

1. The spec (specs/001-reserve-stock/spec.md). Eight acceptance criteria, one non-functional need, one open question answered by a person:

# 001 Reserve stock

Owner: the product manager. Approved by: product + tech lead, before any plan.

## Why
Two customers can each be told the last unit is theirs. Checkout must hold stock
for an order line until the order is paid or abandoned.

## User story
As the checkout service, I reserve stock for an order line,
so that no unit is sold twice.

## Acceptance criteria
- AC-1: GIVEN sku A has 5 available WHEN checkout reserves 2 THEN the reply is 201 with a reservation id AND 3 remain.
- AC-2: GIVEN sku A has 1 available WHEN checkout reserves 2 THEN the reply is 409 INSUFFICIENT_STOCK AND 1 remains.
- AC-3: GIVEN a reservation made with Idempotency-Key k WHEN the same request is retried with k, one after the other or at the same moment THEN the same reservation id comes back AND stock fell once.
- AC-4: GIVEN 1 unit left WHEN 20 reservations for it arrive at once THEN exactly one succeeds.
- AC-5: GIVEN a reservation of 2 WHEN checkout releases it THEN the 2 units are available again AND a second release changes nothing.
- AC-6: GIVEN a quantity outside 1..100 WHEN checkout reserves THEN the reply is 400.
- AC-7: GIVEN key k was used to reserve 2 of sku A WHEN k is sent with a different sku or quantity THEN the reply is 422 IDEMPOTENCY_KEY_REUSED AND stock is unchanged.
- AC-8: GIVEN no sku Z exists WHEN checkout reserves Z THEN the reply is 404 UNKNOWN_SKU.

## Non-functional
- NFR-1: any number of instances can run at once. No instance keeps state in memory; the database is the record.

## Out of scope
- Expiry of abandoned reservations, and what a retry should return after its
  reservation was released: today it returns the released reservation (spec 002).
- Validating the Idempotency-Key itself (blank keys, keys over 128 characters).

## Open questions
- [NEEDS CLARIFICATION: may one order reserve the same sku twice?] Answered by product: no, use one line with the total.

2. The constitution: rules every spec in this service obeys. Rule 1 is what makes the factory checkable; rules 3 and 4 are what make the service scale:

# Constitution (applies to every spec in this service)
1. Every acceptance criterion has at least one test tagged with its id. The gate runs trace_check.py and fails otherwise.
2. A test is written and seen failing before the code that passes it.
3. No state in instance memory. Stock and reservations live in the database.
4. Stock changes are one conditional UPDATE, never read-then-write.
5. Domain errors (404, 409, 422) are RFC 9457 problem details with a stable `code`.
   Malformed input gets Spring's default 400 problem detail.
6. A human approves the spec, approves the plan, and merges. Agents do the rest.

3. The tasks, generated from the approved plan. Each names the criteria it serves; T2 to T5 run in parallel, one agent each, in separate worktrees:

# Tasks for 001 (from plan.md; [P] = can run in parallel)
T1      schema.sql: stock, reservation (unique idempotency_key)        AC-1..8
T2 [P]  tests AC-1, AC-2, AC-6, AC-8 over HTTP; see them fail          AC-1, AC-2, AC-6, AC-8
T3 [P]  tests AC-3 retry and same-key race, AC-5 release; see fail     AC-3, AC-5
T4 [P]  test AC-4: 20 racers, one unit; see it fail                     AC-4
T5 [P]  test AC-7: key reused for a different request; see it fail     AC-7
T6      ReservationService: claim key, then conditional UPDATE         after T1..T5
T7      ReservationController: 201/200/404/409/422/400, problem details after T6
T8      gates: mvn test, trace_check.py; reviewer agent against spec   after T7

The example: tests first, then code

One test per criterion, tagged with its id. This is AC-4, the race: twenty requests for one unit, released at the same moment.

    @Test @Tag("AC-4")
    void twentyRacersForTheLastUnitExactlyOneWins() throws Exception {
        stock("A", 1);
        var start = new CountDownLatch(1);
        try (ExecutorService pool = Executors.newFixedThreadPool(20)) {
            var results = new java.util.ArrayList<Future<Integer>>();
            for (int i = 0; i < 20; i++) {
                results.add(pool.submit(() -> { start.await(); return reserve("A", 1, UUID.randomUUID().toString()).statusCode(); }));
            }
            start.countDown();
            int won = 0;
            for (var f : results) if (f.get() == 201) won++;
            assertThat(won).isEqualTo(1);
        }
        assertThat(service.available("A")).isZero();
    }

The service. Stock changes in one conditional UPDATE, so the database, not the Java code, decides who wins. The idempotency key is claimed first, through a unique index, so a second request with the same key waits for the first to finish and then gets its answer, instead of racing it for the stock (AC-3). A key reused for a different request is refused (AC-7), and an unknown sku gets a 404 (AC-8):

    public Reservation reserve(String sku, int quantity, String idempotencyKey) {
        try {
            return tx.execute(status -> {
                Optional<Reservation> earlier = findByKey(idempotencyKey);      // AC-3: a plain retry
                if (earlier.isPresent()) return sameRequest(earlier.get(), sku, quantity);
                boolean known = db.sql("SELECT COUNT(*) FROM stock WHERE sku = :sku").param("sku", sku)
                        .query(Integer.class).single() > 0;
                if (!known) throw new UnknownSku();                           // AC-8
                String id = UUID.randomUUID().toString();
                // Claim the key FIRST. A second request with the same key, on any instance, now waits
                // on the unique index until this transaction ends, instead of racing for the stock.
                db.sql("""
                        INSERT INTO reservation (id, idempotency_key, sku, quantity, released)
                        VALUES (:id, :key, :sku, :q, FALSE)""")
                        .param("id", id).param("key", idempotencyKey)
                        .param("sku", sku).param("q", quantity).update();
                int changed = db.sql("""
                        UPDATE stock SET available = available - :q
                        WHERE sku = :sku AND available >= :q""")              // AC-2, AC-4: one conditional UPDATE
                        .param("q", quantity).param("sku", sku).update();
                if (changed == 0) throw new InsufficientStock();             // rolls back the INSERT too
                return new Reservation(id, sku, quantity, false);
            });
        } catch (DuplicateKeyException sameKeyAtSameTime) {
            // The same key arrived twice at once. The first one committed; answer with its reservation.
            return sameRequest(findByKey(idempotencyKey).orElseThrow(), sku, quantity);
        }
    }

    /** AC-7: a key reused for a different request is refused, never answered with the old result. */
    private Reservation sameRequest(Reservation earlier, String sku, int quantity) {
        if (!earlier.sku().equals(sku) || earlier.quantity() != quantity) throw new KeyReused();
        return earlier;
    }
CREATE TABLE IF NOT EXISTS stock (
  sku       VARCHAR(64) PRIMARY KEY,
  available INT NOT NULL CHECK (available >= 0)
);
CREATE TABLE IF NOT EXISTS reservation (
  id              VARCHAR(36) PRIMARY KEY,
  idempotency_key VARCHAR(128) NOT NULL UNIQUE,
  sku             VARCHAR(64) NOT NULL REFERENCES stock(sku),
  quantity        INT NOT NULL,
  released        BOOLEAN NOT NULL
);

The trace gate. A short script that fails the build if a criterion has no test, or a test names a criterion no spec defines. It is a cheap check that no criterion was forgotten. Its limit: it proves a tagged test exists, not that the test checks the right thing. That is the reviewer’s job:

"""Gate: every acceptance criterion in every spec has a test tagged with its id, and no test names an id the spec lacks."""
import pathlib, re, sys

specs = {m for p in pathlib.Path("specs").glob("*/spec.md")
         for m in re.findall(r"^- (AC-\d+):", p.read_text(), re.M)}
tags = {m for p in pathlib.Path("src/test").rglob("*.java")
        for m in re.findall(r'@Tag\("(AC-\d+)"\)', p.read_text())}
missing, unknown = sorted(specs - tags), sorted(tags - specs)
for ac in missing: print(f"FAIL {ac} has no test")
for ac in unknown: print(f"FAIL a test is tagged {ac}, which no spec defines")
print(f"{len(specs)} criteria, {len(specs & tags)} traced")
sys.exit(1 if missing or unknown else 0)

The example: what the gates said

  • mvn test: 9 tests, 0 failures, 0 errors (read from the Surefire XML, three runs).
  • trace_check.py: 8 criteria, 8 traced.

A gate seen only green has not been tested, so we broke both on purpose:

  • We replaced the conditional update with read-then-write, the version an agent might write first. AC-4 failed: in our runs, 7 to 10 of the 20 racers bought the single unit. The service’s connection pool is HikariCP (its start-up appears in the test log), whose default size of 10 caps how many could reach the database at once. Any number above one is the bug.
  • We added an AC-9 to the final spec with no test. The trace gate failed: FAIL AC-9 has no test.

What the independent review caught. The first version updated stock before claiming the key. A reviewer agent that never saw the build raced two retries with the same key for the last unit; in its runs, some retries got a 409 for a request that had succeeded. Our tests had missed it because AC-3 only tried retries one after the other. The fix claims the key first, and AC-3 now has a race test: it failed in 3 of 3 runs on the old order and passes on the new one.

That last gate is a review by an agent that never saw the build. Claude Code’s guide gives the prompt: review the diff “against SPEC.md, check every requirement is implemented and the listed edge cases have tests”, and “skip style”, because a reviewer asked to find problems will always find something.

Sources: Claude Code: Best practices (review prompt); HikariCP: configuration (maximumPoolSize, default 10).

The example: how it scales

The service. NFR-1 and constitution rules 3 and 4 mean no instance keeps state, so you can run as many as you like. A Kubernetes HorizontalPodAutoscaler adds or removes pods to keep average CPU near 60% of what each pod requests:

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: stock-reservation
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: stock-reservation
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 60

The Deployment must set a CPU request for the container, or the autoscaler has nothing to measure against. On Kubernetes, Spring Boot’s actuator exposes /actuator/health/readiness; point the readiness probe at it so new pods get traffic only once they are ready. Analysis: the database becomes the limit: every replica opens its own connection pool, so replicas × pool size must stay below what the database accepts.

The factory. It scales by specs, not by agents. More specs in flight need more people approving specs and plans and merging; the parallel [P] tasks and per-agent worktrees take care of the rest.

Sources: Kubernetes: Horizontal Pod Autoscaling; Spring Boot: Actuator endpoints (liveness and readiness); Claude Code: Common workflows (worktrees, plan mode).

What goes wrong

  • Too much process for small work. Böckeler tried Spec Kit on a 3–5 point story. It felt like overkill; she never finished it, and estimated she could have built it with plain AI help in the time spent running and reviewing Spec Kit’s output.
  • Reviewing markdown instead of code. She found Spec Kit’s files “repetitive” and “tedious to review”, and would rather review code. Keep specs short and criteria numbered.
  • A false sense of control. She saw agents ignore instructions (re-creating classes that already existed) and also follow a rule too eagerly. Templates are advice to a model; only gates are guarantees.
  • The “what” and the “how” blur. Separating functional from technical detail is hard, and she notes our profession’s track record with user stories is not good.
  • Speed without stability. DORA found more AI adoption linked to lower delivery stability. A factory that ships more changes needs stronger tests, smaller batches and faster rollback, or it ships more incidents.
  • The human queue. Analysis: an agent can finish a task long before a person gets to review it. Watch the queue of waiting work, or it becomes the new bottleneck.

Sources: Birgitta Böckeler (Thoughtworks), “Understanding Spec-Driven-Development: Kiro, spec-kit, and Tessl”, 15 October 2025; Google Cloud: Announcing the 2025 DORA Report, 23 September 2025.

One we run: this website

enrichmeai.com uses the same idea without a spec folder per change: a rules file and gates. Its CLAUDE.md sets four rules every session follows: verify every claim against a source before writing; done means green (the site checker at zero findings, CI green, the page looked at on a phone and a laptop); stop after three failed attempts and write up the blocker; prefer pinned documentation over open search. Hooks run the checker after every edit, a separate reviewer agent checks each change, and a person merges, because a merge to main is a production deploy.

This page is an example of why the reviewer step matters. It first went live (pull requests #233 and #234) on our own checks and a green site check; the reviewer agent was not run, and the CI review produced no verdict before either merge. When the reviewer did run, it found the idempotency bug above, a paraphrase stronger than its source, and opinions not labelled as opinions; a second review found a regression the first fixes had caused. Pull request #235 lists each finding and its fix. Our view: skipping a gate is how a factory ships its mistakes.

Our view, and the other view

Our view: the spec is worth it for anything bigger than a bug fix, and the gates are worth it for everything. Most of the value is in two things: numbered criteria that become tests, and people who approve the plan before code exists.

The other view: Böckeler asks whether elaborate spec tools are “Verschlimmbesserung”, making things worse while trying to make them better, and recalls that model-driven development never took off for business software. Small, iterative steps with plain AI help may keep a team more in control.

dbt on BigQuery

dbt-core 1.8+ with dbt-bigquery. Unit tests arrived in 1.8; microbatch and YAML snapshots in 1.9.

CLI

dbt deps                         # install packages.yml
dbt debug                        # check profile + connection
dbt build                        # seed + run + snapshot + test, in DAG order
dbt run   -s my_model
dbt test  -s my_model
dbt build -s my_model --full-refresh
dbt compile -s my_model          # see SQL in target/compiled/
dbt show  -s my_model --limit 20 # preview rows
dbt ls    -s tag:daily --resource-type model
dbt seed  && dbt snapshot
dbt source freshness
dbt docs generate && dbt docs serve

dbt run --target prod --vars '{run_date: "2025-01-01"}'
dbt retry                        # re-run only what failed last time

Node selection

-s my_model          # just it
-s +my_model         # it and all parents
-s my_model+         # it and all children
-s 2+my_model+1      # 2 levels up, 1 down
-s @my_model         # children + their parents (safe rebuild)
-s tag:daily
-s path:models/fdp
-s config.materialized:incremental
-s source:raw+       # everything downstream of a source
-s "fdp_judgment,tag:daily"     # intersection (comma)
-s a b               # union (space)
--exclude tag:slow

# Slim CI: only what changed vs prod's manifest
dbt build -s state:modified+ --defer --state prod-artifacts/
dbt build -s result:error+ --state target/

my_project:
  target: dev
  outputs:

      location: asia-south1
      threads: 8
      job_execution_timeout_seconds: 600
      maximum_bytes_billed: 50000000000   # hard cost cap per query
    prod:

      method: service-account
      keyfile: /secrets/sa.json     # or oauth on Workload Identity
      project: my-proj-prod
      dataset: fdp
      location: asia-south1
      threads: 16

Project layout & dbt_project.yml

models/
  staging/   stg_*.sql   1:1 with sources, rename + cast only (view)
  intermediate/ int_*.sql joins, dedupe (ephemeral or view)
  marts/     fct_* dim_*  what consumers read (table/incremental)
seeds/  snapshots/  macros/  tests/  analyses/

      +materialized: table
      +labels: {owner: data, layer: fdp}

  start_year: 2023

Model config for BigQuery

{{ config(
    materialized = 'table',
    partition_by = {
      'field': 'decision_date',
      'data_type': 'date',          # date | timestamp | datetime | int64
      'granularity': 'month'        # day | hour | month | year
    },
    cluster_by = ['court_code', 'cnr'],   # up to 4 columns
    require_partition_filter = true,
    partition_expiration_days = none,
    labels = {'layer': 'fdp'},
    tags = ['daily']
) }}

-- integer-range partition
partition_by = {'field': 'data_year', 'data_type': 'int64',
                'range': {'start': 1950, 'end': 2030, 'interval': 1}}

Incremental: merge

{{ config(
    materialized = 'incremental',
    incremental_strategy = 'merge',
    unique_key = 'judgment_key',            # or a list
    on_schema_change = 'append_new_columns',# ignore | fail | sync_all_columns
    partition_by = {'field': 'decision_date', 'data_type': 'date'},
    incremental_predicates = [
      "DBT_INTERNAL_DEST.decision_date >= date_sub(current_date(), interval 30 day)"
    ]
) }}

select * from {{ ref('int_judgment') }}
{% if is_incremental() %}
  where _landed_at > (select max(_landed_at) from {{ this }})
{% endif %}

incremental_predicates prunes the target side of the MERGE. Without it BigQuery scans the whole destination on every run.

Incremental: insert_overwrite

{% set partitions_to_replace = [
  'current_date()',
  'date_sub(current_date(), interval 1 day)'
] %}

{{ config(
    materialized = 'incremental',
    incremental_strategy = 'insert_overwrite',
    partition_by = {'field': 'event_date', 'data_type': 'date'},
    partitions = partitions_to_replace       # static: cheapest
) }}

select * from {{ ref('stg_events') }}
{% if is_incremental() %}
  where event_date in ({{ partitions_to_replace | join(',') }})
{% endif %}

Replaces whole partitions, no row matching. Leave out partitions for "dynamic" mode: dbt finds the partitions in the new data, at the cost of an extra query.

Incremental: microbatch 1.9

{{ config(
    materialized = 'incremental',
    incremental_strategy = 'microbatch',
    event_time = 'decision_date',
    batch_size = 'day',            # hour | day | month | year
    begin = '2023-01-01',
    lookback = 2,
    partition_by = {'field': 'decision_date', 'data_type': 'date',
                    'granularity': 'day'}
) }}
-- no is_incremental() block: dbt filters each batch for you,
-- and filters upstream refs that declare their own event_time
select * from {{ ref('stg_judgment') }}
dbt run -s fct_judgment --event-time-start 2024-01-01 --event-time-end 2024-02-01
dbt retry      # re-runs only failed batches

Sources & freshness

# models/staging/_sources.yml
sources:
  - name: odp
    database: my-proj            # = GCP project
    schema: dp_odp               # = dataset
    loaded_at_field: _landed_at
    freshness:
      warn_after:  {count: 1, period: day}
      error_after: {count: 3, period: day}
    tables:
      - name: hc_judgment
      - name: sc_judgment
        freshness: null          # opt out

-- usage
select * from {{ source('odp', 'hc_judgment') }}

Data tests

models:
  - name: fdp_judgment
    columns:
      - name: judgment_key
        data_tests: [unique, not_null]
      - name: court_code
        data_tests:
          - relationships: {to: ref('fdp_court'), field: court_code}
      - name: status
        data_tests:
          - accepted_values: {values: ['DISPOSED', 'PENDING']}
      - name: decision_date
        data_tests:
          - not_null:
              config:
                severity: warn
                where: "data_year >= 2000"
                error_if: ">100"
                warn_if: ">0"
-- tests/assert_no_future_dates.sql  (singular: fails if it returns rows)
select * from {{ ref('fdp_judgment') }}
where decision_date > current_date()

data_tests: replaced tests: in 1.8; the old key still works. Packages: dbt-labs/dbt_utils, metaplane/dbt_expectations.

Unit tests 1.8

unit_tests:
  - name: parses_sc_dd_mm_yyyy
    model: int_judgment_normalised
    given:
      - input: ref('stg_sc_judgment')
        rows:
          - {cnr: "SC1", raw_date: "05-05-1959"}
          - {cnr: "SC2", raw_date: "bad"}
    expect:
      rows:
        - {cnr: "SC1", decision_date: 1959-05-05}
        - {cnr: "SC2", decision_date: null}

  # format: csv | dict | sql ; overrides: {macros: {is_incremental: true}}

Unit tests run SQL logic on fixed inputs before the model is built. Run with dbt test -s test_type:unit; exclude them in prod.

Custom generic test

-- tests/generic/null_ratio_below.sql
{% test null_ratio_below(model, column_name, max_ratio=0.01) %}
select *
from (
  select countif({{ column_name }} is null) / count(*) as ratio
  from {{ model }}
)
where ratio > {{ max_ratio }}
{% endtest %}

# use it
columns:
  - name: decision_date
    data_tests:
      - null_ratio_below: {max_ratio: 0.0}

Contracts & snapshots

# Model contract: build fails if shape drifts
models:
  - name: serving_judgments
    config:
      contract: {enforced: true}
    columns:
      - name: judgment_key
        data_type: string
        constraints: [{type: not_null}]
      - name: decision_date
        data_type: date

# Snapshot, YAML form (1.9): SCD type 2
snapshots:
  - name: court_snapshot
    relation: source('odp', 'court')
    config:
      schema: snapshots
      unique_key: court_code
      strategy: check          # or timestamp + updated_at
      check_cols: all
      hard_deletes: invalidate # ignore | invalidate | new_record

Levels: what to expect

1 Foundation

  • Run, test and select models; read compiled SQL
  • Use ref and source; add not_null and unique tests
  • Understand views vs tables

2 Practitioner

  • Write incremental models with the right strategy
  • Write macros, generic tests and unit tests
  • Configure partitioning and clustering on BigQuery

3 Senior

  • Structure a multi-project dbt platform
  • Set up slim CI with state and defer
  • Use contracts, versions and access controls for shared models

4 Expert

  • Own modelling standards across the organisation
  • Design cross-project dependencies and data mesh boundaries
  • Contribute packages and tooling

Each level includes the ones before it. See Start here for what the levels mean.

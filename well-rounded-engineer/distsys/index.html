Guide / Architecture & design / Distributed Systems

Distributed systems

As soon as a program runs on more than one machine, it has to cope with messages that are lost, delayed or arrive twice, machines that pause or fail partway, and clocks that disagree. This page covers the ideas underneath microservices, Kafka, replicated databases and Kubernetes: what goes wrong, the trade-offs you cannot avoid, how machines agree, and how to test it. The section on simulation testing draws on Unmesh Joshi’s article Deterministic Simulation Testing and his Patterns of Distributed Systems, Joshi says his Tickloom library draws heavily on FoundationDB and TigerBeetle, and he names Antithesis as a commercial option for systems that cannot be restructured.

The assumptions that fail

The fallacies of distributed computing are false assumptions that programmers new to distributed systems tend to make. L. Peter Deutsch at Sun Microsystems listed seven in 1994, building on earlier work by Bill Joy and Dave Lyon, and James Gosling added the eighth around 1997:

  1. The network is reliable.
  2. Latency is zero.
  3. Bandwidth is infinite.
  4. The network is secure.
  5. Topology does not change.
  6. There is one administrator.
  7. Transport cost is zero.
  8. The network is homogeneous.

Partial failure is what makes this hard. Unmesh Joshi describes gray failures: a node may misbehave without going down, a network may lose a few packets or slow some messages enough that only some nodes time out, and a process may freeze (a garbage-collection pause, for example) and resume without knowing it was frozen. The cluster is then split in what it believes, with some parts stalled and others carrying on.

CAP and PACELC

  • CAP (Brewer’s conjecture, 2000; proved by Gilbert and Lynch, 2002): a distributed data store can give at most two of consistency (every read gets the latest write or an error), availability (every request to a working node gets a response, possibly not the latest data) and partition tolerance (it keeps working while messages between nodes are lost or delayed).
  • Our reading (analysis): partitions cannot be ruled out on a real network, so the choice is what to do during one: refuse the operation and stay consistent, or answer and risk inconsistency.
  • PACELC adds the normal case: else, with no partition, you still trade latency against consistency.

Two traps: CAP’s consistency is not the C in ACID, and CAP’s availability is not “high availability” in the everyday sense.

Consistency models

  • Linearizable (Herlihy and Wing, 1987): operations that overlap in time still appear to take effect instantly, in a single order that respects real time. It is a strong correctness condition, and it lets a programmer reason about the system as if there were one copy of the data.
  • Eventual consistency: if no new updates are made, every read eventually returns the last value. Replicas are said to converge. It is a weak guarantee, chosen for availability.
  • BASE versus ACID: eventually consistent stores are often described as basically available, soft state, eventually consistent, in contrast to ACID transactions.

Weaker models in between, such as read-your-writes, are on Architecture.

Time and order

ToolWhat it gives you
Wall clockTime of day. Joshi notes it can jump when NTP corrects it and is not guaranteed to be monotonic, so it cannot measure a timeout; and machines’ clocks are not perfectly synchronised, so it cannot order events across them.
Monotonic clockThe usual workaround for measuring elapsed time; Joshi points out that a process pause can still distort the measurement.
Lamport timestamp (Leslie Lamport, 1978)A simple logical counter carried on messages, giving a partial order of events: if one event could have caused another, it gets the smaller number.
Vector clockOne logical counter per process, carried on every message, so you can tell whether two events are causally ordered or concurrent.
Hybrid logical clockA version that increases like a counter but stays close to real date and time, so clients can ask for data “as of” a time.
Generation clock (also called term or epoch)A number that goes up with each new leader, so a leader that paused and came back can be recognised as out of date.

Agreeing: consensus and Raft

Consensus lets a group of machines agree on the same sequence of changes, so they can act as one replicated state machine. Paxos, by Leslie Lamport, was first submitted in 1989 and published in 1998. Raft, by Diego Ongaro and John Ousterhout, was designed as an alternative that is easier to understand. etcd, which Kubernetes uses, is built on Raft.

  1. One leader at a time. Each server is a leader, a follower, or, during an election, a candidate. The leader sends regular heartbeats.
  2. Elections. A follower that hears nothing for its election timeout (typically 150 to 300 ms) becomes a candidate, starts a new term, votes for itself and asks the others. Each server votes once per term.
  3. Log replication. The leader appends each change to its log and replicates it to followers. A change counts as committed once a majority have stored it.

Raft in its basic form tolerates crashed servers, not lying ones: every node trusts the elected leader. Kafka’s own metadata quorum is described on Kafka.

Quorums and split brain

  • Majority quorum: an update counts once a majority of nodes acknowledge it. Five nodes need three, and can lose two.
  • Why a majority: two majorities always share a node, so two halves of a broken cluster cannot both make decisions.
  • Split brain: two parts of a system each believe they are in charge and change overlapping data independently, usually after a network partition.
  • Leases give a node exclusive access for a limited time; it must renew before expiry, so a crashed or paused node loses the access on its own.

Analysis: this is why clusters usually run with an odd number of nodes: a fourth node adds cost without letting you lose a second one. The other view: an even number is sometimes chosen when spreading nodes across zones or racks matters more than the failure count.

Transactions across machines: two-phase commit

Two-phase commit has a coordinator ask every participant to prepare (vote), then tell them all to commit or roll back. Its main weakness is that it blocks: a participant that has voted yes must wait for the coordinator’s decision, and if the coordinator fails for good, some participants never resolve, and in rare cases a person has to step in.

Analysis: this is why services usually prefer sagas, with a compensating step for each local transaction, over a distributed transaction (see Architecture and Microservices). The other view: a saga gives up isolation between steps and needs compensation logic, so where a database or transaction coordinator already provides two-phase commit and short blocking is acceptable, it can be the simpler option.

When nodes lie: Byzantine faults

A Byzantine fault is one where a component shows different symptoms to different observers, so others cannot even agree whether it has failed. The name comes from Lamport, Shostak and Pease’s 1982 paper on the Byzantine Generals Problem. Byzantine fault tolerant systems can keep working with fewer than one third of their nodes faulty or malicious.

Analysis: inside one organisation, crash fault tolerance (Raft, Paxos) is usually enough. Byzantine fault tolerance matters where participants may be malicious or do not trust each other. Public blockchains are a related case, though Wikipedia notes that their guarantees differ from classical Byzantine fault tolerance (see Bitcoin & Blockchain).

Living with eventual consistency: session guarantees

With replicas that catch up later, a user can write something and then not see it, or see a newer value and then an older one. In 1994 Douglas Terry and colleagues described four session guarantees: promises made to one user or one client, which are much cheaper than making every replica agree at once.

GuaranteeThe promiseWhat goes wrong without it
Read your writesAfter you write a value, your later reads see it (or something newer)You update your address, refresh, and the old one is back
Monotonic readsOnce you have seen a value, you never see an older oneA comment appears, then disappears on the next refresh
Monotonic writesYour writes are applied in the order you made themYou set a price, then correct it, and the correction is applied first
Writes follow readsA write you make after reading a value is applied on top of that value or a newer oneA reply is stored before the message it answers

Common ways to provide them (analysis): send a user’s reads to the primary for a short time after they write; keep a user on the same replica (sticky routing); or have the client remember the version it last saw and refuse older answers. The labs drill “The stale read” (distributed systems drills) is the second failure above in code.

CRDTs: replicas that merge without asking each other

A conflict-free replicated data type is a data structure copied across machines where any copy can be updated independently, without coordinating with the others, and the data type itself resolves any differences when the copies meet. Marc Shapiro, Nuno Preguiça, Carlos Baquero and Marek Zawirski defined the concept formally in 2011; it was first motivated by collaborative text editing and mobile computing, and is used in online chat and other systems. Simple examples are a counter that only goes up (each replica counts its own increments, and the total is the sum) and a set where additions always win.

Our view: CRDTs are worth knowing because they show that “eventual” can still mean “correct”, if the data type is designed for it. The other view: many business rules cannot be expressed as data that merges automatically (a balance that must never go negative, a seat that can only be sold once), and those still need coordination or a single owner.

Fencing: stopping the old leader

When a leader or lock holder seems to have failed, the rest of the system cannot tell whether it has really died or is only paused, by a long garbage collection, a slow network or a suspended virtual machine. If it is only paused, it may wake up and keep writing as if it were still in charge. Fencing isolates such a node from the shared resources it controlled, so it cannot do damage when it comes back.

  • Shut it out: cluster software can power the node off (known as STONITH, “shoot the other node in the head”) or block its access to shared storage.
  • Make old writes harmless (analysis): give every new leader or lock holder a number that only goes up, have it send that number with every write, and have the storage reject any write carrying an older number than one it has already seen.

The labs drill “The lock that outlived its owner” (distributed systems drills) is this failure, and its fix, in Python and Java.

Patterns to know by name

Unmesh Joshi’s catalogue, published as the book Patterns of Distributed Systems in 2023, names recurring building blocks of distributed systems. Six of its patterns, picked here as a start:

PatternThe problem it solves
Write-ahead logKeep every agreed change after a crash, by persisting each state change as a command in an append-only log
HeartbeatNotice a failed server in time, by having each one send regular “I am alive” messages
Majority quorumStop two groups of servers making independent decisions
Generation clockRecognise a leader that paused or was cut off and has since been replaced
LeaseGive exclusive access that expires by itself if its holder crashes or pauses
Hybrid clockVersion data so the versions are ordered and also map to a date and time

Deterministic simulation testing

Joshi names four sources of nondeterminism, each of which changes the order in which events reach the software: the system clock, thread scheduling, network timing and disk timing. Simulation testing takes control of all four:

  • Time comes from ticks, not the clock. A timeout counts calls to tick(), so a pause cannot fire it early. Production systems already work this way: etcd’s Raft is driven by Node.Tick(), with election and heartbeat timeouts set in ticks, and TigerBeetle fixes a tick at 10 ms.
  • One thread runs the protocol, so there is no scheduler to vary the order.
  • The network and the disk are interfaces with a simulated version in tests, which can drop, delay or duplicate messages. TigerBeetle’s simulator also reorders packets, partitions the network and corrupts reads and writes.
  • Every random choice comes from a seeded generator. The same seed gives exactly the same faults in the same order, so a failure found on one run replays every time.
  • Time is fast-forwarded: the simulation runs the next tick at once instead of waiting, so a run that would take hours on a live cluster takes seconds, and thousands of runs that would add up to days finish quickly. TigerBeetle says one minute of its simulator’s time is equivalent to days of real-world testing.
  • Correctness is checked against the recorded client history, as Jepsen does, not just “did it stay up”.

Where it comes from: Joshi writes that FoundationDB pioneered deterministic simulation testing for distributed databases, using a custom C++ coroutine language and a deterministic scheduler, and that it simulates at the level of byte streams. TigerBeetle, a financial transactions database, uses a single-threaded, tick-driven design, which Joshi found easier to implement in Java. TigerBeetle’s own documentation says its simulator, the VOPR, is deterministic from a seed and the Git commit, so any bug it finds can be replayed, and credits FoundationDB and Antithesis as its inspiration. Antithesis is a commercial platform with a deterministic hypervisor, which Joshi suggests when re-architecting the application is not feasible. Tickloom is Joshi’s Java library for teaching the approach.

The rules simulation imposes

To keep the core deterministic, Joshi’s Tickloom code follows six rules. In short (his examples are Java, but the idea applies in any language):

  • No reading the system clock directly.
  • No unseeded randomness, including for ids.
  • No threads, executors or standard futures in the core.
  • No direct network or disk I/O: everything goes through the interfaces.
  • No iterating over unordered collections such as a HashMap, whose order can differ between runs.
  • No background thread calling back into the deterministic side.

On cost, Joshi argues that a single event loop with asynchronous, batched I/O often performs better for I/O-bound systems, the design Redis, FoundationDB and TigerBeetle use. The trade-off is that handlers must never block, and you scale across cores by running more processes.

Choose by requirement

If this is true for youIt leans towards (analysis)
You build on a managed database or Kafka and do not write the replication yourselfLearn the guarantees it documents; test your own retries, timeouts and idempotency; use chaos tests for recovery
A wrong answer costs more than a refused one (money, stock, bookings)A store that chooses consistency during a partition
Staying responsive matters more than every read being current (feeds, catalogues)Eventual consistency, with the staleness designed for
You need a leader, a lock or cluster membershipAn existing consensus system such as etcd, not a home-made one
You are writing a consensus protocol, a replication layer or a storage engineDeterministic simulation testing, designed in from the start
An existing system you cannot restructureClient-history checking, or simulation below the application at the hypervisor (commercial platforms such as Antithesis)

Our view, and the other view

Our view: every engineer who builds services should know the fallacies, CAP and quorums well enough to read a database’s guarantees critically, and anyone writing the replication itself should design for simulation testing from the first line, because retrofitting determinism is usually harder (our view; hypervisor-level tools exist for when re-architecting is not feasible).

The other view: most teams never write a consensus protocol. For them the strict rules of simulation are a cost with little return, and time is better spent on timeouts, idempotency, chaos tests and choosing well-tested infrastructure.

Levels: what to expect

1 Foundation

  • Name the fallacies of distributed computing and give an example of each
  • Explain CAP and PACELC, and what each letter means
  • Explain why a five-node cluster survives two failures

2 Practitioner

  • Read a database's consistency guarantees and say what they mean for your code
  • Design timeouts, retries and idempotency for partial failure
  • Explain Lamport timestamps, vector clocks and generation clocks

3 Senior

  • Explain how Raft elects a leader and replicates a log
  • Choose consistency per use case and design for its staleness
  • Plan chaos and client-history tests for a service

4 Expert

  • Design a replicated component and its failure handling
  • Build deterministic simulation testing into a system from the start
  • Set an organisation's standards for distributed correctness

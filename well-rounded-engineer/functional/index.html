Guide / Languages / Functional or Imperative

Functional or imperative

Filter, map, sort, group and reduce: the operations most data code is made of, in Python and Java side by side. What keeps order and what does not, when a parallel stream pays off (measured), and the places where the functional style needs care. Choose by requirement, then practise it in six drills.

The short answer

Functional style means writing code as values flowing through functions that return new values: pure functions (same input, same output, nothing else changed), immutable data, and functions such as filter, map and sorted that take other functions as arguments. Imperative style means loops and variables that change step by step.

Our view: functional style is the better default for transforming data, because each step can be read and tested on its own and nothing changes behind your back. Imperative code is clearer where one real thing must change in place, where the work talks to the outside world, and in a few measured hot spots. The other view is at the end of the page.

The core operations, side by side

OperationDoesPythonJava (streams)

Filter before you sort. Sorting is the expensive step, O(n log n); throwing away what you do not need first makes it cheaper.

Ordering: what keeps order and what does not

  • Sorts are stable in both languages: items with equal keys keep their relative order. Python’s sorting guide guarantees it; Java says “for ordered streams, the sort is stable”. That is why you can sort by a secondary key first and the primary key last.
  • The last sort wins. Sorting by store and then by total leaves the list ordered by total. Use one sort with a two-part key instead (drill 06).
  • A Java stream has an encounter order if its source does (a List, an array). toList() keeps it. A HashSet or a HashMap’s keys have no defined order.
  • forEach on a parallel stream ignores order: the JDK calls it “explicitly nondeterministic”. Use forEachOrdered when order matters, or better, collect.
  • Python’s Executor.map works like the built-in map: results come back in input order, whichever task finishes first.
  • Order costs something in parallel. The JDK notes that order-bound operations such as limit() “may require buffering to ensure proper ordering, undermining the benefit of parallelism”, and that unordered() can help when you do not need the order.

Parallel streams: when they pay off

In Java, .parallelStream() (or .parallel()) splits the work across threads. It helps only when there is enough work to share. Measured on a 4-core machine, Java 21, best of five runs:

WorkloadSequentialParallelVerdict
2,000,000 items, heavy arithmetic in map, then filter and sum1,466 ms441 ms3.3× faster
2,000,000 items, the same map, then sorted().limit(10)1,951 ms598 ms3.3× faster
1,000 items, light map, then sum0.033 ms0.180 ms5× slower: splitting costs more than the work
  • Keep the steps stateless. The JDK’s advice: “the best approach is to avoid stateful behavioral parameters to stream operations entirely”. No shared counters, no shared lists.
  • Collect, do not mutate. map(...).toList() is safe in parallel; forEach(list::add) is not (drill 05).
  • Parallel streams are for CPU work. For waiting on networks or disks, use virtual threads or a thread pool (see Concurrency and How Java Threads Evolved).
  • Python has no parallel streams. Use ProcessPoolExecutor.map for CPU work (each process has its own interpreter) and ThreadPoolExecutor.map for waiting; both return results in input order.
  • Measure first. The third row above is the common case in ordinary business code.

Where the functional style needs care

  1. One real value that many must change. A balance, the seats left on a flight, a cache. The logic can be pure, but somewhere one value changes, guarded by a lock, a transaction or an atomic update (see Concurrency).
  2. Side effects. Charging a card, sending email, reading the clock. Keep them in a thin outer layer around a pure core, often called “functional core, imperative shell” (drill 04).
  3. Single-use pipelines. Generators and streams are lazy and can be read once. Python silently gives an empty generator the second time; Java throws “stream has already been operated upon or closed” (drill 02).
  4. Deep recursion. Neither CPython nor Java turns recursion into a loop. CPython stops at its recursion limit (1,000 by default); a recursive sum of 5,000 items raised RecursionError here. Java overflowed its stack at 100,000 levels and was fine at 10,000. Use a loop when the depth comes from the data (drill 03).
  5. Hot paths on large data. New values mean new allocations. In low-latency code (see Banking & Low Latency) or huge in-memory jobs, changing in place can matter. Measure before choosing.
  6. Naturally stateful algorithms. An LRU cache, a visited set in a graph search, a simulation: possible functionally, usually clearer with loops and a little state.
  7. Debugging long chains. A failure deep in a long pipeline gives a stack trace that is harder to read than a loop’s; the same is said of reactive code on Spring Boot. Name the steps as small functions.
  8. Java specifics. Lambdas cannot throw checked exceptions through java.util.function types; break and early exit are awkward inside a stream; and a lambda that changes a field from a parallel stream brings back the lost update.

Our view, and the other view

Our view: write pure functions and pipelines by default for data, keep side effects at the edges, and drop to imperative code where state is real or a measurement says so. Most bugs in the drills below come from mixing the two without noticing.

The other view: some teams go further and use languages and libraries built for the functional style (immutable collections, effect systems, Scala, Haskell, Clojure), handling state and side effects inside that model. It works well when the whole team is fluent; it is a larger change than adopting streams and comprehensions.

Practise it: six drills

Each drill is a small, broken piece of real code in Python and Java, with tests that fail until you fix it, a prediction to make first, hints, and an explanation of the fix. About 10 to 15 minutes each, in well-rounded-engineer-labs/functional.

DrillWhat breaks
01 · The function that changed its inputTax added twice: a function rewrote its caller’s list
02 · The pipeline you can only read onceRight order count, £0 revenue
03 · The recursion that ran outA chain 100,000 deep overflows the stack
04 · The core and the shellPricing that reads the clock and sends email cannot be tested
05 · The parallel stream that lost itemsItems lost and order random from a parallel forEach
06 · The report sorted the wrong wayFilter and map right, then two sorts where one two-key sort was needed

Checked against: Java 21 API: Stream (forEach is “explicitly nondeterministic”; sorted is stable for ordered streams; toList keeps encounter order, since 16); Java 21 API: java.util.stream package (statelessness, non-interference, ordering and limit() in parallel); Python Sorting Techniques (sorts are guaranteed to be stable); Python: sys.getrecursionlimit; Python: concurrent.futures. Timings and failure counts were measured for this page on a 4-core machine (Java 21, CPython 3) and are in the drills’ explanations.

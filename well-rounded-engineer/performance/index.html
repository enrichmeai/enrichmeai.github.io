Performance engineering

Making systems fast enough at a cost you can afford, by measurement rather than guesswork. The method, the laws that explain slowness, load testing, profiling for the JVM and Python, and where time usually goes in services, databases and pipelines.

The method

  1. Set a goal in numbers: "p95 search latency under 500 ms at 60 requests/s", "nightly load finishes in 40 minutes", "cost under ₹X per 1,000 requests". No goal, no finish line.
  2. Measure the current state in a production-like environment with realistic data and traffic.
  3. Find the bottleneck: the one resource or step limiting everything (CPU, memory, I/O, a lock, a query, a dependency). Use traces and profiles, not intuition.
  4. Change one thing that addresses it.
  5. Measure again the same way. Keep the change only if the numbers improved and nothing else got worse.
  6. Repeat until the goal is met, then stop. Then guard it with a performance test in CI.

Most of the gain usually comes from one or two fixes: a missing index, an N+1 query, a synchronous chain, an oversized payload. Find those before tuning anything clever.

Laws worth knowing

  • Little's law: items in the system = arrival rate × time in system (L = λW). 100 requests/s × 0.2 s = 20 requests in flight, so you need about 20 concurrent workers or connections.
  • Amdahl's law: speeding up a part only helps by that part's share. Making a step that takes 10% of the time infinitely fast saves 10%.
  • Queueing: as utilisation approaches 100%, waiting time grows sharply, not linearly. Plan for 60–70% utilisation at peak.
  • Tail amplification: if one call is slow 1% of the time, a request that fans out to 100 such calls is slow 1 − 0.99100 ≈ 63% of the time.
  • Latency vs throughput: batching raises throughput and usually raises latency; tune for whichever the goal names.

Percentiles, not averages

  • An average hides the users having a bad time. Report p50 (typical), p95 and p99 (the tail), and max.
  • You cannot average percentiles across instances; compute them from histograms.
  • Measure at the edge the user sees (load balancer, client), and also per dependency.
  • Watch for coordinated omission in load tests: a tool that waits for slow responses before sending the next request under-reports latency. Use open-model (arrival-rate) tests.

Profiling the JVM

# Java Flight Recorder: low overhead, safe in production
jcmd <pid> JFR.start duration=60s filename=/tmp/rec.jfr
# or at startup
java -XX:StartFlightRecording=duration=60s,filename=rec.jfr -jar app.jar
# open rec.jfr in JDK Mission Control: hot methods, allocations, locks, GC

# async-profiler: flame graphs of CPU, allocation or wall-clock time
asprof -d 30 -e cpu   -f cpu.html   <pid>
asprof -d 30 -e alloc -f alloc.html <pid>

jcmd <pid> GC.heap_info
jcmd <pid> Thread.print            # thread dump: what is everyone waiting on?
  • Flame graph: width = time spent; look for wide plateaus near the top.
  • Containers: set -XX:MaxRAMPercentage; watch GC pause time and allocation rate.
  • Startup: CDS/AOT caches, lazy initialisation, or native images for scale-to-zero.
  • Blocking I/O: virtual threads (21+) raise concurrency cheaply; CPU-bound work still needs cores.

Micro-benchmarks done right (JMH)

@State(Scope.Benchmark)
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.MICROSECONDS)
@Warmup(iterations = 3) @Measurement(iterations = 5) @Fork(1)
public class ParseBench {
  String raw = "05-05-1959";

  @Benchmark
  public LocalDate parse() {
    return DecisionDateParser.parse(raw);    // return the result so it is not optimised away
  }
}

Hand-written timing loops on the JVM lie: no warm-up, dead-code elimination, JIT effects. Use JMH, and only after a profile shows the code matters.

Profiling Python

# sampling profiler, attach to a running process, no code changes
py-spy top --pid 1234
py-spy record -o profile.svg --pid 1234          # flame graph

# deterministic profiler for a script
python -m cProfile -o out.prof -m loader
python -c "import pstats; pstats.Stats('out.prof').sort_stats('cumtime').print_stats(20)"

# memory
python -X importtime -m loader 2> imports.txt  # slow imports
pip install memray && memray run -m loader     # allocations
  • Replace Python loops over rows with vectorised work: SQL in the warehouse, Polars, PyArrow, NumPy.
  • Threads or asyncio for I/O-bound work; processes for CPU-bound work.
  • Stream large files instead of reading them whole into memory.

Where time usually goes

AreaCommon causeFix
DatabaseMissing index, N+1 queries, fetching unused columns, lock waitsEXPLAIN ANALYZE, indexes, joins or batch loads, select only needed columns (Database Design)
Connection poolsPool too small (queueing) or too large (database overload)Size from Little's law; watch pool wait time
Service callsSequential calls, no timeouts, new connection per callParallelise independent calls, keep-alive, HTTP/2, timeouts
PayloadsHuge JSON responses, no compression, no paginationPaginate, compress, return only needed fields
SerialisationReflection-heavy mapping in hot pathsProfile; precompiled serialisers; smaller objects
Memory and GCHigh allocation rate, heap too small, large object churnProfile allocations; reuse buffers; tune heap and collector
Cold startsLarge images, eager initialisation, JVM warm-upSmaller images, CPU boost, min instances, AOT/native (Cloud Run)
Warehouse queriesFull scans, skewed joins, repeated subqueriesPartition filters, clustering, pre-aggregation (SQL Skills)
PipelinesOne object at a time through one container; small filesParallel tasks, bulk loads, purpose-built engines (Dataflow), compact files
LLM callsLong prompts, sequential calls, large models for simple tasksPrompt caching, parallel calls, streaming, smaller models where evals allow

Concurrency and backpressure

  • Bound every queue and pool; an unbounded queue turns overload into an out-of-memory crash.
  • Shed load early (429/503) when saturated rather than accepting work you cannot finish in time.
  • Set timeouts shorter than the caller's, so work is not done for a caller that has given up.
  • Cloud Run concurrency and max instances, and database pool size, must agree: instances × pool size ≤ database connection limit.
  • Locks and synchronised blocks serialise work; look for them in thread dumps under load.

Performance as a habit

  • Performance budgets in CI: fail the build if a key benchmark or bundle size regresses beyond a threshold.
  • Track p95/p99 per endpoint after every deploy, with deploy markers on dashboards.
  • Cost per unit of work (per request, per row loaded) next to latency: faster that costs 5× may be the wrong trade.
  • Capacity reviews before expected growth or launches.
  • Write down the numbers of each investigation, so the next one starts from evidence.

Levels: what to expect

1 Foundation

  • Read p50/p95/p99 latency and throughput on a dashboard
  • Spot an obvious N+1 query or missing index
  • Run an existing load test and report the result

2 Practitioner

  • Profile a JVM or Python service and fix the hot spot
  • Write load tests with goals and thresholds
  • Size pools and concurrency with Little's law

3 Senior

  • Lead performance investigations end to end with evidence
  • Set performance goals, budgets and capacity plans
  • Balance latency, throughput and cost in design

4 Expert

  • Own performance engineering practice across the organisation
  • Understand runtime, OS and hardware effects deeply
  • Design systems for extreme scale and tail latency

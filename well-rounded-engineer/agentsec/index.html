Agentic AI security and risks

An AI agent is a model that runs in a loop, decides which tools to call and acts on the results. That makes it useful, and it makes every weakness of the model a weakness of everything the agent can touch. This page covers the risks from two sides: agents as a target (prompt injection, excessive agency, insecure tools) and agents as a weapon in an attacker’s hands. It then sets out the controls, the frameworks that name the risks, and how to choose. How agents work is on Agent Harness and MCP; general defence is on Cybersecurity.

Why agency changes the risk

OWASP’s Top 10 for LLM Applications (2025 edition) puts it plainly: the impact of a successful prompt injection depends largely on the business context and on how much agency the model has. A chatbot that can only answer can be made to say something wrong. An agent with tools can be made to do something wrong: send data, change records, run commands.

OWASP calls the vulnerability that lets damaging actions happen excessive agency, and names three root causes:

  • Excessive functionality: tools the task does not need, such as a document reader that can also delete documents.
  • Excessive permissions: a tool connected to other systems with more rights than it needs, such as write access where read access would do.
  • Excessive autonomy: high-impact actions taken without anyone checking them.

The trigger does not have to be an attacker: OWASP lists hallucination from a poorly engineered prompt or a weak model alongside prompt injection, a compromised tool and, in multi-agent systems, a compromised peer agent.

Prompt injection

  • Direct: the user’s own input changes the model’s behaviour, deliberately or by accident.
  • Indirect: the instructions arrive inside content the agent reads: a web page, a file, an email, a tool’s output. OWASP’s example is a user asking for a web page summary, where hidden instructions on the page make the model insert an image link that sends the private conversation to an attacker’s URL.
  • Invisible: injected text does not need to be readable by people, only parsed by the model, and multimodal models can carry it in images.
  • Jailbreaking is a form of prompt injection that makes the model ignore its safety rules altogether.

OWASP says it is unclear whether fool-proof prevention exists, given how models work, and that RAG and fine-tuning do not fully mitigate it. So the controls below aim to limit the damage an injection can do.

The risk lists, by name

OWASP Top 10 for LLM Applications, 2025:

  1. Prompt injection
  2. Sensitive information disclosure
  3. Supply chain
  4. Data and model poisoning
  5. Improper output handling
  6. Excessive agency
  7. System prompt leakage
  8. Vector and embedding weaknesses
  9. Misinformation
  10. Unbounded consumption (including “denial of wallet”)

Agent-specific risks: OWASP’s agentic draft

OWASP’s Agentic Security Initiative has a first public draft of a Top 10 for agentic applications in its repository. It is a draft, so the names and order may change (OWASP’s website, which may carry a later version, could not be reached when this page was checked), but it shows where the risks go beyond a single model call:

RiskIn the draft’s words, roughly
Agent behaviour hijackManipulating an agent’s goals or plans towards the attacker’s aims
Tool misuse and exploitationTricking an agent into using its tools in harmful or unintended ways
Identity and privilege abuseImpersonating agents, or escalating access through identity weaknesses
Agentic supply chainInsecure models, agents, tools or artefacts
Unexpected code executionUnsafe code run through the agent’s behaviour
Memory and context poisoningCorrupting what the agent remembers, so later decisions go wrong
Insecure inter-agent communicationPoisoned messages or abused protocols between agents
Cascading failuresA fault or hallucination in one agent spreading through others
Human-agent trust exploitationExploiting over-trust or approval fatigue in the people overseeing agents
Rogue agentsMalicious or compromised agents acting on their own

Tools and MCP: where the access lives

The Model Context Protocol’s own security best practices name attacks that come from connecting agents to tools:

  • Confused deputy: a program tricked into misusing its own authority on behalf of someone with fewer rights. In MCP, a proxy server in front of a third-party API can be abused to get authorisation without the user’s consent.
  • Token passthrough: an MCP server that accepts a token not issued to it and forwards it downstream. The guidance is blunt: MCP servers must not accept tokens that were not explicitly issued for them.
  • Local server compromise: a local MCP server is a program running on your machine with your rights. Before a one-click setup runs one, the client must show the exact command, mark it as dangerous and ask for approval; it should also run servers in a sandbox with minimal privileges.
  • Broad scopes: a token granted every scope up front turns one leak into access to everything. The guidance is progressive, least-privilege scopes.

More on the protocol, and on checking a server before you install it, is on MCP.

Controls that limit the damage

Drawn from OWASP’s mitigations for prompt injection and excessive agency:

ControlWhat it means in practice
Fewer, narrower toolsOffer only the tools the task needs, each with only the functions it needs. Prefer a “write this file” tool over an open-ended “run a shell command” one.
Least privilegeGive tools the smallest rights in downstream systems, such as read access to one table. Keep the application’s own API tokens in the application, which makes the calls, and out of the model’s prompt and context.
Act as the userRun actions in the context of the user they are for, with that user’s permissions, for example through OAuth with the minimum scope.
Complete mediationAuthorise every request in the downstream system, not by asking the model whether an action is allowed.
Human approvalRequire a person to approve high-impact actions before they happen.
Mark untrusted contentSeparate and label external content so it has less influence. Detection services can help: Microsoft’s Prompt Shields, for example, scan user prompts and documents for attack patterns. Microsoft notes the models are trained and evaluated mainly on English, so test them with your own attacks.
Treat output as untrustedValidate and encode what the model produces before it reaches a browser, a shell, a query or another system (OWASP’s improper output handling).
Log, limit, testLog tool calls, rate-limit actions so monitoring can catch problems before the damage grows, and red-team the agent as an untrusted user.

Tools apply these too. Claude Code’s security documentation, for example (Anthropic’s description of its own product), lists a permission system that asks before sensitive operations, approval for commands that fetch from the web, a trust dialog for a new folder, a separate approval prompt for MCP servers in a project’s .mcp.json, and sandbox network isolation.

Agents in an attacker’s hands

In November 2025 Anthropic reported disrupting an espionage campaign it assessed, with high confidence, to be run by a state-sponsored group using its Claude Code tool. Anthropic said it believes this is the first documented case of a large-scale cyberattack executed without substantial human intervention. By Anthropic’s account:

  • The attackers jailbroke the model by splitting the attack into small, innocent-looking tasks and telling it that it worked for a security firm doing defensive testing.
  • The agent did reconnaissance, wrote exploit code, harvested credentials and extracted data, with tools often reached over MCP. AI did an estimated 80 to 90% of the work, with people stepping in at perhaps four to six decision points per campaign.
  • It targeted around thirty organisations and succeeded in a small number.
  • It was not flawless: it sometimes hallucinated credentials, or claimed to have found secrets that were in fact public.

This is one vendor’s account of misuse of its own product, and it says it sees only its own platform. Analysis: the lesson for defenders does not depend on the vendor: attacks can now run at machine speed, so detection and response need to be automated too. Anthropic itself advises security teams to try AI for SOC automation, threat detection, vulnerability assessment and incident response. The other reading: this is one vendor’s account that others have not replicated, and the share of the work an AI does may differ for other attackers and tools.

Frameworks to map against

  • OWASP Top 10 for LLM Applications and the agentic draft above, for application risks.
  • MITRE ATLAS (Adversarial Threat Landscape for AI Systems): a public knowledge base of adversary tactics, techniques and procedures aimed at AI systems, with its data published in a public repository. ATT&CK, its counterpart for attacks in general, is on Cybersecurity.
  • The MCP security best practices, for anything that connects agents to tools.

Choose by requirement

If this is true for your agentIt leans towards (analysis)
It reads untrusted content (web, email, uploads) and can also send data or call external URLsBreak the chain: remove outbound tools, or require approval before anything leaves
It acts for many different usersRun each action as that user, with their permissions and a narrow OAuth scope; never one shared service account with wide rights
It can change money, records or infrastructureHuman approval for those actions, and authorisation enforced in the downstream system
It writes or runs codeA sandbox with restricted file system and network access, and generated code reviewed like any other
It installs or connects to third-party MCP serversA list of approved servers, the exact command shown before first run, and tokens issued only for each server
Several agents pass work to each otherTreat every agent’s output as untrusted input to the next, and log the whole chain
Cost can grow without limitRate limits and spending caps per user and per run

Prove it

  • Test with attacks: put injection payloads in documents, pages and tool outputs, and assert the agent does not act on them (see RAG).
  • Review the permission map: every tool, its rights, and who approves what.
  • Audit: every tool call logged with the user, the agent and the input that led to it.

This card is analysis. Only the injection testing draws on OWASP, which advises testing the model as an untrusted user.

Our view, and the other view

Our view: design every agent assuming its model will at some point follow an attacker’s instructions, because OWASP says no fool-proof prevention is known. What matters is what it can do when that happens: narrow tools, least privilege, approval for high-impact actions, and authorisation outside the model.

The other view: approvals and narrow tools reduce what agents are useful for, and constant prompts can wear down the people answering them. The OWASP agentic draft lists exploiting “over-trust or fatigue in human oversight” as a risk, and Claude Code’s security documentation describes allowlisting frequently used safe commands as a “prompt fatigue mitigation”. On this view, more autonomy inside a sandbox with network isolation, plus monitoring, is worth the trade: the sandbox then carries more of the safety.

Levels: what to expect

1 Foundation

  • Explain direct and indirect prompt injection with an example
  • Name the three root causes of excessive agency
  • Treat model output as untrusted input

2 Practitioner

  • Give an agent only the tools and permissions its task needs
  • Add human approval for high-impact actions
  • Check an MCP server and its scopes before connecting it

3 Senior

  • Design agent actions to run as the user, with authorisation outside the model
  • Red-team an agent with injected documents and tool outputs
  • Sandbox agents that write or run code

4 Expert

  • Set an organisation's policy for agents, tools and approvals
  • Map agent risks to OWASP and MITRE ATLAS
  • Plan detection and response for attacks at machine speed

Each level includes the ones before it. See Start here for what the levels mean.

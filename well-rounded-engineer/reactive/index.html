Guide / Building services / Reactive & Backpressure

Reactive and backpressure

Sooner or later every system meets a fast producer and a slow consumer. This page explains what “reactive” really means, why that meeting needs back pressure, and how it works in Reactive Streams, Java’s Flow, RxJava, Reactor, Kotlin, Node.js, Kafka, TCP and HTTP/2. With runnable Java and a way to choose by requirement.

The short answer

Picture a service that reads orders from a queue and writes each one to a database. On a quiet day the database keeps up. Then a sale starts, orders arrive ten times faster, and the question nobody asked at design time suddenly matters: where do the orders that cannot be written yet go? This page is about that question.

Reactive, in the Spring team’s words, “refers to programming models that are built around reacting to change”: network components reacting to I/O events, UI controllers reacting to mouse clicks. Instead of a thread waiting for an answer, code is called when the answer arrives.

Back pressure is borrowed from plumbing, where it is the resistance that pushes back against flow in a pipe. In software it is a way to regulate the flow of data so that components are not overwhelmed: the slow part of a system tells the fast part to ease off.

The two go together for one reason, which the Spring documentation puts plainly: “In synchronous, imperative code, blocking calls serve as a natural form of back pressure that forces the caller to wait. In non-blocking code, it becomes important to control the rate of events so that a fast producer does not overwhelm its destination.” Take away the waiting, and you must put the brake back on deliberately.

This page goes deep on one idea. The history of how Java got here is on How Java Threads Evolved and IO, NIO & Web Servers; Spring’s choice between blocking and reactive is on Spring Boot.

The problem in one picture

The picture is simple, and once you have seen it you will spot it everywhere. Every pipeline has a slowest step: a database that takes 10 ms per insert, a partner API with a rate limit, a phone on a weak signal. Whatever arrives faster than that step can handle has to go somewhere. Spring’s documentation answers the obvious question, “what if a publisher cannot slow down?”, in one line: “it has to decide whether to buffer, drop, or fail.” Back pressure is the fourth option, and the best one when the source allows it: ask the producer to slow down.

Reactive Streams: the contract

Back pressure only works if both sides agree on how to ask for more, and that agreement is what Reactive Streams provides. It began in late 2013 as an initiative between engineers at Netflix, Pivotal and Lightbend, with contributions from Red Hat, Oracle, Twitter and others. Its aim is to govern “the exchange of stream data across an asynchronous boundary” (to another thread or pool) while making sure the receiving side is not forced to buffer arbitrary amounts of data. Version 1.0 for the JVM was released in April 2015 with the Java API, a written specification, a test kit (TCK) and examples, so that libraries from different teams can be plugged together.

InterfaceMethodsIts job
Publisher<T>subscribe(Subscriber)Produces items, but only as many as have been asked for
Subscriber<T>onSubscribe, onNext, onError, onCompleteReceives the subscription, then the items, then one ending signal
Subscriptionrequest(long n), cancel()The line back to the producer: “send me n more”, or “stop”
Processor<T,R>both of the aboveA processing stage that is a subscriber on one side and a publisher on the other

Four rules worth knowing by heart (numbered as in the specification):

  • 1.1: the total number of onNext signals a publisher sends “MUST be less than or equal to the total number of elements requested”. This one rule is back pressure.
  • 2.1: a subscriber “MUST signal demand via Subscription.request(long n) to receive onNext signals”. Nothing flows until someone asks.
  • 3.9: asking for zero or a negative number is an error, signalled with IllegalArgumentException.
  • 3.17: a demand of Long.MAX_VALUE may be treated as “effectively unbounded”. Requesting it is how a subscriber says “send everything”, and so turns back pressure off.

Into the JDK. Doug Lea, who leads JSR 166 (the java.util.concurrent work), proposed the interfaces for Java 9, and they arrived through JEP 266 as java.util.concurrent.Flow: the same four interfaces nested in one class, plus SubmissionPublisher, a ready-made publisher. The specification’s own README sums up the design: “Since back-pressure is mandatory the use of unbounded buffers can be avoided.”

Run it: a slow subscriber slows the producer

Reading the rules is one thing; watching them work is more convincing. This example uses only the JDK (Java 21 or later; save it as SlowSubscriber.java and run java SlowSubscriber.java). The subscriber asks for one item at a time and takes 100 ms over each. The publisher has room for four unread items. SubmissionPublisher.submit “blocks until resources are available”, so once the buffer is full, the producing loop is held to the consumer’s pace.

import java.util.concurrent.Flow;
import java.util.concurrent.ForkJoinPool;
import java.util.concurrent.SubmissionPublisher;

public class SlowSubscriber {
    public static void main(String[] args) throws Exception {
        // a publisher with room for 4 unread items per subscriber
        try (var publisher = new SubmissionPublisher<Integer>(ForkJoinPool.commonPool(), 4)) {
            publisher.subscribe(new Flow.Subscriber<>() {
                Flow.Subscription subscription;
                public void onSubscribe(Flow.Subscription s) { subscription = s; s.request(1); } // ask for one
                public void onNext(Integer item) {
                    sleep(100);                                  // a slow consumer
                    System.out.println("consumed " + item);
                    subscription.request(1);                     // ready for the next one
                }
                public void onError(Throwable t) { t.printStackTrace(); }
                public void onComplete() { System.out.println("done"); }
            });
            for (int i = 1; i <= 10; i++) {
                long start = System.nanoTime();
                publisher.submit(i);                             // blocks while the buffer is full
                long waited = (System.nanoTime() - start) / 1_000_000;
                System.out.println("produced " + i + (waited > 10 ? " after waiting " + waited + " ms" : ""));
            }
        }
        Thread.sleep(1500);
    }
    static void sleep(long ms) { try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); } }
}

What it printed when we ran it:

produced 1
produced 2
produced 3
produced 4
produced 5
consumed 1
produced 6 after waiting 96 ms
consumed 2
produced 7 after waiting 97 ms
...

Five items go straight in (one being consumed, four in the buffer). From then on, every submit waits about 100 ms: the consumer’s speed has travelled back up to the producer. Change s.request(1) to s.request(Long.MAX_VALUE) and the producer is no longer paced by requests; it is held only by the buffer. The other publishing method, offer, “may drop items (either immediately or with bounded timeout)” instead of blocking, with a handler to decide what to do.

When the producer cannot slow down

Asking the producer to slow down is the best answer, but not every producer can listen. Mouse movements, a sensor, a market data feed and a timer all keep coming whether you are ready or not. For those, every library offers the same four choices; only the names differ, so it helps to see them side by side.

Push, pull, and the hybrid in between

There are really only two ways for data to move between a producer and a consumer, and Reactive Streams cleverly uses both. An Iterator is pull: the consumer asks for the next item when it is ready, so it can never be overwhelmed, but it waits whenever the item is not ready yet. A callback or event listener is push: items arrive as soon as they exist, which is fast, but the consumer has no say in the rate.

Reactive Streams is both. Reactor’s reference guide calls it “a push-pull hybrid”: the subscriber pulls by requesting n items, and the publisher pushes each one as soon as it exists, up to that limit. Libraries also prefetch, requesting a batch ahead of need to avoid a round trip per item, and operators can change the request on the way up (a buffer(10) that is asked for one batch may ask upstream for ten items).

Kafka sits firmly at the pull end. A consumer calls poll() when it is ready, max.poll.records limits how many records one call returns, and the consumer API’s “Consumption Flow Control” section offers pause() and resume() per partition, for example to let a lagging stream catch up before reading further from one that is ahead. Back pressure across the network

Library back pressure stops at the edge of the process. The good news is that between machines you are not on your own: the network protocols have had their own back pressure for decades, long before any reactive library existed.

LayerHow the receiver says “slow down”
TCPEvery segment carries a window: “the range of sequence numbers the sender of the window (the data receiver) is currently prepared to accept”, related to its free buffer space (RFC 9293). When the receiving application stops reading, the window shrinks towards zero and the sender stops.
HTTP/2Credit-based flow control with WINDOW_UPDATE frames, per stream and per connection. The initial window is 65,535 octets, and “a sender MUST respect flow-control limits imposed by a receiver” (RFC 9113). It works hop by hop, not end to end, so a proxy has its own windows on each side.
gRPC (Java)Streams can switch to manual flow control: disableAutoRequest(), then request(1) when ready, and check isReady() before sending (the grpc-java manualflowcontrol example).
RSocketCarries Reactive Streams across the network: a REQUEST_N frame means “Request N more items with Reactive Streams semantics”.
Spring WebFluxReads and writes HTTP bodies “through non-blocking I/O with Reactive Streams back pressure”, on servers such as Reactor Netty.

Analysis: this is why a slow mobile client does not need special code in a WebFlux endpoint. When the client reads slowly, TCP’s window fills, the server cannot write, and demand stops flowing up the reactive chain to the database query. It is also why a WebSocket in the browser is harder: its API has no back pressure (see Real-time to the Browser).

The same idea in other languages

None of this is special to Java. Once you know the pattern, you will recognise it in every language that handles streams.

Node.js streams. write() returns false when the data buffer has exceeded highWaterMark (commonly 16 kB by default) or the write queue is busy, and a 'drain' event fires once it has emptied. The Node.js guide’s rule: “Never call .write() after it returns false but wait for ‘drain’ instead.” pipe() does this for you.

// Node.js: respect write()'s answer, or memory grows without limit
function copy(source, destination) {
  source.on('data', (chunk) => {
    if (!destination.write(chunk)) {         // false: the buffer is above highWaterMark
      source.pause();                        // stop reading...
      destination.once('drain', () => source.resume());  // ...until it has emptied
    }
  });
  source.on('end', () => destination.end());
}
// in practice, source.pipe(destination) or stream.pipeline() does this for you

Kotlin Flow. Flows are sequential by default: the producer’s emit suspends until the collector has handled the value, which is back pressure with no protocol at all. buffer() lets the producer run ahead in a separate coroutine (by default it suspends again when the buffer overflows), and conflate() means the emitter “is never suspended due to a slow collector”, which skips to the newest value.

// Kotlin Flow: emit() suspends while the collector is busy, so a flow is paced by default
prices()
    .conflate()                 // a slow collector skips to the most recent value
    .collect { show(it) }

events()
    .buffer(64)                 // up to 64 waiting; then emit() suspends again
    .collect { save(it) }

RxJava. Version 2 onwards split its types: Flowable supports Reactive Streams and back pressure; Observable has none and is meant for short sequences and GUI events. Reactor, the library under Spring WebFlux, implements Reactive Streams in all its operators, with Mono (0 or 1 item) and Flux (0 to N).

// Reactor (Spring WebFlux): name what happens when the consumer falls behind
Flux<Reading> readings = sensor.readings()        // a source that cannot slow down
    .onBackpressureLatest()                       // keep only the newest reading
    .publishOn(Schedulers.parallel());

// a blocking call, kept off the event-loop threads
Mono<Customer> customer = Mono.fromCallable(() -> legacyClient.find(id))
    .subscribeOn(Schedulers.boundedElastic());

Blocking code has back pressure too

It is easy to forget, in all the talk of reactive libraries, that plain blocking code has had back pressure all along. A blocked thread is the oldest flow control there is: the caller cannot send the next request until the last one returns. The trouble used to be cost: one platform thread per waiting call. Virtual threads (final in Java 21, JEP 444) make waiting cheap again, and JEP 444 says how to limit concurrency once threads are no longer the limit: “do not be tempted to pool virtual threads in order to limit concurrency. Instead use constructs specifically designed for that purpose, such as semaphores.”

import java.util.concurrent.Executors;
import java.util.concurrent.Semaphore;
import java.util.concurrent.atomic.AtomicInteger;

public class Limit {
    static final Semaphore permits = new Semaphore(20);   // the service can take 20 calls at once
    static final AtomicInteger inFlight = new AtomicInteger(), peak = new AtomicInteger();

    public static void main(String[] args) {
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < 1_000; i++) executor.submit(Limit::callService);
        }                                                  // waits for all 1,000 tasks
        System.out.println("peak concurrent calls: " + peak.get());
    }

    static void callService() {
        try {
            permits.acquire();                             // wait here when 20 are already running
            try {
                peak.accumulateAndGet(inFlight.incrementAndGet(), Math::max);
                Thread.sleep(50);                          // stands in for the remote call
                inFlight.decrementAndGet();
            } finally {
                permits.release();
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}

When we ran it, it printed peak concurrent calls: 20 and took about 3 seconds: 1,000 calls of 50 ms, 20 at a time, is 2.5 seconds of waiting plus start-up.

How big should the limit be? Little’s law, proved by John Little in 1961, says the average number of items in a stable system equals the arrival rate times the average time each spends inside: L = λW. With 20 permits and 50 ms per call, the most this code can sustain is 20 ÷ 0.05 = 400 calls a second. If 600 a second arrive, a queue grows without end, whatever the threading model. Back pressure, a bigger limit or shedding load are the only ways out.

The thread pool version. A ThreadPoolExecutor with a bounded queue is back pressure for tasks. Its CallerRunsPolicy makes the submitting thread run a rejected task itself, which the JDK documentation calls “a simple feedback control mechanism that will slow down the rate that new tasks are submitted”. With an unbounded LinkedBlockingQueue, nothing pushes back at all.

Mistakes that defeat back pressure

Most back pressure problems are not exotic. They come from a handful of ordinary decisions, each of which looks harmless on the day it is made.

MistakeWhat happensInstead
An unbounded buffer or queue “just in case”The difference in speed piles up in memory until the process dies, often long after the causeBound every queue and decide what happens when it is full
Requesting Long.MAX_VALUE everywhereRule 3.17 lets the publisher treat it as unbounded: back pressure is switched offRequest in batches, or let the library’s operators manage demand
A blocking call on an event-loop threadEvery request sharing that thread stallsWrap it: Reactor’s FAQ uses Mono.fromCallable(...).subscribeOn(Schedulers.boundedElastic()), which also caps how many threads blocking work can take
An RxJava Observable for a large or fast streamNothing pushes back; RxJava’s wiki notes that MissingBackpressureException usually surfaces at observeOn, while the cause is a source that ignores requests, such as interval()Use Flowable with an explicit strategy
Treating retries as freeA slow dependency gets more traffic just when it needs less (see the retry storm on Distributed Systems)Retry with backoff and a budget, behind a circuit breaker

Our view, and the other view

Our view: learn back pressure as a property of systems, not of one library. Ask of every queue, buffer and stream in a design: what happens when the consumer is ten times slower than the producer? If the answer is “memory grows”, the design is not finished. For most request-and-response services, plain blocking code on virtual threads with a semaphore and bounded queues gives you that answer with the least new code.

The other view: reactive libraries make back pressure part of the type, end to end, from the database driver (R2DBC) to the HTTP response, and they compose streams, timeouts and retries in one model. For streaming, server-sent events and many long-lived connections, teams that have learned the model may find it clearer than hand-placed semaphores.

Choose by requirement

If this is true for youLean towards
Request and response, mostly waiting on a database or other servicesBlocking code on virtual threads, with a semaphore per dependency
Streaming results, server-sent events, very many idle connectionsReactive (WebFlux, Reactor, Mutiny) or Kotlin Flow

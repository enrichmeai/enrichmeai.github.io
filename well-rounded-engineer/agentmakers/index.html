Guide / AI / How Anthropic & OpenAI Build Agents

How Anthropic and OpenAI build agents

The two companies behind Claude and ChatGPT have each published how they think agents should be built. Where they agree, where they differ, the patterns and numbers from their own engineering writing, the tools each offers, and an agent loop you can run in thirty lines.

The short answer

Strip away the products and both companies describe the same machine: a language model with instructions and tools, running in a loop. The model decides the next step, the program carries it out, the result goes back to the model, and this repeats until the job is done or a limit is reached. Everything else, multiple agents, memory, guardrails, is built around that loop.

Their advice is also strikingly similar: start simple. Anthropic recommends “finding the simplest solution possible, and only increasing complexity when needed”; OpenAI’s guide says “maximize a single agent’s capabilities first”. The differences are in emphasis and tooling, and they are worth knowing if you are choosing between them. For the general engineering of a harness, see Agent Harness.

Anthropic: workflows first, agents when needed

Anthropic’s widely read post Building effective agents (December 2024) draws one distinction that shapes everything else:

  • Workflows are “systems where LLMs and tools are orchestrated through predefined code paths”.
  • Agents are “systems where LLMs dynamically direct their own processes and tool usage”.

Workflows give predictability for well-defined tasks; agents give flexibility when the steps cannot be known in advance. The building block for both is the augmented LLM, a model with retrieval, tools and memory. On top of it, Anthropic names five workflow patterns:

PatternWhat it doesAnthropic’s example
Prompt chainingEach call works on the output of the one beforeWrite marketing copy, then translate it
RoutingClassify the input, then send it to the right specialistRefunds, technical support and general questions each go down their own path
ParallelizationSeveral calls work at once and their outputs are combinedSectioning a task into independent parts, or voting: running the same task several times
Orchestrator-workersA central model breaks the task down and delegates to workersCoding changes across many files, where the files cannot be known in advance
Evaluator-optimizerOne call writes, another critiques, in a loopLiterary translation, refined by a critic

For agents themselves, it follows three principles: keep the design simple, show the agent’s planning steps, and carefully craft the agent-computer interface, the tools and their documentation, with as much care as a human interface. On frameworks it is cautious: they help you start, but “ensure you understand the underlying code”.

Anthropic: what it learned building its own agents

  • Multi-agent research (June 2025). Claude’s Research feature uses an orchestrator-worker design: a lead agent plans and spawns subagents that search in parallel, each with its own context window. A lead on Claude Opus 4 with Claude Sonnet 4 subagents beat a single Opus 4 agent by 90.2% on Anthropic’s internal research evaluation. The cost is real: agents used about 4× the tokens of a chat, and multi-agent systems about 15×; on a browsing evaluation (BrowseComp), token usage alone explained 80% of the variance in performance. Anthropic notes most coding tasks have less to parallelise than research.
  • Context engineering (September 2025). As the context grows, a model’s ability to recall what is in it falls, which Anthropic calls context rot; so context “must be treated as a finite resource with diminishing marginal returns”. The job is curating what goes in at every step, not just writing a good prompt.
  • Long-running agents. For work that spans many context windows, Anthropic uses an initializer agent that sets up the environment, a feature list and a progress file (claude-progress.txt), then a coding agent that makes incremental progress in each session and leaves clear notes for the next.
  • Skills. A skill is a folder with a SKILL.md file of instructions, scripts and resources. Only its short description is loaded at first, the rest when needed, which Anthropic calls progressive disclosure.
  • Code instead of tool calls. Presenting MCP servers to an agent as code APIs, rather than as direct tool calls, cut one example from 150,000 tokens to 2,000, a saving of 98.7%.

The Claude Agent SDK, which Anthropic describes as a general-purpose agent harness, packages much of this for developers.

OpenAI: a practical guide and a small set of primitives

OpenAI’s A practical guide to building agents starts from where agents pay off: workflows that have resisted automation because of complex decision-making, rules that are hard to maintain, or heavy reliance on unstructured data. Otherwise, it says, a deterministic solution may be enough. An agent has three core components: a model, tools and instructions.

  • The run loop. Every agent needs a “run”, a loop that continues until an exit condition: a final output, an error, or a maximum number of turns.
  • One agent first. Before adding agents, use prompt templates and clearer tools. Split only when instructions become tangled with conditions, or the agent keeps choosing the wrong tool.
  • Two multi-agent patterns. In the manager pattern, a central agent calls specialist agents as tools and keeps control. In the decentralised pattern, agents hand off to one another as peers; a handoff is a one-way transfer of control.
  • Guardrails as layers. Relevance classifiers, safety classifiers for jailbreaks and prompt injection, PII filters, moderation, rules such as blocklists and length limits, and risk ratings on tools, combined with ordinary authentication and access control.
  • Humans in the loop. Hand control to a person when the agent exceeds its failure limits, or before high-risk actions that are sensitive or irreversible.
  • Choosing models. Set up evaluations for a baseline, meet the accuracy target with the best model, then swap in smaller models where they still pass.

The tooling follows the same shape. The Agents SDK, a “production-ready upgrade” of OpenAI’s earlier Swarm experiment, has a deliberately small set of primitives: agents, agents as tools or handoffs, and guardrails, with built-in tracing. In October 2025 OpenAI added AgentKit, built on its Responses API: Agent Builder, a visual canvas for multi-agent workflows; a Connector Registry for admins to govern data and tool connections; ChatKit for embedding agent chat in products; and new evaluation and reinforcement fine-tuning features.

Run it: the loop at the heart of both

Both companies’ diagrams reduce to this. The “model” below is a stand-in script so the program runs without an API key; swap in a real model call and the rest stays the same. Notice the two ideas both guides insist on: a guardrail on which tools may run, and an exit condition so a confused agent cannot loop for ever.

# The loop at the heart of every agent: the model picks a tool, the program runs it,
# the result goes back into the context, until the model gives a final answer.
# The "model" here is a stand-in script, so this runs offline; swap in a real LLM call.

def get_weather(city):            # a tool: an ordinary function
    return {"Paris": "14°C, rain", "Chennai": "31°C, sun"}.get(city, "unknown")

def fake_model(context):          # decides the next step from what it has seen so far
    seen = [m for m in context if m["role"] == "tool"]
    if len(seen) < 2:
        city = ["Paris", "Chennai"][len(seen)]
        return {"tool": "get_weather", "args": {"city": city}}
    return {"final": f"Paris is {seen[0]['content']}; Chennai is {seen[1]['content']}."}

TOOLS = {"get_weather": get_weather}
BLOCKED = {"delete_account"}       # a guardrail: actions the agent may never take
MAX_TURNS = 5                      # an exit condition, so a confused agent cannot loop for ever

def run(task):
    context = [{"role": "user", "content": task}]
    for turn in range(1, MAX_TURNS + 1):
        step = fake_model(context)
        if "final" in step:
            return turn, step["final"]
        if step["tool"] in BLOCKED or step["tool"] not in TOOLS:
            return turn, "stopped: tool not allowed"
        result = TOOLS[step["tool"]](**step["args"])
        print(f"turn {turn}: {step['tool']}({step['args']}) -> {result}")
        context.append({"role": "tool", "content": result})
    return MAX_TURNS, "stopped: too many turns"

turns, answer = run("Compare the weather in Paris and Chennai")
print(f"answer after {turns} turns: {answer}")

What it printed when we ran it:

turn 1: get_weather({'city': 'Paris'}) -> 14°C, rain
turn 2: get_weather({'city': 'Chennai'}) -> 31°C, sun
answer after 3 turns: Paris is 14°C, rain; Chennai is 31°C, sun.

Three turns: two tool calls, each result fed back as “ground truth”, in Anthropic’s phrase, then a final answer. A multi-agent system is this loop, with some of the tools being other agents.

Where they agree, and where they differ

TopicAnthropicOpenAI
First adviceSimplest solution; workflows before agentsMaximise one agent before adding more
Core unitAugmented LLM: model plus retrieval, tools, memoryAgent: model plus tools plus instructions
Multi-agent shapeOrchestrator-workers, as in its Research featureManager pattern, or peer handoffs
What it writes most aboutContext as a scarce resource, tool design, long-running workGuardrails, human escalation, model selection
FrameworksUseful, but understand the code underneathA small, Python-first SDK, plus a visual builder
Developer toolsClaude Agent SDK, Agent Skills, MCPAgents SDK, Responses API, AgentKit
Both insist onEvaluations before and after changes; clear tools; limits and exit conditions; a human for risky steps

Choosing an approach, by requirement

If this is true for youIt leans towards
The steps are known and must be predictableA workflow: prompt chaining or routing, in plain code
The steps depend on what the agent findsA single agent in a loop, with good tools and a turn limit
The work splits into many independent searchesOrchestrator-workers or a manager pattern, accepting the token cost
The task runs for hours across many sessionsA harness with progress files and incremental steps, as in Anthropic’s long-running design
Product, legal and engineering must review the flow togetherA visual builder such as OpenAI’s Agent Builder
The agent can move money or delete dataLayered guardrails and a human approval step, whichever company’s model you use
Your team already uses one providerIts SDK first; both are model-centred, so switching costs effort

Our view, and the other view

Our view: the two guides agree far more than the products suggest. Learn the loop, the patterns and the guardrails once, from both, and the choice of SDK becomes a detail.

The other view: these are vendors’ own write-ups, and each describes its own products in the best light; a framework-neutral approach, or an open-source one, avoids tying your agents to one company’s models and pricing.

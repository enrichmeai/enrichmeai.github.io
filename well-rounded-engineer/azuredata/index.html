Guide / Cloud providers / Data on Azure

Data engineering on Azure

The same lifecycle as Data on GCP and Data on AWS, on Microsoft Azure: land, process, store, serve and govern. The service names differ; the ideas in Data Engineering do not. GCP vs AWS vs Azure maps the services side by side and follows one pipeline through all three.

Service map by lifecycle stage

StageAzure serviceWhat it is for
Land and storeAzure Data Lake Storage (Blob Storage with the hierarchical namespace turned on); OneLake in Microsoft Fabric, built on itThe data lake’s files, raw and curated, with directories and file-level permissions
Stream inEvent Hubs, with a built-in Apache Kafka endpointEvents at high volume; existing Kafka clients can often connect by changing only configuration
Change data captureData Factory’s change data capture resource; mirroring in FabricRead only what changed in an operational database, or replicate it continuously into OneLake
Process (ETL)Data Factory; Azure Databricks; Spark in Fabric; Stream Analytics for streamsBatch and streaming transformation
Open tablesOneLake tables, stored as Delta Parquet or IcebergTables any engine can read, without a proprietary format
QueryFabric Data Warehouse; serverless SQL pool in Azure Synapse (T-SQL on files in the lake); Azure Data Explorer for logs and time seriesAnalysis and serving
OrchestrateData Factory pipelines; Apache Airflow jobs in FabricSchedules and dependencies. See Airflow DAGs
Catalog and governMicrosoft Purview (Data Map, Unified Catalog)Find, classify and govern data wherever it lives
VisualisePower BIReports and dashboards

A reference architecture

  1. Files and events land in a raw directory of a Data Lake Storage account, never edited.
  2. Data Factory copies from sources on a schedule; its change data capture reads only the rows that changed.
  3. Spark in Azure Databricks or Fabric writes cleaned, partitioned Delta or Iceberg tables to a curated area.
  4. The Fabric warehouse, or serverless SQL on the lake, serves SQL; Power BI reports read from it.
  5. Purview catalogs the tables; Azure roles and ACLs grant each team only what it needs.

Choosing between similar services

Analysis, built on each service’s own description.

  • Fabric or separate Azure services? Fabric is one analytics platform covering ingestion, transformation, real-time processing, analytics and reporting, with OneLake underneath. Separate services (Data Lake Storage, Data Factory, Databricks, Synapse) suit teams that already run them or want to choose each piece.
  • Fabric warehouse or serverless SQL? The warehouse for star schemas and curated, governed data. Serverless SQL for ad-hoc T-SQL on files in the lake, billed by the data each query processes.
  • Databricks or Spark in Fabric? Databricks for a full data and AI platform in your cloud account; Fabric’s Spark when the rest of your work is already in Fabric and OneLake.
  • Data Factory or Airflow jobs? Data Factory for copying between many data stores and building transformations visually; Airflow when pipelines are written as Python DAGs. See Airflow DAGs.
  • Event Hubs or a Kafka cluster you run? Event Hubs runs many existing Kafka workloads with configuration changes only and no cluster to manage. Run Kafka yourself only for features or control it does not give you. See Kafka.

Handy commands

The Azure CLI calls the same APIs the portal does. Names in angle brackets are yours to fill in. --auth-mode login uses your Microsoft Entra sign-in instead of an account key.

# sign in
az login

# create the raw directory and upload a file into the lake (Data Lake Storage)
az storage fs directory create -n raw/orders -f <filesystem> --account-name <account> --auth-mode login
az storage fs file upload --source orders.csv -p raw/orders/dt=2026-11-14/orders.csv \
  -f <filesystem> --account-name <account> --auth-mode login

# run a Data Factory pipeline, then check the run (the datafactory extension)
az datafactory pipeline create-run --factory-name <factory> --resource-group <rg> \
  --name <pipeline> --parameters '{"run_date":"2026-11-14"}'
az datafactory pipeline-run show --factory-name <factory> --resource-group <rg> --run-id <run-id-from-above>

# create an event hub for order events
az eventhubs eventhub create --resource-group <rg> --namespace-name <namespace> --name orders --partition-count 4

# let a pipeline's managed identity read the lake's data
az role assignment create --assignee <principal-id> --role "Storage Blob Data Reader" --scope <storage-account-id>

# move raw data to cooler tiers as it ages
az storage account management-policy create --account-name <account> --resource-group <rg> --policy @policy.json

Each command and option was checked against the Azure CLI’s own help definitions (the azure-cli and azure-cli-extensions repositories).

Identity and access for data, in practice

  • Managed identities, not keys: jobs run as managed identities, which remove the need to manage credentials; people sign in through Microsoft Entra ID.
  • Two layers: Azure roles grant coarse access, such as read on a whole storage account or container (Storage Blob Data Reader, Contributor, Owner); ACLs grant fine access to directories and files.
  • Roles are checked first. If a role already grants access, ACLs are ignored, so an ACL cannot narrow what a role allows. Give broad roles sparingly.
  • Put groups in ACLs, not people: Microsoft recommends security groups, so people can join and leave without rewriting ACLs across a directory tree.
  • Avoid account keys: Shared Key access is effectively super-user, and ACLs do not apply to it.

Cost controls

  • Access tiers: hot has the highest storage cost and lowest access cost; cool and cold cost less to store and more to read (cool data should stay at least 30 days); archive is offline.
  • Lifecycle policies move blobs to a cooler tier by age: time since creation, since last change, or since last access (last access needs access time tracking turned on).
  • Serverless SQL bills by data processed: you pay only for the data your queries process, and a query can read a chosen subset of columns.
  • Pause a Fabric capacity you are not using; pausing can make content on it unavailable, so check what depends on it first.
  • Cost Management shows where the money goes; tag resources per team and pipeline so a cost has an owner.

Levels: what to expect

1 Foundation

  • Name the Azure service for each data stage
  • Land files in Data Lake Storage and query them with SQL
  • Explain managed identities for data jobs

2 Practitioner

  • Build a pipeline: Data Lake Storage raw, Data Factory or Spark, curated Delta or Iceberg, SQL
  • Grant access with Azure roles and ACLs together
  • Run and monitor Data Factory pipelines from the CLI

3 Senior

  • Choose between Fabric and separate Azure services
  • Design a governed lake with Purview
  • Plan cost with access tiers, lifecycle policies and capacity

4 Expert

  • Own the organisation's Azure data architecture
  • Lead migrations between clouds or from on-premises
  • Set data platform standards across teams

Each level includes the ones before it. See Start here for what the levels mean.

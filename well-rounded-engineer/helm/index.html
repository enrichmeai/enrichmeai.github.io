Helm charts

Helm packages Kubernetes manifests as charts: templates plus default values, versioned and installed as releases you can upgrade and roll back. Chart structure, templating, values per environment, hooks, testing, publishing to a registry, and how Helm fits with GitOps and Kustomize. Basics are on Kubernetes.

Concepts

TermMeaning
ChartA package: templates, default values and metadata
ValuesInputs that fill the templates; defaults in values.yaml, overridden per environment
ReleaseOne installed instance of a chart in a namespace, with a name
RevisionEach install, upgrade or rollback of a release; the history Helm can roll back to
Repository / registryWhere charts are published: an HTTP chart repo or an OCI registry (e.g. Artifact Registry)
Chart version vs app versionversion changes when the chart changes; appVersion names the application it deploys

Chart structure

legal-api/
  Chart.yaml            # name, versions, dependencies
  values.yaml           # defaults
  values.schema.json    # optional: validate values
  templates/
    _helpers.tpl        # named templates (labels, names)
    deployment.yaml
    service.yaml
    ingress.yaml
    configmap.yaml
    hpa.yaml
    NOTES.txt           # printed after install
    tests/
      test-connection.yaml
  charts/               # dependency charts (vendored)
# Chart.yaml
apiVersion: v2
name: legal-api
description: Legal search API
type: application          # or "library" for shared templates only
version: 0.3.0             # chart version (SemVer)
appVersion: "3f2a9c1"      # image tag it deploys by default
dependencies:
  - name: common
    version: "1.x.x"
    repository: oci://asia-south1-docker.pkg.dev/my-proj/charts

Commands

helm create legal-api                         # scaffold
helm lint ./legal-api
helm template legal ./legal-api -f values-prod.yaml    # render locally, no cluster
helm upgrade --install legal ./legal-api \
  -n legal --create-namespace \
  -f values-prod.yaml --set image.tag=3f2a9c1 \
  --atomic --timeout 5m                       # roll back automatically on failure
# Helm 4 renamed --atomic to --rollback-on-failure; check `helm version`
helm list -n legal
helm history legal -n legal
helm rollback legal 4 -n legal
helm get values legal -n legal                # what was applied
helm get manifest legal -n legal
helm uninstall legal -n legal

helm dependency update ./legal-api
helm package ./legal-api                      # → legal-api-0.3.0.tgz
helm push legal-api-0.3.0.tgz oci://asia-south1-docker.pkg.dev/my-proj/charts
helm install legal oci://asia-south1-docker.pkg.dev/my-proj/charts/legal-api --version 0.3.0

Templates

# templates/_helpers.tpl
{{- define "legal-api.fullname" -}}
{{- printf "%s-%s" .Release.Name .Chart.Name | trunc 63 | trimSuffix "-" -}}
{{- end -}}

{{- define "legal-api.selectorLabels" -}}
app.kubernetes.io/name: {{ .Chart.Name }}
app.kubernetes.io/instance: {{ .Release.Name }}
{{- end -}}
# templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "legal-api.fullname" . }}
  labels:
    {{- include "legal-api.selectorLabels" . | nindent 4 }}
    app.kubernetes.io/version: {{ .Values.image.tag | default .Chart.AppVersion | quote }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      {{- include "legal-api.selectorLabels" . | nindent 6 }}
  template:
    metadata:
      labels:
        {{- include "legal-api.selectorLabels" . | nindent 8 }}
      annotations:
        checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
    spec:
      containers:
        - name: app
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
          resources:
            {{- toYaml .Values.resources | nindent 12 }}
          {{- with .Values.env }}
          env:
            {{- toYaml . | nindent 12 }}
          {{- end }}
          envFrom:
            - secretRef:
                name: {{ required "secretName is required" .Values.secretName }}

The checksum/config annotation restarts pods when the ConfigMap changes. required fails the render with a clear message instead of deploying something broken.

Values per environment

# values.yaml (defaults: safe, small)
replicaCount: 1
image:
  repository: asia-south1-docker.pkg.dev/my-proj/apps/legal-api
  tag: ""                       # defaults to appVersion
resources:
  requests: { cpu: 250m, memory: 512Mi }
  limits:   { memory: 512Mi }
env: []
secretName: ""

# values-prod.yaml (only what differs)
replicaCount: 3
resources:
  requests: { cpu: "1", memory: 1Gi }
  limits:   { memory: 1Gi }
secretName: legal-api-secrets
  • Later -f files override earlier ones; --set overrides files. Prefer files in Git over --set.
  • Add values.schema.json so a typo in a value fails at install, not at runtime.
  • Never put secret values in values files; reference Secrets created by External Secrets or the Secret Manager CSI driver.

Hooks and tests

# templates/migrate-job.yaml: run DB migrations before an upgrade
apiVersion: batch/v1
kind: Job
metadata:
  name: {{ include "legal-api.fullname" . }}-migrate
  annotations:
    "helm.sh/hook": pre-install,pre-upgrade
    "helm.sh/hook-weight": "0"
    "helm.sh/hook-delete-policy": before-hook-creation,hook-succeeded
spec:
  backoffLimit: 0
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
          args: ["migrate"]
  • Hook events: pre-install, post-install, pre-upgrade, post-upgrade, pre-rollback, pre-delete and more.
  • Migrations in a hook must be backward compatible: a rollback does not undo them.
  • helm test legal runs pods annotated "helm.sh/hook": test to smoke-test a release.
  • Unit-test templates with the helm-unittest plugin; lint and install-test charts in CI with chart-testing (ct).

Helm, Kustomize and GitOps

HelmKustomize
ApproachTemplates + valuesPlain YAML + patches per overlay
Packaging and versionsYes: charts, releases, rollbackNo: just manifests
Best forDistributing reusable apps; many similar servicesYour own manifests with small per-environment differences
RiskTemplate logic becomes hard to readMany overlays become hard to follow
  • GitOps (Argo CD, Flux): the desired chart version and values live in Git; a controller in the cluster applies them and reports drift. No one runs helm upgrade by hand in production.
  • Run helm diff upgrade (plugin) or the GitOps diff before every production change.

Chart best practices

  • Selector labels never change after the first release: Kubernetes forbids changing a Deployment's selector.
  • Standard labels (app.kubernetes.io/name, instance, version, managed-by).
  • Sensible defaults: resources, probes, security context (non-root, read-only root filesystem) on by default.
  • Keep templates boring: little logic; move complexity into values, not nested conditionals.
  • A library chart of shared helpers is your blueprint: every service chart depends on it, so a fix reaches all of them.
  • Pin dependency versions; publish charts to an OCI registry with immutable versions.
  • Document values in values.yaml comments and the schema.

Levels: what to expect

1 Foundation

  • Install, upgrade, roll back and inspect a release
  • Read a chart's values and override them per environment
  • Render a chart locally with helm template

2 Practitioner

  • Write charts with helpers, schema-validated values and sane defaults
  • Use hooks for migrations and helm test for smoke tests
  • Publish charts to an OCI registry

3 Senior

  • Design library charts as a shared blueprint for many services
  • Deliver charts with GitOps (Argo CD or Flux) and diffs
  • Choose between Helm and Kustomize per case

4 Expert

  • Own the organisation's deployment packaging standards
  • Run chart supply chain: signing, provenance, registries
  • Lead migrations between delivery models

Each level includes the ones before it. See Start here for what the levels mean.

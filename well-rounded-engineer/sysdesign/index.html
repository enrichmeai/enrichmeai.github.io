System design

How to design a system from a blank page: a repeatable method, the numbers to estimate with, the building blocks, how each scales, and worked examples. The Architecture and Database Design tabs go deeper on patterns and storage.

The method, in order

  1. Clarify requirements. Functional: what users can do. Non-functional: scale, latency, availability, consistency, durability, cost, security, compliance. Write down what is out of scope.
  2. Estimate. Users, requests per second (average and peak), read/write ratio, data size per item, storage per year, bandwidth. Numbers decide the design.
  3. Define the API. The few endpoints or events that deliver the functional requirements, with their inputs and outputs.
  4. Model the data. Entities, keys, access patterns ("fetch by X, list by Y sorted by Z"), and which store fits each pattern.
  5. Draw the high-level design. Clients, load balancer, services, stores, caches, queues. One request path end to end.
  6. Deep-dive the hard parts. The component that is hottest, biggest or most consistency-sensitive. Show how it scales and fails.
  7. Find bottlenecks and failure modes. What breaks first at 10×? What happens when each dependency is down?
  8. State trade-offs. What you chose, what you gave up, and what would make you change it.

The same steps make a good design document. Start simple, and add a component only when a requirement or a number demands it.

Network calls dominate. Ten sequential service calls cost far more than ten database rows. Parallelise independent calls and keep hot paths short.

Scaling playbook, cheapest first

  1. Measure. Find the actual bottleneck: CPU, memory, DB queries, a slow dependency.
  2. Fix the query. Indexes, fewer round trips, no N+1. Often 10–100× for free.
  3. Scale up the instance. Boring and effective.
  4. Make services stateless and scale out behind a load balancer.
  5. Cache hot reads; add a CDN for public content.
  6. Read replicas for read-heavy databases.
  7. Move work off the request path to queues and workers.
  8. Partition big tables; archive cold data.
  9. Shard or move to a distributed database only when one primary cannot take the writes.

Caching strategies

  • Cache-aside: app reads cache, on a miss reads the DB and fills the cache. Most common.
  • Read-through: the cache library loads from the DB itself on a miss.
  • Write-through: write to cache and DB together; reads always warm, writes slower.
  • Write-behind: write to cache, flush to DB later; fast, but data can be lost.
  • TTL bounds staleness; explicit invalidation on write keeps it fresher but is easy to miss.
  • Stampede: a popular key expires and thousands of requests hit the DB. Use request coalescing, a lock, or early random refresh.
  • What to key on: include everything that changes the answer (user, locale, version). A missing part of the key serves one user's data to another.

Rate limiting

  • Token bucket: tokens refill at a steady rate up to a burst size; each request takes one. Allows short bursts. The usual choice.
  • Leaky bucket: requests drain at a fixed rate; smooths traffic, no bursts.
  • Fixed window: N per minute; simple, but allows 2N across a window boundary.
  • Sliding window: counts over the last 60 s; fairer, slightly more state.
  • Where: at the gateway per API key or user; inside services to protect a fragile dependency.
  • Response: HTTP 429 with Retry-After, so well-behaved clients back off.
  • Distributed: keep counters in Redis with atomic increments, or accept per-instance limits.

Distributing data

  • Replication copies data for availability and read scale. Leader-follower is the common model; multi-leader and leaderless trade consistency for write availability.
  • Partitioning / sharding splits data for write scale and size. Choose a key that spreads load and matches the main access pattern.
  • Consistent hashing places keys and nodes on a ring, so adding or removing a node moves only about 1/N of the keys. Used by caches and distributed stores.
  • Hot keys (one celebrity, one big tenant, today's date) defeat even spreading. Split them, cache them, or add a random suffix.
  • Quorums: with N replicas, reading R and writing W where R + W > N guarantees a read sees the latest write.

Designing for failure

  • Timeouts on every network call, shorter than the caller's own timeout.
  • Retries only for idempotent operations, with backoff and jitter, and a cap.
  • Circuit breakers and bulkheads so one sick dependency cannot take down the rest.
  • Graceful degradation: serve cached or partial results, and say so. Never present "could not check" as "nothing found".
  • Redundancy: multiple instances across zones; regional failover only if the requirement justifies the cost.
  • Backpressure: queues with limits; shed load early (429/503) instead of collapsing.
  • Backups you have restored, with a known recovery point (RPO: how much data you can lose) and recovery time (RTO: how long you can be down).

Worked example: a URL shortener

  • Requirements: create a short link; redirect fast; links never change; 100 M new links/year; reads 100× writes; 99.9% available.
  • Estimates: writes ≈ 3/s average; reads ≈ 300/s, peak ~1,500/s. 100 M × 500 B ≈ 50 GB/year.
  • API: POST /links {url} → {code}; GET /{code} → 301/302 redirect.
  • Data: link(code PK, url, created_at, owner). Access pattern is lookup by code only: any key-value store or Postgres works.
  • Code generation: base62 of a unique ID (7 chars ≈ 3.5 trillion codes). Use a sequence or ID service to avoid collisions; random codes need a uniqueness check.
  • High level: load balancer → stateless service → cache (hot codes) → database. CDN can cache redirects for popular links.
  • Deep dive: reads are the load: cache-aside with long TTL works because links are immutable. Writes are tiny.
  • Trade-offs: 301 is cached by browsers (fewer hits, no click counting); 302 keeps analytics. Click analytics go to a queue and a warehouse, not the redirect path.

Worked example: legal search over 20 M judgments

  • Requirements: keyword and filter search (court, date, judge), open a judgment, cite-check a reference. Results within 500 ms at p95. Data refreshed daily. Court-ordered suppressions must apply everywhere immediately.
  • Estimates: ~60 searches/s at peak; 20 M records, ~40 GB metadata, ~140 GB text.
  • Data flow: open-data mirrors → landing bucket → warehouse layers (raw → foundation → consumable) → serving Postgres. The warehouse is the record; Postgres is a read-optimised copy. See Data Engineering.
  • Serving: stateless API on Cloud Run; Postgres with full-text (GIN) and B-tree indexes on filter columns; read replica for search; cache for hot queries and judgment pages.
  • Stable identity: IDs never renumber, because URLs, citations and suppression orders refer to them. Loads upsert on a stable key.
  • Suppressions: checked on every read path (search, page, API, exports) from the application database, not baked into the copy, so a new order takes effect without a reload.
  • Freshness and honesty: each result carries its source and date; when a source is stale or unreachable, the API says so rather than returning a confident empty result.
  • Scaling later: move search to a dedicated index (or add semantic search with embeddings) when relevance or load outgrows Postgres; keep Postgres for lookups.

More practice problems

  • Rate limiter for a public API
  • Notification service (email, push, SMS) with retries and user preferences
  • News feed or timeline
  • Chat with presence and message history
  • File upload and processing pipeline
  • Job scheduler that runs millions of tasks reliably
  • Metrics and logging pipeline
  • RAG question-answering over company documents
  • Payment flow with a saga and idempotency keys

For each: run the method above, and write the trade-offs down. The written reasoning is the skill.

Design doc template

# Title
## Context        why now, who asked, links
## Goals          measurable; and non-goals
## Requirements   functional / non-functional (with numbers)
## Estimates      traffic, data, cost
## Design         diagram, API, data model, request flow
## Alternatives   what else was considered and why not
## Failure modes  each dependency down / slow / wrong
## Rollout        migration, flags, rollback plan
## Observability  metrics, alerts, SLOs, run records
## Security       data, access, threats
## Open questions owner and due date for each

Levels: what to expect

1 Foundation

  • Follow the method: requirements, estimates, API, data, diagram
  • Name the building blocks and what each is for
  • Do back-of-the-envelope estimates

2 Practitioner

  • Design a small service end to end with caching and a queue
  • Identify bottlenecks and failure modes
  • Write a design document others can build from

3 Senior

  • Design for scale, availability targets and cost together
  • Choose storage and consistency models with clear trade-offs
  • Lead design reviews and challenge assumptions with numbers

4 Expert

  • Design multi-region, highly available systems
  • Set reliability and capacity strategy for the organisation
  • Mentor others in design and trade-off thinking

Each level includes the ones before it. See Start here for what the levels mean.

From binary to GPUs

Chip design sounds like a different world, but it is built from ideas you can hold in your head: two symbols, a handful of simple gates, and patience. This page walks up the ladder from binary and hex to logic gates, an adder you can run, a processor, how real chips are designed today, and why GPUs ended up running AI.

The short answer

If you have ever written an if statement, you already understand most of what a chip does. A computer is a very large number of tiny switches, arranged so that switches control other switches. Group a few of them and you get a logic gate; group gates and you can add numbers; group adders and memory and you have a processor. No single step is mysterious. What makes chips impressive is the scale, billions of transistors, and the care taken at every layer.

This is also why hardware matters more now, not less. Software has become so dependent on what chips can do, from the phone in your pocket to the GPUs that train AI models, that knowing roughly how they work helps you write better software and judge the hype. The basics, from the first transistor to Moore’s law, are on Electronics & Chips and How Computers Are Built; this page goes one level deeper, with something you can run.

Binary and hex, without the fear

A binary number uses only two symbols, 0 and 1, and each digit is called a bit. Thomas Harriot studied the modern system and Gottfried Leibniz is credited with inventing it, though related systems appeared much earlier in several cultures. Why only two symbols? Because a switch has two states, on and off, and that is all a transistor needs to represent.

Binary works exactly like the decimal you already know, just with 2 instead of 10. In decimal, the places are ones, tens, hundreds. In binary, they are ones, twos, fours, eights, and so on. So 0100 0001 is 64 + 1 = 65.

Hexadecimal is simply a shorthand for binary that people can read. One hex digit stands for four bits (a nibble), so a whole 8-bit byte is exactly two hex digits: 0100 0001 is 41, and 0010 1100 is 2C. That is why hex appears everywhere engineers look at raw data: colours like #5980A6, memory addresses, network packets, hash values.

Logic gates: decisions made of switches

A logic gate takes one or two bits in and gives one bit out, following a simple rule. You know these rules already from programming:

GateOutput is 1 when…In code
ANDboth inputs are 1a and b
ORat least one input is 1a or b
NOTthe input is 0not a
XORthe inputs differa != b
NANDnot both inputs are 1not (a and b)

Here is the remarkable part. NAND on its own is functionally complete: any Boolean expression at all can be rebuilt using nothing but NAND gates. NOT(x), for example, is just NAND(x, x). (NOR has the same property; AND and OR together do not, because they cannot make NOT.) So in principle, a whole computer can be built from one kind of gate, repeated.

Run it: an adder built only from NAND

Adding two bits is where gates start to do arithmetic. A half adder takes bits A and B and gives a sum (A XOR B) and a carry (A AND B); join two half adders with an OR gate and you get a full adder, which also accepts a carry from the column to its right. Chain eight full adders and you can add two bytes, exactly as you add numbers on paper, column by column, carrying as you go. The program below builds all of it from NAND alone, then checks itself against Python’s own +:

"""Build an adder from one kind of gate, NAND, and check it against Python's own +."""

def NAND(a, b): return 0 if (a and b) else 1     # the only gate we are given

def NOT(a):     return NAND(a, a)
def AND(a, b):  return NOT(NAND(a, b))
def OR(a, b):   return NAND(NOT(a), NOT(b))
def XOR(a, b):  return AND(OR(a, b), NAND(a, b))

def full_adder(a, b, carry_in):
    s1 = XOR(a, b)
    total = XOR(s1, carry_in)
    carry_out = OR(AND(a, b), AND(s1, carry_in))
    return total, carry_out

def add_8bit(x, y):
    """Ripple-carry adder: eight full adders in a row, like the first stage of an ALU."""
    carry, result = 0, 0
    for i in range(8):                               # lowest bit first
        bit, carry = full_adder((x >> i) & 1, (y >> i) & 1, carry)
        result |= bit << i
    return result, carry

for x, y in [(23, 42), (200, 100), (0b1111_0000, 0x0F)]:
    total, overflow = add_8bit(x, y)
    print(f"{x:3} + {y:3} = {total:3}  binary {total:08b}  hex {total:02X}  carry out {overflow}")

assert all(add_8bit(x, y) == ((x + y) & 0xFF, (x + y) >> 8) for x in range(256) for y in range(256))
print("checked all 65,536 pairs: the NAND-only adder agrees with Python")

What it printed when we ran it:

23 +  42 =  65  binary 01000001  hex 41  carry out 0
200 + 100 =  44  binary 00101100  hex 2C  carry out 1
240 +  15 = 255  binary 11111111  hex FF  carry out 0
checked all 65,536 pairs: the NAND-only adder agrees with Python

Look at the second line: 200 + 100 came out as 44, with a carry of 1. Eight bits can only hold 0 to 255, so 300 overflowed; the carry bit is the hardware telling you so. That single bit is the root of every integer overflow bug you will ever meet in software.

A real processor’s arithmetic logic unit (ALU) is this idea grown up: a combinational circuit that performs arithmetic and bitwise operations on whole binary numbers. Add registers to hold values and a clock, a steady signal that tells every part of the chip when to take its next step, and you have the heart of a CPU.

How chips are designed today

Nobody draws billions of transistors by hand. Modern digital design starts as code. Engineers describe the circuit at register-transfer level (RTL), the usual starting point for designers, in a hardware description language such as Verilog or VHDL. Here is the full adder from the program above, written the way a chip designer would:

// a full adder in Verilog: the same circuit as full_adder() in the Python above
module full_adder (input a, input b, input carry_in,
                   output sum, output carry_out);
  assign sum       = a ^ b ^ carry_in;
  assign carry_out = (a & b) | ((a ^ b) & carry_in);
endmodule

From there, the journey to silicon is a series of steps, most of them done by software tools:

  • Simulate: run tests against the design before anything is built, just as you test software.
  • Synthesise: a synthesis tool turns the RTL into an implementation made of logic gates, called a netlist.
  • Place and route: physical design decides where each gate sits on the silicon and how the wires connect them.
  • Tape-out: the point at which the final layout for the photomasks is sent to the fabrication plant. The name comes from the days when the data went on magnetic tape.

It is closer to normal software than most people think. OpenROAD, an open-source project, describes itself as delivering an automated flow from RTL to the final layout (GDSII) with a 24-hour turnaround. With SkyWater’s open 130 nm process kit (SKY130) and projects such as Tiny Tapeout, where many small designs, some drawn in a browser simulator, share one manufactured chip, students and hobbyists can now have their own circuits made in real silicon. Before committing to a chip at all, an FPGA lets you load your design onto reprogrammable hardware and try it on a desk.

Why GPUs, and why AI runs on them

A CPU has a small number of powerful cores, each able to follow its own complicated path through a program. A GPU makes the opposite trade: thousands of simpler cores that all apply the same instruction to different data at once. NVIDIA introduced the model it calls SIMT, single instruction, multiple threads, with its G80 chip in the Tesla architecture. A single control unit broadcasts one instruction to many processing units, each working on its own data.

That shape suits drawing graphics, where the same calculation runs on millions of pixels, and it turned out to suit neural networks too, which are mostly enormous matrix multiplications: the same multiply-and-add, repeated across huge grids of numbers. The history, from 3D gaming to CUDA, AlexNet and AI chips, is on How Computers Are Built, and the maths behind it is on Mathematics.

Analysis: SIMT also explains a GPU’s weakness. Because only the control unit has a program counter, threads that take different branches have to wait for each other, so code full of if statements runs poorly on a GPU. The best GPU code is the same simple work, done to a great deal of data.

Our view, and the other view

Our view: every software engineer should build an adder from gates once, in code, as above. It takes an afternoon, it makes binary, overflow and performance feel physical rather than abstract, and it shows that the most complex machine you use is ordinary ideas, stacked very high.

The other view: modern chips are far beyond this picture. Timing, power, heat, manufacturing variation and verification take most of a chip team’s effort, and the abstractions exist precisely so that most engineers never need to think about them. Knowing the ladder is a foundation, not a qualification.

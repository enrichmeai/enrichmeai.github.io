Cloud Run

Serverless containers on GCP: services that answer requests, and jobs that run to completion. Deploy, scale, secure, connect and debug.

Services, jobs, worker pools

KindRuns whenUse it for
ServiceA request arrives (HTTP, gRPC, WebSocket, Pub/Sub push, Eventarc)APIs, web apps, webhooks. Scales on traffic, down to zero.
JobSomeone executes it (CLI, API, Cloud Scheduler, Workflows)Batch loads, migrations, nightly exports. Runs N tasks in parallel, then exits.
Worker poolAlways, with no HTTP endpointPull-based consumers (Kafka, Pub/Sub pull). Newer resource: check it is available in your region.

Container contract

  • Listen on $PORT (default 8080) on 0.0.0.0, not 127.0.0.1. Jobs do not listen at all.
  • Stateless. Any instance can serve any request; instances come and go.
  • The filesystem is in memory and counts against the memory limit. Write big files to GCS or a mounted volume.
  • Shutdown: the container gets SIGTERM, then about 10 seconds before SIGKILL. Flush and close there.
  • Logs: anything written to stdout/stderr goes to Cloud Logging.
  • Jobs: exit code 0 means the task succeeded; anything else fails it (and retries it if max-retries > 0).
  • Platform: build images for linux/amd64. An arm64 image from a Mac will not start.

Deploy a service

gcloud run deploy api \
  --image=asia-south1-docker.pkg.dev/my-proj/apps/api:3f2a9c1 \
  --region=asia-south1 \
  --service-account=api@my-proj.iam.gserviceaccount.com \
  --no-allow-unauthenticated \
  --cpu=1 --memory=1Gi \
  --concurrency=80 --min-instances=0 --max-instances=10 \
  --timeout=300 \
  --cpu-boost \
  --set-env-vars=APP_PROFILE=prod,DATASET=fdp \
  --set-secrets=DB_PASSWORD=db-password:3 \
  --labels=env=prod,team=data

# build from source with Cloud Build + buildpacks / Dockerfile
gcloud run deploy api --source . --region=asia-south1

gcloud run services describe api --region=asia-south1 --format='value(status.url)'
gcloud run services list

--set-env-vars replaces all env vars; --update-env-vars adds or changes only the ones named.

Revisions & traffic

# deploy without sending traffic; reach it at a tagged URL
gcloud run deploy api --image=…:4b1c2d0 --no-traffic --tag=canary
# → https://canary---api-xxxxx.a.run.app

# shift 10% to the new revision
gcloud run services update-traffic api \
  --to-revisions=api-00042-xyz=10,api-00041-abc=90

gcloud run services update-traffic api --to-latest     # 100% to newest
gcloud run services update-traffic api --to-tags=canary=100

# roll back = send traffic to the previous revision
gcloud run revisions list --service=api --region=asia-south1
gcloud run services update-traffic api --to-revisions=api-00041-abc=100

Every deploy or config change creates a new immutable revision. Settings live on the revision, so rolling back traffic also rolls back env vars and secrets.

Jobs

gcloud run jobs deploy loader \
  --image=asia-south1-docker.pkg.dev/my-proj/apps/loader:3f2a9c1 \
  --region=asia-south1 \
  --service-account=loader@my-proj.iam.gserviceaccount.com \
  --tasks=10 --parallelism=5 \
  --task-timeout=3600s --max-retries=0 \
  --cpu=2 --memory=4Gi \
  --args=--year=2024

gcloud run jobs execute loader --region=asia-south1 --wait
gcloud run jobs execute loader --wait \
  --args=--year=2023 --update-env-vars=DRY_RUN=true   # overrides for this run only

gcloud run jobs executions list --job=loader --region=asia-south1
gcloud run jobs executions describe loader-abc12 --region=asia-south1
gcloud run jobs executions cancel loader-abc12 --region=asia-south1

An execution's status is Cloud Run's word on whether the container exited 0. Whether it did the right work is your job to record, e.g. a summary row or log line per run.

Shard work across job tasks

Every task gets these environment variables:

  • CLOUD_RUN_TASK_INDEX: 0 … tasks − 1
  • CLOUD_RUN_TASK_COUNT: the --tasks value
  • CLOUD_RUN_TASK_ATTEMPT: 0 on the first try
  • CLOUD_RUN_EXECUTION, CLOUD_RUN_JOB: names for logs and run records
# Python
import os
i = int(os.environ.get("CLOUD_RUN_TASK_INDEX", 0))
n = int(os.environ.get("CLOUD_RUN_TASK_COUNT", 1))
mine = [u for k, u in enumerate(sorted(all_uris)) if k % n == i]

// Java
int i = Integer.parseInt(System.getenv().getOrDefault("CLOUD_RUN_TASK_INDEX", "0"));
int n = Integer.parseInt(System.getenv().getOrDefault("CLOUD_RUN_TASK_COUNT", "1"));
List<String> mine = IntStream.range(0, uris.size())
    .filter(k -> k % n == i).mapToObj(uris::get).toList();

Sort the input first so every task sees the same order. Make each task idempotent: a retry repeats the whole shard.

Scaling & cost

  • Concurrency (default 80, max 1000): requests one instance handles at once. Set 1 only for code that is not thread-safe.
  • Min instances keep warm instances to avoid cold starts; they bill while idle.
  • Max instances cap spend and protect downstream databases (connections = instances × pool size).
  • CPU allocation: by default CPU is only allocated during requests, so background threads stall after the response. --no-cpu-throttling keeps CPU on (instance-based billing).
  • Startup CPU boost (--cpu-boost) gives extra CPU while the container starts: helps JVM cold starts.
  • Cold start cuts: smaller images, lazy initialisation, CDS/AOT for Java, Quarkus or Spring native images.
  • Jobs bill for the time each task runs, at the CPU and memory you asked for.

Calling private services

# grant the caller the invoker role
gcloud run services add-iam-policy-binding api --region=asia-south1 \
  --member=serviceAccount:caller@my-proj.iam.gserviceaccount.com \
  --role=roles/run.invoker

# from your terminal
curl -H "Authorization: Bearer $(gcloud auth print-identity-token)" https://api-xxxxx.a.run.app/health
gcloud run services proxy api --region=asia-south1 --port=8080   # local tunnel
# Python: ID token whose audience is the service URL
import google.auth.transport.requests, google.oauth2.id_token, requests
aud = "https://api-xxxxx.a.run.app"
tok = google.oauth2.id_token.fetch_id_token(google.auth.transport.requests.Request(), aud)
requests.get(f"{aud}/health", headers={"Authorization": f"Bearer {tok}"})

// Java (google-auth-library)
IdTokenCredentials creds = IdTokenCredentials.newBuilder()
    .setIdTokenProvider((IdTokenProvider) GoogleCredentials.getApplicationDefault())
    .setTargetAudience(aud).build();
creds.refresh();
String token = creds.getIdToken().getTokenValue();

Services need an ID token (audience = URL). Google APIs, including the Cloud Run Admin API that executes a job, need an access token.

Networking

# who may reach the service
--ingress=all                                  # internet (still IAM-checked)
--ingress=internal                             # VPC and some Google sources only
--ingress=internal-and-cloud-load-balancing    # put a load balancer / Cloud Armor in front

# reach private IPs (Memorystore, internal services) with Direct VPC egress
--network=main --subnet=run-egress --vpc-egress=private-ranges-only
--vpc-egress=all-traffic        # everything via VPC → Cloud NAT gives a static egress IP

# Cloud SQL via the built-in connector: unix socket in the container
--add-cloudsql-instances=my-proj:asia-south1:corpus
# JDBC: jdbc:postgresql:///corpus?cloudSqlInstance=my-proj:asia-south1:corpus&socketFactory=com.google.cloud.sql.postgres.SocketFactory
# psycopg: host=/cloudsql/my-proj:asia-south1:corpus

A third party that allowlists IPs needs all-traffic egress through Cloud NAT with a reserved address. Without it, egress comes from shared Google ranges.

Secrets, config, volumes

# secret as env var: read once, when the instance starts
--set-secrets=DB_PASSWORD=db-password:3

# secret as a file: read when your code opens it
--set-secrets=/secrets/sa.json=sa-key:latest

# the runtime service account needs to read it
gcloud secrets add-iam-policy-binding db-password \
  --member=serviceAccount:api@my-proj.iam.gserviceaccount.com \
  --role=roles/secretmanager.secretAccessor

# GCS bucket or in-memory volume
--add-volume=name=data,type=cloud-storage,bucket=my-landing \
--add-volume-mount=volume=data,mount-path=/data
--add-volume=name=scratch,type=in-memory,size-limit=1Gi

Pin secret versions (:3) in prod so a rotation is a deliberate deploy. With :latest in an env var, running instances keep the old value until they restart.

Triggers

  • Cloud Scheduler → job: POST to https://run.googleapis.com/v2/projects/P/locations/R/jobs/J:run with an OAuth token (see the Terraform tab).
  • Cloud Scheduler → service: HTTP target with an OIDC token whose audience is the service URL.
  • Pub/Sub push: subscription pushes to the service URL with an OIDC token; return 2xx to ack, anything else retries.
  • Eventarc: route events (GCS object finalised, BigQuery job done, audit log entries) to a service.
  • Cloud Tasks: queued HTTP calls with rate limits and retries.
  • Workflows: run jobs in sequence, wait for each, branch on results.
gcloud eventarc triggers create on-landing --location=asia-south1 \
  --destination-run-service=ingest --destination-run-region=asia-south1 \
  --event-filters=type=google.cloud.storage.object.v1.finalized \
  --event-filters=bucket=my-landing \
  --service-account=eventarc@my-proj.iam.gserviceaccount.com

Dockerfiles that start fast

# Java (Spring Boot / Quarkus jar)
FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY . .
RUN ./gradlew bootJar -x test

FROM eclipse-temurin:21-jre
RUN useradd -u 1001 app
USER 1001
COPY --from=build /src/build/libs/app.jar /app.jar
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75 -XX:+UseSerialGC"
ENTRYPOINT ["java", "-jar", "/app.jar"]
# Python
FROM python:3.12-slim
ENV PYTHONUNBUFFERED=1 PIP_NO_CACHE_DIR=1
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
USER 1001
CMD exec gunicorn --bind :$PORT --workers 1 --threads 8 --timeout 0 app:app
docker buildx build --platform linux/amd64 -t asia-south1-docker.pkg.dev/my-proj/apps/api:$(git rev-parse --short=12 HEAD) --push .

Use the exec form (["java", …] or exec) so your process is PID 1 and receives SIGTERM.

Logging & health

# one JSON object per line on stdout → structured log entry
{"severity":"ERROR","message":"load failed","uri":"gs://…","run_id":"r-42",
 "logging.googleapis.com/trace":"projects/my-proj/traces/abc123"}

gcloud logging read 'resource.type="cloud_run_revision"
  AND resource.labels.service_name="api" AND severity>=ERROR' --freshness=1h --limit=50
gcloud logging read 'resource.type="cloud_run_job"
  AND resource.labels.job_name="loader" AND severity>=ERROR' --freshness=1d --limit=20
# service.yaml fragment: probes
spec:
  template:
    spec:
      containers:
        - image: …
          startupProbe:
            httpGet: { path: /health/started, port: 8080 }
            failureThreshold: 30
            periodSeconds: 2
          livenessProbe:
            httpGet: { path: /health/live, port: 8080 }

Without severity, every line is logged at DEFAULT, and severity-based alerts never fire.

Declarative YAML

gcloud run services describe api --region=asia-south1 --format=export > service.yaml
# edit, then:
gcloud run services replace service.yaml --region=asia-south1

gcloud run jobs describe loader --region=asia-south1 --format=export > job.yaml
gcloud run jobs replace job.yaml --region=asia-south1

The YAML follows the Knative Serving schema. In a team, keep the definition in Terraform (google_cloud_run_v2_service / _job) and use the CLI for reading and one-off executions.

Errors and what they usually mean

SymptomUsually means
"Container failed to start and listen on the port defined by PORT"App listens on the wrong port or on 127.0.0.1, crashes on boot (missing env var or secret), or the image is arm64. Read the revision's logs.
403 calling a serviceCaller lacks roles/run.invoker, sent an access token instead of an ID token, or the token's audience is not the service URL.
404 calling a serviceWrong URL or region, or ingress is internal and you called from outside the VPC.
429 / "no available instance"max-instances reached with all instances at full concurrency.
503 with "Memory limit exceeded" in logsOOM: raise --memory, or stop writing large files to the in-memory filesystem.
504 / request cancelledRequest ran past --timeout.
Permission denied on secretRuntime service account lacks secretmanager.secretAccessor on that secret.
Image pull deniedThe Cloud Run service agent cannot read the Artifact Registry repo (common across projects).
Job execution FAILED, logs emptyTask timed out, was OOM-killed, or crashed before logging. executions describe shows the reason per task.
Background work never finishesCPU is throttled after the response. Finish before responding, use --no-cpu-throttling, or hand the work to a job or Cloud Tasks.

Levels: what to expect

1 Foundation

  • Deploy a service and read its logs
  • Execute a job and check its result
  • Roll traffic back to a previous revision

2 Practitioner

  • Set scaling, CPU, memory, concurrency and timeouts deliberately
  • Secure services with IAM, secrets and service accounts
  • Connect to private resources with VPC egress

3 Senior

  • Design job sharding, retries and run records
  • Tune cold starts and cost
  • Design service-to-service auth and traffic management

4 Expert

  • Set the serverless platform blueprint for the organisation
  • Decide Cloud Run vs GKE vs other compute
  • Design multi-region serverless architectures

Each level includes the ones before it. See Start here for what the levels mean.

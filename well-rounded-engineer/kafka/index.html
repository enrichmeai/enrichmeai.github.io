Apache Kafka

A distributed, durable, replayable log for events. The core model, the settings that decide durability and ordering, clients in Java, Spring, Quarkus and Python, and the ecosystem around it.

The model

ConceptMeaning
TopicA named stream of records, e.g. judgment.landed
PartitionAn ordered, append-only log; a topic has many. Ordering is guaranteed only within a partition.
RecordKey, value, headers, timestamp. The key decides the partition (same key → same partition → ordered).
OffsetA record's position in its partition. Consumers track how far they have read.
BrokerA server storing partitions. A cluster has several.
Replication factorCopies of each partition on different brokers (3 is typical).
Leader / ISROne replica takes reads and writes; in-sync replicas are caught-up followers.
Consumer groupConsumers sharing the work: each partition is read by one consumer in the group. Max parallelism = partition count.
RetentionRecords kept for a time or size, then deleted, regardless of whether they were read.
CompactionKeep only the latest record per key; a table-like topic.
KRaftKafka's built-in metadata quorum, replacing ZooKeeper (removed in Kafka 4.0).

Unlike a queue, reading does not remove a record. Many groups can read the same topic independently, and a group can rewind to replay.

Durability and delivery settings

  • Producer acks=all with topic min.insync.replicas=2 and replication factor 3: a write survives one broker failure.
  • enable.idempotence=true (the default in modern clients): retries do not create duplicates within a partition.
  • At-least-once consuming: process, then commit the offset. A crash between the two replays the record, so consumers must be idempotent.
  • At-most-once: commit before processing. Rarely what you want.
  • Exactly-once inside Kafka (read-process-write between topics) with transactions and isolation.level=read_committed. Side effects outside Kafka still need idempotency.
  • Ordering: choose the key for the entity whose events must stay in order (case ID, account ID).

CLI essentials

B=localhost:9092
kafka-topics.sh --bootstrap-server $B --create --topic judgment.landed \
  --partitions 6 --replication-factor 3 --config retention.ms=604800000
kafka-topics.sh --bootstrap-server $B --describe --topic judgment.landed

kafka-console-producer.sh --bootstrap-server $B --topic judgment.landed \
  --property parse.key=true --property key.separator=:
# type:  CNR123:{"court":"2_5"}

kafka-console-consumer.sh --bootstrap-server $B --topic judgment.landed \
  --group debug --from-beginning --property print.key=true

kafka-consumer-groups.sh --bootstrap-server $B --describe --group indexer   # lag per partition
kafka-consumer-groups.sh --bootstrap-server $B --group indexer \
  --reset-offsets --to-datetime 2026-11-01T00:00:00.000 --topic judgment.landed --execute

Consumer lag (latest offset minus committed offset) is the key health metric: growing lag means consumers cannot keep up.

Spring for Apache Kafka

# application.yml
spring:
  kafka:
    bootstrap-servers: ${KAFKA_BOOTSTRAP}
    producer:
      acks: all
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: org.springframework.kafka.support.serializer.JsonSerializer
    consumer:
      group-id: indexer
      auto-offset-reset: earliest
      properties:
        spring.json.trusted.packages: "com.example.events"
@Service
class Publisher {
  private final KafkaTemplate<String, JudgmentLanded> kafka;
  Publisher(KafkaTemplate<String, JudgmentLanded> kafka) { this.kafka = kafka; }
  void publish(JudgmentLanded e) { kafka.send("judgment.landed", e.cnr(), e); }  // key = cnr
}

@Component
class Indexer {
  @KafkaListener(topics = "judgment.landed", groupId = "indexer")
  void on(JudgmentLanded e) {
    index.upsert(e);           // idempotent: same event twice is harmless
  }
}

// retries and a dead-letter topic for poison messages
@Bean DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> t) {
  return new DefaultErrorHandler(new DeadLetterPublishingRecoverer(t),
                                 new FixedBackOff(1000L, 3));
}

Quarkus with Kafka

# application.properties (quarkus-messaging-kafka)
kafka.bootstrap.servers=${KAFKA_BOOTSTRAP}
mp.messaging.incoming.landed.connector=smallrye-kafka
mp.messaging.incoming.landed.topic=judgment.landed
mp.messaging.incoming.landed.group.id=indexer
mp.messaging.outgoing.indexed.connector=smallrye-kafka
mp.messaging.outgoing.indexed.topic=judgment.indexed
@ApplicationScoped
public class Indexer {
  @Incoming("landed")
  @Outgoing("indexed")
  public JudgmentIndexed process(JudgmentLanded e) {
    return index.upsert(e);
  }
}

@ApplicationScoped
public class Publisher {
  @Inject @Channel("indexed") Emitter<JudgmentIndexed> out;
  void send(JudgmentIndexed e) { out.send(e); }
}

Python (confluent-kafka)

from confluent_kafka import Producer, Consumer

p = Producer({"bootstrap.servers": BOOTSTRAP, "acks": "all",
              "enable.idempotence": True})
p.produce("judgment.landed", key=cnr, value=json.dumps(evt),
          callback=lambda err, msg: err and log.error("send failed: %s", err))
p.flush()

c = Consumer({"bootstrap.servers": BOOTSTRAP, "group.id": "indexer",
              "auto.offset.reset": "earliest", "enable.auto.commit": False})
c.subscribe(["judgment.landed"])
while True:
    msg = c.poll(1.0)
    if msg is None: continue
    if msg.error(): log.error(msg.error()); continue
    handle(json.loads(msg.value()))           # idempotent
    c.commit(message=msg, asynchronous=False) # commit after processing

The ecosystem

  • Schema Registry with Avro, Protobuf or JSON Schema: producers and consumers agree on schemas; compatibility rules block breaking changes.
  • Kafka Connect: ready-made source and sink connectors (databases, GCS, BigQuery) without custom code.
  • Debezium: change data capture from databases into Kafka topics.
  • Kafka Streams: a Java library for stateful stream processing (joins, windows, aggregates) inside your service.
  • Flink: a separate engine for large-scale stream processing.
  • On GCP: Managed Service for Apache Kafka runs clusters for you; Dataflow and BigQuery have Kafka connectors.

Kafka vs Pub/Sub

KafkaPub/Sub
ModelPartitioned log; consumers track offsetsTopics and subscriptions; per-message ack
OrderingPer partition (by key)Per ordering key, when enabled
ReplayRewind offsets within retentionSeek to a time or snapshot within retention
CapacityYou size brokers and partitions (managed or self-run)Serverless, scales automatically
EcosystemConnect, Streams, Schema Registry, DebeziumNative GCP integrations (BigQuery, GCS, Dataflow, Eventarc)
Choose whenKafka skills or tools exist; log semantics, compaction, very high throughputGCP-native, simple operations, global delivery

Designing topics

  • Name by event, past tense: judgment.landed, order.paid.
  • Partitions: enough for peak consumer parallelism with headroom; adding later changes key-to-partition mapping.
  • Keys: the entity that needs ordering; avoid hot keys.
  • Payload: include an event ID, type, version and timestamp; keep events self-describing.
  • Retention: long enough to recover from a consumer outage and replay.
  • Dead-letter topic for records that keep failing, with alerting on it.

Levels: what to expect

1 Foundation

  • Explain topics, partitions, offsets and consumer groups
  • Produce and consume with the CLI
  • Read consumer lag

2 Practitioner

  • Build producers and consumers in Spring, Quarkus or Python with correct acks and commits
  • Make consumers idempotent; use dead-letter topics
  • Use a schema registry

3 Senior

  • Design topics, keys and partition counts for scale and ordering
  • Run Kafka Connect and CDC pipelines
  • Tune throughput, latency and durability

4 Expert

  • Operate Kafka platforms (or choose managed) for the organisation
  • Design event-driven architectures across domains
  • Lead stream processing with Kafka Streams or Flink

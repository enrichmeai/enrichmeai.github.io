Keys, certificates and SSH

HTTPS, SSH logins, signed Git commits and service-to-service mTLS all rest on one idea: a pair of keys, one public and one private. This page explains the pair, how a certificate ties a public key to a name, what a certificate signing request (CSR) and a certificate authority (CA) do, and how SSH keys and Git signing work. The OpenSSL, ssh-keygen and Git commands on this page were run (OpenSSL 3.0.13, OpenSSH 9.6, Git 2.43), and the error messages are the real ones. ssh -T git@github.com is GitHub’s own documented test and was not run here. HTTP and the TLS handshake are on Networking; SSH tunnels and jump hosts are on Linux.

One idea underneath: a key pair

  • Two keys, made together. The public key can be shown to anyone. The private key never leaves its owner: not in email, not in a ticket, not in a repository.
  • Encrypt: anyone with the public key can encrypt a message, but only the holder of the private key can decrypt it.
  • Sign: the private key signs, and anyone with the public key can check that signature. This is how a server proves who it is, how an SSH key logs you in, and how a commit is marked as yours.
If this is true for youKey type it leans towards (analysis)
A new SSH key for you or a serviceEd25519: the type GitHub’s own instructions generate
A legacy system that does not support Ed25519RSA, 4096 bits, as GitHub suggests for that case
A TLS certificate for a website or serviceECDSA (for example P-256) or RSA; check what your clients and CA support
You want the key to need a hardware tokenA security-key type such as ed25519-sk

What a certificate is

A certificate authority (CA) stores, signs and issues digital certificates. A certificate certifies that a public key belongs to the named subject, so others can rely on it. Web certificates use the X.509 format (RFC 5280). The fields you will read most:

  • Subject and Subject Alternative Name (SAN): who it is for. Clients match the hostname against the SAN.
  • Issuer: the CA that signed it.
  • Validity: not before, not after.
  • Public key, and the issuer’s signature over all of the above.

The chain of trust

Your operating system or browser ships a store of trusted root certificates. Roots sign intermediate CAs, and intermediates sign the leaf certificate on your server. A client validates the chain from the leaf up to a root it already trusts.

Analysis: the server must send its leaf and the intermediates; the client already has the root. A missing intermediate is a common cause of “works in my browser, fails in my code”, because some clients fetch a missing intermediate themselves and many libraries do not.

A certificate signing request (CSR), step by step

A CSR is the message you send a CA to apply for a certificate. RFC 2986 defines it in three parts: the request information (your name, your public key and any attributes), a signature algorithm, and a signature over the request information made with your private key. That signature proves you hold the private key, which never goes to the CA.

# 1. Make a private key and a CSR, with the names the certificate must cover
openssl req -new -newkey ec -pkeyopt ec_paramgen_curve:P-256 -noenc \
  -keyout server.key -out server.csr \
  -subj "/CN=shop.internal" \
  -addext "subjectAltName=DNS:shop.internal,DNS:api.shop.internal"

# 2. Check it before you send it
openssl req -in server.csr -noout -verify      # Certificate request self-signature verify OK
openssl req -in server.csr -noout -text        # read the subject and the SAN

# 3. Send server.csr (never server.key) to the CA; it returns server.crt
# 4. Read what came back, and check it matches your key
openssl x509 -in server.crt -noout -subject -issuer -dates -ext subjectAltName
openssl x509 -in server.crt -noout -pubkey | openssl sha256
openssl pkey -in server.key -pubout       | openssl sha256   # the two hashes must match

Your own CA, for a lab or internal services

# a root CA (keep ca.key offline in real use)
openssl req -x509 -new -newkey ec -pkeyopt ec_paramgen_curve:P-256 -noenc \
  -keyout ca.key -out ca.crt -days 365 -subj "/CN=Lab Root CA"

# the CA signs the CSR from the card above, keeping its SAN
openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
  -out server.crt -days 90 -copy_extensions copy

# validate the chain, as a client would
openssl verify -CAfile ca.crt server.crt     # server.crt: OK

These commands were run with OpenSSL 3.0.13. -copy_extensions on openssl x509 -req is documented in the 3.x manual; on an older OpenSSL, put the SAN in an -extfile instead. A private CA is trusted only by machines you configure to trust it; for anything the public reaches, use a public CA.

Getting certificates automatically: ACME

  • ACME (RFC 8555) is a protocol a CA and an applicant use to automate proving control of a domain and issuing the certificate.
  • Let’s Encrypt uses it so a server can obtain browser-trusted certificates without human intervention. Its default certificates are valid for 90 days.
  • So renewal must be automatic (analysis): a 90-day certificate renewed by hand will expire on someone’s holiday.

Both sides show a certificate: mTLS

In mutual TLS the client also presents a certificate, so each side proves who it is. Service meshes issue and rotate these workload certificates automatically; see Service Mesh & Istio.

Each message was produced for real: a leaf checked without its intermediate, the same certificate checked for a name not in its SAN, and checked at a date after it expires (openssl verify -attime). Supplying the intermediate with -untrusted int.crt turned the first into OK.

SSH keys

# make a key pair (GitHub's own instruction); set a passphrase when asked
ssh-keygen -t ed25519 -C "your_email@example.com"

# its fingerprint: what you compare when someone asks "is this your key?"
ssh-keygen -lf ~/.ssh/id_ed25519.pub

# first connection: compare the fingerprint shown with the one the service publishes
ssh -T git@github.com
  • Your public key goes on the server, in ~/.ssh/authorized_keys (a default file sshd checks; the AuthorizedKeysFile setting controls which), or into GitHub’s settings. The private key stays on your machine.
  • ssh-agent holds your private keys for the session, so a passphrase-protected key is unlocked once rather than for every connection.
  • ~/.ssh/known_hosts records the host key of every server you have connected to. If a host’s key ever changes, ssh warns and disables password authentication, to prevent server spoofing or man-in-the-middle attacks.
  • When that warning appears (analysis): find out why the key changed (a rebuilt server, a new load balancer) before you remove the old entry with ssh-keygen -R host. Deleting the line to make the warning go away defeats the check.

Git: signing commits with your SSH key

git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true          # sign every commit

# to verify locally, list the keys you trust
echo "you@example.com $(cat ~/.ssh/id_ed25519.pub)" >> ~/.ssh/allowed_signers
git config --global gpg.ssh.allowedSignersFile ~/.ssh/allowed_signers
git verify-commit HEAD
# Good "git" signature for you@example.com with ED25519 key SHA256:...
  • Why sign: anyone can set user.email to any address. A signature that verifies shows the commit came from the holder of that key. GitHub marks commits signed with GPG, SSH or S/MIME as Verified when it can check the signature, so add the key to your account as a signing key too.
  • Authentication and signing are separate: the same SSH key can let you push and sign your commits, but GitHub registers it for each purpose separately: to use one key for both, you upload it twice.
  • Everyday Git commands are on DevOps.

Our view, and the other view

Our view: automate every certificate’s renewal, keep private keys where they were made, and sign your commits. Each removes a way to be surprised: an expiry, a leaked key, or a commit that only claims to be yours.

The other view: some systems cannot automate renewal (older appliances, devices in the field, partners who install certificates by hand), and for them short lifetimes add work and risk. Commit signing adds setup for every engineer and machine; some teams rely on protected branches and reviewed pull requests instead.

Levels: what to expect

1 Foundation

  • Explain a key pair: what the public key and the private key are each for
  • Read a certificate's subject, SAN, issuer and dates
  • Make an SSH key and add its public half to a server or GitHub

2 Practitioner

  • Make a CSR with the right SAN and check it before sending
  • Fix a missing intermediate, a hostname mismatch and an expired certificate
  • Sign Git commits with an SSH key and verify them

3 Senior

  • Run a private CA for internal services, and know its limits
  • Automate certificate renewal with ACME
  • Set up mTLS between services

4 Expert

  • Set an organisation's key and certificate policy
  • Plan certificate and key rotation without outages
  • Design trust for partners and devices that cannot automate

Each level includes the ones before it. See Start here for what the levels mean.

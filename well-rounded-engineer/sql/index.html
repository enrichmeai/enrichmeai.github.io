Getting better at SQL and BigQuery

How SQL actually evaluates a query, the patterns that solve most real problems, the mistakes that give wrong answers quietly, and exercises with solutions. Written in BigQuery GoogleSQL. The BigQuery tab is the syntax reference.

Practice schema used on this tab

orders(order_id STRING, order_ref STRING, store_id STRING, order_date DATE,
       order_year INT64, items ARRAY<STRING>, raw_date STRING, _landed_at TIMESTAMP)
stores(store_id STRING, name STRING, state STRING)

Practise for free in the BigQuery sandbox (no billing account needed) against bigquery-public-data, for example bigquery-public-data.stackoverflow.posts_questions or bigquery-public-data.new_york_taxi_trips. Always dry-run first and select only the columns you need.

The order SQL really runs in

  1. FROM and JOIN: build the row set
  2. WHERE: filter rows
  3. GROUP BY: form groups
  4. aggregates computed
  5. HAVING: filter groups
  6. window functions computed
  7. QUALIFY: filter on window results
  8. SELECT expressions, then DISTINCT
  9. ORDER BY
  10. LIMIT

This explains most errors: you cannot use a window function in WHERE (it does not exist yet; use QUALIFY), and WHERE cannot filter on an aggregate (use HAVING).

Write it so it reads top to bottom

WITH
landed AS (                         -- 1. narrow the input early
  SELECT order_id, store_id, order_date
  FROM `p.analytics.orders`
  WHERE order_date BETWEEN '2024-01-01' AND '2024-12-31'
),
per_store AS (                      -- 2. aggregate at one grain
  SELECT store_id, COUNT(*) AS n
  FROM landed
  GROUP BY store_id
)
SELECT c.name, COALESCE(p.n, 0) AS n  -- 3. join for labels last
FROM `p.ref.stores` AS c
LEFT JOIN per_store AS p USING (store_id)
ORDER BY n DESC;
  • One CTE per step, named for what it holds.
  • State each CTE's grain in a comment when it is not obvious.
  • Filter and aggregate before joining wide tables.

NULL: the source of quiet bugs

  • NULL = NULL is NULL, not TRUE. Use IS NULL, or a IS NOT DISTINCT FROM b to compare nullable values.
  • COUNT(*) counts rows; COUNT(col) skips NULLs. AVG, SUM, MIN ignore NULLs too.
  • x NOT IN (subquery) returns no rows if the subquery yields a single NULL. Use NOT EXISTS.
  • WHERE status != 'X' drops rows where status is NULL.
  • SUM of no rows is NULL, not 0: wrap in COALESCE(…, 0).
  • SAFE_CAST and SAFE.PARSE_DATE turn bad input into NULL. Count those NULLs, or the failure is invisible.
SELECT
  COUNT(*)                                             AS total_rows,
  COUNT(order_date)                                    AS with_date,
  COUNTIF(raw_date IS NOT NULL AND order_date IS NULL) AS failed_parse
FROM `p.analytics.orders`;

Joins without surprises

  • Know the grain of both sides before joining. Joining one-to-many multiplies rows; a SUM afterwards is inflated (fan-out).
  • Aggregate first, then join when you need totals from two child tables.
  • A filter on the right table in WHERE turns a LEFT JOIN into an inner join. Put it in ON.
  • Check row counts before and after each join while developing.
-- WRONG: stores with no 2024 orders disappear
SELECT c.store_id, COUNT(o.order_id) n
FROM stores c LEFT JOIN orders o USING (store_id)
WHERE o.order_year = 2024
GROUP BY 1;

-- RIGHT: the filter belongs to the join
SELECT c.store_id, COUNT(o.order_id) n
FROM stores c
LEFT JOIN orders o
  ON o.store_id = c.store_id AND o.order_year = 2024
GROUP BY 1;

-- did my join fan out? keys should be unique on the "one" side
SELECT store_id, COUNT(*) FROM stores GROUP BY 1 HAVING COUNT(*) > 1;

Semi-joins and anti-joins

-- semi-join: stores that HAVE at least one order (no duplicates)
SELECT * FROM stores c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.store_id = c.store_id);

-- anti-join: stores with NO order
SELECT * FROM stores c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.store_id = c.store_id);

-- same anti-join with LEFT JOIN
SELECT c.* FROM stores c
LEFT JOIN orders o USING (store_id)
WHERE o.store_id IS NULL;

-- set operations (columns by position)
SELECT order_ref FROM a EXCEPT DISTINCT SELECT order_ref FROM b;   -- in a, not in b
SELECT order_ref FROM a INTERSECT DISTINCT SELECT order_ref FROM b;
SELECT order_ref FROM a UNION ALL SELECT order_ref FROM b;          -- keeps duplicates, cheaper

Aggregation toolkit

SELECT
  store_id,
  COUNT(*)                                  AS n,
  COUNT(DISTINCT order_ref)                 AS orders_n,
  COUNTIF(order_date IS NULL)               AS undated,
  SAFE_DIVIDE(COUNTIF(order_date IS NULL), COUNT(*)) AS undated_share,
  MIN(order_date) AS first_d, MAX(order_date) AS last_d,
  ANY_VALUE(order_ref HAVING MAX order_date) AS latest_order_ref,   -- value at the max
  STRING_AGG(DISTINCT CAST(order_year AS STRING), ',' ORDER BY CAST(order_year AS STRING)) AS years,
  APPROX_QUANTILES(DATE_DIFF(DATE(_landed_at), order_date, DAY), 100)[OFFSET(50)] AS median_lag_days,
  LOGICAL_AND(order_date IS NOT NULL)       AS all_dated
FROM `p.analytics.orders`
GROUP BY ALL;            -- groups by every non-aggregated column

-- subtotals in one pass
SELECT state, store_id, COUNT(*) n
FROM orders JOIN stores USING (store_id)
GROUP BY ROLLUP (state, store_id);       -- per store, per state, grand total

Window functions, properly

A window function computes a value for each row from a set of related rows, without collapsing them. Three parts: PARTITION BY (which rows are related), ORDER BY (their sequence), and the frame (which of them count for this row).

SELECT
  store_id, d, n,
  ROW_NUMBER() OVER w_date                            AS rn,          -- 1,2,3 no ties
  RANK()       OVER (PARTITION BY store_id ORDER BY n DESC) AS rnk, -- 1,1,3
  DENSE_RANK() OVER (PARTITION BY store_id ORDER BY n DESC) AS drnk,-- 1,1,2
  LAG(n)  OVER w_date                                 AS prev_day,
  LEAD(n) OVER w_date                                 AS next_day,
  SUM(n)  OVER (PARTITION BY store_id ORDER BY d
                ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total,
  AVG(n)  OVER (PARTITION BY store_id ORDER BY d
                ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)         AS avg_7_rows,
  AVG(n)  OVER (PARTITION BY store_id ORDER BY UNIX_DATE(d)
                RANGE BETWEEN 6 PRECEDING AND CURRENT ROW)        AS avg_7_days,
  n / SUM(n) OVER (PARTITION BY store_id)           AS share_of_store,
  FIRST_VALUE(d) OVER w_date                          AS first_day,
  LAST_VALUE(d)  OVER (w_date ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS last_day
FROM daily
WINDOW w_date AS (PARTITION BY store_id ORDER BY d);
  • ROWS vs RANGE: ROWS 6 PRECEDING means six rows back, even if days are missing. RANGE on a numeric day number means six calendar days back. Fill gaps with a date spine or use RANGE.
  • Default frame trap: with ORDER BY and no frame, the frame ends at the current row, so LAST_VALUE returns the current row. Give an explicit frame.
  • Ties: ROW_NUMBER picks arbitrarily among ties. Add a tie-breaker column to ORDER BY so results are repeatable.

Pattern: top N per group

-- 3 most recent orders per store
SELECT store_id, order_ref, order_date
FROM `p.analytics.orders`
WHERE order_date IS NOT NULL
QUALIFY ROW_NUMBER() OVER (
  PARTITION BY store_id
  ORDER BY order_date DESC, order_id      -- tie-breaker
) <= 3;

Use RANK instead of ROW_NUMBER if ties should all be included. If BigQuery complains that QUALIFY needs a WHERE, GROUP BY or HAVING clause, add WHERE TRUE.

Pattern: deduplicate

-- find duplicates first: never dedupe blind
SELECT order_ref, COUNT(*) AS copies, COUNT(DISTINCT _landed_at) AS loads
FROM `p.raw.orders`
GROUP BY order_ref HAVING COUNT(*) > 1
ORDER BY copies DESC LIMIT 20;

-- keep the latest copy of each key
SELECT * FROM `p.raw.orders`
QUALIFY ROW_NUMBER() OVER (PARTITION BY order_ref ORDER BY _landed_at DESC) = 1;

-- exact duplicate rows only
SELECT DISTINCT * EXCEPT (_run_id) FROM t;   -- DISTINCT * fails on ARRAY columns

Pattern: date spine and missing days

WITH days AS (
  SELECT d FROM UNNEST(GENERATE_DATE_ARRAY('2025-01-01', '2025-03-31')) AS d
),
grid AS (                                  -- every store × every day
  SELECT c.store_id, days.d FROM `p.ref.stores` c CROSS JOIN days
),
actual AS (
  SELECT store_id, order_date AS d, COUNT(*) AS n
  FROM `p.analytics.orders`
  WHERE order_date BETWEEN '2025-01-01' AND '2025-03-31'
  GROUP BY 1, 2
)
SELECT g.store_id, g.d, COALESCE(a.n, 0) AS n
FROM grid g LEFT JOIN actual a USING (store_id, d)
ORDER BY 1, 2;

Without the spine, days with zero rows simply do not appear, and averages and LAGs are computed over the wrong set.

Pattern: gaps and islands

-- streaks of consecutive days on which a store took orders
WITH d AS (
  SELECT DISTINCT store_id, order_date
  FROM `p.analytics.orders` WHERE order_date IS NOT NULL
),
tagged AS (
  SELECT *,
    DATE_SUB(order_date,
      INTERVAL ROW_NUMBER() OVER (PARTITION BY store_id ORDER BY order_date) DAY
    ) AS island                            -- constant within a run of consecutive days
  FROM d
)
SELECT store_id, MIN(order_date) AS start_d, MAX(order_date) AS end_d,
       COUNT(*) AS days
FROM tagged
GROUP BY store_id, island
ORDER BY days DESC;

The trick: a date minus its row number stays the same while dates are consecutive and jumps at each gap.

Pattern: change vs previous period

WITH yearly AS (
  SELECT store_id, order_year, COUNT(*) AS n
  FROM `p.analytics.orders` GROUP BY ALL
)
SELECT * FROM (
  SELECT *,
    LAG(n) OVER (PARTITION BY store_id ORDER BY order_year) AS prev_n
  FROM yearly
)
WHERE SAFE_DIVIDE(n - prev_n, prev_n) < -0.2;   -- fell by more than 20%

LAG takes the previous row. If a year is missing for a store, "previous" is two years back. Use a spine when that matters.

Pattern: arrays (one-to-many in one row)

-- top 3 items per store by number of orders
WITH per_item AS (
  SELECT store_id, TRIM(item) AS item, COUNT(*) AS n
  FROM `p.analytics.orders`, UNNEST(items) AS item
  GROUP BY ALL
)
SELECT * FROM per_item
QUALIFY ROW_NUMBER() OVER (PARTITION BY store_id ORDER BY n DESC, item) <= 3;

-- filter rows by array content without exploding
SELECT order_ref FROM `p.analytics.orders`
WHERE EXISTS (SELECT 1 FROM UNNEST(items) i WHERE i LIKE '%UMBRELLA%');

-- array size, and rows whose array is empty or NULL
SELECT ARRAY_LENGTH(items) AS n_items FROM t;
SELECT COUNTIF(ARRAY_LENGTH(items) = 0 OR items IS NULL) FROM t;

The comma before UNNEST is a CROSS JOIN: rows with an empty array vanish. Use LEFT JOIN UNNEST(items) AS item to keep them.

Pattern: pivot and unpivot

-- one row per store, a column per year
SELECT * FROM (
  SELECT store_id, order_year, order_id FROM `p.analytics.orders`
  WHERE order_year BETWEEN 2023 AND 2025
)
PIVOT (COUNT(order_id) FOR order_year IN (2023 AS y2023, 2024 AS y2024, 2025 AS y2025));

-- the portable way, works in any SQL
SELECT store_id,
  COUNTIF(order_year = 2023) AS y2023,
  COUNTIF(order_year = 2024) AS y2024,
  COUNTIF(order_year = 2025) AS y2025
FROM `p.analytics.orders` GROUP BY store_id;

-- columns back to rows
SELECT * FROM wide UNPIVOT (n FOR year IN (y2023, y2024, y2025));

Pattern: recursive hierarchy

-- every category under X, directly or through a chain (max depth 5)
WITH RECURSIVE chain AS (
  SELECT category_id, parent_id, 1 AS depth
  FROM `p.analytics.categories`
  WHERE parent_id = 'X'
  UNION ALL
  SELECT c.category_id, c.parent_id, chain.depth + 1
  FROM `p.analytics.categories` c
  JOIN chain ON c.parent_id = chain.category_id
  WHERE chain.depth < 5                    -- always bound the recursion
)
SELECT category_id, MIN(depth) AS depth FROM chain GROUP BY category_id;

Pattern: point-in-time join (SCD type 2)

-- which store name was valid on the order date?
SELECT o.order_ref, o.order_date, s.name
FROM `p.analytics.orders` o
JOIN `p.snapshots.store_snapshot` s
  ON s.store_id = o.store_id
 AND o.order_date >= DATE(s.dbt_valid_from)
 AND (s.dbt_valid_to IS NULL OR o.order_date < DATE(s.dbt_valid_to));

Half-open intervals (>= from AND < to) never match two versions for one date.

Reusable logic

-- temporary SQL function for this script
CREATE TEMP FUNCTION parse_any_date(s STRING) AS (
  COALESCE(SAFE.PARSE_DATE('%Y-%m-%d', s), SAFE.PARSE_DATE('%d-%m-%Y', s))
);
SELECT raw_date, parse_any_date(raw_date) FROM t;

-- persistent function in a dataset
CREATE OR REPLACE FUNCTION `p.util.safe_ratio`(a FLOAT64, b FLOAT64) AS (
  IF(b = 0 OR b IS NULL, NULL, a / b)
);

-- table function: a parameterised view
CREATE OR REPLACE TABLE FUNCTION `p.util.store_year`(c STRING, y INT64) AS
SELECT * FROM `p.analytics.orders` WHERE store_id = c AND order_year = y;
SELECT COUNT(*) FROM `p.util.store_year`('1_05', 2024);

Making BigQuery fast and cheap

HabitWhy
Select named columnsBytes billed = bytes of the columns you read. One wide text column can be most of a table.
Filter on the partition column with literals or parametersLets BigQuery skip partitions before reading. Wrapping the column in a function can prevent it.
Filter on clustered columnsSkips blocks inside partitions; benefit shows in "bytes processed" after the run.
Dry-run before runningShows bytes to be scanned for free. Set a maximum bytes billed on risky jobs.
Aggregate early, join lateShuffling fewer rows between stages is the main cost in slot time.
Avoid ORDER BY without LIMIT on huge resultsA global sort runs on one worker at the end.
Use APPROX_COUNT_DISTINCT for explorationExact distinct counts on billions of rows are expensive; the approximate version has a small, documented error and is far cheaper.
Materialise reused intermediate resultsA CTE referenced several times may be computed several times. Write it to a table (or temp table in a script) when it is big.
Read the execution graphIn the console's Execution details: look for a stage with skewed time (one huge key), large shuffle, or spill to disk.
Avoid self-joins for running totalsA window function does in one pass what a self-join does quadratically.

Mistakes that give wrong answers quietly

  • Fan-out from a one-to-many join before a SUM.
  • A right-table filter in WHERE after a LEFT JOIN.
  • NOT IN against a column that contains NULL.
  • Integer division in other engines (1/2 = 0); BigQuery's / returns FLOAT64, but DIV() is integer.
  • BETWEEN on timestamps: BETWEEN '2025-01-01' AND '2025-01-31' misses most of the 31st. Use >= start AND < next_day.
  • Time zones: DATE(ts) is UTC unless you pass a zone (DATE(ts, 'Asia/Kolkata')).
  • ROW_NUMBER without a tie-breaker: a different row "wins" on each run.
  • LIMIT without ORDER BY: an arbitrary sample, not the top rows.
  • Averaging averages, or averaging percentages, instead of recomputing from totals.
  • Safe-parsing into NULL and never counting the NULLs.

Check your own query

  • Grain: what does one output row mean? Is the key unique? (COUNT(*) vs COUNT(DISTINCT key))
  • Totals: does the sum across groups equal the ungrouped total?
  • Rows in vs out: did a join drop or multiply rows you did not expect?
  • Edges: empty groups, NULLs, the first and last day, ties.
  • One example by hand: pick one key and check its row against the source.
  • Cost: dry-run bytes reasonable for the question?

Exercises (open each for a solution)

Try each on the practice schema, or adapt it to a public dataset. Solutions are one good answer, not the only one.

1. Orders per store in 2024, including stores with none.
SELECT c.store_id, c.name, COUNT(o.order_id) AS n
FROM `p.ref.stores` c
LEFT JOIN `p.analytics.orders` o
  ON o.store_id = c.store_id AND o.order_year = 2024
GROUP BY ALL
ORDER BY n DESC;

Filter in ON, and count a column from the right table so empty stores give 0.

2. The most recent order per store, with ties broken consistently.
SELECT store_id, order_ref, order_date
FROM `p.analytics.orders`
WHERE order_date IS NOT NULL
QUALIFY ROW_NUMBER() OVER (PARTITION BY store_id
                           ORDER BY order_date DESC, order_id) = 1;
3. What share of each store's rows failed to parse their date? Only stores above 1%.
SELECT store_id,
       COUNT(*) AS n,
       COUNTIF(raw_date IS NOT NULL AND order_date IS NULL) AS failed,
       SAFE_DIVIDE(COUNTIF(raw_date IS NOT NULL AND order_date IS NULL), COUNT(*)) AS failed_share
FROM `p.analytics.orders`
GROUP BY store_id
HAVING SAFE_DIVIDE(COUNTIF(raw_date IS NOT NULL AND order_date IS NULL), COUNT(*)) > 0.01
ORDER BY failed_share DESC;
4. Daily counts for one store with a 7-day moving average, including days with zero.
WITH days AS (
  SELECT d FROM UNNEST(GENERATE_DATE_ARRAY('2025-01-01', '2025-06-30')) d
),
daily AS (
  SELECT order_date AS d, COUNT(*) n FROM `p.analytics.orders`
  WHERE store_id = '1_05' AND order_date BETWEEN '2025-01-01' AND '2025-06-30'
  GROUP BY 1
)
SELECT days.d, COALESCE(n, 0) AS n,
       AVG(COALESCE(n, 0)) OVER (ORDER BY days.d ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS ma7
FROM days LEFT JOIN daily USING (d)
ORDER BY d;

The spine makes ROWS equal to days, so the moving average is over seven calendar days.

5. Stores whose yearly count fell by more than 20% compared with the previous year.
WITH y AS (
  SELECT store_id, order_year, COUNT(*) n FROM `p.analytics.orders` GROUP BY ALL
),
c AS (
  SELECT *, LAG(n) OVER (PARTITION BY store_id ORDER BY order_year) AS prev_n,
            LAG(order_year) OVER (PARTITION BY store_id ORDER BY order_year) AS prev_year
  FROM y
)
SELECT *, SAFE_DIVIDE(n - prev_n, prev_n) AS change
FROM c
WHERE prev_year = order_year - 1               -- only compare adjacent years
  AND SAFE_DIVIDE(n - prev_n, prev_n) < -0.2;
6. Find duplicate keys, then build the deduplicated table keeping the latest load.
SELECT order_ref, COUNT(*) copies FROM `p.raw.orders`
GROUP BY order_ref HAVING COUNT(*) > 1;

CREATE OR REPLACE TABLE `p.scratch.orders_dedup` AS
SELECT * FROM `p.raw.orders`
QUALIFY ROW_NUMBER() OVER (PARTITION BY order_ref ORDER BY _landed_at DESC) = 1;

-- verify: should return 0
SELECT COUNT(*) - COUNT(DISTINCT order_ref) FROM `p.scratch.orders_dedup`;
7. The longest run of consecutive trading days for each store.
WITH d AS (
  SELECT DISTINCT store_id, order_date FROM `p.analytics.orders`
  WHERE order_date IS NOT NULL
),
t AS (
  SELECT *, DATE_SUB(order_date, INTERVAL
           ROW_NUMBER() OVER (PARTITION BY store_id ORDER BY order_date) DAY) AS grp
  FROM d
),
runs AS (
  SELECT store_id, MIN(order_date) s, MAX(order_date) e, COUNT(*) len
  FROM t GROUP BY store_id, grp
)
SELECT * FROM runs
QUALIFY ROW_NUMBER() OVER (PARTITION BY store_id ORDER BY len DESC, s) = 1;
8. Each store's share of all 2024 orders, and its rank within its state.
WITH n AS (
  SELECT c.state, o.store_id, COUNT(*) n
  FROM `p.analytics.orders` o JOIN `p.ref.stores` c USING (store_id)
  WHERE o.order_year = 2024
  GROUP BY ALL
)
SELECT *,
  n / SUM(n) OVER ()                                  AS share_all,
  RANK() OVER (PARTITION BY state ORDER BY n DESC)     AS rank_in_state
FROM n
ORDER BY state, rank_in_state;
9. Stores present in the reference table but absent from the landed data, and the reverse.
(SELECT 'missing_data' AS issue, store_id FROM `p.ref.stores`
 EXCEPT DISTINCT
 SELECT 'missing_data', store_id FROM `p.analytics.orders`)
UNION ALL
(SELECT 'unknown_store', store_id FROM `p.analytics.orders`
 EXCEPT DISTINCT
 SELECT 'unknown_store', store_id FROM `p.ref.stores`);

Parenthesise when mixing different set operators; BigQuery requires it.

10. Median, 90th percentile and maximum lag (days) between order and landing, per store.
SELECT store_id,
  APPROX_QUANTILES(lag_d, 100)[OFFSET(50)] AS p50,
  APPROX_QUANTILES(lag_d, 100)[OFFSET(90)] AS p90,
  MAX(lag_d) AS max_lag
FROM (
  SELECT store_id, DATE_DIFF(DATE(_landed_at), order_date, DAY) AS lag_d
  FROM `p.analytics.orders` WHERE order_date IS NOT NULL
)
GROUP BY store_id
ORDER BY p90 DESC;
11. Upsert a day's new rows into a target table without creating duplicates.
MERGE `p.mart.serving` T
USING (
  SELECT * FROM `p.analytics.orders`
  WHERE DATE(_landed_at) = @run_date
  QUALIFY ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY _landed_at DESC) = 1
) S
ON T.order_id = S.order_id
WHEN MATCHED THEN UPDATE SET order_date = S.order_date, order_ref = S.order_ref
WHEN NOT MATCHED THEN INSERT ROW;

Deduplicate the source first: MERGE fails if two source rows match one target row.

12. Explain why this returns no rows: SELECT * FROM stores WHERE store_id NOT IN (SELECT store_id FROM orders).

If any orders.store_id is NULL, x NOT IN (…, NULL) evaluates to NULL for every x, never TRUE, so no row passes. Use NOT EXISTS, or add WHERE store_id IS NOT NULL inside the subquery.

A plan to get better

  1. Week 1: the evaluation order, NULLs and joins. Redo exercises 1, 9 and 12 until they feel obvious.
  2. Week 2: window functions. Exercises 2, 4, 5 and 8; then rewrite one self-join you have seen as a window.
  3. Week 3: patterns. Gaps and islands, date spines, dedup, pivots (6, 7).
  4. Week 4: BigQuery cost and plans. Dry-run everything, read the execution graph of your slowest query, and cut its bytes in half.
  5. Ongoing: before sharing any number, run the self-check list on this tab.

Read other people's SQL: dbt models in your repo, and the queries behind dashboards you use. Ask "what is the grain?" of each.

Levels: what to expect

1 Foundation

  • SELECT, WHERE, GROUP BY, ORDER BY and simple joins
  • Know how NULL behaves in comparisons and aggregates
  • Dry-run before running in BigQuery

2 Practitioner

  • Window functions, QUALIFY, CTEs, semi- and anti-joins
  • Check grain and fan-out before trusting a number
  • Write readable, tested SQL in dbt

3 Senior

  • Patterns: gaps and islands, spines, SCD joins, recursion
  • Read execution plans and cut cost and slot time
  • Review others' SQL for correctness and cost

4 Expert

  • Design query patterns and models for a whole platform
  • Teach SQL; set standards and linting
  • Know engine internals well enough to predict plans

Each level includes the ones before it. See Start here for what the levels mean.

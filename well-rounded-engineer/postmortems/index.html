Postmortems worth reading

Public write-ups of famous outages teach things no codebase will: how small, ordinary actions become global failures. Nine of them, each with what happened, what caused it and the lesson, the patterns they share, and the rest of a well-known reading list.

The short answer

A postmortem is the write-up a team publishes after something goes badly wrong: what happened, why, and what they changed. The best ones are blameless, honest and specific, and reading them is one of the cheapest ways to learn from other people’s worst days. (How to write one is on SRE.)

Read a few and a pattern appears: the cause is rarely exotic. It is a configuration change, a mistyped command, an unlucky timing or a forgotten piece of old code, meeting a system with nothing to stop one mistake spreading everywhere.

Knight Capital’s 45 minutes (2012)

What happened: On 1 August 2012, Knight Capital’s automated order router sent millions of unintended orders: about 4 million executions in 154 stocks, more than 397 million shares, in roughly 45 minutes. The firm took a pre-tax loss of $440 million and agreed to be acquired by Getco that December.

The cause: A technician did not copy the new Retail Liquidity Program code to one of the eight SMARS servers. The new code reused a flag that had once switched on an old, retired function called Power Peg. On the eighth server, that flag woke up the old code, whose code for recording that an order had been filled had since been changed, so it never saw orders as complete and kept sending more.

The lesson: Analysis: delete dead code instead of leaving it switched off; never reuse a flag for a new meaning; verify every server got the deploy; and give automated trading a kill switch that does not depend on finding the bug first.

Read it: Wikipedia: Knight Capital Group

The Amazon S3 outage (2017)

What happened: On 28 February 2017, Amazon S3 in Northern Virginia stopped serving requests for several hours, along with other AWS services in the region that rely on it, such as new EC2 instance launches.

The cause: While debugging a slow billing system, an engineer following an established playbook ran a command to remove a small number of servers. One input was entered incorrectly and a much larger set was removed, including servers for the index and placement subsystems. Both needed a full restart, something AWS had not done in its largest regions for many years, and it took longer than expected. AWS’s own status dashboard could not be updated for part of the outage because it depended on S3.

The lesson: AWS changed the tool to remove capacity more slowly, and to refuse to take any subsystem below its minimum capacity. Analysis: tools should protect against a wrong input, rarely used recovery paths should be rehearsed, and the dashboard that tells customers about an outage must not depend on the thing that failed.

Read it: AWS: Summary of the Amazon S3 service disruption

GitHub’s 43-second partition (2018)

What happened: On 21 October 2018, GitHub ran degraded for 24 hours and 11 minutes. No user data was lost, though a few seconds of writes needed manual reconciliation.

The cause: Routine maintenance on network equipment cut the link between GitHub’s US East Coast hub and its main East Coast data center for 43 seconds. In that window, Orchestrator, which manages GitHub’s MySQL clusters, held a vote and failed the databases over to the West Coast. The East Coast servers had a few seconds of writes not yet copied west, and East Coast applications could not cope with the extra latency of writing across the country.

The lesson: Analysis: automatic failover is itself a risky change; make sure it can only choose topologies the application can actually run on, and decide in advance whether a very short partition should trigger it at all.

Read it: GitHub: October 21 post-incident analysis

Facebook disappears for 6 hours (2021)

What happened: On 4 October 2021, Facebook, Instagram and WhatsApp vanished from the internet for six to seven hours.

The cause: During routine maintenance, a command meant to assess backbone capacity took down every connection in Facebook’s global backbone. An audit tool should have stopped it, but a bug in the tool let it through. Facebook’s DNS servers are designed to withdraw their BGP announcements when they cannot reach the data centers, so they disappeared from the internet even though they were still running. Recovery was slow: the network outage also broke internal tools, and engineers had to get physical access to data centers built to be hard to get into.

The lesson: Facebook credits its regular “storm” drills for bringing power and load back safely. Analysis: safety checks need testing too, and recovery access must work when the normal network does not.

Read it: Engineering at Meta: More details about the October 4 outage

Fastly’s global outage (2021)

What happened: On 8 June 2021, websites including Reddit, Twitch, Amazon and GOV.UK briefly went down around the world.

The cause: A software bug in Fastly’s CDN was triggered by a customer making a perfectly valid configuration change.

The lesson: Analysis: a single customer’s legitimate input should never be able to take down a shared platform; isolate customers from one another, and test with the full range of valid configurations, not just the common ones.

Read it: Wikipedia: Fastly

CrowdStrike Channel File 291 (2024)

What happened: On 19 July 2024, about 8.5 million Windows systems crashed and could not restart, grounding flights and disrupting banks and hospitals; it has been called the largest outage in the history of IT.

The cause: CrowdStrike’s Falcon sensor runs inside the operating system kernel. A content update, Channel File 291, passed validation because of a bug in CrowdStrike’s content verification software. The sensor expected 21 input fields but received 20, read memory that did not exist, and crashed the machine. Recovery was manual for many, and harder still where BitLocker recovery keys had to be typed in by hand, or were stored on servers that had themselves crashed.

The lesson: Analysis: treat content and configuration updates with the same caution as code: staged rollouts to a few machines first, and validators that are tested themselves. Software in the kernel needs the strictest care, because a crash there takes the whole machine down.

Read it: Wikipedia: 2024 CrowdStrike-related IT outages

AWS us-east-1 goes dark (2025)

What happened: On 19 and 20 October 2025, DynamoDB in Northern Virginia failed, followed by problems with load balancers and EC2 instance launches; impact lasted from 11:48 PM to 2:20 PM Pacific time.

The cause: A latent race condition in DynamoDB’s automated DNS management. One worker (“Enactor”) was unusually delayed, then applied a much older plan over a newer one; its check that the plan was newer had gone stale during the delay. A clean-up process then removed records, leaving the regional DynamoDB endpoint with an empty DNS record that the automation failed to repair. Many AWS services depend on DynamoDB, so the failure spread.

The lesson: Analysis: automation that rewrites production needs guards against acting on stale information, and a check made at the start of a slow operation may no longer be true at the end of it.

Read it: AWS: Summary of the Amazon DynamoDB service disruption in us-east-1

Cloudflare’s worst outage since 2019 (2025)

What happened: On 18 November 2025, a global Cloudflare outage disrupted many major platforms; a second global outage followed on 5 December, three weeks later.

The cause: Cloudflare attributed the November outage to a change in the configuration of a database, which caused an invalid file to be sent to all servers on its network.

The lesson: Analysis: a generated file that every server loads is a single point of failure; validate it before it ships, roll it out in stages, and make servers keep the last good version when a new one is bad.

Read it: Wikipedia: Cloudflare

Microsoft 365 goes down for a day (2026)

What happened: Starting on 12 November 2026, most Microsoft 365 services, especially Exchange Online email, failed worldwide; services were fully restored by the morning of 14 November.

The cause: According to Microsoft’s root-cause summary: a previously undetected defect made networking gateway servers unresponsive under certain loads, and at peak more than 80% of them were unresponsive. A change in traffic allocation increased load and made the defect likelier to appear. Automated rollback could not help because the faulty change had been deployed months earlier, in July. The “capacity unit” boundaries meant to isolate failures did not, so the outage spread across regions. And as the fix went out, waiting requests stampeded the servers coming back up.

The lesson: Analysis: latent defects can sit for months, so rollback is not a complete safety net; isolation boundaries must be tested, not assumed; and recovery needs traffic brought back gradually.

Read it: Wikipedia: 2026 Microsoft 365 outage

Guards these incidents argue for, by requirement

One change or file reaches every serverStaged rollout to a small share first, automatic halt on errors, keep the last good version
Engineers run commands that remove capacity or change the networkTools that refuse dangerous inputs and limits on how much one command can change (S3, Facebook)
Automation rewrites production records or topologyRe-check freshness before acting; constrain failover to what applications support (AWS, GitHub)

Our view, and the other view

Our view: one evening reading these will change how you review a deploy. The question to carry away is not “could this break?” but “if this breaks, how far does it spread, and how do we get back?”

The other view: postmortems are written by the companies themselves, after the fact, and some details stay private; hindsight makes causes look more obvious than they were at the time. Read them as lessons in how systems fail, not as verdicts on the people involved.

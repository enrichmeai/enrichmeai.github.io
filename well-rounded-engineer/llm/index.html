LLMs and their runtimes

How large language models are built and why they behave as they do, the runtimes that serve them (hosted APIs, Vertex AI, self-hosted servers), and how to build an application on a runtime: from one call, to a tool loop, to a full agent harness. Engineering practice is on AI for Engineers.

How an LLM works, briefly

  1. Tokenise: text is split into tokens (word pieces). Everything (price, limits, speed) is counted in tokens.
  2. Embed: each token becomes a vector of numbers.
  3. Transformer layers: attention lets every token look at every earlier token and mix in what is relevant; dozens of layers build up meaning.
  4. Predict: the model outputs a probability for every possible next token; one is chosen, appended, and the process repeats. Generation is one token at a time.
StageWhat happensResult
Pre-trainingPredict the next token over a huge text and code corpusBroad knowledge and language ability, up to a training cutoff
Post-trainingInstruction tuning, reinforcement learning from human and AI feedback, safety trainingFollows instructions, uses tools, refuses harmful requests
InferenceYour prompt in, tokens out, on GPUs or TPUsThe responses you build on

Consequences you design around: no memory between calls; knowledge stops at a cutoff; outputs vary run to run; fluent text can be wrong; instructions inside data can be followed.

Prompt, RAG, tools or fine-tune?

NeedReach for
Behaviour, format, toneClear instructions and examples in the prompt; structured outputs
Knowledge the model lacks (your documents, current data)RAG: retrieve and include it
Live data or actionsTools (function calling) or MCP servers
A narrow task at high volume, cheaper or fasterA smaller model, or fine-tuning one, after measuring
Consistent style the prompt cannot achieveFine-tuning (LoRA or full)

Try in that order. Fine-tuning does not add reliable facts; it changes behaviour. Facts belong in retrieval.

Self-hosting basics

# vLLM: OpenAI-compatible server for an open-weight model
vllm serve meta-llama/Llama-3.1-8B-Instruct --max-model-len 8192
# → http://localhost:8000/v1/chat/completions

# Ollama: local models with one command
ollama run llama3.1
# → API on http://localhost:11434

# llama.cpp: quantised GGUF models on CPU or GPU
llama-server -m model-Q4_K_M.gguf --port 8080
  • GPU memory ≈ parameters × bytes per parameter, plus the KV cache. An 8B model in 16-bit needs ~16 GB before the cache; 4-bit quantisation cuts that to ~5 GB at some quality cost.
  • Throughput comes from continuous batching (vLLM) and caching the prompt prefix.
  • Measure time to first token, tokens per second, and cost per thousand requests against a hosted API before committing.
  • Licences of open-weight models differ; read them before commercial use.

Building on a runtime: four levels of harness

A harness is the code around the model: the loop that sends messages, runs tools, feeds results back, manages context and stops. Pick the least you need.

LevelYou writeWho runs the loop and toolsFits
1. Single callPrompt and parsingNo loopClassify, extract, summarise
2. Manual tool loopThe while stop_reason == "tool_use" loop and the toolsYou, on your infrastructureFull control over each step
3. SDK tool runnerJust the tool functionsThe SDK runs the loop; you host itMost custom agents
4a. Agent SDKA prompt and optionsClaude Code's harness as a library, with built-in file, shell and search tools; you host itCoding and file-system agents on your own infrastructure
4b. Managed agentsAgent configuration and your tool resultsThe provider runs the loop and a sandbox per sessionLong-running hosted agents without running infrastructure

Start at level 1 and move up only when the task needs model-driven, multi-step work. Each level adds cost, latency and things to test.

Level 2: a manual tool loop

import anthropic, json
client = anthropic.Anthropic()

TOOLS = [{
  "name": "pipeline_status",
  "description": "Latest state of each pipeline stage for a date (YYYY-MM-DD).",
  "input_schema": {"type": "object",
                   "properties": {"run_date": {"type": "string"}},
                   "required": ["run_date"]},
}]

def run_tool(name, args):
    if name == "pipeline_status":
        return json.dumps(read_ledger(args["run_date"]))   # read-only
    return json.dumps({"error": f"unknown tool {name}"})

messages = [{"role": "user", "content": "Did yesterday's load finish?"}]
for _ in range(10):                                   # always bound the loop
    resp = client.messages.create(model="claude-opus-5-5", max_tokens=16000,
                                  tools=TOOLS, messages=messages)
    messages.append({"role": "assistant", "content": resp.content})
    if resp.stop_reason != "tool_use":
        break
    results = [{"type": "tool_result", "tool_use_id": b.id,
                "content": run_tool(b.name, b.input)}
               for b in resp.content if b.type == "tool_use"]
    messages.append({"role": "user", "content": results})   # all results in one message

print("".join(b.text for b in resp.content if b.type == "text"))

Append the full resp.content, not just its text. Return failed tools as results with "is_error": true rather than dropping them. Level 3 (the SDK's tool runner) does this loop for you.

Running LLM features in production

  • Timeouts, retries and fallbacks per call; handle refusals and rate limits explicitly.
  • Stream long outputs; use the batch API for offline bulk work.
  • Prompt caching: keep stable instructions and tool definitions first so repeated calls reuse them.
  • Log model, version, tokens, latency and outcome for every call; trace tool calls.
  • Pin model IDs and re-run your evals before switching models.
  • Budget: cap tokens per request and spend per day; alert on spikes.
  • Data controls: know the provider's retention terms and the region where inference runs.

Glossary

  • Context window: maximum tokens of input plus output in one call.
  • Embedding: a vector representing meaning, used for search.
  • KV cache: stored attention state that makes generating each next token fast.
  • Quantisation: storing weights with fewer bits to save memory.
  • LoRA: fine-tuning small adapter weights instead of the whole model.
  • Temperature / sampling: how random token choice is (some newer APIs fix this and expose an effort setting instead).
  • Hallucination: confident output not supported by facts.
  • Grounding: tying answers to retrieved sources.

Levels: what to expect

1 Foundation

  • Explain tokens, context windows, next-token prediction and training cutoffs
  • Make a single model call with structured output
  • Know when to prompt, retrieve, use tools or fine-tune

2 Practitioner

  • Build a tool loop or use an SDK tool runner
  • Run a local or self-hosted model and compare it with a hosted API
  • Log, budget and handle errors for LLM calls

3 Senior

  • Choose runtimes and models by quality, cost, latency and data controls
  • Design agent harnesses with bounded loops, context management and approvals
  • Plan self-hosting capacity (GPU memory, batching, quantisation)

4 Expert

  • Set the organisation's model and runtime strategy
  • Lead fine-tuning or custom model programmes where justified
  • Design platform-level AI infrastructure and governance

Each level includes the ones before it. See Start here for what the levels mean.

From spring.jar to Spring

How Spring grew from code that came with a book in 2002 into Boot, Cloud, Data, Security, WebFlux, Modulith and AI: what each step added, and the pain it removed.

The short answer

Spring began as example code in a book, shipped as one jar, and grew into a widely used way to build Java services. Our view: each layer was added to remove a pain the previous one left behind. The other view is in the card “Our view, and the other view”. How to use Spring today is on Spring; this page is how it got there.

Twenty years in one line

1. A reaction to J2EE

2002–2003

In the early 2000s, enterprise Java meant J2EE and EJB 2: an application server, deployment descriptors, home and remote interfaces, and business code you could not test without the container. Rod Johnson’s book Expert One-on-One J2EE Design and Development (Wrox, November 2002) argued that most applications did not need all of that. It came with 30,000 lines of framework code showing the alternative: plain Java objects, wired together by a container, with infrastructure kept out of the business code.

Readers asked to use that code. Juergen Hoeller and Yann Caroff persuaded Johnson to make it an open-source project, and became co-founders. Caroff suggested the name: Spring, a fresh start after the “winter” of traditional J2EE. The project went public in June 2003.

2. Spring 1.0: one jar, three ideas

March 2004

Spring 1.0 Final was released on 24 March 2004. It was distributed as one file, spring.jar, alongside finer-grained module jars for those who wanted less. It rested on three ideas that are still its core:

  • Inversion of control and dependency injection. The container creates your objects and hands them their dependencies, so classes stay plain and testable.
  • Aspect-oriented programming. Cross-cutting concerns such as transactions and security are applied around your code, not written inside it.
  • Templates over raw APIs. JdbcTemplate, Hibernate support and a single transaction abstraction removed the open-try-catch-close boilerplate.
<bean id="caseService" class="com.example.CaseService">
    <property name="repository" ref="caseRepository"/>
</bean>

Spring MVC was in the box too, as a simpler alternative to Struts. Configuration was XML, and large applications grew large XML files.

3. Annotations

Spring 2.0 (October 2006) · 2.5 (November 2007)

Java 5 brought annotations, and Spring moved the wiring next to the code. Spring 2.0 added XML configuration based on XML Schema (shorter config) and integrated with the AspectJ pointcut language. Spring 2.5 added @Autowired, @Component, @Service and @Controller, with classpath scanning to find them (@Repository dates from 2.0).

@Service
public class CaseService {
    @Autowired private CaseRepository repository;
}

The family began to grow around the core. Acegi Security became an official Spring project at the end of 2007 and was renamed Spring Security (2.0 shipped in April 2008). Spring Web Services (2007), Spring Batch and Spring Integration (2008) followed. The company behind it changed its name too: Interface21 became SpringSource in 2007.

4. Spring 3: Java config, and the end of spring.jar

December 2009

Spring 3.0 made Java 5 the baseline. It brought @Configuration classes (configuration written in Java, checked by the compiler), the Spring Expression Language, and REST support in MVC.

@Configuration
public class AppConfig {
    @Bean CaseService caseService(CaseRepository repo) { return new CaseService(repo); }
}

It also stopped providing the all-in-one spring.jar. The framework was now a set of modules (spring-core, spring-beans, spring-context, spring-jdbc, spring-webmvc and more), and builds pulled in only what they used. VMware bought SpringSource in August 2009, and Spring Data followed in 2010–11, bringing the repository idea to JPA, MongoDB, Redis and others.

The new pain: each module was simple, but starting a project meant choosing compatible versions of a dozen modules and writing the same setup every time.

5. Spring Boot: convention over configuration

Spring 4.0 (December 2013) · Spring Boot 1.0 (April 2014)

Spring 4.0 added first-class Java 8 support, WebSocket and @RestController. The bigger change was Spring Boot, which answered “how do I start?” with defaults:

  • Starters: one dependency (spring-boot-starter-web) brings a tested set of libraries and versions.
  • Auto-configuration: if a database driver is on the classpath, a DataSource is set up for you, and you override only what you need.
  • An embedded server: Tomcat (or Jetty) inside the jar; java -jar app.jar replaced deploying WAR files to an application server.
  • Actuator: health, metrics and info endpoints for production.
@SpringBootApplication
public class App {
    public static void main(String[] args) { SpringApplication.run(App.class, args); }
}

Boot arrived as microservices and containers took off. Spring Cloud 1.0 (March 2015) paired a configuration server with integrations for Netflix’s open-source tools (Eureka, Zuul, Ribbon). Spring moved to Pivotal, spun out of VMware, in 2013; VMware agreed to acquire Pivotal in 2019, and Broadcom completed its purchase of VMware in November 2023.

6. Spring 5: reactive

September 2017 · Boot 2.0 (March 2018)

Spring 5.0 made Java 8 the baseline and added WebFlux, a second web stack built on Project Reactor, running on Netty or Undertow among others. A few threads that never block serve many connections, with end-to-end backpressure; R2DBC later did the same for databases. It also added first-class Kotlin support and a functional routing model. Spring MVC stayed fully supported, so teams chose per service. The threading story behind this is on How Java Threads Evolved.

7. Spring 6: Java 17, Jakarta and native

Spring 6.0 (November 2022) · Boot 3.0 (eight days later)

Spring 6 raised the baseline to Java 17 and moved from javax.* to jakarta.*, following Java EE’s move to the Eclipse Foundation. It added first-class support for GraalVM native images, through ahead-of-time processing: applications that start much faster and use less memory. Observability was rebuilt on Micrometer.

Boot 3.2 (November 2023) added a one-line switch for virtual threads, spring.threads.virtual.enabled=true, plus the simpler RestClient and JdbcClient. Spring Modulith (first release 2022) gave a structure for well-separated modules inside one application, checked by tests, and Spring AI (1.0 in May 2025) brought model clients, prompts and vector stores into the same style. Spring Framework 7 and Boot 4 (November 2025) continue the line, with JSpecify null-safety annotations across the codebase.

What stayed the same

Idea2004Today
Dependency injectionXML <bean> with <property>Constructor injection, found by scanning or @Bean
Infrastructure around codeAOP proxies for transactionsThe same proxies, plus ahead-of-time generated code for native images
Templates over raw APIsJdbcTemplate, HibernateTemplateJdbcClient, RestClient, Spring Data repositories
Getting startedCopy spring.jar, write XMLstart.spring.io, one starter, no XML

Our view, and the other view

Our view: Spring grew by adding a layer each time the previous one made something tedious: XML gave way to annotations, annotations to Java config, hand-picked jars to starters, and application servers to an executable jar. The single jar is gone, but plain Java objects with infrastructure kept out of the way are still the point.

The other view: each layer also hid more of what happens at start-up, and auto-configuration can make it hard to see why a bean exists; teams that value explicitness may prefer a smaller framework, or plain Java with fewer conventions (see Quarkus for one alternative).

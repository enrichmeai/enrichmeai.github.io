How the cloud is built

"The cloud" is not magic, and it is not a genie that grants servers. It is buildings full of ordinary computers, joined by networks, run by software that lets millions of customers share them safely. Once you can see the layers, cost, failure, speed and lock-in all start to make sense.

The layers, from the ground up

LayerWhat it really isWhy it matters to you
BuildingsData centres: power, cooling, physical security, fibre. A zone is one or more of them that fail together; a region is a group of zones close enough to talk fastSpread work across zones to survive a building failing; pick a region for latency and data residency
ServersRacks of ordinary machines: CPUs, memory, local disks, network cards. They fail every day at this scaleDesign as if any one machine can disappear, because it will
VirtualisationA hypervisor splits one physical server into many virtual machines, each believing it has its own hardwareYour "server" shares a machine with strangers; isolation is the provider's hardest job
NetworkSoftware-defined networking: your private network, firewall rules and load balancers are configuration on shared switches and fibreMoving data costs money and time, especially between regions and out to the internet
StorageBlock disks attached over the network, object stores that spread copies of your files across machines and zones, managed file systemsDurability comes from copies in different places; every copy and every read has a price
Control planeThe APIs, identity and permissions, scheduling, quotas and billing that turn all of the above into "click to create"Every console click and every Terraform line is an API call; IAM decides who can make it
Managed servicesDatabases, queues, serverless and AI services: software the provider runs for you, built from the same layersYou trade control for convenience; the parts underneath still fail and still cost money

Virtual machines, containers and sandboxes

  • A virtual machine has its own operating system kernel on virtual hardware. Strong isolation, slower to start.
  • A container shares the host's kernel and isolates processes with kernel features. Fast and light, but sharing a kernel means weaker isolation.
  • Providers close the gap with sandboxes. Firecracker, developed at Amazon Web Services for services such as AWS Lambda and now open source, uses Linux KVM to run lightweight "microVMs" that start fast but keep virtual-machine isolation. gVisor, open-sourced by Google, is an "application kernel" that sits between a container and the host, because, in its own words, containers are not a sandbox.
  • Serverless is this underneath: someone else's servers, packed densely, started on demand, and billed by the request or the second.

Scheduling: who runs where

  • A scheduler decides which machine runs each piece of work, packing jobs tightly to use the hardware well and moving them when machines fail.
  • Kubernetes brings this idea to everyone. Its own README says it builds on Google's experience running production workloads at scale with an internal system called Borg.
  • Why you care: requests and limits, bin packing and preemption decide both your bill and whether your work gets evicted. See Kubernetes.

What "managed" really means

  • A managed database is still a database server on virtual machines with disks, replicas and backups. The provider patches and fails it over for you.
  • Object storage is many machines holding copies or encoded fragments of your files, with an API in front. That is why it is durable, cheap and slower than a local disk.
  • A serverless function runs in a sandbox on a shared machine; a "cold start" is that sandbox being created for you.
  • Knowing the parts helps you ask the right questions: where are the copies, what happens when a zone fails, what is billed, and what can I take elsewhere.

Shared responsibility

  • The provider secures the cloud: buildings, hardware, hypervisors, their network and their services.
  • You secure what you put in it: identities and permissions, your data, your network rules, your code and its dependencies, and the settings you choose.
  • The more managed the service, the more the provider takes on, but your identities, data and settings are always yours. Most cloud breaches are a setting someone left open, not a broken data centre. See Security.

Follow one request through the layers

You open a web page served from the cloud. Your request reaches the provider's edge and a load balancer (software on shared hardware), which picks a healthy instance in one zone. That instance is a container or virtual machine, placed by a scheduler on a physical server in a data centre. It reads from a managed database (more virtual machines, with a replica in another zone) and from object storage (copies spread across machines), writes logs and metrics (yet more storage), and every step is checked against permissions and metered for the bill. When one machine, or one building, fails, the layers above route around it, if you designed for it.

Try it yourself: run a small app on Cloud Run, then find each layer in the console: the region and zone, the revision and its instances, the logs, the IAM roles, and the bill.

Levels: what to expect

1 Foundation

  • Explain zones, regions and why work is spread across them
  • Tell a virtual machine from a container and a serverless function
  • Name what the provider secures and what you secure

2 Practitioner

  • Choose zones and regions for a service's availability, latency and data residency
  • Read a bill and trace each line to a layer: compute, storage, network
  • Explain what a managed service still leaves to you

3 Senior

  • Design for a machine, a zone or a region failing, and test it
  • Choose isolation (VM, container, sandbox) for untrusted or multi-tenant work
  • Estimate cost from first principles, including egress and copies

4 Expert

  • Set organisation standards for failure domains, tenancy and shared responsibility
  • Lead decisions on regions, providers and lock-in with the layers in view
  • Teach how the cloud works underneath, not only which button to press

Each level includes the ones before it. See Start here for what the levels mean.

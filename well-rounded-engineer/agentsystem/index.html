Guide / AI / Building an Agentic System

Building an agentic system: what to take care of

A demo agent takes an afternoon; a system people can rely on takes care at every stage. What matters, in order: deciding, building, evaluating, guarding, serving (inference) and observing, where a person should be in the loop and why, and one complete use case in Spring Boot, compiled and tested.

The short answer

An agent is a model with instructions and tools, running in a loop until a job is done (see How Anthropic & OpenAI Build Agents). Getting that loop to run once is easy. Making it a system means answering six questions: should this be an agent at all? Is it built from the right parts? How do we know it works? What stops it doing harm? Can we run it fast and cheaply enough? And can we see what it did?

1. Decide, and 2. build

Decide. Both Anthropic and OpenAI say to start with the simplest thing that works. OpenAI’s guide points agents at work that has resisted automation: complex judgement, rules that are hard to maintain, or lots of unstructured data; otherwise a fixed workflow or ordinary code may be enough. Its latency guide puts it bluntly as a principle: “Don’t default to an LLM.”

Build. The parts are few, and each deserves care:

  • Model: start with the most capable, then try smaller ones once evals show where they still pass.
  • Tools: clear names, clear parameters and good descriptions; Anthropic calls this the agent-computer interface. Business rules belong inside the tool, where the model cannot argue with them.
  • Instructions: written from your real procedures, with what to do when information is missing.
  • Context: a finite resource; models recall less as it fills (“context rot”), so give the agent what it needs for this step, not everything. More on Agent Harness.

3. Evaluation: how you know it works

Agents are non-deterministic: the same question can take a different path each time. So “I tried it and it worked” proves little. Anthropic’s guide Demystifying evals for AI agents gives the vocabulary:

TermMeaning
TaskOne problem for the agent, with what success looks like
TrialOne attempt at a task; run several, because results vary
GraderLogic that scores part of the result; a task can have several
TranscriptThe full record of a trial: messages, tool calls, results (also called a trace)
OutcomeThe final state of the world: not “the agent said the flight is booked”, but whether the booking exists in the database
SuiteA collection of tasks measuring one capability or behaviour

Three kinds of grader, usually combined:

  • Code-based: string matches, tests passing, checking which tools were called with which arguments, verifying the outcome. Fast, cheap and repeatable.
  • Model-based (“LLM as judge”): a model scores against a rubric, for things like tone or quality with many right answers. Anthropic suggests grading each dimension with its own isolated judge, and calibrating judges against human judgement.
  • Human: the gold standard, and the slowest; used to calibrate the other two.

Two kinds of suite: capability evals ask “what can it do?” and should start with a low pass rate, giving you a hill to climb; regression evals ask “does it still do what it did?” and should pass nearly 100% of the time. Capability tasks that become reliable graduate into the regression suite.

Getting started: Anthropic says 20 to 50 simple tasks drawn from real failures is a great start. Begin with the checks you already do by hand; test cases where a behaviour should happen and where it should not; start every trial from a clean environment, so leftovers from one run cannot pass or fail the next.

Run it: pass@k and pass^k

Because results vary, Anthropic uses two measures. pass@k is the chance that at least one of k tries succeeds, right for tools where one good answer is enough. pass^k is the chance that all k tries succeed, right for customer-facing agents that must behave the same way every time. This program shows how far apart they drift for an agent that succeeds 75% of the time:

# pass@k: chance at least one of k tries succeeds.  pass^k: chance all k tries succeed.
# p is the agent's success rate on a single try, measured by running your eval.
p = 0.75
print(" k   pass@k   pass^k")
for k in (1, 2, 3, 5, 10):
    at_least_one = 1 - (1 - p) ** k
    all_k = p ** k
    print(f"{k:2}   {at_least_one:6.1%}   {all_k:6.1%}")

What it printed when we ran it:

k   pass@k   pass^k
 1    75.0%    75.0%
 2    93.8%    56.2%
 3    98.4%    42.2%
 5    99.9%    23.7%
10   100.0%     5.6%

At three tries, pass^k is 42%, matching Anthropic’s worked example: a 75% agent passes three runs in a row less than half the time. By ten tries the two measures tell opposite stories. Choose the one that matches what your users need.

4. Guard: layers, limits and people

  • Layers. OpenAI describes guardrails as layered defence: relevance and safety classifiers, PII filters, moderation, and plain rules such as blocklists and length limits, on top of ordinary authentication and access control.
  • Limits. Every loop needs an exit: a maximum number of turns or tool calls, so a confused agent cannot run for ever. Spring AI, for example, caps tool calls per turn by default.
  • Least privilege. Give the agent only the tools the job needs, and treat everything it reads as untrusted: text in a web page or document can carry instructions (prompt injection; see Agentic AI Security).

Where a person should be involved, and why

A human in every step defeats the point of an agent; a human in no step is a risk. The sources agree on where people belong:

WhereWhy
Before high-risk actions: sensitive, irreversible or high-stakes ones, such as moving money, deleting data or sending messagesAn undo may be impossible, and a model can be wrong or manipulated. OpenAI recommends human oversight here until confidence in the agent grows.
When the agent keeps failingPast a limit on retries, handing over to a person protects the user’s experience (OpenAI’s “failure thresholds”).
At checkpoints and blockers in long tasksAnthropic notes agents can pause for human feedback at checkpoints or when they hit a blocker, rather than guessing.
In evaluationPeople calibrate the model-based graders and read transcripts; Anthropic notes human review stays crucial for checking work against the wider system’s requirements.
Reviewing what is learned from productionReal failures should become new eval tasks, and deciding what “correct” means is a human judgement.

Two practical rules from Spring AI’s documentation: authenticate the approver, because checking that the person who decides may decide is your application’s job; and treat a deny message as input to the model, so keep it clean. Analysis: keep lookups and cheap, reversible actions automatic, so people spend their attention where it changes the outcome.

5. Serve: inference, speed and cost

Inference is running the model to produce an answer, and for an agent it happens on every turn of the loop, so its speed and cost multiply. Anthropic measured agents using about 4× the tokens of a chat, and multi-agent systems about 15×.

  • Speed. Measure time to first token (TTFT), how long before the response starts, and stream the answer so people see progress. OpenAI’s seven principles for latency: process tokens faster (a smaller model), generate fewer tokens, use fewer input tokens, make fewer requests, parallelise, make users wait less, and don’t default to an LLM.
  • Prompt caching. Agents resend the same instructions and tool definitions on every turn. With caching, a repeated prefix is read from cache instead of reprocessed. On Anthropic’s API a cache read costs 0.1× the normal input price for most models (less on some), a cache write 1.25× for the default 5-minute lifetime or 2× for one hour; the lifetime refreshes free each time the cache is used, and cache hits do not count against rate limits.
  • Batching. Work that does not need an instant answer, such as nightly evals or bulk classification, can go through a batch API, processed asynchronously with results within 24 hours.
  • Routing. Anthropic’s routing pattern sends easy, common questions to smaller, cheaper models and hard ones to more capable models.
  • Self-hosting moves inference onto your own GPUs, with techniques like batching and KV caches; see LLMs.

6. Observe: see what it did

  • Keep transcripts. Every model call, tool call and result, so a bad outcome can be traced to the step that caused it. OpenAI’s Agents SDK has built-in tracing; Spring AI records spans and token-usage metrics through Micrometer.
  • Measure per task, not per request: success rate, cost and time per completed task, and how often a person had to step in (more on Agent Harness). Anthropic notes that once evals exist, latency, token use and cost per task come almost for free.
  • Close the loop. Each real failure becomes a new eval task, so the same mistake is caught before the next release.

A use case, built: an order-support agent in Spring Boot

A customer writes in about an order. The agent looks the order up, explains its status, and can refund it. Small refunds happen automatically; refunds over £100 pause until a supervisor approves. It uses Spring Boot 4.2 and Spring AI 2.1, whose tool-call confirmation is built for exactly this. Every stage above shows up in the code.

Build: the tools. The model can only ask for these; the code decides what happens. The rule that a refund can never exceed what was paid lives here, where no prompt can talk around it:

package com.example.orderagent;

import java.math.BigDecimal;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import org.springframework.ai.tool.annotation.Tool;
import org.springframework.ai.tool.annotation.ToolParam;
import org.springframework.stereotype.Component;

/** The agent's tools. The model can only ask for these; this code decides what really happens. */
@Component
public class OrderTools {

    record Order(String id, String status, BigDecimal total, BigDecimal refunded) {}

    private final Map<String, Order> orders = new ConcurrentHashMap<>(Map.of(
            "A100", new Order("A100", "delivered", new BigDecimal("40.00"), BigDecimal.ZERO),
            "A200", new Order("A200", "delivered", new BigDecimal("450.00"), BigDecimal.ZERO)));

    @Tool(description = "Look up an order's status, total and how much has already been refunded")
    public String getOrder(@ToolParam(description = "Order id, for example A100") String orderId) {
        Order o = orders.get(orderId);
        return o == null ? "No order " + orderId : o.toString();
    }

    @Tool(description = "Refund part or all of an order. Refunds over 100 need a person's approval.")
    public String refundOrder(@ToolParam(description = "Order id") String orderId,
                              @ToolParam(description = "Amount to refund, in pounds") BigDecimal amount,
                              @ToolParam(description = "Why the customer is owed a refund") String reason) {
        Order o = orders.get(orderId);
        if (o == null) return "No order " + orderId;
        // A business rule the model cannot talk its way around: never refund more than was paid.
        if (o.refunded().add(amount).compareTo(o.total()) > 0) {
            return "Refused: " + amount + " would exceed the order total of " + o.total();
        }
        orders.put(orderId, new Order(o.id(), o.status(), o.total(), o.refunded().add(amount)));
        return "Refunded " + amount + " on " + orderId + " (" + reason + ")";
    }
}

Guard: the person in the loop, and the agent. A ToolCallConfirmationPolicy bean marks refunds over the limit as needing confirmation; Spring AI then pauses the loop before anything in that reply runs:

package com.example.orderagent;

import java.math.BigDecimal;
import java.util.regex.Matcher;
import java.util.regex.Pattern;
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.model.tool.ToolCallConfirmationPolicy;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class AgentConfig {

    static final BigDecimal APPROVAL_LIMIT = new BigDecimal("100");
    private static final Pattern AMOUNT = Pattern.compile("\"amount\"\\s*:\\s*\"?([0-9]+(?:\\.[0-9]+)?)");

    /** Human in the loop: a refund above the limit pauses the agent until a person decides. */
    @Bean
    ToolCallConfirmationPolicy largeRefunds() {
        return (toolCall, toolMetadata) ->
                toolCall.name().equals("refundOrder") && amountOf(toolCall.arguments()).compareTo(APPROVAL_LIMIT) > 0;
    }

    static BigDecimal amountOf(String jsonArguments) {
        Matcher m = AMOUNT.matcher(jsonArguments);
        return m.find() ? new BigDecimal(m.group(1)) : BigDecimal.ZERO;
    }

    @Bean
    ChatClient supportAgent(ChatClient.Builder builder, OrderTools tools) {
        return builder
                .defaultSystem("""
                        You are a customer support agent for an online shop.
                        Always look an order up before acting on it. Be brief and polite.
                        If a refund is refused or denied, explain why to the customer.""")
                .defaultTools(tools)
                .build();
    }
}

Serve: the API, with the approval step. /support/chat answers, or parks a paused reply and returns an approval id; /support/approve/{id} runs the person’s decision and lets the agent finish:

package com.example.orderagent;

import java.util.List;
import java.util.Map;
import java.util.UUID;
import java.util.concurrent.ConcurrentHashMap;
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.chat.messages.AssistantMessage;
import org.springframework.ai.chat.messages.Message;
import org.springframework.ai.chat.messages.UserMessage;
import org.springframework.ai.chat.model.ChatResponse;
import org.springframework.ai.chat.prompt.Prompt;
import org.springframework.ai.model.tool.ToolCallDecision;
import org.springframework.ai.model.tool.ToolCallDecisions;
import org.springframework.ai.model.tool.ToolCallingChatOptions;
import org.springframework.ai.model.tool.ToolCallingManager;
import org.springframework.ai.model.tool.ToolExecutionResult;
import org.springframework.ai.support.ToolCallbacks;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/support")
public class SupportController {

    record Answer(String text, String approvalId, List<String> waitingFor) {}
    private record Pending(List<Message> conversation, ChatResponse reply) {}

    private final ChatClient agent;
    private final ToolCallingManager toolCallingManager;
    private final OrderTools tools;
    // Demo only: production keeps pending approvals in a database, so they survive restarts.
    private final Map<String, Pending> pending = new ConcurrentHashMap<>();

    public SupportController(ChatClient agent, ToolCallingManager toolCallingManager, OrderTools tools) {
        this.agent = agent;
        this.toolCallingManager = toolCallingManager;
        this.tools = tools;
    }

    @PostMapping("/chat")
    public Answer chat(@RequestBody String message) {
        ChatResponse reply = agent.prompt().user(message).call().chatResponse();
        AssistantMessage out = reply.getResult().getOutput();
        if (!ToolCallDecisions.isAwaitingDecision(reply)) {
            return new Answer(out.getText(), null, List.of());
        }
        // The loop paused: nothing in this reply has run. Park it and ask a person.
        String id = UUID.randomUUID().toString();
        pending.put(id, new Pending(List.of(new UserMessage(message), out), reply));
        List<String> calls = out.getToolCalls().stream().map(c -> c.name() + " " + c.arguments()).toList();
        return new Answer("This needs a supervisor's approval before it happens.", id, calls);
    }

    @PostMapping("/approve/{id}")
    public Answer decide(@PathVariable String id, @RequestParam boolean allow) {
        // In production, check here that the person deciding is allowed to approve refunds.
        Pending p = pending.remove(id);
        if (p == null) return new Answer("No pending approval " + id, null, List.of());
        AssistantMessage reply = p.reply().getResult().getOutput();
        List<ToolCallDecision> decisions = ToolCallDecisions.toolCallKeys(reply).stream()
                .map(key -> allow ? ToolCallDecision.allow(key)
                                  : ToolCallDecision.deny(key, "A supervisor declined this refund."))
                .toList();
        var options = ToolCallingChatOptions.builder().toolCallbacks(ToolCallbacks.from(tools)).build();
        ToolExecutionResult result = toolCallingManager.executeToolCalls(
                new Prompt(p.conversation(), options), p.reply(), new ToolCallDecisions(decisions));
        String text = agent.prompt().messages(result.conversationHistory()).call().content();
        return new Answer(text, null, List.of());
    }
}

Evaluate, part 1: fast, offline tests of the rules. No model, no API key, runs on every build:

package com.example.orderagent;

import static org.assertj.core.api.Assertions.assertThat;

import java.math.BigDecimal;
import org.junit.jupiter.api.Test;
import org.springframework.ai.chat.messages.AssistantMessage.ToolCall;
import org.springframework.ai.model.tool.ToolCallConfirmationPolicy;
import org.springframework.ai.tool.metadata.ToolMetadata;

/** Fast, offline tests of the rules the model cannot override. No API key needed. */
class GuardrailTest {

    private final ToolCallConfirmationPolicy policy = new AgentConfig().largeRefunds();
    private final ToolMetadata metadata = ToolMetadata.builder().build();

    @Test
    void smallRefundRunsWithoutAPerson() {
        var call = new ToolCall("1", "function", "refundOrder", "{\"orderId\":\"A100\",\"amount\":40,\"reason\":\"late\"}");
        assertThat(policy.requiresConfirmation(call, metadata)).isFalse();
    }

    @Test
    void largeRefundWaitsForAPerson() {
        var call = new ToolCall("2", "function", "refundOrder", "{\"orderId\":\"A200\",\"amount\":300,\"reason\":\"broken\"}");
        assertThat(policy.requiresConfirmation(call, metadata)).isTrue();
    }

    @Test
    void lookupsNeverWait() {
        var call = new ToolCall("3", "function", "getOrder", "{\"orderId\":\"A200\"}");
        assertThat(policy.requiresConfirmation(call, metadata)).isFalse();
    }

    @Test
    void refundCannotExceedWhatWasPaid() {
        var tools = new OrderTools();
        assertThat(tools.refundOrder("A100", new BigDecimal("50"), "test")).startsWith("Refused");
        assertThat(tools.refundOrder("A100", new BigDecimal("40"), "test")).startsWith("Refunded");
    }
}

Evaluate, part 2: evals against the real model. A code-based grader on the answer, and an outcome grader on the pause. Each runs three times, because a 75% agent would pass once by luck:

package com.example.orderagent;

import static org.assertj.core.api.Assertions.assertThat;

import org.junit.jupiter.api.RepeatedTest;
import org.junit.jupiter.api.condition.EnabledIfEnvironmentVariable;
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.model.tool.ToolCallDecisions;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;

/**
 * Evals against the real model: slow, cost money, and non-deterministic, so each runs several
 * times. Only runs when ANTHROPIC_API_KEY is set.
 */
@SpringBootTest
@EnabledIfEnvironmentVariable(named = "ANTHROPIC_API_KEY", matches = ".+")
class AgentEvalTest {

    @Autowired ChatClient agent;

    // Code-based grader on the answer: the order's real status must appear.
    @RepeatedTest(3)
    void answersOrderStatusFromTheTool() {
        String answer = agent.prompt().user("What is the status of order A100?").call().content();
        assertThat(answer.toLowerCase()).contains("delivered");
    }

    // Outcome grader: a large refund must pause for a person, every time.
    @RepeatedTest(3)
    void largeRefundAlwaysPausesForApproval() {
        var reply = agent.prompt().user("Order A200 arrived broken. Please refund 300 pounds.").call().chatResponse();
        assertThat(ToolCallDecisions.isAwaitingDecision(reply)).isTrue();
    }
}

What we verified: the project compiles against Spring Boot 4.2.0 and Spring AI 2.1.0, the four guardrail tests pass, and the application context starts with the agent, tools and approval flow wired (a fifth test). The two evals were skipped in our environment because they call the real model and need an ANTHROPIC_API_KEY; we have not run them, so treat their pass rate as yours to measure.

Where to put your effort first, by requirement

If this is true for youInvest first in
The agent can move money, delete data or contact peopleHuman confirmation for those tools, and authenticated approvers
Customers will see its answers directlyRegression evals measured with pass^k, and a human hand-off
It is an internal tool where one good answer is enoughCapability evals measured with pass@k
It runs many turns or many requests a dayPrompt caching, routing to smaller models, and cost per task
It reads web pages, emails or documents from outsidePrompt-injection defences and least-privilege tools
Your team already runs Java and SpringSpring AI, so the agent lives with your existing services; switching stacks has a cost

Our view, and the other view

Our view: evaluation is the part that turns an agent demo into a product. Build the eval suite with the agent, from its first real failures, and put people exactly where an action cannot be undone.

The other view: early on, a few hand-checked examples may teach you more than a formal suite, and heavy guardrails can make an agent too timid to be useful. Formal evals and confirmations pay off once real users and real money are involved.

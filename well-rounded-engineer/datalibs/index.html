Data processing libraries

The major libraries and engines for processing data in Python and Java, what scale each suits, the same task written in several of them, and the habits that make any of them fast. Frameworks that sit around these engines, such as Culvert, are on their own tab.

Choosing by situation

  • Data already in BigQuery: SQL or dbt first; bigframes if you need a DataFrame API. Do not pull it out to process it.
  • Files up to a few GB on one machine: Polars or DuckDB; pandas if a library you need expects it.
  • Tens to low hundreds of GB on one large machine: Polars (lazy, streaming) or DuckDB.
  • Beyond one machine, batch: BigQuery, Dataflow (Beam) or Spark on Dataproc.
  • Streaming: Dataflow (Beam), Flink, or Kafka Streams inside a service.
  • Inside a Java service: plain Java streams for small sets; Beam for pipelines; Spring Batch for restartable business jobs.
  • Reading and writing Parquet in Python: PyArrow underneath, whatever DataFrame you use on top.

Validation libraries

  • pandera: schemas for pandas and Polars DataFrames (types, ranges, nullability) checked in code and tests.
  • Great Expectations: expectation suites and data docs for pipelines.
  • Pydantic: validating individual records and API payloads in Python.
  • dbt tests: keys, relationships and accepted values in the warehouse.
  • Jakarta Bean Validation: record validation in Java.

Whatever the tool: reject or quarantine what does not parse, and count it. Never coerce failures to NULL silently.

The same task in five libraries

Count judgments per court since 2020 from Parquet files partitioned by year.

# pandas: reads into memory, eager
import pandas as pd
df = pd.read_parquet("data/", columns=["court", "year"],
                     filters=[("year", ">=", 2020)])   # pushdown; partition columns arrive as category
out = (df.groupby("court", observed=True).size()
         .sort_values(ascending=False))
# Polars: lazy; filters and column selection pushed into the scan
import polars as pl
out = (pl.scan_parquet("data/year=*/*.parquet", hive_partitioning=True)
         .filter(pl.col("year") >= 2020)
         .group_by("court").agg(pl.len().alias("n"))
         .sort("n", descending=True)
         .collect())
# DuckDB: SQL straight over the files
import duckdb
out = duckdb.sql("""
  SELECT court, count(*) AS n
  FROM read_parquet('data/year=*/*.parquet', hive_partitioning = true)
  WHERE year >= 2020
  GROUP BY court ORDER BY n DESC
""").df()
# PySpark: distributed, writes results back to GCS
from pyspark.sql import SparkSession, functions as F
spark = SparkSession.builder.getOrCreate()
(spark.read.parquet("gs://landing/data/")
   .where(F.col("year") >= 2020)
   .groupBy("court").count()
   .orderBy(F.desc("count"))
   .write.mode("overwrite").parquet("gs://out/court_counts/"))
# BigQuery DataFrames: pandas-like code, executed inside BigQuery
import bigframes.pandas as bpd
df = bpd.read_gbq("my-proj.dp_fdp.fdp_judgment")
out = df[df["data_year"] >= 2020].groupby("court_code").size()

Arrow and Parquet in Python

import pyarrow.dataset as ds
import pyarrow.parquet as pq

dataset = ds.dataset("data/", format="parquet", partitioning="hive")
table = dataset.to_table(columns=["cnr", "court", "decision_date"],
                         filter=ds.field("year") >= 2020)   # pushdown

print(table.schema)          # check types before trusting them
pq.write_table(table, "out.parquet",
               compression="zstd",
               coerce_timestamps="us",           # many readers expect microseconds
               allow_truncated_timestamps=True)

Timestamp units are a classic trap: Parquet written with nanosecond timestamps can be read wrongly or refused by some engines, especially for dates before 1970. Check the schema and write the unit the reader expects.

Java options

  • Java streams and collectors for in-memory work (Java tab).
  • Apache Beam (Java) for pipelines on Dataflow, Flink or Spark.
  • Spark (Java/Scala) on Dataproc or Databricks.
  • Spring Batch for chunked, restartable jobs with skip and retry policies.
  • parquet-java and Arrow Java for columnar file IO.
  • Jackson (JSON), Apache Commons CSV or FastCSV for text formats; stream rather than loading whole files.
  • DuckDB JDBC for SQL over local or remote Parquet from Java.

Habits that make any library fast

  • Columnar formats (Parquet) over CSV and JSON for anything read more than once.
  • Read only the columns and rows you need (projection and predicate pushdown).
  • Lazy evaluation (Polars, Spark, Beam) lets the engine optimise the whole plan.
  • No row-by-row loops (apply, iterrows); use vectorised expressions.
  • Right types: categoricals for repeated strings, Arrow-backed strings, proper dates.
  • Partition by the common filter (date, year); avoid thousands of tiny files.
  • Stream or chunk data larger than memory.
  • Push work to the warehouse when the data is already there.

Correctness traps

  • Silent type coercion: integers with nulls become floats in classic pandas; IDs with leading zeros become numbers. Set dtypes explicitly.
  • Date parsing: mixed formats (dd-mm-yyyy and yyyy-mm-dd) parse wrongly or to null; specify the format and count failures.
  • Time zones: naive vs aware timestamps compared silently.
  • Joins: duplicate keys multiply rows, just as in SQL.
  • Floating-point money: use decimals or integer minor units.
  • Schema drift: a new or renamed source column must fail loudly or be mapped on purpose.

Levels: what to expect

1 Foundation

  • Load, filter and aggregate a file with pandas or Polars
  • Read Parquet and inspect its schema
  • Know which library suits which data size

2 Practitioner

  • Use lazy Polars, DuckDB or PyArrow with pushdown on large files
  • Write a PySpark or Beam job for data beyond one machine
  • Validate data with pandera or dbt tests and count rejects

3 Senior

  • Choose engines per workload: warehouse SQL, single-node, distributed, streaming
  • Tune memory, partitioning and file layout
  • Design portable pipelines with open formats

4 Expert

  • Set the organisation's processing stack and standards
  • Lead migrations between engines (pandas to Polars, Spark to BigQuery)
  • Understand engine internals: query optimisers, vectorised execution

Each level includes the ones before it. See Start here for what the levels mean.

Data structures and algorithms

Every program stores data somewhere and does something with it. How the data is arranged decides how fast each operation can be, and the same task can take 20 steps or a million depending on that choice. This page covers how to talk about cost (Big O), the structures you meet every day, the classic algorithms, and where real systems use them. Graph databases are on Graph Databases; measuring real speed is on Performance.

The short answer

Our view: pick the structure that makes your most frequent operation cheap. Looking things up by key: a hash table. Keeping things in order: a sorted array or a balanced tree. Always taking the smallest or most urgent next: a heap. Then estimate the cost with Big O, and measure, because constants and hardware matter too.

Big O: how cost grows

Big O notation describes how a function grows as its input gets large, as an upper bound, and is used for both time and memory. It ignores constant factors, so it tells you how an approach scales, not how fast it runs today.

Searching

Binary search finds a value in a sorted array by halving the range each step, so a million items take about 20 comparisons. Python’s bisect module does this for you, and a set does hash lookups.

from bisect import bisect_left

def linear_steps(items, target):
    for steps, value in enumerate(items, start=1):
        if value == target:
            return steps
    return len(items)

def binary_steps(items, target):
    lo, hi, steps = 0, len(items) - 1, 0
    while lo <= hi:
        steps += 1
        mid = (lo + hi) // 2
        if items[mid] == target:
            return steps
        if items[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    return steps

items = list(range(1_000_000))          # already sorted
target = 999_999
print("linear:", linear_steps(items, target), "steps")
print("binary:", binary_steps(items, target), "steps")
print("bisect finds index", bisect_left(items, target))
print("set lookup:", target in set(items))

linear: 1000000 steps
binary: 20 steps
bisect finds index 999999
set lookup: True

Sorting

  • Merge sort (John von Neumann, 1945): divide and conquer, O(n log n), and most implementations are stable, keeping equal items in their original order.
  • Quicksort (Tony Hoare, 1959): efficient in practice; its worst case, O(n2), is rare when the pivot is chosen well, but a naive pivot makes already-sorted input the worst case.
  • Timsort (Tim Peters, 2002): a stable hybrid of merge sort and insertion sort that uses runs already in order. It was Python’s standard sort from 2.3 until 3.11 replaced it with Powersort, and Java SE 7 uses it for arrays of objects.

Analysis: in everyday code, call your language’s built-in sort; knowing how they work tells you when stability or the worst case matters. The other view: a hand-written sort can win when the data has a known shape, but measure first.

Graphs and harder problems

  • Breadth-first search explores all nodes at one depth before the next: the fewest hops between two nodes in an unweighted graph.
  • Depth-first search goes as far as possible along each branch before backtracking: cycles, dependency order.
  • Dijkstra’s algorithm (conceived in 1956) finds shortest paths in a weighted graph, such as a road network, with non-negative weights.
  • Dynamic programming (Richard Bellman, 1950s) solves a problem from the stored answers to overlapping subproblems, instead of recomputing them.

Choose by requirement

If this is true for youIt leans towards (analysis)
Most operations look things up by an exact keyA hash table (dict, map, set)
You need items in order, or ranges (“everything between A and F”)A sorted array if it rarely changes; a balanced tree if it changes often
You always want the most urgent or smallest item nextA heap (priority queue)
Data lives on disk and must be found with few readsA B-tree index, which your database already uses
You must check membership in a huge set with little memory, and an occasional false “maybe” is acceptableA Bloom filter in front of the real lookup
Prefix search or autocompleteA trie
The data is small (hundreds of items)Whatever is simplest to read (our view): Big O ignores constant factors, and at that size they can dominate

Our view, and the other view

Our view: every engineer should be able to estimate the Big O of their own code and know the common structures well enough to pick one. It prevents the nested loop that only fails at production scale.

The other view: libraries, databases and frameworks already embody these choices, and interview-style puzzles test something different from day-to-day work. Measuring real code with a profiler often teaches more than theory.

Levels: what to expect

1 Foundation

  • Read and compare O(1), O(log n), O(n), O(n log n) and O(n^2)
  • Explain arrays, lists, hash tables, stacks and queues
  • Write a binary search

2 Practitioner

  • Pick a structure for the most frequent operation
  • Spot an accidental O(n^2) loop and fix it
  • Use heaps, sets and sorted collections from the standard library

3 Senior

  • Explain B-tree indexes, tries and Bloom filters, and where systems use them
  • Choose graph algorithms: BFS, DFS, Dijkstra
  • Solve problems with dynamic programming

4 Expert

  • Design data layouts for scale and hardware (cache, disk)
  • Review designs for algorithmic risk
  • Teach and interview for these skills fairly

Each level includes the ones before it. See Start here for what the levels mean.

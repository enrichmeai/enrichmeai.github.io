Running agents on Google Cloud

Many teams run coding agents on GitHub: an issue starts the agent, Actions runs it, a pull request comes back. That is convenient, but the work, the secrets and the logs then live on someone else's platform. This page shows the other way: a cloud workspace in your own Google Cloud project, in the style of browser-based tools such as Replit, where people and agents share a running environment, and where triggers, secrets, models, approvals and audit all stay under your project's control.

The shape of it

NeedOn GitHubIn your Google Cloud project
A place to workCodespacesCloud Workstations: managed development environments from a container image you define, in the browser or your own IDE
Run an agent taskAn Actions jobA Cloud Run job: a container that runs to completion, with its own service account, timeout and retries
Start itIssue, comment, scheduleCloud Scheduler, Pub/Sub messages, Eventarc events, or a Workflow
Several steps and a human approvalWorkflow jobs and environmentsWorkflows, which can run steps in order, wait, and call your services
SecretsRepository secretsSecret Manager, with IAM on each secret and audit logs of every access
Build and testActionsCloud Build
A live previewA preview deploymentA Cloud Run revision with no traffic and its own tagged URL
The modelCopilot, or a key in a secretVertex AI (Google's models and partner models in Model Garden), or any provider with its key in Secret Manager

Git stays: the history of the code still lives in a Git repository, wherever you host it. What moves is where the agent runs, what it can reach, and who can see what it did.

Why run it yourself

  • Your data stays in your project and region. Useful when code or data may not leave a country or a company.
  • One identity model. The agent is a service account with exactly the IAM roles it needs, like any other workload.
  • One audit trail. Cloud Audit Logs record what the agent touched, next to everything else in the project.
  • Your choice of model, including models you are allowed to use under your own agreements.
  • The trade-off: you build and run the plumbing that a hosted service gives you for free. Start small.

A shared workspace, Replit style

# a workspace image you control, in your project
gcloud workstations configs create agent-ws \
  --cluster=dev --region=europe-west2 \
  --machine-type=e2-standard-4 \
  --container-custom-image=europe-west2-docker.pkg.dev/my-proj/tools/agent-ws:1 \
  --service-account=agent-ws@my-proj.iam.gserviceaccount.com \
  --idle-timeout=3600 \
  --disable-public-ip-addresses

gcloud workstations create alice \
  --config=agent-ws --cluster=dev --region=europe-west2
gcloud workstations start alice \
  --config=agent-ws --cluster=dev --region=europe-west2

Bake the agent's tools (CLI, language runtimes, test tools) into the image, so every workspace and every agent run starts the same. --idle-timeout is in seconds and stops idle workspaces, which saves money.

An agent task as a Cloud Run job

gcloud run jobs create agent-task \
  --image=europe-west2-docker.pkg.dev/my-proj/agents/runner:1 \
  --region=europe-west2 \
  --service-account=agent-runner@my-proj.iam.gserviceaccount.com \
  --set-secrets=MODEL_API_KEY=model-api-key:latest \
  --task-timeout=30m --max-retries=0

# run one task and wait for the result
gcloud run jobs execute agent-task --region=europe-west2 \
  --update-env-vars=TASK="add tests for the date parser" --wait

# or on a schedule, calling the Cloud Run API
gcloud scheduler jobs create http nightly-triage \
  --location=europe-west2 --schedule="0 6 * * 1-5" \
  --uri="https://run.googleapis.com/v2/projects/my-proj/locations/europe-west2/jobs/agent-task:run" \
  --http-method=POST \
  --oauth-service-account-email=scheduler@my-proj.iam.gserviceaccount.com

One container, one task, a hard timeout, and no automatic retries for work that changes things: an agent that failed halfway should be looked at, not rerun blindly.

Preview what the agent built

# deploy the agent's branch with no traffic, at its own URL
gcloud run deploy web --image=…/web:agent-1234 \
  --region=europe-west2 --no-traffic --tag=agent-1234
# open https://agent-1234---web-xxxxx.a.run.app, then
# move traffic only after a person has looked

This is the "see it running" moment that makes Replit-style tools feel good, with the same blue-green and canary steps as any release (see DevOps).

Guard rails, before the first run

  • A service account per agent, with only the roles its task needs. No owner or editor roles, ever.
  • No direct path to production. The agent proposes (a branch, a preview, a plan); a person approves the merge or the deploy.
  • Secrets from Secret Manager at run time, never in the image, the prompt or the repository.
  • Limit the network: private workspaces (--disable-public-ip-addresses), egress only to what the agent needs, and VPC Service Controls around sensitive data.
  • Budgets and alerts on the project, and timeouts on every job, so a runaway loop costs minutes, not a month.
  • Log every step the agent takes with a run ID, so a person can follow the journey and undo it if needed (see Observability).
  • Evaluate the agent on real tasks before trusting it with more (see Agent Harness).

One open-source option for the agent runtime itself is Penstock, our headless, self-hosted harness, which runs agents from CI, Slack or webhooks and can run as a container like the job above. It is ours, so we are not neutral.

Levels: what to expect

1 Foundation

  • Explain where an agent runs, what it can reach and who sees its logs
  • Run a containerised task as a Cloud Run job
  • Keep secrets in Secret Manager

2 Practitioner

  • Give each agent its own least-privilege service account
  • Trigger agent jobs from Scheduler, Pub/Sub or a Workflow
  • Preview agent changes on a tagged, no-traffic revision

3 Senior

  • Design an agent platform with workspaces, approvals and audit
  • Set budgets, timeouts and network limits for agents
  • Evaluate agents on real tasks before widening their access

4 Expert

  • Own the organisation's policy for where agents run and what they touch
  • Balance hosted agent services against self-run ones
  • Make agent work auditable end to end

Each level includes the ones before it. See Start here for what the levels mean.

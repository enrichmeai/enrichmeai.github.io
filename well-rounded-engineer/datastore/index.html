Choosing a data store

Relational databases, document stores, key-value stores, wide-column stores, search engines, time series databases, vector databases, warehouses and object storage all exist because each makes some operations cheap and others expensive. This page sets out what each family is for, so the choice follows from your requirements. How to design a relational schema is on Database Design; graphs are on Graph Databases; caches are on Caching.

The short answer

Our view: start with one relational database unless a requirement clearly calls for something else, and add a specialised store when that requirement appears. The other view: some teams pick a document or key-value store from the start because their data and access patterns are known to fit it; this can avoid a later migration. The table below sets out which requirements point where.

A first pass

The families

FamilyWhat it stores, and what it is good atExamples and typical uses
RelationalTables of rows and columns, queried with SQL, with ACID transactions (atomicity, consistency, isolation, durability)PostgreSQL (which also stores JSON, including a binary JSONB type)
DocumentSemi-structured documents, such as JSON, each with its own shape; one of the main NoSQL familiesMongoDB, which stores JSON-like documents (BSON) with optional schemas
Key-valueRecords stored and retrieved by a unique key, like a dictionaryRedis, which works on data in main memory and persists it to disk
Wide-columnTables where the columns can vary from row to row; a two-dimensional key-value storeApache Cassandra (from Facebook, 2008), built on ideas from Amazon’s Dynamo and Google’s Bigtable
Search engineAn index for full-text search and relevance rankingElasticsearch, based on Apache Lucene
Time seriesData points indexed in time order, with high ingestion rates and heavy compressionMeasurements from physical sensors, and other time-stamped data
VectorEmbeddings, searched by approximate nearest neighbour for similar meaning; used for semantic search and retrieval-augmented generationDedicated vector databases, or PostgreSQL with pgvector
Columnar warehouseA data warehouse serves reporting and data analysis; analytics databases benefit from storing data by column, while transactional ones suit rowsBigQuery, Amazon Redshift and Snowflake use column-oriented formats; Apache Parquet is a column-oriented file format
Object storageBlobs with metadata and a unique identifier, rather than files in foldersFiles and other large objects with their metadata
In-memoryData held mainly in main memory, which gives faster and more predictable performance than diskSystems where response time is critical

Many products now span several families: a multi-model database supports more than one data model, such as document, graph, relational and key-value, against one backend.

More than one store: polyglot persistence

Martin Fowler wrote in 2011 that any decent-sized enterprise would come to use a variety of data storage technologies for different kinds of data, a shift he called polyglot persistence (crediting Scott Leberknight with the term). He also said it comes at a cost.

Analysis: each extra store is another system to run, back up, secure and keep consistent with the others; on keeping copies in step, see Solution Architecture: A to B (the outbox and change data capture).

NoSQL is not one thing

NoSQL, “not only SQL”, covers several designs that store data differently from relational tables: key-value pairs, wide columns, graphs or documents. They do not need a fixed schema, which suits large and often unstructured datasets.

Analysis: “schema-less” usually means the schema lives in your code instead of the database, so it still needs designing and versioning.

Choose by requirement

If this is true for youIt leans towards (analysis)
Changes that must happen together across several records (orders and stock, money)A relational database with transactions
Each record is read and written whole, and its shape variesA document store, or JSON columns in a relational database
Very high write volume, spread over many machines, with known query patternsA wide-column store
Fast lookups by key, where losing some data is tolerable or it can be rebuiltAn in-memory key-value store, usually as a cache in front of the main store
Users search text and expect ranked resultsA search engine, fed from the main store
Metrics or sensor readings over timeA time series database
Semantic search or retrieval for an AI featureA vector index; start with one inside a database you already run if it offers one
Analysis over large historyA columnar warehouse, separate from the operational database
Your team already runs a database that meets the requirementUse it before adding another: each extra store has a cost, as Fowler noted (2011)

Our view, and the other view

Our view: the questions that decide it are what must change together, how data is read, how much of it there is, and who will run the store at 3 a.m. Popularity and brand are not on that list. A team’s existing operational experience is, because switching has a cost; the table’s last row says so.

The other view: the store a team already knows well, and can operate safely, may suit better than a better-fitting store nobody can run; that familiarity reduces operational risk, and is more than preference.

Levels: what to expect

1 Foundation

  • Name the main families of data store
  • Say what ACID transactions guarantee
  • Tell row storage (OLTP) from column storage (OLAP)

2 Practitioner

  • Choose between a table, a JSON column and a document store
  • Add a search index or cache fed from the main store
  • Explain why a store suits a workload

3 Senior

  • Choose stores for a system by requirement
  • Keep several stores consistent (outbox, change data capture)
  • Weigh the cost of each extra store

4 Expert

  • Set an organisation's approved data stores and when to add one
  • Plan migrations between stores
  • Balance fit against operational risk

Each level includes the ones before it. See Start here for what the levels mean.

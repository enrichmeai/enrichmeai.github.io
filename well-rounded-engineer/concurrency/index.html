Guide / Foundations / Concurrency

Concurrency

A web server handling thousands of requests, a phone app that stays responsive while it downloads, a database serving many users at once: all of them do several things in overlapping time. That is concurrency, and it brings a class of bugs that appear only under particular timing. This page covers the core ideas, the classic bugs, the tools for avoiding them, and the main models. Language specifics are on Java (virtual threads), Go, Rust and JavaScript (the event loop); across machines, see Distributed Systems.

The short answer

Concurrency means several computations in overlapping time periods; parallelism means running at the same physical instant, on separate processors, usually to speed a computation up. Wherever two threads share data that one of them changes, you need a rule for who may touch it when.

Race conditions: the lost update

A race condition is when a system’s behaviour depends on the sequence or timing of events it does not control. They are hard to reproduce, because the result depends on timing between threads, and they can disappear when you add logging or run in a debugger.

import threading

balance = 0
both_have_read = threading.Barrier(2)
lock = threading.Lock()

def deposit_unsafe(amount):
    global balance
    seen = balance            # 1. read
    both_have_read.wait()     # (force the bad interleaving: both threads read first)
    balance = seen + amount   # 2. write, based on a stale read

def deposit_safe(amount):
    global balance
    with lock:                # read and write as one step
        balance = balance + amount

def run(worker):
    global balance
    balance = 0
    threads = [threading.Thread(target=worker, args=(100,)) for _ in range(2)]
    for t in threads: t.start()
    for t in threads: t.join()
    return balance

print("two deposits of 100, unsafe:", run(deposit_unsafe))
print("two deposits of 100, locked:", run(deposit_safe))

two deposits of 100, unsafe: 100
two deposits of 100, locked: 200

Run as shown with Python 3; the second block is its real output, the same on every run because the barrier forces the bad order. In real code the order is not forced, which is why the bug comes and goes.

Deadlock

A deadlock is a set of threads each waiting for a resource another holds. Edward Coffman described four conditions in 1971; all four must hold for a deadlock:

  1. Mutual exclusion: a resource can be used by only one at a time.
  2. Hold and wait: a thread holds one resource while waiting for another.
  3. No preemption: a resource is released only voluntarily.
  4. Circular wait: each waits for the next, in a cycle.

Most prevention breaks one condition, especially the circular wait. Analysis: the everyday fix is to take locks in one fixed global order. The other view: a fixed order is hard to keep across a large code base, so some teams use timeouts or lock-free structures instead.

Tools for shared data

  • Mutex (lock): only one thread at a time runs the protected section.
  • Semaphore: a counter that limits how many may enter, invented by Edsger Dijkstra in 1962 or 1963.
  • Compare-and-swap: an atomic processor instruction that updates a value only if it still holds what you last read; the basis of lock-free structures.
  • Optimistic concurrency: do the work, then check for conflicting changes at commit and retry if there were any; common in databases.
  • Memory models define when one thread’s writes become visible to another. In Java, everything before releasing a lock is visible to the next thread that acquires it (the happens-before order).

Models of concurrency

ModelThe ideaWhere you meet it
Threads and locksThreads share memory; locks guard itJava, C#; Python’s threading module
Lightweight threadsMany cheap threads managed by the runtime; a blocked one does not hold an operating-system threadJava’s virtual threads, stable since Java 21
Event loop and async/awaitOne thread runs many tasks, switching at each waitJavaScript, Python’s asyncio
Communicating sequential processes (Tony Hoare, 1978)Share data by sending it over channels between processesGo, whose channels follow the CSP idea (see Go)
Actors (1973)Each actor has private state and reacts to messages: it can decide, create actors and send messagesErlang, Akka

In CPython, a global interpreter lock lets only one thread run Python code at a time, so threads help with waiting on I/O more than with CPU work. Python 3.13 added an experimental free-threaded build without it (PEP 703).

How much parallelism helps: Amdahl’s law

Gene Amdahl’s law (1967) predicts the speed-up from more processors. If a fraction p of the work can run in parallel on s processors, the speed-up is 1 / ((1 − p) + p / s).

p = 90% parallelSpeed-up
2 processors1.82×
8 processors4.71×
64 processors8.77×
unlimited10×, never more

Worked out from the formula. The serial 10% sets the ceiling, however many processors you add.

Choose by requirement

If this is true for youIt leans towards (analysis)
Many requests that mostly wait on I/O (databases, other services)Virtual threads, or async/await, or an event loop: many waits, few CPU cores
CPU-heavy work that can be splitParallel workers or processes, sized by Amdahl’s law; in CPython, processes rather than threads
A small piece of shared state updated by several threadsA lock, or an atomic or concurrent collection from the standard library
Components that should not share memory at allChannels or actors: pass messages instead
Rows that many users may change at onceThe database’s transactions, with optimistic concurrency (a version column) where conflicts are rare
Your team already uses one model wellStay with it unless a requirement above forces a change: switching has a cost

Our view, and the other view

Our view: share as little mutable state as you can, and where you must share it, use a higher-level tool your platform offers (a concurrent collection, a database transaction, a channel) before reaching for raw locks.

The other view: high-level abstractions hide costs and can make performance harder to predict; for latency-critical code, some teams prefer explicit locks or lock-free structures that they can measure and reason about directly.

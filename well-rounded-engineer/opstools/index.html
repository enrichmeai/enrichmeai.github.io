Ops tooling: Prometheus, Grafana, Fluentd, Dynatrace, ServiceNow

The tools you will meet in operations teams, what each does, how they fit together, and working configuration. Concepts are on Observability and SRE.

How they fit together

ToolCategoryDoesGCP-native alternative
PrometheusMetricsScrapes and stores time-series metrics; PromQL; alert rulesManaged Service for Prometheus, Cloud Monitoring
AlertmanagerAlert routingGroups, silences and routes Prometheus alerts to people and toolsCloud Monitoring notification channels
GrafanaVisualisationDashboards and alerting over many data sources; Loki (logs), Tempo (traces), Mimir (metrics) in the same familyCloud Monitoring dashboards
Fluentd / Fluent BitLog shippingCollect, parse, enrich and forward logs to any backendThe built-in logging agents on GKE and Cloud Run
DynatraceFull-stack APM / observability platformAuto-instrumentation, topology, traces, logs, metrics, AI root-cause analysisCloud Trace, Profiler, Logging, Monitoring together
ServiceNowIT service managementIncidents, problems, changes, requests, CMDB, approvals and workflowNone: ITSM sits above monitoring

Typical flow: apps emit telemetry → Fluent Bit ships logs, Prometheus scrapes metrics (or Dynatrace's agent collects all) → Grafana or Dynatrace shows it → alerts route through Alertmanager → ServiceNow opens an incident, pages on-call, and tracks the change that fixes it.

Prometheus: model

  • Pull model: Prometheus scrapes /metrics endpoints on an interval (Spring: /actuator/prometheus).
  • Exporters expose metrics for systems that do not: node_exporter (hosts), postgres_exporter, blackbox_exporter (probes).
  • Time series = metric name + labels. Keep label values bounded.
  • Service discovery finds targets in Kubernetes, GCE and others.
  • Short-term storage locally; long-term in Thanos, Mimir or Google's managed service.
  • Recording rules precompute expensive queries; alerting rules fire when an expression holds for a duration.

Prometheus: configuration

# prometheus.yml
global:
  scrape_interval: 30s
scrape_configs:
  - job_name: legal-api
    metrics_path: /actuator/prometheus
    static_configs:
      - targets: ["legal-api:8080"]
rule_files: ["rules/*.yml"]
alerting:
  alertmanagers:
    - static_configs:
        - targets: ["alertmanager:9093"]
# rules/legal-api.yml
groups:
  - name: legal-api
    rules:
      - record: job:http_5xx_ratio:rate5m
        expr: |
          sum by (job) (rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
          / sum by (job) (rate(http_server_requests_seconds_count[5m]))
      - alert: LegalApiHighErrorRate
        expr: job:http_5xx_ratio:rate5m{job="legal-api"} > 0.02
        for: 10m
        labels: { severity: page }
        annotations:
          summary: "legal-api 5xx above 2% for 10 minutes"
          runbook_url: "https://runbooks.example.com/legal-api/high-errors"
      - alert: CorpusLoadMissing
        expr: time() - corpus_last_success_timestamp_seconds > 26 * 3600
        labels: { severity: page }
        annotations: { summary: "No successful corpus load for 26 hours" }

PromQL you will use

rate(http_server_requests_seconds_count[5m])                 # per-second rate of a counter
sum by (status) (rate(http_server_requests_seconds_count[5m])) # grouped
histogram_quantile(0.95,
  sum by (le) (rate(http_server_requests_seconds_bucket[5m])))  # p95 latency
increase(odp_objects_total{outcome="failed"}[1h])             # count over a window
up == 0                                                       # targets not scraped
absent(corpus_last_success_timestamp_seconds)                 # metric missing entirely
topk(5, sum by (pod) (container_memory_working_set_bytes))    # top memory users

Always rate() a counter before summing; never sum raw counters. Alert on absent() or up == 0 so a dead exporter is not mistaken for health.

Alertmanager routing

route:
  receiver: team-ticket
  group_by: [alertname, job]
  group_wait: 30s
  repeat_interval: 4h
  routes:
    - matchers: [ 'severity="page"' ]
      receiver: oncall-page
receivers:
  - name: oncall-page
    pagerduty_configs:
      - routing_key_file: /etc/alertmanager/secrets/pagerduty_key
  - name: team-ticket
    webhook_configs:
      - url: https://integration.example.com/servicenow/alerts   # creates a ServiceNow incident

Group related alerts, silence during planned work, and inhibit child alerts when the parent (a whole cluster down) is firing.

Grafana

  • Data sources: Prometheus, Loki, Tempo, Cloud Monitoring, BigQuery, Postgres and many more, in one dashboard.
  • Dashboards as code: provision from files or the Grafana Terraform provider; keep JSON in Git and review changes.
  • Variables ($service, $env) make one dashboard serve every service: a dashboard template is a blueprint.
  • Grafana Alerting can evaluate rules across data sources; pick one alerting system per signal to avoid duplicates.
  • Explore view for ad-hoc queries, and jumping from a metric spike to logs and traces of the same time window.
# provisioning/datasources/prometheus.yaml
apiVersion: 1
datasources:
  - name: Prometheus
    type: prometheus
    access: proxy
    url: http://prometheus:9090
    isDefault: true

Fluentd and Fluent Bit

  • Fluent Bit: lightweight (C), the usual choice as a node agent or sidecar in Kubernetes.
  • Fluentd: heavier (Ruby), huge plugin ecosystem, often used as a central aggregator.
  • Pipeline: input → parser → filter (enrich, drop, mask) → buffer → output.
  • On GKE and Cloud Run logs are collected for you; add Fluent Bit when you need other destinations or self-managed clusters.
  • Mask secrets and personal data in filters before logs leave the node.
# Fluent Bit (Kubernetes node agent)
[INPUT]
    Name    tail
    Path    /var/log/containers/*.log
    multiline.parser  cri
    Tag     kube.*
[FILTER]
    Name    kubernetes
    Match   kube.*
[FILTER]
    Name    grep
    Match   kube.*
    Exclude log healthcheck
[OUTPUT]
    Name    stackdriver
    Match   *
# Fluentd
<source>
  @type tail
  path /var/log/app/*.log
  pos_file /var/log/fluentd/app.pos
  tag app
  <parse>
    @type json
  </parse>
</source>
<filter app>
  @type record_transformer
  <record>
    env prod
  </record>
</filter>
<match app>
  @type stdout
</match>

Dynatrace

  • OneAgent: installed on hosts or via the Kubernetes Operator; instruments JVM, Python, Node, databases and more without code changes.
  • Smartscape: a live topology of hosts, processes, services and their dependencies.
  • PurePath: end-to-end distributed traces, down to code-level timing.
  • Davis AI: detects anomalies and groups related events into one "problem" with a probable root cause.
  • Grail and DQL: stores logs, metrics, traces and events together and queries them with Dynatrace Query Language.
  • SLOs, synthetic monitoring, real-user monitoring and OpenTelemetry ingestion.
// DQL example: error logs per namespace in the last hour
fetch logs, from:now()-1h
| filter loglevel == "ERROR"
| summarize errors = count(), by:{k8s.namespace.name}
| sort errors desc

Commercial platforms trade cost for breadth and automation. Instrument with OpenTelemetry where you can, so changing vendor later does not mean re-instrumenting.

ServiceNow: the ITSM side

RecordIs
IncidentSomething is broken now; restore service
ProblemThe underlying cause of one or more incidents; fix it for good
Change requestA planned change to production: standard (pre-approved), normal (assessed and approved), emergency
RequestA user asking for something (access, a new environment)
CMDB CIA configuration item: a service, app, database or host and its relationships
  • Event management turns monitoring alerts into correlated alerts and incidents, linked to the affected CI.
  • Change automation: CI/CD pipelines (Harness, GitHub Actions, Jenkins) open and update change requests automatically, so low-risk deploys are approved by policy rather than a weekly board.
  • Keep the CMDB generated from real sources (cloud APIs, Terraform state, service catalogues); hand-maintained CMDBs drift.

ServiceNow Table API

# open P1 incidents
curl -s -u "$SN_USER:$SN_PASS" -H "Accept: application/json" \
  "https://$INSTANCE.service-now.com/api/now/table/incident?sysparm_query=active=true^priority=1&sysparm_limit=10&sysparm_fields=number,short_description,state"

# create an incident from an automated check
curl -s -u "$SN_USER:$SN_PASS" -X POST \
  -H "Content-Type: application/json" -H "Accept: application/json" \
  "https://$INSTANCE.service-now.com/api/now/table/incident" \
  -d '{"short_description":"Corpus load missing for 26h",
       "urgency":"2","impact":"2",
       "assignment_group":"<sys_id of the Data Platform group>",
       "description":"Ledger shows no SUCCEEDED LAND since 2026-11-11 06:15 UTC. Runbook: …"}'

Use an integration user with only the roles it needs, OAuth rather than basic auth where available, and dedupe on a correlation ID so a flapping alert does not open fifty incidents.

Choosing and combining

  • All on GCP, small team: Cloud Logging, Monitoring and Trace with OpenTelemetry; little to run.
  • Kubernetes-heavy, open source: Prometheus + Grafana + Loki + Tempo + Fluent Bit; you operate them (or use managed versions).
  • Large enterprise, many stacks: Dynatrace (or similar) for automatic coverage and root cause, ServiceNow for process.
  • Whatever you choose: one alerting path per signal, runbooks on every alert, telemetry defined as code, and OpenTelemetry at the source.

Levels: what to expect

1 Foundation

  • Read a Grafana or Dynatrace dashboard and find a service's errors
  • Look up and update a ServiceNow incident
  • Know what Prometheus, Fluent Bit and Alertmanager each do

2 Practitioner

  • Write PromQL queries, recording and alerting rules
  • Configure log shipping and Grafana dashboards as code
  • Connect alerts to ServiceNow incidents and CI/CD to change requests

3 Senior

  • Design the monitoring stack and alert routing for a platform
  • Integrate Dynatrace or open-source tooling with OpenTelemetry
  • Automate change management while keeping control

4 Expert

  • Own observability and ITSM tooling strategy and cost
  • Lead tool consolidation or migration across the organisation
  • Set standards for telemetry, alerting and incident process

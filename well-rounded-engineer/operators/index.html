Kubernetes operators

An operator extends Kubernetes with your own resource types and a controller that manages them, encoding the knowledge a human operator would apply: how to install, upgrade, back up, fail over and heal a system. The reconcile pattern, CRDs, building operators in Go, Java and Python, and the well-known operators worth using rather than writing.

The pattern

  1. A Custom Resource Definition (CRD) adds a new resource type to the Kubernetes API, such as PostgresCluster or PipelineRun.
  2. Users create custom resources stating the desired state (spec): "three Postgres replicas, version 16, nightly backups".
  3. A controller watches those resources and the objects it owns, and reconciles: observe the actual state, compare it with the spec, act to close the gap, and record what it saw in status.
  4. Reconcile runs again on every change and periodically, so the system heals itself when reality drifts.

Controllers are level-triggered: they act on the current state, not on the event that woke them. That makes them robust to missed events and restarts, as long as every reconcile is idempotent.

Operator or Helm chart?

Helm chartOperator
DoesInstalls and upgrades a set of manifestsContinuously manages a system through its whole life
Day-2 operationsNone after applyBackups, failover, scaling, upgrades, repair
FitsStateless services, most applicationsStateful systems (databases, Kafka), complex platforms
CostTemplatesA program to build, test, secure and maintain

Most teams should use well-tested operators (often installed with Helm), not write their own. Write one only when you have real operational knowledge to automate and no existing operator does it.

Operators worth knowing

  • cert-manager: issues and renews TLS certificates.
  • Prometheus Operator: Prometheus, Alertmanager and scrape targets as resources (ServiceMonitor, PrometheusRule).
  • CloudNativePG: PostgreSQL clusters with replication, failover and backups.
  • Strimzi: Kafka clusters, topics and users.
  • Spark operator: Spark applications as resources.
  • Argo CD / Flux: GitOps controllers.
  • External Secrets Operator: syncs secrets from Secret Manager into Kubernetes.
  • Config Connector / Crossplane: manage cloud resources (GCS buckets, Cloud SQL) as Kubernetes objects.

A Custom Resource Definition

apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: pipelineruns.data.example.com
spec:
  group: data.example.com
  scope: Namespaced
  names:
    plural: pipelineruns
    singular: pipelinerun
    kind: PipelineRun
    shortNames: [plr]
  versions:
    - name: v1alpha1
      served: true
      storage: true
      subresources:
        status: {}
      additionalPrinterColumns:
        - { name: Date,  type: string, jsonPath: .spec.runDate }
        - { name: Phase, type: string, jsonPath: .status.phase }
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              required: [runDate, stages]
              properties:
                runDate: { type: string, format: date }
                stages:
                  type: array
                  items: { type: string, enum: [LAND, ODP_LOAD, BUILD] }
            status:
              type: object
              x-kubernetes-preserve-unknown-fields: true
apiVersion: data.example.com/v1alpha1
kind: PipelineRun
metadata: { name: run-2026-11-12, namespace: data }
spec:
  runDate: "2026-11-12"
  stages: [LAND, ODP_LOAD, BUILD]

# kubectl get plr -n data

Go: kubebuilder and controller-runtime

kubebuilder init --domain example.com --repo github.com/example/pipeline-operator
kubebuilder create api --group data --version v1alpha1 --kind PipelineRun
make manifests      # generate CRDs and RBAC from code markers
make install run    # install CRDs, run the controller locally
func (r *PipelineRunReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    var run datav1alpha1.PipelineRun
    if err := r.Get(ctx, req.NamespacedName, &run); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)   // deleted: nothing to do
    }

    // 1. observe: the Jobs this run owns
    // 2. compare: which stage should run next, given spec and finished Jobs?
    // 3. act: create that stage's Job with a deterministic name
    //    (creating it twice returns AlreadyExists: idempotent)
    //    and set an owner reference so it is garbage-collected with the run
    // 4. record: update status.phase and conditions via the status subresource

    return ctrl.Result{RequeueAfter: time.Minute}, nil
}

Java and Python

// Java Operator SDK
@ControllerConfiguration
public class PipelineRunReconciler implements Reconciler<PipelineRun> {
  @Override
  public UpdateControl<PipelineRun> reconcile(PipelineRun run, Context<PipelineRun> ctx) {
    // observe owned Jobs, create the next stage's Job if missing
    run.setStatus(computeStatus(run, ctx));
    return UpdateControl.patchStatus(run);
  }
}

import kopf

@kopf.on.create("data.example.com", "v1alpha1", "pipelineruns")
@kopf.on.update("data.example.com", "v1alpha1", "pipelineruns")
def reconcile(spec, name, namespace, status, logger, **_):
    next_stage = choose_next_stage(spec["stages"], status)
    if next_stage:
        ensure_job(name, namespace, next_stage)    # idempotent create
    return {"phase": "Running" if next_stage else "Succeeded"}   # Kopf stores it under status.reconcile

Rules for a good controller

  • Idempotent reconcile: running it ten times gives the same result as once.
  • No in-memory state: everything needed is in the cluster (spec, status, owned objects), so restarts are safe.
  • Status and conditions: report Ready, Progressing, Degraded with reasons and the observed generation.
  • Owner references so owned objects are cleaned up automatically; finalizers to clean up things outside the cluster (cloud resources) before deletion.
  • Requeue with backoff on errors; never tight-loop.
  • Leader election so only one replica acts at a time.
  • Least-privilege RBAC, generated from the code.
  • Validate early: OpenAPI schema and CEL rules (x-kubernetes-validations) reject bad specs at the API.
  • Distinguish unknown from failed: if the controller cannot read a dependency, report that, rather than marking the resource failed or healthy.

Testing and operating operators

  • Unit-test the decision logic (spec + observed state → actions) without a cluster.
  • envtest (Go) runs a real API server for integration tests; kind or k3d clusters for end-to-end tests.
  • CRD versioning: start at v1alpha1; add conversion webhooks when you introduce new versions; never break stored objects.
  • Metrics: reconcile counts, errors, duration and queue depth (controller-runtime exposes them).
  • Capability levels (Operator Framework): basic install → seamless upgrades → full lifecycle → deep insights → autopilot. Aim for the level your users need.
  • Distribution: package the operator with a Helm chart or OLM bundle.

Levels: what to expect

1 Foundation

  • Explain CRDs, custom resources, controllers and reconcile
  • Use existing operators (cert-manager, CloudNativePG, Strimzi)
  • Read a resource's status and conditions

2 Practitioner

  • Write a CRD with schema validation
  • Build a simple controller with kubebuilder, Java Operator SDK or Kopf
  • Use owner references, finalizers and status correctly

3 Senior

  • Design operators for stateful systems and day-2 operations
  • Test with envtest and real clusters; version CRDs with conversion
  • Decide operator vs Helm vs managed service

4 Expert

  • Build platform APIs on Kubernetes for the organisation
  • Maintain operators at high capability levels
  • Contribute to the operator ecosystem

Each level includes the ones before it. See Start here for what the levels mean.

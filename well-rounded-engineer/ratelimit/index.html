Guide / Architecture & design / Rate Limiting

Rate limiting, end to end

How every API request gets an allow or a 429, how counters stay correct across many gateways, the four common algorithms with a simulation you can run, and what to do when the limiter itself breaks. This page grew out of a whiteboard sketch of a distributed API rate limiter; every limit, key and number here is illustrative, not a default of any product.

The short answer

It is three in the morning and a partner’s integration has a bug: a retry loop with no pause, sending thousands of requests a second at your orders API. Without a rate limiter, those requests queue up behind your real customers’ requests, the database slows down, and soon nobody can place an order. With one, the partner gets a polite “not now” in milliseconds, and everyone else carries on as if nothing had happened.

That is the whole job: count requests per caller, compare against a policy, and say yes or no before the expensive work starts. The difficult parts are the details: who counts as a caller, which algorithm does the counting, how many servers share one count, and what happens when the counter itself is slow or gone. The short version of the system design card is on System Design; this page takes each of those details in turn.

The path of one request

It helps to follow a single request from start to finish, because each step answers one question.

  1. The edge (a CDN or WAF) absorbs volumetric attacks before anything else; a rate limiter is not the place to soak up a flood.
  2. The gateway matches the route and works out who is calling: an API key, a user and tenant from a verified token, or, for anonymous traffic, an IP address.
  3. The limiter picks every policy that applies to this caller and route (a per-user limit, a per-tenant limit, a global limit for the endpoint), and runs the algorithm each one names.
  4. The counter store checks and updates the count in a single atomic step, so two requests arriving together cannot both take the last slot.
  5. The decision goes back to the gateway: forward the request to the backend, or answer 429 itself, straight away.

The limiter is a logical step, not necessarily a separate service. It can run as a plugin inside the gateway (no extra network hop), as a dedicated limiter service the gateways call, or as a library inside each application. Most teams start with the first and only move when they need limits shared across many gateways or products.

What the client sees

A good limiter does not just refuse; it tells the client what happened and when to try again, so well-behaved clients slow down by themselves.

HTTP/1.1 429 Too Many Requests
Retry-After: 30
RateLimit-Policy: "basic";q=100;w=60
RateLimit: "basic";a=0;w=30
  • 429 Too Many Requests was defined in RFC 6585 (2012): it “indicates that the user has sent too many requests in a given amount of time”, the response should explain the condition, and it may include Retry-After.
  • Retry-After, defined in RFC 9110, tells the client how long it ought to wait before a follow-up request.
  • RateLimit-Policy and RateLimit are newer header fields from the IETF HTTP APIs working group: one describes the quota policies, the other the quota available right now. In the example, q=100;w=60 is a quota of 100 in a 60-second window, and a=0 says none is left. They are still an Internet-Draft (revision 12 at the time of writing), so check what your clients understand before relying on them. Many APIs still send their own X-RateLimit-* headers.

On the client side, the matching courtesy is to honour Retry-After and back off with jitter (see the retry storm on Distributed Systems). A client that retries a 429 immediately is the problem the limiter exists to solve.

Who is the caller? Designing the key

Every counter lives under a key made of three parts: an identity, a scope, and the window or policy it belongs to. Get the key wrong and the cleverest algorithm counts the wrong thing.

Key (illustrative)What it limits
rate:user:123:ordersOne user, on one API
rate:apikey:abc:globalOne API key, across every route
rate:tenant:acme:readA whole customer organisation, on read operations
rate:ip:203.0.113.7:loginAnonymous attempts to log in from one address
  • Prefer a verified identity. Limits by IP alone hit everyone behind one corporate proxy or mobile carrier at once, and let an attacker with many addresses slip through.
  • Trust forwarded addresses only from your own proxies. The client’s address usually arrives in X-Forwarded-For or the standard Forwarded header (RFC 7239), and anyone can write those headers. Take the address added by your own outermost proxy, not the first one in the list.
  • Give keys an expiry, so counters for callers who have gone away do not pile up for ever.

Four algorithms, one simulation

There are four algorithms you will meet again and again. A policy picks one of them; they are alternatives, not layers. The quickest way to feel the difference is to feed them all the same traffic. This plain Python program sends 100 requests in the last second of one minute and another 100 in the first second of the next, against a limit of 100 a minute:

"""Four rate-limiting algorithms, limit 100 requests a minute, fed the same traffic."""

def fixed_window(times, limit=100, window=60):
    counts, allowed = {}, 0
    for t in times:
        w = int(t // window)                          # which clock-aligned minute
        if counts.get(w, 0) < limit:
            counts[w] = counts.get(w, 0) + 1
            allowed += 1
    return allowed

def sliding_log(times, limit=100, window=60):
    log, allowed = [], 0
    for t in times:
        log = [x for x in log if x > t - window]       # drop timestamps older than a minute
        if len(log) < limit:
            log.append(t)
            allowed += 1
    return allowed

def sliding_counter(times, limit=100, window=60):
    counts, allowed = {}, 0
    for t in times:
        w = int(t // window)
        elapsed = (t % window) / window                # how far into the current minute
        estimate = counts.get(w - 1, 0) * (1 - elapsed) + counts.get(w, 0)
        if estimate < limit:
            counts[w] = counts.get(w, 0) + 1
            allowed += 1
    return allowed

def token_bucket(times, capacity=100, rate=100 / 60):
    tokens, last, allowed = capacity, 0.0, 0
    for t in times:
        tokens = min(capacity, tokens + (t - last) * rate)   # refill lazily, no timer needed
        last = t
        if tokens >= 1:
            tokens -= 1
            allowed += 1
    return allowed

# 100 requests in the last second of one minute, then 100 in the first second of the next
burst = [59 + i / 100 for i in range(100)] + [60 + i / 100 for i in range(100)]
print("200 requests within 2 seconds, across a minute boundary:")
for f in (fixed_window, sliding_log, sliding_counter, token_bucket):
    print(f"  {f.__name__:16} allowed {f(burst)}")

The token bucket comes from networking, where it checks that packets conform to limits on bandwidth and burstiness. Its close relative, the leaky bucket, drains requests at a fixed rate instead, and the generic cell rate algorithm used in ATM networks is one form of it. Redis’s own documentation for INCR shows the fixed-window pattern with a counter per IP per second.

Many gateways, one limit

Here is the trap that catches almost every first distributed limiter. Put three gateways behind a load balancer, give each its own in-memory counter with a limit of 100 a minute, and one user spread across them can make 300 requests. Each gateway honestly thinks the user is under the limit. Local counters do not add up to a global limit.

The fix is a shared counter store that every gateway consults, commonly Redis, though it is one option among several. Sharing brings a second trap: two gateways reading the counter at 99, both comparing it with 100, and both writing 100. Both requests were allowed; the limit was 100 and you served 101. The read, the comparison and the write must happen as one atomic step.

-- the counter and its expiry in one atomic step (the pattern in Redis's INCR documentation)
local current = redis.call("incr", KEYS[1])
if current == 1 then
    redis.call("expire", KEYS[1], 60)
end
return current

Redis’s documentation walks through exactly this. It shows a version with a race condition (a client that increments but never sets the expiry leaks the key) and fixes it with a short Lua script, because Redis guarantees a script’s atomic execution.

If this is true for youLean towards
One instance, or a rough limit per instance is good enoughA local limiter: fastest, no network, nothing extra to fail
The limit is a promise to customers or protects a shared backendA distributed limiter with a shared, atomic store
You need both speed and accuracyA cheap local pre-check, then the global check; a common combination

When the limiter itself breaks

A limiter is a dependency on the hot path of every request, so sooner or later the counter store will be slow, partitioned or down. Decide what happens before it does, per route, because there is no single right answer (analysis):

ChoiceWhat happensSuits
Fail open: allowUsers are not blocked by a limiter outage, but the backend is unprotected exactly when something is already wrongPublic read APIs, ideally with a local emergency limit as a floor
Fail closed: rejectStrong protection, but a limiter failure becomes a user-facing outageLogin, one-time passwords, payments and other abuse-sensitive or costly operations
Local fallbackEach instance enforces a share of the global limit on its own until the store returnsMost production systems: rough, but bounded

The other failures are quieter: a timeout with no budget (a few milliseconds, no long retries), a stale policy cache that keeps enforcing old limits, replica lag after a failover that loses recent increments, and retries that turn a slow store into a stampede.

Scaling, and several limits at once

Hot keys. One large tenant can send all its traffic to a single counter on a single shard. The usual remedies, each a trade-off (analysis): partition the counter, accepting a merge step; give each gateway a lease of tokens to spend locally (say 500 of a global 10,000), accepting that leases make the global limit approximate; build a hierarchy of local, regional and global limits; or give exceptionally hot tenants dedicated capacity.

Several limits on one request. A request may have to pass a global limit, a tenant limit, a user limit and an endpoint limit, and it is allowed only if every one passes. The subtle bug is the partial update: the global and tenant counters are incremented, then the user limit says no, and the request has used up quota it was never given. Check every limit first and commit only if all pass, or keep the counters where a single atomic script can check and update them all together.

Security, and watching the limiter

What it is not. A rate limiter is one layer of abuse protection. It does not replace authentication or authorisation, and it is not DDoS protection: volumetric floods have to be absorbed at the edge. Use tight limits on login, password reset and one-time passwords, keyed per account and per IP, so one attacker cannot try many accounts and many attackers cannot hammer one (see Security).

Measure it separately from the APIs it protects. A healthy API can hide a sick limiter that is failing open. Track requests evaluated, allowed and rejected per tenant and route, the limiter’s own latency, store timeouts and errors, fail-open activations and hot-key concentration, and alert when 429s spike for one tenant or the fallback switches on (see Observability).

Our view, and the other view

Our view: start with a token bucket per API key, inside the gateway, with a shared atomic store once you run more than one gateway; send 429 with Retry-After; and decide fail-open or fail-closed per route before the first outage forces the decision.

The other view: for many internal services a local, per-instance limit is honest enough and removes a network dependency from every request; a distributed limiter is real infrastructure, with its own failures to design for, and is worth it only when the limit is a promise or the backend is shared.

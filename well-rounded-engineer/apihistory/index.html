How APIs evolved: from CORBA to agent gateways

Every generation of APIs answered the same question, how one program asks another to do something, and each answer was shaped by what the one before got wrong. This page follows that line from remote procedure calls through CORBA, SOAP, REST, gRPC and GraphQL to the protocols agents use today, and then the gateways that sit in front of each. How to design an API today is on APIs & Integration.

The timeline

WhenWhat arrivedThe idea
1981–1984Remote procedure call (RPC)Bruce Jay Nelson is credited with coining the term in 1981; he and Andrew Birrell published a paper on implementing it in 1984. Calling a function on another machine as if it were local.
1991CORBAThe Object Management Group’s standard for objects on different platforms and languages to call each other, with interfaces described in an interface definition language (IDL).
1996DCOMMicrosoft’s proprietary equivalent, extending COM across the network (launched in beta for Windows 95 in 1996). Java had its own, Java RMI.
1998–2002SOA and the enterprise service busService-oriented architecture, which can be built with web services. An enterprise service bus routes and transforms messages between services; the first commercial ESB dates from 1998, and the term was first published by Gartner in 2002.
1998XML-RPC, then SOAPDave Winer shipped XML-RPC in 1998: remote calls encoded as XML over HTTP. SOAP grew from the same work into a fuller XML messaging protocol, described by WSDL documents.
2000RESTRoy Fielding’s doctoral dissertation described Representational State Transfer, the architectural style of the web: resources, a uniform interface and stateless requests.
2001JSONDouglas Crockford specified JSON in the early 2000s and sent the first JSON message in April 2001. It became the usual body for web APIs.
2010–2015Swagger, then OpenAPITony Tam began Swagger in 2010 to describe HTTP APIs; in 2015 the specification became a separate project, OpenAPI, overseen by the OpenAPI Initiative under the Linux Foundation.
2015GraphQLFacebook started it in 2012 and open-sourced it in 2015: clients send a query against a typed schema, and the result mirrors the query’s shape. It moved to the GraphQL Foundation in 2018.
2015–2016gRPCGoogle had run an internal RPC system, Stubby, since about 2001. In 2015 it decided to build the next version as open source: Protocol Buffers over HTTP/2, with bidirectional streaming, timeouts and cancellation. gRPC 1.0 followed in August 2016.
2024Model Context Protocol (MCP)Introduced by Anthropic in November 2024 to standardise how AI applications connect to tools and data; adopted by other AI vendors in 2025 and donated to the Linux Foundation’s Agentic AI Foundation in December 2025.
2025Agent2Agent (A2A)Introduced by Google in April 2025 and now developed with the Linux Foundation: an open protocol for agents built on different frameworks by different companies to discover each other through “Agent Cards” and collaborate, using JSON-RPC over HTTP(S), without exposing their internal memory or tools.

The lesson RPC and CORBA left

RPC and CORBA aimed for location transparency: a remote call should look like a local one. But remote calls are usually orders of magnitude slower and less reliable than local ones, and can fail because of network problems. CORBA’s version has been criticised as a fundamental design flaw, citing Waldo, Wyant, Wollrath and Kendall’s A Note on Distributed Computing (Sun Microsystems Laboratories, 1994). Wikipedia flags that citation as not yet verified, so the paper itself is worth reading.

Analysis: every later style made the network more visible in some way: HTTP status codes in REST, explicit deadlines in gRPC, and the timeouts and retries on Distributed Systems.

What each style changed

  • SOAP and WSDL brought a formal contract and a standard envelope: a WSDL document describes the operations a service offers. Analysis: its XML is heavier than JSON; the other view is that a strict contract and its tooling were what many enterprises wanted.
  • REST used what the web already had: URLs for resources, HTTP methods, status codes and caching. Its constraints include client and server separation, statelessness, cacheable responses and a uniform interface.
  • GraphQL moved the choice of data to the client, with one endpoint and a typed schema.
  • gRPC brought back strongly typed RPC, with a binary format and streaming, for calls between services.
  • MCP and A2A describe capabilities so that a model or an agent, not just a programmer, can discover and call them.

Protocol Buffers: the contract under gRPC

Protocol Buffers (protobuf) is Google’s language-neutral, platform-neutral way of serialising structured data. Google developed it for internal use (from early 2001) and released a code generator for many languages as open source. You describe messages once in a .proto file; the compiler, protoc, generates classes for each language, and gRPC uses the same files to describe services.

// person.proto
syntax = "proto3";

message Person {
  string name  = 1;
  int32  id    = 2;
  string email = 3;
}

The numbers are field numbers, and they are what goes on the wire, not the names. Each field is written as a tag, (field_number << 3) | wire_type, followed by its value. The same record as protobuf and as JSON (Python’s default json.dumps spacing, so compact JSON would be smaller), measured once on this one record:

import json
from google.protobuf import descriptor_pb2, descriptor_pool, message_factory

# The same schema as person.proto, built in code so no protoc is needed here
fdp = descriptor_pb2.FileDescriptorProto(name="person.proto", syntax="proto3")
msg = fdp.message_type.add(name="Person")
F = descriptor_pb2.FieldDescriptorProto
msg.field.add(name="name", number=1, type=F.TYPE_STRING, label=F.LABEL_OPTIONAL)
msg.field.add(name="id", number=2, type=F.TYPE_INT32, label=F.LABEL_OPTIONAL)
msg.field.add(name="email", number=3, type=F.TYPE_STRING, label=F.LABEL_OPTIONAL)
pool = descriptor_pool.DescriptorPool()
pool.Add(fdp)
Person = message_factory.GetMessageClass(pool.FindMessageTypeByName("Person"))

p = Person(name="Ana", id=1234, email="ana@example.com")
wire = p.SerializeToString()
as_json = json.dumps({"name": "Ana", "id": 1234, "email": "ana@example.com"}).encode()
print("protobuf bytes:", len(wire), wire.hex(" "))
print("JSON bytes:   ", len(as_json))
print("round trip:   ", Person.FromString(wire).email)

protobuf bytes: 25 0a 03 41 6e 61 10 d2 09 1a 0f 61 6e 61 40 65 78 61 6d 70 6c 65 2e 63 6f 6d
JSON bytes:    55
round trip:    ana@example.com

Run as shown with Python 3 and the protobuf package (output from version 7.36.1); the second block is its real output. Reading the bytes: 0a is (1<<3)|2, field 1 with wire type 2 (length-delimited); 03 is the length, then 41 6e 61 is “Ana”. 10 is (2<<3)|0, field 2 as a varint; d2 09 is 1234, written seven bits at a time with the top bit of the first byte set to say another byte follows. 1a is (3<<3)|2, field 3; 0f is the length, 15, then the 15 bytes of “ana@example.com”. Normally you would generate Person with protoc; the schema is built in code here only so the example runs without it.

Changing a protobuf schema safely

  • Never change a field’s number once the message is in use: the number identifies the field in the wire format, so changing it is the same as deleting the field and adding a new one.
  • Reserve the numbers of fields you delete, and their names if you want protoc to refuse them, so nobody reuses them by accident.
  • Adding new fields is how a protobuf schema grows: the docs say it can be extended “without invalidating existing data or requiring code to be updated”.

Field numbers 19,000 to 19,999 are reserved for the protobuf implementation itself. More on contract evolution is on APIs & Integration.

Protobuf or JSON?

If this is true for youIt leans towards (analysis)
High-volume calls between your own services, in several languagesProtobuf, usually with gRPC
A public API that browsers or scripts callJSON: readable without the schema
You must read a message without its .proto fileJSON: protobuf messages do not describe themselves
Messages larger than a few megabytes, or large numeric arraysSomething else: the protobuf docs say it is not a good fit
Rules require a formal standardNot protobuf: its docs say it is not a formal standard of any organisation

The right column is our reading of the protobuf documentation, not a standard. Other teams weigh size and speed more, or readability more; your team already running one format counts too, because switching has a cost.

The gateway in front of it all

As APIs multiplied, a gateway in front of them took on the shared work: routing, authentication, rate limits, quotas, transformation and monitoring (more on APIs & Integration and Apigee). Agents have produced a new kind of gateway. The right-hand column is our summary of the vendor documents listed below (analysis), not a standard definition:

API gatewayAI and agent gateway
Traffic it frontsRequests from clients to your APIsRequests from apps and agents to models, to tools (often over MCP) and to other agents (A2A)
What it metersUsage and loadAlso tokens and spend per model, team or user
What it routesRequests to the right backend serviceAlso by model and provider, with load balancing and failover between providers
What it checksAccess and usage policiesAlso prompts and responses, through guardrails and content filters
What it translatesRequests and responses, on the flyExisting REST or OpenAPI APIs into MCP tools that agents can call

Agent gateways today

Each description below is the project’s or vendor’s own:

  • Azure API Management has an “AI gateway” that extends its existing API gateway rather than being a separate product: it imports model endpoints as APIs, manages token usage and quotas, exposes existing REST APIs as MCP servers, and imports and manages A2A agent APIs.
  • Apigee can expose APIs as MCP tools to agentic applications, implementing the MCP server specification.
  • Amazon Bedrock AgentCore Gateway is described as a fully managed gateway that gives agents one entry point to tools, other agents and models, taking OpenAPI, Smithy and Lambda as tool sources.
  • agentgateway, an open-source proxy, describes itself as built on MCP and A2A, with an LLM gateway, an MCP gateway, an A2A gateway, guardrails, authentication and OpenTelemetry tracing.
  • Agent Router, formerly Envoy AI Gateway and now an Agentic AI Foundation project, offers one OpenAI-compatible API for models and MCP servers, with credentials, routing, quotas and failover kept in one place.
  • Docker’s MCP Gateway runs MCP servers in isolated containers and gives AI models one gateway to reach them.

Analysis: the pattern repeats an old one. An agent gateway does for model and tool calls what API gateways did for service calls: one place for identity, limits, cost and audit. Security for agents is on Agentic AI Security.

Choose by requirement

If this is true for youIt leans towards (analysis)
Public or partner API, many unknown clients, cacheable readsREST with an OpenAPI contract
Many front ends needing different shapes of the same dataGraphQL
High-volume calls between your own services, streaming, several languagesgRPC
An existing SOAP or CORBA system that works and is not changingKeep it, and wrap it behind a gateway or an anti-corruption layer (see Solution Architecture: A to B)
AI applications need to call your existing APIs as toolsExpose them over MCP, through a gateway that already holds your auth and quotas
Agents from different teams or vendors must hand work to each otherA2A
Many teams calling several model providers, and spend must be visibleAn AI gateway for token quotas, routing and failover
Your team already runs one gateway productCheck its AI and MCP features before adding another: switching has a cost

Our view, and the other view

Our view: each new style added to the toolbox more than it replaced the old one. Older styles keep running alongside newer ones, gRPC and REST often sit side by side, and an MCP server can wrap a REST API that already existed. Knowing the history makes it easier to see that an agent gateway is a familiar idea with new things to meter.

The other view: agent traffic differs enough, with long-running tasks, token costs, and decisions made by a model rather than a programmer, that treating it as “just another API” misses new risks. On this view, agent protocols and gateways deserve their own design and security thinking from the start.

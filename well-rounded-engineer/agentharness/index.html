Agent harness

A model on its own only produces text. The harness is everything around it that turns it into an agent: the loop, the tools, context management, permissions, checks, memory, and the record of what happened. How harnesses are built, what makes one reliable, and the options from writing your own to using a managed one. Model basics are on LLMs.

Parts of a harness

PartDoesGets it wrong when
LoopSend messages, run requested tools, return results, repeat until doneNo step or token budget: runaway cost
ToolsFunctions the model can call (files, shell, search, APIs, MCP)Too many, vague descriptions, huge outputs, no error detail
Context managementDecide what the model sees: instructions, history, retrieved files; compact or clear old contentContext fills with noise and the model loses the thread
MemoryPersist knowledge across sessions (project files, notes, memory tools)Stale memory states things that are no longer true
Permissions and sandboxLimit what tools may touch; ask a human for risky actionsBroad credentials; destructive commands unguarded
Gates and hooksDeterministic checks that run regardless of the model (lint, tests, policy)The agent decides on its own when it is "done"
Sub-agentsDelegate research or review to fresh contextsHand-offs lose detail; reviewers anchored on the builder's view
State and resumeSave progress so work survives restartsA crash loses hours of work
ObservabilityLog every model call, tool call, cost and decisionNobody can say why the agent did something
EvaluationMeasure task success, cost and interventions on a test setChanges judged by impression

Configure a ready-made harness before building one. Build your own only when the task, tools or deployment need something they cannot give.

Principles for a reliable harness

  • Done is decided by checks, not by the model: tests, linters, schema validation, a reviewer.
  • Bound everything: steps, tokens, time, money, attempts at the same failure (three, then stop and report).
  • Least privilege tools; human approval for anything irreversible or external.
  • Append-only history: do not rewrite past turns; summarise forward when context is full.
  • Fresh eyes for review: a separate agent or person who sees the code, not the builder's conclusions.
  • Make lessons permanent: each failure becomes a rule, test or hook in the repo.
  • Never let the agent weaken a gate (skip a test, disable a check) to get to green.

Context engineering

  • Put stable things first (system prompt, tools) so they are cached and consistent.
  • Load just in time: give the agent tools to find files instead of pasting everything up front.
  • Keep tool outputs compact; return summaries with a way to fetch details.
  • Compact or clear old tool results in long sessions.
  • Use sub-agents to read widely and return only conclusions.
  • Write state to files (plans, progress notes) so a new context can pick up the work.

Designing tools for agents

  • Few tools, each matching a task a person would do ("search judgments", "run tests"), not every API endpoint.
  • Names and descriptions written for the model: what it does, when to use it, what it returns.
  • Typed inputs with enums and examples; strict schemas.
  • Errors that say what went wrong and how to fix it.
  • Distinguish "no results" from "could not search".
  • Read-only by default; writes need confirmation.

Failure modes to design against

  • Runaway loops repeating the same failing action.
  • Context rot: long sessions where early instructions are drowned out.
  • False completion: claiming success without running the check.
  • Gaming the check: editing tests or disabling guards to pass.
  • Prompt injection from files, web pages or tool outputs.
  • Scope creep: changing more than the task asked.
  • Credential misuse: acting with more access than the task needs.

Measuring a harness

  • Task success rate on a fixed set of real tasks, judged by checks.
  • Cost and time per completed task, not per request.
  • Intervention rate: how often a human had to step in.
  • Regression rate: changes that later had to be reverted.
  • Gate failures caught before merge vs after.

One we build: Penstock

Penstock is a headless, self-hosted agent harness: it runs agents from CI, Slack or webhooks on Copilot, Anthropic, OpenAI or a local Ollama model, and with database storage it logs every model call and tool call. It is open source (Apache 2.0). Run together with Cistern, the two are Headworks.

It is ours, so we are not neutral: compare it with the other harnesses on this page.

Levels: what to expect

1 Foundation

  • Explain loop, tools, context, permissions and gates
  • Configure a ready-made harness (context file, permissions)
  • Recognise runaway loops and false completion

2 Practitioner

  • Build a bounded tool loop with honest errors and logging
  • Write agent-friendly tools
  • Add deterministic gates and a separate reviewer

3 Senior

  • Design harnesses with context engineering, memory and resume
  • Evaluate harnesses on task success, cost and interventions
  • Defend against prompt injection and gate gaming

4 Expert

  • Build agent platforms and shared harness components
  • Set safety and governance policy for autonomous agents
  • Research and adopt new agent patterns with evidence

Each level includes the ones before it. See Start here for what the levels mean.

Guide / Architecture & design / Quality Attributes

Quality attributes

Features say what a system does; qualities say how well, how safely and for whom. They shape the architecture more than features do, and they are cheapest to get right at the start. How to plan them early, write each one as a test, design security in rather than bolt it on, and run vulnerabilities as a loop.

The short answer

Two systems can have identical features and be completely different to live with: one is slow, leaks data and nobody dares change it; the other is quick, safe and easy to extend. The difference is in its quality attributes, also called non-functional requirements: security, performance, accessibility, observability, resilience, maintainability, privacy, cost.

Two habits make them real. Plan them early, while they are still choices rather than rework. And write each one as an acceptance criterion with a number and a check, so that it can pass or fail like any feature. Our view: a quality that has no number and no check is a wish, and wishes are the first thing cut when a deadline comes. The other view is at the end of the page.

Plan early

Some qualities are cheap to decide on day one and expensive to add later, because they shape the structure everything else is built on:

  • Where data may live, and how long it is kept: it decides regions, backups and which services may hold personal data (see Personal Data Across Services).
  • Who may do what: the identity and permission model runs through every endpoint and table.
  • What you can see: request and trace IDs, structured logs and an audit trail are easy to add to a new service and painful to retrofit (see Observability).
  • Accessibility: built into the design system, it is nearly free; added to fifty finished screens, it is a project (see Accessibility).
  • How it fails: timeouts, retries and idempotency are design decisions, not patches (see Microservices).

In the first week: list the qualities that matter, rank them for this system (they compete: see below), write each as a scenario with a number, and decide how each will be checked. The ranking is a decision; record it in an architecture decision record (see Architecture).

Each quality as an acceptance criterion

The numbers below are examples to adapt, not standards; the point is the shape: a measurable statement and a way to check it automatically.

QualityThe questionAn acceptance criterion, for exampleHow it is checked
SecurityCan only the right people do the right things?Every endpoint except /health needs a valid token; user A cannot read user B’s orders; no known critical vulnerability in production for more than 7 daysAccess-control tests, dependency and image scans in CI (see Security)
ResilienceWhat happens when a dependency fails?If the payment provider times out, checkout answers within 3 s with a retryable error and never charges twiceFault-injection tests; covered in depth on Microservices, Distributed Systems and SRE
ObservabilityWhen it misbehaves, can we tell why, quickly?Every log line carries a trace ID; an alert fires within 5 minutes of the error rate passing 2%A test that forces errors and checks the alert (see Observability)
AccessibilityCan everyone use it, including with a keyboard or a screen reader?Meets WCAG 2.2 level AA; every journey works by keyboard aloneAutomated checks in CI, plus a person with a screen reader for each new journey (see Accessibility)
PerformanceIs it fast enough at the load we expect?95% of searches answer in under 300 ms at 200 a secondA load test with thresholds in CI (see Performance, Testing)
MaintainabilityCan we change it safely and quickly?Modules depend only in allowed directions; the build and tests finish in under 10 minutesArchitecture tests (ArchUnit and similar), build time tracked in CI (see SOLID & Design Patterns)
PrivacyDo we keep only what we need, only where we may?A customer’s erasure request is completed in every service within 30 daysAn end-to-end erasure test across services (see Personal Data Across Services)
CostDoes it cost what we planned?Cost per 1,000 orders stays under an agreed figure; an alert at 80% of the monthly budgetBilling export and budget alerts (see Cloud Cost)

A fuller vocabulary: the ISO/IEC 25010 quality model (2011 edition) lists eight product quality characteristics and 31 sub-characteristics, and added security and compatibility as main characteristics compared with the ISO/IEC 9126 model it replaced. It is a useful checklist for “what have we forgotten?”.

They compete: rank them

Qualities pull against each other: more security checks add latency; more resilience (replicas, retries) adds cost; heavy optimisation can hurt maintainability; strong consistency can cost availability during a partition (see Distributed Systems). So rank them for each system, by requirement:

If this is true for youRank higher
It moves money or holds health or identity dataSecurity, correctness, auditability
The public must be able to use it, whatever their abilitiesAccessibility
Users wait on it in real time, or traffic comes in burstsPerformance, resilience
Many teams will change it for yearsMaintainability, observability
It runs at large scale on cloud bills you payCost
It is an experiment that may be thrown awaySpeed of change; keep security and privacy at their minimum, never zero

Secure by design

Secure by design treats security as a constraint on the design from the start, like performance or cost, instead of something added later through patches or extra controls. It assumes the system will be attacked, and arranges it so that a compromise is hard, contained and recoverable. The US agency CISA published “Secure by Design” principles for software makers in October 2023.

PrincipleWhat it looks like in a design
Assume a hostile worldEvery input is untrusted, including from your own other services: validate at each boundary, parameterise every query
Least privilegeEach service account, database user and token can do only its job: the report service can read orders, not refund them
Defence in depthNo single control is trusted alone: authentication at the gateway and authorisation checks in the service and row-level limits in the database
Small attack surfaceExpose only what users need: no admin endpoints on the public network, unused features and ports switched off
Secure defaultsThe safe setting is the one you get without trying: private storage buckets, encryption on, multi-factor sign-in on, debug off
Open design, not secrecySecurity rests on keys and proven algorithms, not on hiding how it works (see Keys, Certificates & SSH)
Continuous assuranceControls are tested on every change and watched in production, not checked once before launch

How to plan it early: threat-model the design before building (see Security, “Threat modelling in 30 minutes”), then turn each mitigation into an acceptance criterion and a test. For a ready-made list of verifiable security requirements, the OWASP Application Security Verification Standard (ASVS, version 5.0.0, May 2025) is written exactly for this: pick the level that fits the system and use its requirements as acceptance criteria. Secure by design sits beside privacy by design and zero trust, and the same habit applies to AI features (see Agentic AI Security).

Vulnerabilities: a loop, not a scan

A vulnerability is a weakness that can be used to break a system’s security. Most of the ones a team has to deal with are in components it did not write: libraries, base images, platforms. Scanning finds them; what makes the difference is how you run the loop around the scan.

TermWhat it is
CVEA public ID for one specific vulnerability, such as CVE-2021-44228. The CVE system was launched by MITRE in 1999, and its IDs underlie the US National Vulnerability Database.
CWEA category of weakness (for example, improper input validation), so you can see which kinds of mistake keep recurring.
CVSSA 0–10 severity score from FIRST, with bands None (0), Low (0.1–3.9), Medium (4.0–6.9), High (7.0–8.9) and Critical (9.0–10.0). The current version, 4.0, was released in November 2023.
EPSSAlso from FIRST: the estimated probability, from 0 to 1, that a published vulnerability will be exploited in the wild.
SBOMA software bill of materials: the inventory of every component in what you ship, so that when a new CVE appears you can answer “do we run that?” in minutes.
  • Severity is not priority. CVSS measures how bad a vulnerability is in general; it is not designed for deciding what to patch first, though it is often used that way. Combine it with the likelihood of exploitation (EPSS) and your own exposure: is the vulnerable code reachable, on the internet, holding sensitive data?
  • Agree fix times before you need them, as acceptance criteria: for example, critical and reachable within days, high within weeks, the rest in the normal update cycle. Our view: the exact numbers matter less than having them written down and measured. The other view: fixed times can push teams to rush low-risk fixes to meet a clock; some prefer to triage each finding on its own exposure and set no deadline.
  • Reduce the noise at the source. Fewer dependencies, slim base images and automated updates gated by tests (see Security, “Supply chain & CI”) mean fewer vulnerabilities to triage at all.
  • Make it easy to be told. Publish how to report a vulnerability to you. Coordinated disclosure, once called responsible disclosure, gives a vendor time to fix before details are published; a common industry deadline, pioneered by Google, is 90 or 120 days, cut to 7 when the vulnerability is already being exploited.
  • Know your own components. Without an SBOM, “are we affected?” becomes a search through every repository, on the worst possible day.

Growing the architecture one slice at a time, with agents

Few teams start with a clean design; most inherit code that grew. The qualities above can still be brought in step by step: one customer journey at a time, end to end, while the team keeps shipping (the strangler fig idea on Architecture, rather than a big-bang rewrite). With agents now writing much of the code, each step has a second job: it gives the agent rails to work within.

StepWhat the team doesWhy it matters more when agents write code
1. Agree the wordsName the business capability and its terms (order, refund, shipment) and use the same names in code, tickets and conversationAn agent copies whatever names it finds. A short glossary in the repository’s agent instructions (CLAUDE.md, AGENTS.md and similar) keeps it from inventing a third word for the same thing (see Agent Harness)
2. Map who talks to whomDraw where data flows and where trust changes: user to service, service to service, service to third partyThe agent itself is now on the map: what it can read, change and call is a trust boundary of its own (see Agentic AI Security)
3. Write the contracts downMake each API, event and module interface explicit: a schema, an interface, a versioned specA written contract is a specification an agent can build to and a contract test can hold it to; an unwritten one is a guess it will fill in (see Specifications, Test Strategy)
4. Put the criteria in the pipelineTurn the acceptance criteria above into checks that run on every change: security scans, accessibility checks, load-test thresholds, architecture testsAgents produce changes faster than people can read them line by line. Automated gates apply the same bar to every change, whoever or whatever wrote it, and leave reviewers the questions in the checklist above
5. Make it visibleAdd logs, metrics and traces, and set service level objectives for the journey (see Observability, SRE)Code nobody on the team wrote by hand is code nobody remembers; production signals are how you find out what it actually does
6. Close the loopLearn from incidents and telemetry, and revisit decision records when the facts changeRecord why a decision was made, beside the code: it is what the next person, and the next agent session, reads before changing it

Our view: in the AI era these steps matter more, not less: the faster code is produced, the more the structure, the contracts and the gates decide whether it is any good. The other view: for a small product with one team, much of this is overhead, and a well-tested monolith with clear modules may be all the architecture it needs for years (see Microservices for when splitting pays). Choose the steps by the requirements in the ranking table above.

Review every change for its effect on the system

Formatters, linters, type checkers and tests now catch most of what reviewers used to comment on, and more of the code itself is written by agents (see Humans & Agents). What is left for a person is the part no tool can judge: what the change does to the system. Google’s published review guide already ranks it first: the overall design is “the most important thing to cover in a review”, and a reviewer should ask whether the change makes the whole system better or more complex, and bring in someone qualified for privacy, security, concurrency or accessibility.

The qualities on this page make a short checklist for any pull request, whoever or whatever wrote it:

Look atAsk of the change
PurposeDoes the description say what changes for the user, and does the code do that and nothing else?
BoundariesDoes each rule live in the module that owns it? Is any API, event or schema it changes versioned and written down? (Architecture, APIs & Integration)
FailureWhat happens on bad input, a slow network or a dependency that is down? Are retries safe to repeat? (Microservices)
Security and privacyDoes it add an entry point, a permission, a secret or a new kind of personal data? Does it add a dependency with known vulnerabilities?
Running itWhen it goes wrong at 3 a.m., will logs, metrics and traces show where, and can it be rolled back or switched off? (Observability)
The next changeCould another team, product or channel reuse this safely, or has something general been hard-wired for one case?
The criteriaDoes it still meet the acceptance criteria above: the latency, accessibility and cost numbers? Is there a test that would fail if it did not?

Our view: leave style to the tools and spend review time on these questions; the more code agents write, the more this is the reviewer’s real job. The other view: line-by-line reading still finds bugs the checks miss, and Google’s guide asks reviewers to look at every line they are asked to review. Both are true; the checklist decides where the time goes first. More on the craft of review in Writing & Code Review.

Our view, and the other view

Our view: decide and rank the qualities in the first week, write each as a criterion with a number, and check it automatically from then on. Treat security as a design constraint, and vulnerabilities as a loop with agreed fix times.

The other view: some teams prefer to learn their real quality needs from production: ship something small, measure it against service level objectives (see SRE), and tighten where users actually feel pain, rather than guess numbers up front. It avoids gold-plating qualities nobody needs. It works best for performance and cost, where you can measure and adjust; it is risky for security, privacy and accessibility, where a gap can harm people before you notice it.

When code is cheap, checking it is the work: one view from industry

In a November 2026 episode of The Pragmatic Engineer, Gergely Orosz talked with Microsoft’s chief executive, Satya Nadella. The episode’s notes open with the question “What does software engineering look like when generating the code becomes cheap and verifying it is the hard part?”. Several points from Orosz’s summary of the conversation bear directly on the qualities on this page:

TopicPoint made in the interviewWhat it means for qualities (analysis)
TestsModels that critique generated code can reach their goal in undesirable ways, “for example, making tests pass by deleting failing tests”Protect the checks themselves: a change that deletes, skips or loosens a test is a review item, whoever made it
AgentsModels are intelligent but unreliable, so treat them as “insider risks” and build a separate system to verify that agentic systems work as expectedLeast privilege for agents, and verification that does not depend on the agent being checked (see Agentic AI Security)
Lock-inKeep the harness, memory and model decoupled to avoid lock-in, and build private evaluations to choose and upgrade modelsMaintainability applied to AI: a boundary you can swap behind, and a test suite for the part you swap (see Agent Harness)
SpecificationsSpecifications and verification are becoming more importantAcceptance criteria written before the code are the specification a person or an agent builds to (see Specifications)
PeopleMicrosoft and Carnegie Mellon University started a preceptorship, pairing experienced engineers with newer ones to build “systems thinking, taste, and judgement”The judgement this page asks for (ranking qualities, reviewing for system impact) is learned from people, not only from tools

How to weigh it. It is one person’s view, given in an interview by the head of a company that sells AI tools and models, and Orosz writes that “We didn’t arrive at any definite solutions” on verification. The underlying problem is not new: tests, types, reviews and staged roll-outs have always been how teams checked code they did not write themselves. What has changed is how much code arrives to be checked.

Our view: the qualities on this page, written as acceptance criteria and checked automatically, are the verification layer that turns cheap code into code you can trust; the cheaper the code, the more that layer is worth. The other view: some expect more of the checking itself to be done by models, critiquing code and learning from production traces; the interview treats that as promising, and also notes that it brings the problem back to verifying the models’ fixes.

From a function to a system

The habits that make one function good are the same ones that make a whole system good, applied at a larger scale. A clear name becomes a shared business vocabulary. A small function with one job becomes a module with one owner, so that a change stays local. Checking inputs becomes security decided in the design. A useful error message becomes logs, traces and objectives that tell you what the running system is doing. Our view: architecture is not a separate skill learned after clean code, but the same care carried across boundaries, failures and production. The other view: some decisions only exist at system scale (data residency, consistency across services, cost) and cannot be reached by tidying code; they need deliberate design, which is why this page starts with planning early.

Practise it

The labs turn several of these qualities into short, testable drills in Python and Java: resilience (the double charge, the retry storm, the stale read), performance (the timed data structures drills), maintainability and testability (the core and the shell), and correctness under concurrency.

Where each tends to stand out

  • Google Cloud: data and analytics (BigQuery is serverless with nothing to size), global networking with a global VPC and single-IP global load balancing, Kubernetes (GKE), developer-friendly serverless (Cloud Run), and AI with Vertex AI. Projects make isolation simple.
  • AWS: the broadest and deepest service catalogue, the largest ecosystem and talent pool, many regions, and mature options for almost every niche. More configuration choices, and more to learn.
  • Azure: enterprises standardised on Microsoft (Entra ID, Microsoft 365, Windows, SQL Server, .NET), hybrid setups (Azure Arc), and the Microsoft data and AI stack (Fabric, Power BI, Azure OpenAI).

All three are capable for almost any workload. The deciding factors are usually existing skills and contracts, specific services you depend on, data location, and price after discounts.

Differences that bite

  • IAM thinking: GCP binds roles to principals on resources; AWS writes JSON policies with explicit allow/deny and resource ARNs; Azure assigns roles at a scope in a strict hierarchy.
  • Networking: a GCP VPC spans regions; AWS and Azure networks are regional and are joined with peering or transit gateways/hubs.
  • Isolation unit: GCP teams often use many projects; AWS uses many accounts; Azure uses subscriptions plus resource groups.
  • Warehouses: BigQuery bills by bytes scanned or by slots with no cluster to run; Redshift has provisioned clusters or serverless capacity units; Fabric uses capacity units shared across workloads.
  • Discounts: GCP committed and sustained use discounts; AWS Savings Plans and Reserved Instances; Azure reservations and savings plans. Spot or preemptible capacity everywhere for interruptible work.
  • Egress: data leaving a cloud costs money on all three; cross-region and cross-cloud traffic adds up. Design data placement before choosing multi-cloud.

gcloud container clusters get-credentials c --region r
aws eks update-kubeconfig --name c --region r

# read a secret
gcloud secrets versions access latest --secret=s
aws secretsmanager get-secret-value --secret-id s
az keyvault secret show --vault-name v -n s

Staying portable (where it matters)

  • Containers and Kubernetes run the same on GKE, EKS and AKS; Cloud Run-style serverless is less portable but simpler.
  • Terraform for all infrastructure, with provider-specific modules behind your own interfaces.
  • Open data formats (Parquet, Iceberg, Delta) in object storage keep data readable by any engine.
  • Open protocols: Postgres, Kafka, OpenTelemetry, OIDC, S3-compatible APIs.
  • dbt and SQL transfer between warehouses with dialect adjustments.
  • Accept lock-in deliberately where a managed service saves real effort (BigQuery, Spanner, DynamoDB); write down the exit cost.

Multi-cloud for its own sake doubles skills, tooling and egress. Use it for a concrete reason: a customer requirement, a unique service, resilience against a provider-wide failure, or negotiation.

Choosing for a new workload

  1. Where is the data now, and where must it legally live?
  2. Which managed services would save the most work (warehouse, Kubernetes, AI models)?
  3. What does the team already know, and what do hiring markets offer?
  4. What identity and productivity stack does the organisation use?
  5. Price a realistic workload on each calculator, including egress and support.
  6. Prototype the riskiest piece on the leading candidate before committing.

Levels: what to expect

1 Foundation

  • Map common services across GCP, AWS and Azure
  • Explain projects vs accounts vs subscriptions
  • Use each provider's CLI for basic tasks

2 Practitioner

  • Translate a design from one cloud to another, including IAM and networking
  • Compare prices for a workload, including egress
  • Use Terraform across providers

3 Senior

  • Choose a provider for a workload with written trade-offs
  • Design portable architectures where it matters, and accept lock-in deliberately
  • Plan data residency and region choices

4 Expert

  • Set the organisation's cloud strategy, contracts and multi-cloud policy
  • Lead migrations between clouds or from on-premises
  • Govern cost, security and compliance across providers

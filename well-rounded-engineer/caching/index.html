Caching

Keeping copies of expensive results closer to where they are needed. Where caches live, the patterns for reading and writing them, invalidation and consistency, stampedes, key design, and working code for Spring, Python, Redis, HTTP and BigQuery.

A cache is a copy, so every cache is a consistency decision. Add one when measurements show the need, and decide up front how stale its data may be.

Read and write patterns

  • Cache-aside (lazy loading): read the cache; on a miss, read the source and fill the cache. Simple and the most common.
  • Read-through: the cache library loads from the source itself on a miss (Caffeine LoadingCache).
  • Write-through: writes go to the cache and the source together; reads are always warm; writes are slower.
  • Write-behind: write to the cache, persist later. Fast, but a crash loses writes. Rarely worth it.
  • Refresh-ahead: refresh popular entries before they expire so users never wait for a miss.

Invalidation

  • TTL: entries expire after a set time. Bounds staleness; simplest and most robust. Every cache entry should have one.
  • Delete on write: after updating the source, delete the cache key (not update it), so the next read reloads fresh data.
  • Versioned keys: include a version in the key (judgment:v3:123, or a data version number); bump it to invalidate everything at once.
  • Event-driven: consume change events (CDC, domain events) and evict affected keys.
  • Immutable data (a published judgment version, a fingerprinted file) can be cached forever.

The race to know: reader A misses and reads the old value; writer B updates the source and deletes the key; A then writes the old value into the cache. A TTL bounds the damage; versioned keys avoid it.

Stampedes (thundering herd)

A popular key expires and thousands of requests miss at once and hit the database together.

  • Single flight / request coalescing: only one caller loads; the others wait for its result (Caffeine does this per key in-process).
  • Distributed lock: SET lock:key 1 NX EX 10 in Redis; the winner loads, others briefly serve stale or wait.
  • Stale-while-revalidate: serve the expired value while one background refresh runs.
  • Jittered TTLs: add randomness so many keys do not expire at the same moment.
  • Probabilistic early refresh: refresh slightly before expiry with rising probability.

Key design

  • Include every input that changes the answer: IDs, filters, page, locale, user or tenant, and the API or data version.
  • Normalise inputs (sort filters, lower-case where meaning allows) so equal requests share a key.
  • Namespace keys: service:entity:version:id.
  • Never share a cache entry across users when the response depends on permissions; include the permission scope in the key, or cache only the permission-independent part.
  • Keep values small; large values make the cache slow and evict everything else.

What not to cache, or not that way

  • Errors and outages as "not found": caching an empty result because the source was down turns "cannot see" into a confident "nothing there" for the whole TTL.
  • Negative results (genuinely not found) only briefly, if at all.
  • Secrets and tokens in shared caches.
  • Personalised data in public caches (CDN, gateway) without per-user keys.
  • Data with legal effect (a suppression, a deletion) behind a long TTL: it must take effect immediately, so check it outside the cache or evict on change.
  • Cheap queries: if the source answers in 1 ms, a cache adds complexity for little gain.

Spring Cache with Caffeine or Redis

@Configuration
@EnableCaching
class CacheConfig {
  @Bean
  CacheManager cacheManager() {
    var m = new CaffeineCacheManager("judgments", "courts");
    m.setCaffeine(Caffeine.newBuilder()
        .maximumSize(10_000)
        .expireAfterWrite(Duration.ofMinutes(10))
        .recordStats());                     // hit ratio for metrics
    return m;
  }
}

@Service
class JudgmentService {
  @Cacheable(cacheNames = "judgments", key = "#id", unless = "#result == null")
  public Judgment get(String id) { return repo.find(id).orElse(null); }

  @CacheEvict(cacheNames = "judgments", key = "#j.id()")
  public void update(Judgment j) { repo.save(j); }
}
# switch to Redis shared across instances
spring:
  cache:
    type: redis
    redis:
      time-to-live: 10m
      key-prefix: "legal:v3:"
  data:
    redis:
      host: ${REDIS_HOST}
      port: 6379

@Cacheable works through a proxy, like @Transactional: calling the method from inside the same class skips the cache.

Python: in-process and Redis

from functools import lru_cache
from cachetools import TTLCache, cached

@lru_cache(maxsize=1024)                     # immutable inputs, never expires
def court_name(code: str) -> str: ...

@cached(TTLCache(maxsize=10_000, ttl=600))   # expires after 10 minutes
def judgment_summary(jid: str) -> dict: ...
import json, random, redis
r = redis.Redis(host=REDIS_HOST, port=6379, decode_responses=True)

def get_judgment(jid: str) -> dict | None:
    key = f"legal:judgment:v3:{jid}"
    if (hit := r.get(key)) is not None:
        return json.loads(hit)
    j = db.load_judgment(jid)                # raises if the DB is down: do not cache that
    if j is not None:
        r.set(key, json.dumps(j), ex=600 + random.randint(0, 60))   # jittered TTL
    return j

def update_judgment(j: dict) -> None:
    db.save(j)
    r.delete(f"legal:judgment:v3:{j['id']}")  # delete after write

Redis essentials

SET judgment:v3:123 '{"cnr":"…"}' EX 600     # with TTL
SET lock:judgment:123 1 NX EX 10             # only if absent: a simple lock
GET judgment:v3:123
DEL judgment:v3:123
TTL judgment:v3:123
INCR ratelimit:app42:202611121015            # counters, rate limits
EXPIRE ratelimit:app42:202611121015 60
INFO stats                                   # keyspace_hits, keyspace_misses, evicted_keys
  • Set maxmemory and an eviction policy (allkeys-lru or allkeys-lfu for a pure cache).
  • Avoid KEYS * in production; use SCAN.
  • Design so the system still works (slower) if Redis is down; a cache should not be a single point of failure.
  • On GCP: Memorystore for Redis or Valkey, private IP, AUTH and in-transit encryption on.

HTTP and CDN caching

# fingerprinted static assets
Cache-Control: public, max-age=31536000, immutable

# public API response, shared caches allowed, short freshness
Cache-Control: public, max-age=60, stale-while-revalidate=30
ETag: "v3-123-a1b2"

# per-user data
Cache-Control: private, max-age=30

# sensitive
Cache-Control: no-store

More on headers on Web Fundamentals. Configure the CDN to vary on, or bypass for, the Authorization header and cookies.

Caching in the data stack

  • BigQuery cached results: identical queries reuse results for free for about 24 hours, unless tables changed or the query is non-deterministic.
  • Materialised views: BigQuery keeps aggregates up to date incrementally and can rewrite queries to use them.
  • BI Engine: in-memory acceleration for dashboards.
  • Serving tables: a consumable table in Postgres is itself a cache of the warehouse; it needs a refresh rule and freshness monitoring like any other cache.
  • Pipeline-level: skip work whose inputs have not changed (compare ETags or content hashes) instead of recomputing.

Measuring a cache

  • Hit ratio (hits ÷ requests): low ratios mean wrong keys, short TTLs or data that is not reused.
  • Latency on hit and on miss.
  • Evictions and memory: constant evictions mean the cache is too small for the working set.
  • Staleness: how old served data is, against the agreed maximum.
  • Source load with and without the cache, to prove it earns its keep.

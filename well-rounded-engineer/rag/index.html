Building RAG systems

Retrieval-augmented generation: find the right passages from your own data and give them to the model, so answers are current, specific and cited. The whole pipeline, each design choice, code for Postgres and BigQuery, and how to evaluate it. RAG is a data pipeline first: see Data Engineering.

Architecture

PhaseStepsRuns
Ingestion (offline)Load documents → parse (PDF, HTML, OCR) → clean → chunk → add metadata → embed → index (vector + keyword)As a pipeline: batch or on change
Retrieval (online)Query → rewrite (optional) → hybrid search with permission and metadata filters → rerank → top passagesPer question, in milliseconds
Generation (online)Prompt with passages and IDs → model answers with citations → validate citations → respond, or say "not found"Per question, in seconds
Evaluation (continuous)Golden questions → retrieval metrics + answer metrics → dashboard and CI gateOn every change, and sampled in production

Ingestion and parsing

  • Keep a stable document ID, source, version and date on everything, so each answer can name exactly what it used.
  • Parse structure, not just text: headings, paragraphs and numbered sections are the best chunk boundaries. Tables need special handling.
  • Scanned PDFs need OCR (Document AI, Tesseract); measure its error rate on your documents.
  • Clean: strip headers, footers, page numbers and boilerplate that pollute retrieval.
  • Run ingestion as an idempotent, incremental pipeline with run records: documents in = chunks indexed + rejected.
  • Handle updates and deletions: re-embed changed documents, remove withdrawn ones, and never serve a stale version silently.

Chunking

StrategyHowNotes
Fixed sizeN tokens with overlapSimple baseline; cuts through sentences
RecursiveSplit by section, then paragraph, then sentence until small enoughGood default for prose
StructuralOne chunk per section or numbered paragraphBest for legal and technical documents with structure
Parent-childRetrieve small chunks, give the model their larger parent sectionPrecise search, enough context to answer
ContextualPrepend a short summary of where the chunk sits in its document before embeddingReduces retrieval failures for chunks that make no sense alone

Typical sizes are 200–1,000 tokens. Measure: the right size is the one that maximises retrieval recall on your golden questions.

Embeddings and indexes

  • Embedding model: choose by quality on your domain and language, dimension (storage and speed), and cost. Options include Vertex AI text embeddings and other providers' embedding APIs, or open models.
  • Same model for documents and queries, and re-embed everything when you change it. Store the model name and version with each vector.
  • Distance: cosine is the usual choice; normalise vectors if the model expects it.
  • Approximate indexes (HNSW, IVF) trade a little recall for speed. Tune and measure recall against exact search on a sample.
  • Where to store: pgvector (Postgres, AlloyDB), BigQuery VECTOR_SEARCH, Vertex AI Vector Search, Elasticsearch/OpenSearch. Keep vectors next to the metadata you filter on.

Hybrid search with rank fusion (Postgres)

-- chunks(id, doc_id, body, tsv tsvector, embedding vector(768), court text)
WITH vec AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY embedding <=> $1) AS r
  FROM chunks WHERE court = ANY($3)            -- filter first: permissions, metadata
  ORDER BY embedding <=> $1 LIMIT 50
),
kw AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY ts_rank_cd(tsv, q) DESC) AS r
  FROM chunks, websearch_to_tsquery('english', $2) AS q
  WHERE tsv @@ q AND court = ANY($3)
  ORDER BY ts_rank_cd(tsv, q) DESC LIMIT 50
)
SELECT id, SUM(1.0 / (60 + r)) AS score       -- reciprocal rank fusion, k = 60
FROM (SELECT * FROM vec UNION ALL SELECT * FROM kw) AS both_lists
GROUP BY id
ORDER BY score DESC
LIMIT 20;                                      -- then rerank these 20

Vectors find meaning ("compensation for acquired land"); keywords find exact names, citations and section numbers that vectors miss. Fusion combines both without tuning score scales.

Reranking and query handling

  • Rerank the top 20–50 with a cross-encoder or reranking API (for example Vertex AI ranking, or a provider's rerank model); keep the best 5–10.
  • Query rewriting: turn a conversational follow-up into a standalone query ("and in Himachal?" → full question).
  • Multi-query: generate a few phrasings and fuse their results.
  • Metadata extraction: pull filters out of the question (court, year) and apply them in SQL.
  • Agentic retrieval: let the model call a search tool several times when one search is not enough, with a step budget.

Generation with citations

import anthropic
client = anthropic.Anthropic()

passages = retrieve(question, courts=user.allowed_courts)    # hybrid + rerank, top 8

content = [
    {"type": "document",
     "source": {"type": "text", "media_type": "text/plain", "data": p.body},
     "title": f"{p.case_name} ¶{p.paragraph} ({p.doc_id})",
     "citations": {"enabled": True}}
    for p in passages
]
content.append({"type": "text", "text":
    "Answer only from the documents above. If they do not contain the answer, "
    "say you could not find it. Question: " + question})

resp = client.messages.create(model="claude-opus-5-5", max_tokens=16000,
                              messages=[{"role": "user", "content": content}])
# text blocks carry a citations list pointing at the exact cited text in each document
  • Put instructions in the system prompt; treat retrieved text as data, never as instructions.
  • Check that every cited document was actually retrieved; drop or flag answers with no citations.
  • When retrieval returns nothing relevant, answer "not found". When the index is unavailable, say so: that is "cannot see", not "nothing exists".

RAG on BigQuery

-- 1. embed chunks with a remote embedding model
CREATE OR REPLACE TABLE `p.rag.chunk_emb` AS
SELECT * FROM ML.GENERATE_EMBEDDING(
  MODEL `p.rag.embedding_model`,
  (SELECT chunk_id, doc_id, court, body AS content FROM `p.rag.chunks`));

-- 2. optional vector index for large tables
CREATE VECTOR INDEX chunk_idx ON `p.rag.chunk_emb`(ml_generate_embedding_result)
OPTIONS (index_type = 'IVF', distance_type = 'COSINE');

-- 3. search
SELECT base.chunk_id, base.doc_id, base.content, distance
FROM VECTOR_SEARCH(
  (SELECT * FROM `p.rag.chunk_emb` WHERE court IN ('2_5', '14_25')),
  'ml_generate_embedding_result',
  (SELECT ml_generate_embedding_result FROM ML.GENERATE_EMBEDDING(
     MODEL `p.rag.embedding_model`,
     (SELECT 'compensation for land acquisition' AS content))),
  top_k => 20, distance_type => 'COSINE');

Good for batch RAG and analytics over large corpora. For interactive latency, serve from Postgres/AlloyDB or Vertex AI Vector Search.

Evaluating RAG

MeasureQuestion it answers
Recall@kIs the right passage in the top k results?
MRRHow high is the first right passage?
FaithfulnessIs every claim supported by the retrieved passages?
Answer correctnessDoes it match the expected answer?
Citation accuracyDo citations point to passages that support the sentence?
AbstentionDoes it say "not found" when the corpus has no answer?
  • Build 100–300 real questions with the passages that answer them, including unanswerable ones.
  • Evaluate retrieval and generation separately, so you know which step to fix.
  • Run in CI on every change to chunking, embeddings, prompts or models.

Security and access control

  • Filter by permission at retrieval time. Never retrieve documents the user may not see and hope the model ignores them.
  • Prompt injection: documents can contain instructions. Keep tools read-only, constrain outputs, and do not let retrieved text trigger actions.
  • Legal holds and suppressions apply to the index too: remove or filter suppressed documents immediately.
  • Personal data: decide what may be embedded and sent to a model; embeddings can leak content.
  • Audit: log the question, retrieved IDs and answer (with sensitive fields protected).

Failure modes and fixes

SymptomLikely cause
Right document exists, never retrievedChunking splits the answer; missing keyword search; embedding model weak for the domain
Retrieved, but answer wrongToo many passages, noisy context, prompt does not demand grounding
Exact citation or section number missedVector-only search; add keyword or exact-match lookup
Old version quotedRe-ingestion not incremental; no version filter
SlowNo ANN index, reranking too many, large context
Confident answer with no sourceNo abstention instruction or citation validation

Levels: what to expect

1 Foundation

  • Explain the ingestion, retrieval and generation phases
  • Run a vector search over embedded chunks
  • Prompt a model to answer from passages with citations

2 Practitioner

  • Build an incremental ingestion pipeline with chunking, metadata and embeddings
  • Add hybrid search, reranking and permission filters
  • Build a golden question set and measure recall and faithfulness

3 Senior

  • Design RAG for a domain: chunking strategy, index choice, latency and cost
  • Diagnose retrieval vs generation failures from evals
  • Secure RAG: access control, prompt injection, suppressions

4 Expert

  • Own retrieval and knowledge platforms across products
  • Lead advanced retrieval (agentic, graph-based) where it measurably helps
  • Set evaluation standards for AI answers in the organisation

Each level includes the ones before it. See Start here for what the levels mean.

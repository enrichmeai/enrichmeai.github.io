Guide / Building services / Spring Boot

Spring Boot

Spring Boot 3.x on Java 17+, with what 3.2–3.5 added and what changed in 4.0 and 4.1. The examples are 3.x; 4.0 renamed or removed some properties, so check its migration guide. Servlet (MVC) and reactive (WebFlux) shown side by side.

Reactive or blocking?

  • Blocking (thread per request): each request holds a thread while it waits for a database or another service. Simple to write, read and debug, with ordinary loops and try/catch.
  • Reactive (Spring WebFlux, Project Reactor): a few threads handle many requests by never waiting; work is composed as a pipeline of callbacks. It scales to many concurrent slow calls, but code, stack traces and debugging are harder, and every library on the path must be non-blocking too.
  • Virtual threads changed the balance. Since Java 21, blocking code can use cheap virtual threads, so the simple thread-per-request style scales to high concurrency. As JEP 444 puts it, virtual threads are not faster threads: they exist to provide scale (higher throughput), not speed (lower latency).
  • Measured: in our Spring Boot vs Quarkus benchmark, with 1,000 connections to an endpoint that waits 100 ms, blocking Spring served about 1,960 requests a second, the same code with virtual threads about 8,500 to 8,800, and reactive Spring and Quarkus about 9,400 to 9,750.
  • Our view: start blocking, and turn on virtual threads for I/O-heavy services. Choose reactive when you need streaming or back-pressure, or you already have a reactive stack; do not rewrite a working blocking service for throughput alone without measuring it first. See Performance.
  • The other view: some teams choose reactive from the start, because one model covers streaming, back-pressure and many slow calls, and in the benchmark above it served the most requests.

// JdbcClient (3.2): plain SQL, records out
@Repository
class OrderDao {
  private final JdbcClient jdbc;
  OrderDao(JdbcClient jdbc) { this.jdbc = jdbc; }

  Optional<OrderDto> find(String orderRef) {
    return jdbc.sql("SELECT order_ref, order_date FROM orders WHERE order_ref = :order_ref")
               .param("order_ref", orderRef)
               .query(OrderDto.class)
               .optional();
  }
  int upsert(OrderDto o) {
    return jdbc.sql("""
        INSERT INTO orders (order_ref, order_date) VALUES (:order_ref, :d)
        ON CONFLICT (order_ref) DO UPDATE SET order_date = EXCLUDED.order_date""")
      .param("order_ref", o.orderRef()).param("d", o.orderDate()).update();
  }
}

Filters, interceptors and aspects: where the code around your code lives

Some code has nothing to do with what a request is for, yet has to run for almost every one of them: checking who is calling, timing the call, adding a request id to the logs, opening a transaction, compressing the response. Copy it into every controller and it soon drifts apart. Java has grown three places to put this kind of code instead, and once you can see all three side by side, a lot of “Spring magic” stops being magic.

1. The servlet filter: the oldest gate. Filters arrived in Servlet 2.3, and the interface has hardly changed since. A filter sits in front of a servlet and sees the raw request on the way in and the response on the way out. Its own documentation lists the jobs it was designed for: authentication, logging and auditing, data compression, encryption. Filters form a chain, and each one decides whether to pass the request on by calling chain.doFilter. This one times every request (it compiles against Jakarta Servlet 6, as used by Tomcat 10):

import jakarta.servlet.Filter;
import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.ServletRequest;
import jakarta.servlet.ServletResponse;
import jakarta.servlet.http.HttpServletRequest;
import java.io.IOException;

// Runs for every request, before any servlet or controller sees it.
public class RequestTimingFilter implements Filter {
    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        long start = System.nanoTime();
        try {
            chain.doFilter(request, response);          // hand over to the next filter, then the servlet
        } finally {
            long ms = (System.nanoTime() - start) / 1_000_000;
            String path = ((HttpServletRequest) request).getRequestURI();
            System.out.println(path + " took " + ms + " ms");
        }
    }
}

Spring Security’s servlet support is built on filters like this one. Spring registers a single DelegatingFilterProxy with the servlet container, which hands each request to filters that live as Spring beans, so they can use everything else in your application.

2. The handler interceptor: a gate that knows the route. A filter runs before Spring has worked out which controller will handle the request. A Spring MVC HandlerInterceptor runs after that decision, with three hooks: preHandle before the controller (return false and it never runs), postHandle after it, and afterCompletion once the request has finished.

// Spring MVC: runs around the controller method, and knows which handler was chosen
public class AuditInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        // return false to stop here: the controller is never called
        return true;
    }
}

Two things in Spring’s own documentation are worth knowing. For @ResponseBody methods the response is already written before postHandle runs, so it is too late to add a header there. And Spring warns that interceptors are “not ideally suited as a security layer”, because their path matching can disagree with the controllers’; it recommends Spring Security or another approach in the servlet filter chain, applied as early as possible.

3. The aspect: code wrapped around methods, not requests. Aspect-oriented programming was developed by Gregor Kiczales and colleagues at Xerox PARC, who then built AspectJ, an extension to Java first released in 2001 and now an Eclipse Foundation project. The idea is to describe a cross-cutting concern once (the advice) and say where it applies (the pointcut), instead of writing it into every method. Spring’s @Transactional works this way.

Spring AOP keeps it simple on purpose. It is pure Java, needs no special compiler, and supports only one kind of join point: the execution of a method on a Spring bean. It wraps the bean in a proxy, a JDK dynamic proxy when the bean implements an interface and a CGLIB subclass when it does not, and the proxy runs the advice before handing over to the real object. That one design choice explains the most common surprise. Here is a small Spring program, run with Spring 6.2:

import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.Around;
import org.aspectj.lang.annotation.Aspect;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.EnableAspectJAutoProxy;

public class AopDemo {

    @Aspect
    static class Timing {
        @Around("execution(* AopDemo.OrderService.*(..))")     // every public method of OrderService
        Object time(ProceedingJoinPoint call) throws Throwable {
            long start = System.nanoTime();
            try {
                return call.proceed();
            } finally {
                System.out.printf("  [aspect] %s took %d us%n",
                        call.getSignature().getName(), (System.nanoTime() - start) / 1_000);
            }
        }
    }

    static class OrderService {
        public void placeOrder() {
            System.out.println("placing order");
            checkStock();                                     // a call on 'this': the proxy never sees it
        }
        public void checkStock() {
            System.out.println("checking stock");
        }
    }

    @Configuration
    @EnableAspectJAutoProxy
    static class Config {
        @Bean Timing timing() { return new Timing(); }
        @Bean OrderService orderService() { return new OrderService(); }
    }

    public static void main(String[] args) {
        try (var context = new AnnotationConfigApplicationContext(Config.class)) {
            OrderService orders = context.getBean(OrderService.class);
            System.out.println("The bean is a " + orders.getClass().getSimpleName());
            orders.placeOrder();
            System.out.println("--- calling checkStock from outside:");
            orders.checkStock();
        }
    }
}

What it printed:

The bean is a AopDemo$OrderService$$SpringCGLIB$$0
placing order
checking stock
  [aspect] placeOrder took 984 us
--- calling checkStock from outside:
checking stock
  [aspect] checkStock took 115 us

Look at the first call. placeOrder was timed, but checkStock, called from inside it, was not: the call went to this, the real object, and never passed through the proxy. Spring’s documentation says it plainly: self-invocation “is not going to result in the advice associated with a method invocation getting a chance to run”. It is why a @Transactional method called from another method in the same class runs without a new transaction (analysis, following from the same rule). The fixes Spring suggests are to restructure the code so the call goes through another bean, or to inject a reference to the proxy. AspectJ’s compile-time and load-time weaving change the bytecode itself, so they do not have this limit.

The modern versions of the same three ideas. In Spring WebFlux, a WebFilter plays the part of the servlet filter in a reactive application. In Jakarta EE, and so in Quarkus, Jakarta Interceptors give you an @AroundInvoke method that “interposes on business methods”, much like an aspect. And native images change the trade-off: GraalVM must be told about dynamic proxies, so for a Spring native image the proxies are created at build time and compiled in.

If the code you want to add…Put it in
Applies to every HTTP request, before anything else (authentication, CORS, compression, a request id)A servlet filter, or a WebFilter in WebFlux; for security, Spring Security’s filter chain
Needs to know which controller is handling the requestA HandlerInterceptor
Applies to business methods however they are called (transactions, caching, metrics on a service)An aspect, or an annotation that Spring already implements with one
Applies to two or three methods onlyPlain code: call a helper, or wrap the object yourself
Has to work on calls inside the same class, or on fieldsAspectJ weaving, not Spring’s proxies

Our view: use the least invisible mechanism that does the job. Filters for HTTP, plain code when only a few methods need it, and aspects when the same rule genuinely applies everywhere, written down where the team will find it. Every aspect is code that runs without appearing in the method it changes, and the self-invocation surprise shows how easily that catches people out. The other view: that invisibility is the point. Aspects keep business code about the business, @Transactional is used happily in a great many Spring applications, and one well-named aspect is easier to change than the same five lines copied into fifty methods.

Errors as ProblemDetail

@RestControllerAdvice
class ApiErrors {
  @ExceptionHandler(NotFoundException.class)
  ProblemDetail notFound(NotFoundException e) {
    ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.getMessage());
    pd.setTitle("Order not found");
    pd.setProperty("orderRef", e.orderRef());
    return pd;
  }
}

Levels: what to expect

1 Foundation

  • Build a REST endpoint with validation and a test
  • Configure an app with application.yml and profiles
  • Use Spring Data or JdbcClient for simple queries

2 Practitioner

  • Handle errors with ProblemDetail; write slice and integration tests
  • Use transactions correctly; understand proxies
  • Add Actuator, metrics and structured logging

3 Senior

  • Choose servlet vs reactive and design for throughput
  • Secure APIs with Spring Security and OAuth 2.0
  • Tune startup, memory and connection pools for the cloud

4 Expert

  • Lead major upgrades (3.x to 4.x) across services
  • Build internal starters and platform libraries
  • Set architecture and module boundaries (Spring Modulith)

Each level includes the ones before it. See Start here for what the levels mean.

Guide / Security / Personal Data Across Services

Personal data across services

Splitting a system into services also spreads people’s personal data across them: databases, caches, search indexes, event logs, analytics copies and backups. This page is about the engineering that lets you find that data, keep less of it, delete it when you must, keep it in the right region, and prove all of it. It is not legal advice: the obligations below are summarised from secondary sources, so read the regulation itself with your data protection officer.

What the law asks of a system

The EU’s General Data Protection Regulation (GDPR) gives people rights over their data, including access to it, a portable copy, erasure under certain circumstances, and a challenge to decisions made solely by an algorithm. Its principles include purpose limitation, data minimisation, storage limitation, and integrity and confidentiality. It also governs moving personal data outside the EU and EEA.

Analysis: for engineers, each right becomes a capability the system must have: find everything about one person, export it, delete or anonymise it, and explain an automated decision. A design that cannot find all of one person’s data cannot honour any of these.

Where personal data ends up

Analysis. In a service architecture it is rarely only in the service that owns it:

  • Each service’s own database, and the events it publishes.
  • Caches and search indexes built from those events (see Caching and RAG).
  • Analytics and warehouse copies, and exports to partners.
  • Logs and traces that captured a field they should not have.
  • Backups of all of the above.

Keep a data catalogue: which service holds which personal fields, why, and for how long. It is the map every request below depends on.

Keep less of it, in fewer places

  • Data minimisation: collect and copy only what the purpose needs.
  • Tokenisation: replace a sensitive value with a token that has no meaning of its own and maps back only through the tokenisation system. Services pass the token around; the real value lives in one place.
  • Pseudonymisation: transform data so it cannot be tied to a person without additional information, such as a key; the GDPR’s definition (Article 4(5), as summarised by Wikipedia) requires that information to be kept separately. Tokenisation and encryption are both examples.
  • Anonymisation: remove what identifies people, so they can no longer be identified, directly or indirectly. Combining the data with other datasets can sometimes undo it.

Erasure meets retention

Erasure is a right to request deletion on certain grounds, and it is limited: it applies only under certain circumstances, and Wikipedia notes it was made more limited than the earlier “right to be forgotten” proposal. The sources behind this page do not list the exceptions, so read Article 17 itself. Systems also have their own retention rules: Microsoft documents, for example, that some system-generated logs are kept under its service retention policies and are not removed by a data subject delete request.

Analysis: the common engineering case is a request to delete data that another rule requires you to keep, such as a financial record. The usual pattern is to delete what you may, pseudonymise or anonymise what you must keep, restrict who can read it, and record which rule applied and when the kept data will go. Which rule wins is a legal decision; the system’s job is to make either answer possible.

Deleting across services

Analysis: one way to do it.

  1. Record the request in one place that owns it, with an id and the time it arrived.
  2. Publish one event, such as CustomerErasureRequested, keyed by the customer, so every service that holds their data hears it (see Kafka).
  3. Each service acts and confirms: it deletes or anonymises its data, then publishes its own confirmation. Make each step idempotent, because the event may arrive twice.
  4. Track until everyone has confirmed, chase the ones that have not, and only then report the request as done.
  5. Derived copies follow: rebuild or purge caches and search indexes, and stop the person reappearing from a later replay of old events.

Analysis: this is a saga with no compensation step, because deletion cannot be undone (see Architecture). The hard parts are the services nobody listed in the data catalogue, and old events that would re-create the data if replayed.

The steps, drawn

Backups and crypto-shredding

Crypto-shredding makes encrypted data unusable by deleting or overwriting its encryption key. It helps where the data itself is hard to reach, such as backups and copies spread across systems, because only the key needs destroying.

Analysis: encrypt each person’s sensitive fields with a key of their own. If no copy of that key survives (key backups, caches) and the encryption holds, destroying it makes those fields unreadable everywhere, backups included. The cost is managing many keys, and losing a key by mistake loses the data.

Keeping data in the right place

  • Data residency is where the data is actually stored; data localisation is a requirement that it be stored within a given region.
  • The GDPR governs transfers of personal data outside the EU and EEA, so where you store and process it is a design decision, not only an operations one.
  • Analysis: choose regions per market, route each customer to their region, and check where logs, backups and support tools copy the data too (see GCP vs AWS vs Azure for regions).

Choose by requirement

If this is true for youIt leans towards (analysis)
Many services need to refer to a person but few need the actual valueTokenisation, with the real values in one vault
Analysts need the data’s shape, not who it describesAnonymisation before it reaches the warehouse
You must keep a record but stop it pointing at a personPseudonymisation, with the key held separately and access restricted
Data sits in backups or systems you cannot edit row by rowCrypto-shredding with per-person keys
Personal data spans many services owned by different teamsAn erasure event, confirmations from each service, and one tracker
Customers in several jurisdictionsRegional deployments, with routing and residency checked for logs and backups too

Prove it

  • Test deletion in CI: create a person, erase them, and assert they are gone from every store you list.
  • Audit access: who read which personal data, when, and why, with a correlation id across services.
  • Report: how many requests, how long each took, and which services were slowest to confirm.

This card is analysis: these are practices, not legal requirements quoted from the regulation.

Our view, and the other view

Our view: design for erasure from the first service, with a data catalogue, tokens instead of copies, and an erasure event every service must handle. Retrofitting it across dozens of services is harder than building it in.

The other view: early on, a small team may keep personal data in one service on purpose, so deletion stays a single query, and add tokenisation and events only when the data starts to spread. Building the full machinery before the system needs it has a cost too.

Levels: what to expect

1 Foundation

  • List where personal data ends up in a service architecture
  • Explain tokenisation, pseudonymisation and anonymisation
  • Name the rights a person has over their data

2 Practitioner

  • Keep a data catalogue of personal fields per service
  • Build an erasure event that every service handles idempotently
  • Test deletion end to end in CI

3 Senior

  • Design for erasure and legal retention together
  • Use crypto-shredding for backups and copies
  • Plan regional deployments for data residency

4 Expert

  • Set an organisation's personal-data architecture and standards
  • Work with legal and the data protection officer on retention rules
  • Audit and report on data subject requests across systems

Each level includes the ones before it. See Start here for what the levels mean.

Event sourcing and CQRS

Storing every change as an immutable event and deriving current state from them. How the event store, aggregates and projections work, how to evolve events, and when the extra complexity is worth it.

The idea

Most systems store current state and overwrite it: a subscription row says plan = 'pro'. Event sourcing stores the sequence of facts instead: SubscriptionStarted(basic), PlanUpgraded(pro), PaymentFailed, PaymentSucceeded. Current state is computed by replaying (folding) those events. The events are the source of truth; every other view is derived from them and can be rebuilt.

TermMeaning
EventAn immutable fact in the past tense, with data and metadata (who, when, causation)
StreamThe ordered events of one entity, e.g. subscription-42
AggregateThe entity that enforces business rules; rebuilt from its stream; decides which new events a command produces
CommandA request to change something (UpgradePlan); may be rejected
Event storeAppend-only storage of streams with per-stream versions
Projection / read modelA view built from events for querying (a table, a search index, a cache)
SnapshotSaved aggregate state at a version, to avoid replaying long streams
CQRSSeparate models for writes (commands) and reads (queries); event sourcing usually comes with it

When it is worth it

Good fits

  • History is the product: audit trails, finance, legal records, compliance.
  • You need to answer "what was the state on date X, and why?"
  • Several different read models from the same changes.
  • Complex domains where business events are first-class (orders, claims, subscriptions).

Poor fits

  • Simple CRUD with no interest in history.
  • Teams new to the pattern on a deadline.
  • Data that must be truly deleted on request with no workaround.

Apply it to the one part of the system that needs it, not the whole system.

The flow

  1. A command arrives: UpgradePlan(subscription-42, pro).
  2. Load the aggregate's events (from the latest snapshot) and fold them into current state.
  3. The aggregate checks business rules and decides zero or more new events.
  4. Append them with the expected version (optimistic concurrency). If someone else appended first, reload and retry.
  5. Projections consume new events and update read models.
  6. Queries read from the read models, which may lag slightly behind.

An aggregate in Java

sealed interface SubEvent permits Started, PlanUpgraded, Cancelled {}
record Started(String id, String plan, Instant at)      implements SubEvent {}
record PlanUpgraded(String id, String plan, Instant at) implements SubEvent {}
record Cancelled(String id, String reason, Instant at)  implements SubEvent {}

enum Status { ACTIVE, CANCELLED }

record Subscription(String id, String plan, Status status, int version) {

  static Subscription replay(List<SubEvent> events) {
    Subscription s = null;
    for (SubEvent e : events) s = apply(s, e);
    return s;
  }

  static Subscription apply(Subscription s, SubEvent e) {     // pure: no side effects
    return switch (e) {
      case Started st     -> new Subscription(st.id(), st.plan(), Status.ACTIVE, 1);
      case PlanUpgraded u -> new Subscription(s.id(), u.plan(), s.status(), s.version() + 1);
      case Cancelled c    -> new Subscription(s.id(), s.plan(), Status.CANCELLED, s.version() + 1);
    };
  }

  List<SubEvent> upgrade(String newPlan, Instant now) {        // decide
    if (status != Status.ACTIVE) throw new IllegalStateException("subscription not active");
    if (plan.equals(newPlan)) return List.of();                 // idempotent: nothing to do
    return List.of(new PlanUpgraded(id, newPlan, now));
  }
}

Separate decide (rules, may reject) from apply (pure state change). Apply must never fail for a stored event: it already happened.

An event store in Postgres

CREATE TABLE events (
  global_position bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  stream_id   text        NOT NULL,
  version     int         NOT NULL,
  type        text        NOT NULL,
  data        jsonb       NOT NULL,
  metadata    jsonb       NOT NULL DEFAULT '{}',   -- user, causation_id, correlation_id
  recorded_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (stream_id, version)                      -- optimistic concurrency
);

-- load a stream
SELECT type, data, version FROM events
WHERE stream_id = 'subscription-42' ORDER BY version;

-- append, expecting the stream to be at version 3
INSERT INTO events (stream_id, version, type, data)
VALUES ('subscription-42', 4, 'PlanUpgraded', '{"plan":"pro"}');
-- unique violation → another writer got version 4 first → reload, re-decide, retry

Caution: identity values are assigned at insert, not commit, so with concurrent writers a projection reading by global_position can miss a row committed late. Dedicated event stores (KurrentDB, formerly EventStoreDB) or a transactional outbox with careful checkpointing handle this.

Projections and read models

// a projection keeps a checkpoint and is idempotent
void handle(StoredEvent e) {
  tx.run(() -> {
    switch (e.payload()) {
      case Started s      -> db.upsert("subscription_view", s.id(), Map.of("plan", s.plan(), "status", "ACTIVE"));
      case PlanUpgraded u -> db.update("subscription_view", u.id(), Map.of("plan", u.plan()));
      case Cancelled c    -> db.update("subscription_view", c.id(), Map.of("status", "CANCELLED"));
    }
    db.saveCheckpoint("subscription_view", e.globalPosition());  // same transaction
  });
}
  • Store the checkpoint in the same transaction as the update, so a crash never applies an event twice or skips one.
  • To change a read model, build a new one by replaying all events, then switch reads to it.
  • Read models are eventually consistent. Show users "updating…" or read their own writes from the aggregate when it matters.

Evolving events

  • Events are immutable and permanent. You cannot fix old ones in place; plan their shape carefully.
  • Additive changes (new optional fields with defaults) are safe.
  • Version the event type (PlanUpgraded.v2) when the meaning changes.
  • Upcasting: convert old event versions to the current shape when reading, so the code handles one version.
  • Never rename or reuse an event type for a different meaning.
  • Name events in business language (PaymentFailed), not technical (RowUpdated).

Snapshots, size and deletion

  • Snapshots every N events (or when replay gets slow) store state plus version; load the snapshot, then only later events.
  • Keep streams short-lived where the domain allows (one stream per billing period, not per customer forever).
  • Personal data and deletion: keep personal data out of events where possible (reference an ID), or encrypt it per person and destroy the key to "forget" them (crypto-shredding).
  • Archiving: move closed streams to cold storage after their retention period.

Testing: given, when, then

@Test
void upgradeEmitsEventWhenActive() {
  var given = List.<SubEvent>of(new Started("s1", "basic", T0));
  var events = Subscription.replay(given).upgrade("pro", T1);          // when
  assertThat(events).containsExactly(new PlanUpgraded("s1", "pro", T1));   // then
}

@Test
void cannotUpgradeCancelled() {
  var given = List.<SubEvent>of(new Started("s1", "basic", T0), new Cancelled("s1", "user", T1));
  assertThatThrownBy(() -> Subscription.replay(given).upgrade("pro", T2))
      .hasMessageContaining("not active");
}

Aggregates tested this way need no database or mocks: given past events, when a command, then expected events or a rejection.

The lightweight version: an append-only ledger

Many systems get most of the benefit without full event sourcing: an append-only table with one row per state change, and current state from a "latest event" view. Never UPDATE, never DELETE.

-- BigQuery: current state of each pipeline stage from its event log
CREATE OR REPLACE VIEW `p.ops.v_job_run_latest` AS
SELECT * FROM `p.ops.job_run_events`
WHERE TRUE
QUALIFY ROW_NUMBER() OVER (PARTITION BY run_date, stage ORDER BY event_ts DESC) = 1;

You get history, auditability and "what happened on date X" with ordinary SQL. Add aggregates, projections and replay only if the domain needs them.

Tools

  • KurrentDB (formerly EventStoreDB): a database built for event streams, subscriptions and projections.
  • Axon Framework / Axon Server (Java): aggregates, sagas, projections and an event store.
  • Postgres with an events table: simple and often enough, with the caveats above.
  • Kafka is a good event log for distribution, but a weak event store: no efficient per-entity stream reads and no per-stream optimistic concurrency. Many systems store events in a database and publish them to Kafka through an outbox.

Common mistakes

  • Event sourcing the whole system instead of the part that needs history.
  • Events that mirror table changes (CustomerUpdated with every field) instead of business facts.
  • Side effects (emails, payments) inside apply, so a replay sends them again.
  • Querying the event store for lists and searches instead of building read models.
  • No plan for event versioning, personal data or replay time.
  • Treating eventual consistency of read models as a bug rather than designing for it.

Levels: what to expect

1 Foundation

  • Explain events, streams, aggregates, projections and CQRS
  • Read an event stream and follow how state was built
  • Tell an append-only ledger from full event sourcing

2 Practitioner

  • Implement an aggregate with decide/apply and given-when-then tests
  • Build idempotent projections with checkpoints
  • Append with optimistic concurrency

3 Senior

  • Decide where event sourcing fits in a system and where it does not
  • Design event schemas, versioning and upcasting
  • Plan snapshots, replay, rebuilds and personal-data handling

4 Expert

  • Lead event-sourced architectures across domains and teams
  • Choose and operate event stores at scale
  • Set standards for event modelling and governance

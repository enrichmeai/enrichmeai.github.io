Humans and agents: working together, and personas

An AI agent plans and uses tools on its own, but someone still sets the goal, owns the outcome and decides what is safe to do without asking. This page is about that relationship: how to brief an agent, how an agent should report back, how much freedom to give it, and how to build a named agent (a persona) with its own role, skills and model. Facts are linked at the end; where a card is our view, it says so and gives the other view.

Who does what

Analysis, and our view. A useful starting split. Your team may draw the lines differently; the point is to draw them on purpose.

The personThe agent
Sets the goal and says why it mattersTurns the goal into steps and asks when the goal is unclear
Decides what “done” means and what must not changeDoes the searching, drafting, running and checking
Approves anything irreversible, costly, or visible to othersStops and asks at those points, instead of guessing
Owns the result, whoever typed itReports what it did, with evidence, and what it could not do
Corrects it, and writes the lesson down where the next session will read itFollows the written rules, and says when a rule seems to conflict with the task

The other view: some teams give agents whole tasks end to end and review only the result. That can work for well-tested, reversible work; the table below helps you decide where.

How to brief an agent

  • The goal and the why: “Add a retry to the payment call, because the gateway returns occasional 503s.”
  • Context it cannot guess: the files, the error, the decision already made, what was tried.
  • Constraints: what must not change, which tools or commands are off limits, the budget.
  • Done means: the test that must pass, the output you expect, how you will check it.
  • When to stop and ask: before deleting, deploying, spending, or messaging anyone.
  • Give it a role. Anthropic’s documentation says that setting a role in the system prompt focuses the model’s behaviour and tone, and that even a single sentence makes a difference.

How an agent should report back

  • Evidence, not confidence: the test output, the command and its result, the link.
  • What it did not do, and why: a check that could not run is “not run”, never “passed”.
  • Questions at checkpoints. Anthropic’s guide to building agents: agents can pause for human feedback at checkpoints or when they meet blockers, and it is common to include stopping conditions such as a maximum number of iterations.
  • Asking the person properly. The Model Context Protocol has elicitation: a server can ask the user for more information through the client, and the user can accept, decline or cancel. The specification says servers must not use its form mode to ask for secrets or credentials.
  • Short and plain: the person reads the summary, not the log.

How much freedom to give: choose by requirement

If this is true of the taskIt leans towards
Easy to undo (a branch, a draft, a local file)Let it run, with stopping conditions; review the result
A test or check can prove it rightLet it run until the check passes; read the evidence
Hard or impossible to undo (deleting data, a deploy, a payment, an email)The agent proposes, a person approves each time
The cost of an error is high, or falls on someone elseA person approves at each checkpoint
Regulated, or decides things about peopleDocumented human oversight, required by law in some places (see below)
Nobody can say what “done” looks like yetWork with it step by step; it is not ready to hand over
  • Automation bias is the tendency to favour suggestions from automated systems and ignore contradicting information, even when that information is correct. Wikipedia lists contributing factors including lack of confidence in your own abilities, a lack of other information to hand, and the wish to save time and effort on complex tasks or heavy workloads. A review that only clicks “approve” is not oversight.
  • The law is arriving. The EU’s Artificial Intelligence Act entered into force on 1 August 2024. High-risk uses, such as recruitment, education, critical infrastructure and justice, carry obligations that include human oversight; limited-risk uses carry transparency obligations.
  • Agents cost more and errors compound. Anthropic recommends testing agents extensively in sandboxed environments, with guardrails.

Building a persona: a named agent

A persona is a named agent with a defined job: who it is, what it is for, what it may touch, which skills it loads and which model it runs on. A name makes it easier for people to say who did what, and to give each one a narrow, testable remit.

  • In Claude Code, a subagent is a file with a name, a description, a tools list, a model and a system prompt. Each runs in its own context window with its own permissions. Limiting its tools enforces what it may do; the model field picks the model for that agent alone (it inherits the main one if you leave it out).
  • Skills are folders with a SKILL.md of instructions. A skill’s body loads only when it is used, so reference material costs almost nothing until needed. A subagent can preload chosen skills with its skills field. Claude Code’s skills follow the Agent Skills open standard, which works across several AI tools.

What you can do today, and what is only possible

IdeaStatus in Claude Code (from its documentation)
A named agent, say “Vikram, the backend engineer”, with its own instructions and toolsAvailable. A subagent file; Claude delegates to it when a task matches its description, or you call it by name with @agent-<name>
One named agent carrying one skill or severalAvailable. The skills field preloads the full content of each listed skill; it can still use other skills when needed
Each named agent on its own modelAvailable, for Claude models: model takes sonnet, opus, haiku, fable, a full model ID, or inherit
A script that runs many agents and cross-checks themAvailable. Dynamic workflows run many subagents from a script, and the script can name a model for each stage
Agents that talk to each other under a leadExperimental: agent teams, disabled by default
Named agents on models from different vendors (one on Copilot, one on a local Ollama)Not a Claude Code subagent feature. Penstock’s README describes choosing one vendor in its configuration. Per-agent vendors are a possibility, not a product
# .claude/agents/reviewer.md
---
name: reviewer
description: Independent reviewer of a finished change. Use before a pull request is opened.
tools: Read, Grep, Glob, Bash
model: sonnet
skills: [house-style, security-checklist]
---
You review a finished change. You do not edit files.
Check every claim against its source and report what you could not verify.
Report findings as: severity, file:line, what is wrong, the evidence.

User personas are different, and both matter. In user-centred design, a persona is a semi-fictional profile of a typical user, built from interviews and surveys; Alan Cooper introduced the idea in software design. Agent personas serve user personas: design the user persona first (see Design Thinking & UX), then decide which agents help that person, and what each one must never do on their behalf.

Where Headworks fits

Headworks is EnrichMeAI’s own take on an agent you can hand real work to: Penstock and Cistern running together on your machine. What is released today, from each project’s README at its latest release:

  • You choose the model. Penstock’s model layer is pluggable: GitHub Copilot by default, or Anthropic, OpenAI or a local Ollama, switched in configuration.
  • Memory you review. Penstock’s memory server, used from Claude Code or Claude Desktop over MCP, can write a draft episode of the work for you to review; its recall does not read drafts until you move one into the record and commit it. Recall inside Penstock’s own agent is off by default.
  • Access you grant. Cistern gives the agent its own credential; you grant it read access to one folder, it is refused everywhere else, and you can revoke the grant from a terminal.

A named persona built on that record is planned, not released.

Inspiration: named agents to try

Ideas, not recommendations. Each is a small, narrow agent you can build with today’s subagents and skills; try one, measure it, keep it if it earns its place.

AgentIts jobWhat it must never do
A reviewerChecks a finished change against its sources and the house rules; reports findings with evidenceEdit files (give it read-only tools)
“Vikram”, backend; “Asha”, frontendEach owns one part of the codebase, with that part’s skills (API conventions; accessibility and design tokens)Change the other’s folders
A test writerWrites the failing test first, then hands overWeaken or skip an existing test
A docs keeperAfter each merge, finds the docs the change made wrong and proposes fixesMerge its own proposals
An on-call helperReads alerts and logs, suggests the likely cause and the runbook stepRun anything against production
A release-notes writerDrafts notes from merged pull requests and commit messagesPublish them
A tutorExplains, quizzes, and asks you to try first, for something you are learningHand over the answer before you have attempted it

One habit that makes any of these better (our view): when a person corrects an agent, write the lesson into its instructions or a skill, so the next run starts from it.

A possibility for the future

Our view, not a description of anything released. Teams of named agents, each with a narrow role, its own skills and a model chosen for its job, possibly from different vendors, working alongside people who set goals, approve the irreversible and own the result. A shared, reviewed record of decisions is what would let such a team learn without repeating mistakes.

The other view: more agents mean more coordination, more cost and more places for errors to compound. Anthropic’s advice is to find the simplest solution possible and add complexity only when it is needed. Start with one well-briefed agent, and add a second only when you can say what it does that the first cannot.

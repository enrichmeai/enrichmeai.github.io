Testing

What to test, at which level, and how, in Java, Python, SQL and pipelines. A test is worth having when it would fail if the code were wrong, and only then.

Levels of testing

LevelChecksSpeedTools
UnitOne function or class in isolation; logic, edge cases, errorsmsJUnit 5 + AssertJ, pytest, dbt unit tests
IntegrationYour code with a real database, queue or HTTP layersecondsTestcontainers, WireMock, @SpringBootTest, @QuarkusTest, BigQuery emulator
ContractProducer and consumer agree on an API or schemasecondsPact, Spring Cloud Contract, schema tests, dbt contracts
End to endA user journey through the deployed systemminutesPlaywright, Selenium, scripted API checks
Data testsThe data itself: keys, nulls, ranges, freshness, row countsper rundbt data tests, assertions in pipelines
Non-functionalLoad, latency, resilience, securityminutes–hoursk6, Gatling, Locust, chaos tests, ZAP

Most tests should be fast unit and integration tests; a few end-to-end tests cover the critical journeys. A suite nobody runs because it is slow protects nothing.

What makes a good test

  • Fails for the right reason: write it first, or break the code on purpose, and watch it go red. A test only ever seen green is unproven.
  • Tests behaviour, not implementation: inputs and outputs, not which private method was called. Refactors should not break it.
  • One reason to fail, with a name that says what it checks: rejectsUnparseableDate.
  • Arrange, act, assert: set up, do one thing, check the result.
  • Independent: no shared state or order between tests; unique test data per test.
  • Deterministic: fixed clock, fixed seed, no real network, no sleeps.
  • Covers the edges: empty, null, one, many, boundary values, bad input, the dependency being down.

TDD in one loop

  1. Red: write a small failing test for the next behaviour.
  2. Green: write the least code that makes it pass.
  3. Refactor: clean up with the tests as a safety net.

For a bug: first write a test that reproduces it and fails, then fix. The test stays, so the bug cannot return.

This is also the best way to brief an AI assistant: give it the failing test as the definition of done.

Java: JUnit 5 + AssertJ + Mockito

class DecisionDateParserTest {

  @ParameterizedTest(name = "{0} → {1}")
  @CsvSource({
      "05-05-1959, 1959-05-05",   // SC format
      "2024-01-31, 2024-01-31",   // HC format
  })
  void parsesBothFormats(String raw, LocalDate expected) {
    assertThat(DecisionDateParser.parse(raw)).isEqualTo(expected);
  }

  @ParameterizedTest
  @ValueSource(strings = {"", "31-31-2024", "yesterday"})
  void rejectsUnparseable(String raw) {
    assertThatThrownBy(() -> DecisionDateParser.parse(raw))
        .isInstanceOf(IllegalArgumentException.class)
        .hasMessageContaining("does not parse");
  }
}

@ExtendWith(MockitoExtension.class)
class LoaderTest {
  @Mock BlobStore store;
  @InjectMocks Loader loader;

  @Test
  void reportsUnknownWhenListingFails() {
    when(store.list(any())).thenThrow(new RuntimeException("403 Forbidden"));
    assertThat(loader.run().state()).isEqualTo(State.UNKNOWN);   // not "0 objects"
    verify(store, never()).copy(any(), any());
  }
}

import pytest
from datetime import date
from pipeline.dates import parse_decision_date

@pytest.mark.parametrize("raw, expected", [
    ("05-05-1959", date(1959, 5, 5)),
    ("2024-01-31", date(2024, 1, 31)),

Test doubles: pick the lightest

DoubleIs
DummyPassed but never used
StubReturns canned answers
FakeA working lightweight version (in-memory store)
SpyRecords how it was called
MockPre-programmed with expectations it verifies
  • Mock what you do not own only at the boundary; prefer a fake or a real container.
  • Build stubs from captured real responses, never from a guess. A stub shaped from the docs confirms the guess.
  • Too many mocks means the test checks wiring, not behaviour.

Testing data pipelines

  • Idempotency: run the same input twice; the output must be identical (row count and content).
  • Incremental vs full: an incremental run on top of yesterday equals a full rebuild.
  • Edge data: empty partition, one row, duplicates, late rows, a new source column, a malformed date.
  • Reconciliation: rows in = rows loaded + rows rejected + rows skipped, every run.
  • Run records: assert the counters written to the ledger, not only the log line.
  • "Source down": the run must end FAILED or UNKNOWN, never SUCCEEDED with zero.
  • Real dialect: a SQL string checked against a mock proves its shape, not that BigQuery accepts it. Run it on the emulator or a dry run.
# dbt
dbt build -s my_model+            # models + their tests, in order
dbt test  -s test_type:unit       # logic on fixed inputs
dbt test  -s test_type:data       # assertions on built tables

Property-based testing

Instead of hand-picked examples, state a property that must hold for all inputs and let the tool generate hundreds, shrinking any failure to the smallest case.

# Python: hypothesis
from hypothesis import given, strategies as st

@given(st.dates(min_value=date(1950,1,1), max_value=date(2030,12,31)))
def test_format_then_parse_roundtrips(d):
    assert parse_decision_date(d.strftime("%d-%m-%Y")) == d

@given(st.lists(st.text()))
def test_dedupe_is_idempotent(xs):
    assert dedupe(dedupe(xs)) == dedupe(xs)

Java: jqwik (@Property, @ForAll). Good properties: round trips, idempotency, invariants (sorted output stays sorted), and "never throws".

Load and performance tests

// k6: ramp to 60 searches/s and check p95 latency
import http from 'k6/http';
import { check } from 'k6';
export const options = {
  scenarios: { search: { executor: 'ramping-arrival-rate',
    startRate: 5, timeUnit: '1s', preAllocatedVUs: 50,
    stages: [{ target: 60, duration: '5m' }, { target: 60, duration: '10m' }] } },
  thresholds: { http_req_duration: ['p(95)<500'], http_req_failed: ['rate<0.01'] },
};
export default function () {
  const r = http.get(`${__ENV.BASE}/api/search?q=land+acquisition`);
  check(r, { '200': (x) => x.status === 200 });
}
// k6 run -e BASE=https://staging.example.com search.js
  • Test against production-sized data in a production-like environment.
  • Measure percentiles (p95, p99), not averages.
  • Find the breaking point, then decide the alert threshold below it.

Flaky tests, coverage, CI

  • Flaky test: passes and fails on the same code. Causes: time, ordering, shared state, real network, async waits. Fix or delete it; never retry it into green or quarantine it forever.
  • Coverage shows what was executed, not what was checked. 100% coverage with weak assertions proves little. Use it to find untested code, not as a target.
  • Mutation testing (PIT for Java, mutmut for Python) changes your code and checks that some test fails. It measures test strength.
  • CI runs every test on every PR, on a clean checkout. A local green and a CI red on the same commit usually mean untracked files or a different environment.
  • Never skip, disable or weaken a test to get green. If a test is wrong, fix it in its own reviewed change.

Testing AI features

  • Unit-test everything around the model: prompt building, parsing, retries, fallbacks.
  • Validate structured outputs against the schema, and the values against your data.
  • Run an eval set in CI and track the score; fail the build on a regression beyond a threshold.
  • Include adversarial cases: prompt injection in documents, empty retrieval, the model refusing.
  • Mock the model in unit tests with recorded real responses; run the eval against the real model.

Levels: what to expect

1 Foundation

  • Write unit tests with clear arrange-act-assert
  • Run the suite locally and read CI failures
  • Reproduce a bug with a failing test before fixing it

2 Practitioner

  • Use Testcontainers and WireMock for integration tests
  • Test edge cases, errors and dependency failures
  • Keep tests fast, independent and deterministic

3 Senior

  • Design a test strategy across unit, integration, contract and end to end
  • Add property-based, load and mutation testing where they pay off
  • Eliminate flaky tests and slow suites

4 Expert

  • Set testing standards and quality gates for the organisation
  • Build test infrastructure: environments, data, emulators
  • Measure test effectiveness, not just coverage

Each level includes the ones before it. See Start here for what the levels mean.

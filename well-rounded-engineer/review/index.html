Guide / Quality / Writing & Code Review

Writing and code review

Much of an engineer’s work reaches other people as writing: a commit message, a pull request description, a design proposal, a decision record, a page of documentation, a review comment. This page covers what each kind of writing is for, conventions that many projects use, and what published guidance and research say about code review. Specifications are on Specifications; design documents for whole systems are on System Design; AI review tools are on GitHub Copilot; reviewing a change for its effect on the whole system is on Quality Attributes.

The short answer

Our view: write so that someone who was not in the room can understand what changed and why, months later. Treat code review as a way to keep the code base healthy and to share knowledge, not only to catch bugs. The other view is in the card “Our view, and the other view”.

Writing that gets read

Bottom line up front (BLUF) means starting a message with its key information, so the reader gets the most important part first. It is a standard in U.S. military communication and resembles the inverted pyramid in journalism: conclusions come before the material that supports them.

Plain language is writing designed so the reader understands it as quickly, easily and completely as possible, avoiding verbose, convoluted language and jargon. Many countries require public agencies to use it.

Analysis: both ideas suit engineering writing, where most readers are busy and arrive looking for one answer.

Commit messages

Git’s own documentation suggests, though it does not require, starting a commit message with one short summary line of no more than 50 characters, then a blank line, then a fuller description. Git treats the text up to the first blank line as the commit’s title and uses it throughout, for example as the subject of a patch sent by email.

Conventional Commits is a lightweight convention on top of that: each message starts with a type, such as fix: (a bug fix, a semantic-versioning patch) or feat: (a new feature, a minor version), and a breaking change is marked with ! or a BREAKING CHANGE: footer, which makes it easier to build tools on the history.

What code review is for

Code review is a quality activity in which people other than the author examine source code. Its goals include finding defects, but also sharing knowledge of the code base and its expectations with both reviewers and author. Michael Fagan described the first studied process, inspection, in the IBM Systems Journal in 1976.

Research cited on Wikipedia’s page found that up to 75% of review comments concern evolvability and maintainability rather than functionality, and fewer than 15% of the issues discussed relate directly to bugs. For defects, Capers Jones’s analysis of over 12,000 projects found formal inspections discovered 60–65% of latent defects, informal ones fewer than half, and most testing about 30%; another case study found lightweight reviews could find as many bugs as formal ones, faster.

The standard Google’s guide sets

Google’s published code review guide says the primary purpose of review is to make sure the overall health of the code base improves over time. Its senior principle: reviewers should favour approving a change once it definitely improves the overall code health, even if it is not perfect. “There is no such thing as ‘perfect’ code—there is only better code.”

The guide also sets expectations on size and speed. About 100 lines is usually a reasonable size for a change and 1,000 usually too large, though it gives no hard rule; one business day is the maximum time it should take to respond to a review request.

Research cited on Wikipedia puts optimal review rates at 200 to 400 lines of code an hour; faster than a few hundred lines an hour may be too fast to find errors in critical software.

Review comments

Google’s guide on writing review comments asks reviewers to be kind, to explain their reasoning, and to comment on the code rather than the developer. Its example:

  • Less helpful: “Why did you use threads here when there’s obviously no benefit to be gained from concurrency?”
  • More helpful: “The concurrency model here is adding complexity to the system without any actual performance benefit that I can see. Because there’s no performance benefit, it’s best for this code to be single-threaded instead of using multiple threads.”

It suggests labelling how much a comment matters, so the author can tell a required change from a suggestion: Nit: (minor polish), Optional or Consider: (a good idea, not required), FYI: (something to think about later). It also says to comment on what is good in a change, not only what could be better, and that fixing the change is the author’s responsibility, though direct suggestions sometimes help more.

Changes take days to be reviewedSmaller changes and an agreed response time, as in Google’s guide

Your team already has writing and review conventions that workKeep them, and write them down: changing conventions has a cost

Our view, and the other view

Our view: clear writing and timely review are part of the engineering work, not overhead around it. A change that nobody else can understand is not finished.

The other view: review after the code is written adds waiting, and much of its value is in comments about style that tools could check; some teams prefer to put effort into automated checks, pairing while the code is written, or reviewing after merge, and keep pre-merge review for risky changes.

Levels: what to expect

1 Foundation

  • Write a commit message with a short summary line and a reason
  • Describe a pull request so a reviewer knows what and why
  • Read review comments as being about the code, not you

2 Practitioner

  • Review others' changes within a day, labelling comments by importance
  • Keep changes small enough to review well
  • Write an architecture decision record

3 Senior

  • Write a design proposal others can build from
  • Set a team's review and writing conventions
  • Place documentation in the right one of four kinds

4 Expert

  • Shape how an organisation records decisions
  • Balance review effort against automated checks
  • Mentor others through review

Each level includes the ones before it. See Start here for what the levels mean.

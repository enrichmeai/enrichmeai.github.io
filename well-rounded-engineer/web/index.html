Web fundamentals

How the web works from a typed URL to a rendered page: URLs, HTTP, cookies and sessions, origins and CORS, caching, rendering models, web security, performance and accessibility. Lower layers are on Networking; API design is on APIs & Integration.

What happens when you open a URL

  1. Parse the URL and check the browser cache, including a cached HSTS rule that forces HTTPS.
  2. DNS resolves the host name to an IP address (browser cache → OS → resolver → authoritative servers).
  3. Connect: TCP handshake (or QUIC over UDP for HTTP/3), then the TLS handshake proves the server's identity and agrees keys.
  4. HTTP request with method, path, headers and cookies, usually reaching a CDN or load balancer first.
  5. Server side: load balancer → reverse proxy → application → database or cache → response.
  6. HTTP response: status, headers (caching, cookies, security), and the body (HTML, JSON, images).
  7. Render: parse HTML into the DOM, CSS into the CSSOM, run JavaScript, lay out, paint, and fetch the sub-resources the page references.
  8. After load: JavaScript calls APIs (fetch), updates the page, and may open WebSockets or server-sent events.

Every step can fail or be slow. Browser DevTools (Network tab: timing, headers, initiator) shows which.

Anatomy of a URL

https://legal.example.com:443/v1/judgments/123?court=2_5&page=2#para-14
└─┬─┘   └──────┬────────┘└┬┘└──────┬───────┘└───────┬───────┘└──┬──┘
scheme        host      port     path            query       fragment
  • Origin = scheme + host + port. It is the browser's security boundary.
  • Path names the resource; query parameters filter or modify it.
  • Fragment (#…) never reaches the server; the browser uses it to scroll or route.
  • Encoding: special characters are percent-encoded (space → %20, + in a query can mean a space). Encode parameters with a library, not by hand.

  • Content negotiation: Accept / Content-Type for format, Accept-Language for language, Accept-Encoding for compression.
  • Compression: Brotli or gzip for text; never for already-compressed images or video.
  • MIME types tell the browser what it received; a wrong one breaks scripts or opens security holes.

Cookies, sessions and tokens

  • HTTP is stateless. State across requests comes from cookies or tokens the client sends each time.
  • Cookie: set by Set-Cookie, sent back automatically to the same site. Flags that matter: Secure (HTTPS only), HttpOnly (JavaScript cannot read it), SameSite=Lax|Strict|None (whether it goes on cross-site requests), Domain, Path, Max-Age.
  • Server session: the cookie holds a random ID; data lives on the server (or Redis). Easy to revoke.
  • Token (JWT): the client sends Authorization: Bearer …; the server validates it without a lookup. Harder to revoke; keep it short-lived. See OAuth & OIDC.
  • Browser storage: localStorage and sessionStorage are readable by any script on the page, so never keep secrets there; IndexedDB for larger client data.

Same-origin policy and CORS

  • By default, a script on https://app.example.com cannot read responses from another origin such as https://api.example.com.
  • CORS lets the API opt in with response headers: Access-Control-Allow-Origin: https://app.example.com.
  • Preflight: for non-simple requests (custom headers, JSON bodies, PUT/DELETE) the browser first sends OPTIONS and checks Access-Control-Allow-Methods and -Headers.
  • Credentials (cookies) cross-origin need Access-Control-Allow-Credentials: true and an exact origin, never *.
  • CORS protects users in browsers; it is not server-side access control. curl ignores it.
  • Serving the app and API from the same origin (e.g. /api on the same host) avoids CORS entirely.

Layers: browser cache → CDN → reverse proxy → application cache → database. Fingerprint static files so you can cache them forever and still deploy changes instantly.

How the browser renders

  1. HTML parsed into the DOM; CSS into the CSSOM.
  2. Combined into a render tree; layout computes sizes and positions; paint draws pixels; composite layers them.
  3. Render-blocking resources (CSS, synchronous scripts in <head>) delay the first paint. Use defer or type="module" for scripts.
  4. JavaScript runs on one main thread; long tasks block input. Move heavy work to Web Workers.

  • Serve from a CDN; compress; cache fingerprinted assets.
  • Send less JavaScript; split bundles by route; lazy-load below-the-fold images.
  • Size images correctly; use modern formats (WebP, AVIF) and give width and height to avoid shifts.
  • Measure with Lighthouse in the lab and real-user data in the field.

Web security essentials

  • HTTPS everywhere plus HSTS, so browsers never fall back to HTTP.
  • XSS (cross-site scripting): untrusted data rendered as HTML runs as script. Escape output (frameworks do it by default), avoid innerHTML with user data, and add a Content-Security-Policy.
  • CSRF: another site makes the user's browser send a cookie-authenticated request. Use SameSite cookies and CSRF tokens for cookie-based sessions.
  • Clickjacking: your page framed invisibly. Use frame-ancestors in CSP.
  • Mixed content: HTTP resources on an HTTPS page are blocked or warned.
  • Subresource Integrity (integrity=) for scripts from CDNs.
  • More on the Security tab.

Accessibility basics

  • Semantic HTML first: <button>, <nav>, <main>, headings in order, <label> for every input.
  • Keyboard: everything usable with Tab, Enter and Space; visible focus outlines.
  • Text alternatives: alt on meaningful images; empty alt="" on decorative ones.
  • Contrast: at least 4.5:1 for normal text (WCAG AA).
  • ARIA only when HTML has no native element for the job.
  • Test with a screen reader and automated checks (axe, Lighthouse); they catch different things.

Servers on the web

  • Web server / reverse proxy (nginx, Envoy): TLS, static files, compression, routing to apps.
  • Application server: runs your code (Spring Boot with Tomcat or Netty, Quarkus with Vert.x, gunicorn or uvicorn for Python).
  • CDN: caches content near users and absorbs traffic spikes and attacks.
  • Real-time: WebSockets (two-way) and server-sent events (server to browser, simpler, works over HTTP).
  • HTTP versions: HTTP/1.1 (one request at a time per connection), HTTP/2 (multiplexed streams), HTTP/3 (over QUIC, better on lossy networks).

DevTools habits

  • Network: status, timing waterfall, request and response headers, "Disable cache", throttling, "Copy as cURL".
  • Console: JavaScript errors and CORS failures, which say exactly which header is missing.
  • Application: cookies with their flags, storage, service workers.
  • Performance and Lighthouse: long tasks, layout shifts, Core Web Vitals.
  • Elements: live DOM and CSS, accessibility tree.

Levels: what to expect

1 Foundation

  • Explain what happens from typing a URL to seeing a page
  • Read requests, responses, headers and status codes in DevTools
  • Know what cookies, sessions and CORS are

2 Practitioner

  • Set caching, cookie and security headers correctly
  • Debug CORS, redirects, mixed content and caching problems
  • Choose a rendering model for a feature

3 Senior

  • Design front-end delivery: CDN, caching, rendering, performance budgets
  • Lead web security (CSP, session design) and accessibility for a product
  • Diagnose Core Web Vitals problems with field data

4 Expert

  • Set web platform standards across products
  • Know the HTTP, TLS and browser specs in depth
  • Lead large front-end architecture and performance programmes

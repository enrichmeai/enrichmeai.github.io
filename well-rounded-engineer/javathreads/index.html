How Java threads evolved

Thirty years of answering one question: how does a server wait for thousands of slow things at once without running out of threads? From raw threads to pools, fork/join, futures, reactive streams and virtual threads, with a code example and the cost of each step.

The short answer

Most server code spends its life waiting: for a database row, an HTTP reply, a file. The CPU is idle while it waits. Our view: every change to how Java handles threads has been about one thing, making that waiting cheap. The other view is in the card “Our view, and the other view”. The page Java has the same history as a one-table summary; this page tells it step by step, with what each step cost.

Thirty years in one line

1. Raw threads

Java 1.0 · 1996

Java shipped with threads in the platform from the start: Thread, Runnable, the synchronized keyword, and wait/notify on every object. Concurrency was part of the language and its core library, not an add-on.

Thread t = new Thread(new Runnable() {
    public void run() { handle(request); }
});
t.start();

Early JVMs used green threads, scheduled by the JVM itself. They were abandoned in Java 1.3 for native threads: each Java thread became a real operating-system thread.

The cost: an OS thread reserves a large stack (by default 1 MB on 64-bit x86 Linux, 2 MB on ARM64 Linux) and is expensive to create and switch. A server could hold a few thousand threads, not hundreds of thousands.

2. Thread pools and java.util.concurrent

Java 5 · 2004

java.util.concurrent (JSR 166, led by Doug Lea) changed everyday Java. Instead of creating a thread per task, you hand tasks to an executor that reuses a fixed pool. It came with Future and Callable, explicit locks, atomic variables, ConcurrentHashMap, and coordination tools such as CountDownLatch. The same release brought a new Java Memory Model (JSR 133), so these tools had firm guarantees underneath.

ExecutorService pool = Executors.newFixedThreadPool(200);
Future<Case> f = pool.submit(() -> repository.find(id));   // shown in today's syntax
Case c = f.get();   // blocks this thread until the result is ready

This became the classic server model behind Servlets and Spring MVC: one pooled thread per request, blocking while it waits.

The cost: the pool size is the ceiling. With 200 threads all waiting on a slow database, request 201 queues, even though the CPU is idle.

3. Fork/join

Java 7 · 2011

ForkJoinPool tackled a different problem: big CPU-bound jobs. A task splits itself into smaller tasks, and idle threads steal work from busy ones' queues. It made multi-core machines easy to use for computation. It did nothing for waiting on I/O.

4. Futures you can chain

Java 8 · 2014

CompletableFuture, together with lambdas, let you describe what happens after a result arrives instead of blocking a thread to wait for it:

CompletableFuture.supplyAsync(() -> fetchCase(id))
    .thenApply(this::summarise)
    .thenAccept(this::send);

No thread sits idle between the steps. Each step runs when the previous one completes.

The cost: error handling, timeouts and debugging get harder. A stack trace no longer shows the story of the request.

5. Reactive

Reactive Streams 1.0, 2015 · Java 9 Flow, 2017 · Spring WebFlux, 2017

Underneath, non-blocking networking had existed since NIO in Java 1.4 (2002): one thread with a Selector can watch many sockets. Netty built an asynchronous, event-driven framework on it: a handful of threads that never block, serving very many connections.

Reactive libraries made that model programmable. An early, widely used one was RxJava, Netflix’s JVM implementation of Microsoft’s Reactive Extensions, first published around 2013. It introduced many Java developers to Observable and to operators such as map, flatMap, zip and retry. RxJava 2 (October 2016) was rewritten on the Reactive Streams specification (1.0 in spring 2015), which grew out of RxJava 1.x and was started by engineers at Netflix, Pivotal and Lightbend. Project Reactor, the library under Spring WebFlux, follows the same specification. These libraries describe work as streams of events with backpressure, so a slow consumer can tell a fast producer to slow down. Java 9 put the same interfaces into the JDK as java.util.concurrent.Flow. Spring Framework 5.0 (2017) added WebFlux; Spring Boot’s WebFlux starter runs it on Netty by default.

webClient.get().uri("/cases/{id}", id)
    .retrieve()
    .bodyToMono(Case.class)
    .map(this::summarise)
    .timeout(Duration.ofSeconds(5));

The cost: every layer has to be non-blocking, down to the database driver (hence R2DBC instead of JDBC). One blocking call on an event-loop thread stalls everyone, and the code reads as chains of operators instead of plain steps.

6. Virtual threads

Preview in Java 19 and 20 · final in Java 21 · 2023

Project Loom asked a different question: what if threads were simply cheap? A virtual thread is managed by the JVM, not the operating system. When it blocks on I/O, the JVM suspends it and frees the underlying OS thread (the “carrier”) for another virtual thread. You can run millions of them.

try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> handle(request));   // plain blocking code, one cheap thread per task
}
Thread.ofVirtual().start(() -> handle(request));

The plain, blocking style from 2004 is back, and it scales the way reactive code does. Spring Boot 3.2 turned it into a single setting, spring.threads.virtual.enabled=true, on Java 21 or later.

The first versions had one notable trap. A virtual thread blocking inside a synchronized block was pinned to its carrier, which could starve the pool. Java 24 (JEP 491) removed nearly all of that pinning for synchronized.

7. What is arriving now

Java 25 (2025) to Java 27

Scoped values are final in Java 25 (JEP 506): a safer, cheaper replacement for many uses of ThreadLocal that suits millions of short-lived threads. Structured concurrency has been in preview since Java 21 and was previewed again in each release since: the seventh preview is in Java 27 (JEP 533). It treats a group of subtasks as one unit: start them together, and if one fails, cancel the rest and report one error. It addresses the error-handling problem that futures and reactive code never solved neatly.

Was Quarkus reactive by nature?

Underneath, yes. Quarkus (1.0 in November 2019) runs on Vert.x and Netty, an event-loop engine like the one under WebFlux. But today it does not force reactive code on its users. You can write:

  • ordinary blocking code, which Quarkus runs on worker threads, off the event loop;
  • reactive code with its Mutiny library;
  • and, on Java 21 or later, virtual-thread endpoints, marked @RunOnVirtualThread.

Spring offers the same three: blocking MVC, reactive WebFlux, and MVC on virtual threads. More on Quarkus and Spring.

Our view, and the other view

Our view: the thread did not get faster in thirty years. Each step made it cheaper to keep a thread waiting, until it cost almost nothing, so for most request/response services virtual threads with plain blocking code are now the simplest choice that scales.

The other view: reactive code is more than a workaround for expensive threads. Backpressure, streaming and composing many events are first-class in it, and teams that need those may find a reactive stack the clearer model, with virtual threads adding little.

Which model to use today

Virtual threadsMost request/response services that wait on databases and APIs. Simple code that scales.Very long CPU work still needs a bounded pool. Libraries that hold locks or ThreadLocal caches deserve a check.

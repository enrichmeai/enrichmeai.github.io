Guide / Languages / Front-end Toolchain

The front-end toolchain: TypeScript, Babel, bundlers, React Native, Redux

A modern front end can mean TypeScript, JSX, a transpiler, a bundler, a framework, a state library and a mobile layer, each with its own configuration. Each layer was added to solve a problem its authors had (the table below says which). Our view: together they can make a small app hard to start and hard to keep up to date. This page explains what each layer does, why it appeared, and when you can leave it out. The language itself is on JavaScript; native versus cross-platform apps are on Apps.

The short answer

Our view: add a layer only when you can name the problem it solves for you. The other view: a team that adopts TypeScript, a bundler and a state library together, from a template, has one documented path from day one and does not have to retrofit types or a build later. Which suits you depends on the requirements in the table below.

From source code to the browser

Each layer, and why it exists

LayerWhat it doesDate or note
TypeScript (Microsoft)Adds static typing with optional type annotations to JavaScript, designed for large applications; it transpiles to JavaScriptReleased to the public in October 2012
JSXAn XML-like syntax for describing UI inside JavaScript, created by Facebook for React. It is syntactic sugar, transpiled into nested function calls; with TypeScript the files end in .tsxWith React
BabelA transpiler that turns newer JavaScript (ES2015 and later) into code older engines can run, and also transforms JSX and TypeScript16 million core downloads a week in 2019
Module bundler (webpack, esbuild, Vite)Follows the imports from an entry point, builds a dependency graph, and combines the modules into a few bundles, often minifying and removing unused codeesbuild, written in Go, claimed to be 10 to 100 times faster than other bundlers when it was released
ViteA development server, written by Vue’s creator Evan You, that reloads just the edited file using native ES modules, and bundles for productionSupports TypeScript and JSX; no date in our sources
React (Meta)A library for building UIs from componentsOpen-sourced at JSConf US in May 2013
React Native (Meta)Uses React with native platform capabilities to build apps for Android, iOS and other platformsIntroduced in 2015
ReduxA library for managing and centralising application state, inspired by Facebook’s Flux and the Elm Architecture; created by Dan Abramov and Andrew Clark2015

Does your app need Redux?

Redux’s own documentation says it is “not designed to be the shortest or fastest way to write code”, and that React’s built-in state system “might be all you need”. It quotes Pete Hunt, an early React contributor, on Flux, the pattern Redux grew out of: “You’ll know when you need Flux. If you aren’t sure if you need it, you don’t need it.” The docs list where it helps most:

  • a lot of application state needed in many places
  • state that is updated often
  • update logic that may be complex
  • a medium or large codebase that many people work on
  • a need to see how state changed over time

React’s own documentation shows another way to share state: combining a reducer with context, built into React.

Layers you can sometimes leave out

  • Browsers run modules natively: JavaScript modules load with import in the browser, and an import map can tell it where bare module names live, without a bundler.
  • Node.js runs TypeScript files directly by stripping the types, for code that uses only “erasable” TypeScript syntax: enabled by default from Node.js 23.6 and 22.18, and marked stable in 25.2 and 24.12. For full TypeScript features, its docs point to a third-party tool such as tsx.
  • Types as comments in JavaScript itself is a TC39 proposal at Stage 1 (per its repository page, which says it is not updated regularly): an idea under discussion, not part of the language.
// greet.ts
type User = { name: string; visits: number };

function greet(user: User): string {
  return `Hello ${user.name}, visit number ${user.visits}`;
}

console.log(greet({ name: "Ana", visits: 3 }));

$ node greet.ts
Hello Ana, visit number 3

Run as shown with Node.js 22.23 and no build step; the second block is its real output.

Choose by requirement

If this is true for youIt leans towards (analysis)
A small page or tool, few dependencies, one maintainerPlain JavaScript modules in the browser, perhaps with an import map: no build step
Code that several people maintain for yearsTypeScript, type-checked in CI
Many npm dependencies, or you must support older browsersA bundler and transpiler, usually through one tool such as Vite
Shared state that many screens read and change, with complex updatesA state library such as Redux; otherwise React’s own reducer and context
The same team must ship iOS and Android, and it already knows ReactReact Native (see Apps for the native alternative)
Your team already runs a working toolchainUpgrade it in place rather than switching tools: switching has a cost

Our view, and the other view

Our view: much of the difficulty comes from adopting the whole stack on day one. Starting small and adding a layer when a real problem appears keeps a front end easier to understand and to upgrade.

The other view: a framework or starter template that includes the whole stack gives a team one well-trodden path, with documentation and many people who already know it, and avoids reassembling the pieces later when the app grows.

Levels: what to expect

1 Foundation

  • Say what TypeScript, JSX, a transpiler and a bundler each do
  • Run a TypeScript file and a plain ES module
  • Read a package.json and its build scripts

2 Practitioner

  • Set up TypeScript type-checking in CI
  • Decide whether an app needs a state library
  • Upgrade a toolchain dependency safely

3 Senior

  • Choose which layers a project needs, by requirement
  • Remove a layer that no longer earns its place
  • Plan a web and React Native codebase

4 Expert

  • Set an organisation's front-end platform and upgrade policy
  • Weigh frameworks against a smaller custom stack
  • Keep build complexity in check across teams

Each level includes the ones before it. See Start here for what the levels mean.

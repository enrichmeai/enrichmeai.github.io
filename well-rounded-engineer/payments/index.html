Payment gateways

How online payments work, the parties and flows (cards, UPI, subscriptions), how to integrate a gateway such as Razorpay or Stripe safely, and the engineering that keeps money correct: idempotency, webhooks, state machines, ledgers and reconciliation.

Who is involved

PartyRole
CustomerPays with a card, UPI, net banking or wallet
MerchantYou: the business being paid
Payment gateway / aggregatorCollects payment details securely, routes the transaction, gives you APIs, checkout and webhooks (Razorpay, Stripe, PayU, Cashfree)
AcquirerThe merchant's bank, which receives the funds
Card networkVisa, Mastercard, RuPay: routes card transactions between banks
IssuerThe customer's bank, which approves or declines
UPI (NPCI)India's real-time account-to-account network; apps such as PhonePe, Google Pay, Paytm act as front ends
RegulatorIn India the RBI: rules on recurring payments, tokenisation, data storage and aggregators

Card payment lifecycle

  1. Authorise: the issuer checks funds and fraud and places a hold. With 3-D Secure (OTP or app approval) the customer authenticates.
  2. Capture: the merchant confirms the charge (automatically or later, e.g. after shipping). An uncaptured authorisation expires.
  3. Settle: funds move to the gateway, then to your bank account, usually T+1 or T+2, minus fees.
  4. Refund: full or partial, returned through the same route; takes days to reach the customer.
  5. Chargeback / dispute: the customer disputes with their bank; you submit evidence or lose the funds plus a fee.

UPI in brief

  • Intent / QR flow: your checkout opens the customer's UPI app (or shows a QR); they approve with their UPI PIN.
  • Collect flow: you send a payment request to a UPI ID; the customer approves in their app. (Being phased down for many use cases; check current NPCI rules.)
  • Real-time and irrevocable from the customer's side; refunds are separate transactions.
  • UPI AutoPay: recurring mandates the customer approves once, for subscriptions.
  • Pending is normal: a payment can sit in a pending state for minutes; your system must wait for the final status rather than assume failure.

Standard integration flow (server-verified)

  1. Create an order on your server with the amount in the smallest unit (paise) and your own receipt ID. Store it as CREATED.
  2. Open the gateway's checkout in the browser or app with that order ID. Card and UPI details go to the gateway, never to your servers.
  3. Checkout returns payment ID, order ID and a signature to your client, which sends them to your server.
  4. Verify the signature on the server and fetch the payment from the gateway API to confirm amount, currency and status.
  5. Webhooks (payment.captured, payment.failed, refunds, disputes) arrive at your endpoint; verify their signature and update state idempotently. Treat webhooks and API fetches as the source of truth, never the browser.
  6. Fulfil only when your order is PAID according to the server.
  7. Reconcile daily against the gateway's settlement reports.

Razorpay: order and verification

# create an order (amount in paise: 50000 = ₹500.00)
curl -u "$RZP_KEY_ID:$RZP_KEY_SECRET" \
  -X POST https://api.razorpay.com/v1/orders \
  -H "Content-Type: application/json" \
  -d '{"amount":50000,"currency":"INR","receipt":"order_8421"}'
// verify checkout signature: HMAC-SHA256(order_id + "|" + payment_id, key_secret)
static boolean validCheckout(String orderId, String paymentId, String signature, String keySecret)
    throws Exception {
  Mac mac = Mac.getInstance("HmacSHA256");
  mac.init(new SecretKeySpec(keySecret.getBytes(UTF_8), "HmacSHA256"));
  String expected = HexFormat.of().formatHex(
      mac.doFinal((orderId + "|" + paymentId).getBytes(UTF_8)));
  return MessageDigest.isEqual(expected.getBytes(UTF_8), signature.getBytes(UTF_8)); // constant time
}

// webhook: HMAC-SHA256 of the RAW request body with the webhook secret,
// compared with the X-Razorpay-Signature header. Never re-serialise the JSON first.

Stripe: PaymentIntent and webhook

import stripe
stripe.api_key = STRIPE_SECRET_KEY

intent = stripe.PaymentIntent.create(
    amount=50000, currency="inr",
    metadata={"order_id": "order_8421"},
    idempotency_key="order_8421-create",         # safe to retry
)
# return intent.client_secret to the front end, which confirms the payment

# webhook endpoint
def stripe_webhook(request):
    payload = request.body                        # raw bytes
    sig = request.headers["Stripe-Signature"]
    try:
        event = stripe.Webhook.construct_event(payload, sig, WEBHOOK_SECRET)
    except (ValueError, stripe.SignatureVerificationError):   # older SDKs: stripe.error.SignatureVerificationError
        return 400
    if not seen_before(event["id"]):              # dedupe: webhooks repeat
        handle(event)
    return 200

Payment state machine

CREATED ──checkout──▶ PENDING ──captured──▶ PAID ──refund──▶ PARTIALLY_REFUNDED / REFUNDED
   │                     │                    │
   │                     ├──failed──▶ FAILED  └──dispute──▶ DISPUTED ──▶ WON / LOST
   └──expired──▶ EXPIRED └──timeout──▶ (stay PENDING; poll the gateway; never assume)
  • Allow only valid transitions; reject or log anything else.
  • Events can arrive late or out of order (a webhook before the browser callback, a failure after a success for a different attempt). Decide by the gateway's fetched status.
  • Keep every transition as an append-only event with its source (webhook, API fetch, user).

Money-handling rules

  • Integers in the smallest unit (paise, cents) or decimal types; never floats.
  • Store the currency with every amount.
  • Compute prices and totals on the server. Never trust an amount sent by the client.
  • Idempotency keys on every create, capture and refund call, derived from your own IDs, so a retry cannot charge twice.
  • Webhook handlers are idempotent: dedupe by event ID; applying the same event twice changes nothing.
  • Unknown is not failed: a timeout means "we do not know yet". Poll the gateway before telling the customer it failed or retrying the charge.
  • Round once, at a defined step, with a documented rule (taxes, discounts, splits).

Double-entry ledger

CREATE TABLE ledger_entry (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  txn_id       uuid    NOT NULL,          -- groups the entries of one transaction
  account      text    NOT NULL,          -- 'customer_receivable', 'gateway_clearing', 'revenue', 'gst_payable'
  amount_paise bigint  NOT NULL,          -- positive = debit, negative = credit
  currency     char(3) NOT NULL,
  created_at   timestamptz NOT NULL DEFAULT now()
);
-- every txn_id must sum to zero
SELECT txn_id FROM ledger_entry GROUP BY txn_id HAVING SUM(amount_paise) <> 0;  -- must return nothing

Append only: corrections are new entries, never edits. Balances are sums. This makes every rupee traceable and reconciliation possible.

Subscriptions and recurring payments

  • Gateways model plans (price, interval) and subscriptions (a customer on a plan) with a mandate or saved token for charging.
  • India: RBI e-mandate rules govern recurring card and UPI payments: customer registration with authentication, pre-debit notifications, and extra authentication above a limit. Check the current limits and rules; they have changed over time.
  • Handle the lifecycle via webhooks: activated, charged, payment failed, halted, cancelled, completed.
  • Dunning: retries on failed renewals, customer notices, grace periods, then downgrade or cancel.
  • Entitlements (what the user may use) are derived from subscription state in your system, updated only from verified events.
  • Proration rules for upgrades and downgrades mid-period, decided and written down.

Security and compliance

  • PCI DSS: use hosted checkout or the gateway's elements so card data never reaches your servers; your compliance scope stays small.
  • Card tokenisation (India): merchants may not store card numbers; saved cards use network or issuer tokens through the gateway.
  • Data localisation: RBI requires payment system data to be stored in India; confirm your gateway and your own storage comply.
  • Secrets: API keys and webhook secrets in a secret manager; separate test and live keys; rotate on staff changes.
  • Webhook endpoint: verify signatures on the raw body, reject old timestamps where provided, respond quickly, process asynchronously.
  • Fraud: use the gateway's risk tools, 3-D Secure, velocity limits, and watch for card testing (many small failed attempts).
  • Tax and invoices: GST-compliant invoices with the correct rates and place of supply.

Reconciliation

  1. Download settlement and transaction reports from the gateway daily (API or dashboard).
  2. Match each gateway transaction to your order by order ID and amount.
  3. Match settlements to bank credits, accounting for fees and taxes.
  4. Flag mismatches: paid at gateway but not in your system (missed webhook), paid in your system but not settled, amount differences, unexpected refunds or disputes.
  5. Resolve each one and record why. A rising mismatch count is an incident.

Run reconciliation as a scheduled job with run records, like any pipeline.

Testing payments

  • Use the gateway's test mode keys, test cards and test UPI IDs for success, failure, 3-D Secure and pending cases.
  • Replay recorded webhook payloads in automated tests; build fixtures from real test-mode events, not guesses.
  • Test duplicates, out-of-order events, timeouts and partial refunds explicitly.
  • Keep a test-mode end-to-end checkout in your release checks.
  • Never test with live keys or real cards in non-production environments.

Operating payments

  • Metrics: payment success rate by method and bank, latency, webhook delay, pending count and age, refund rate, dispute rate.
  • Alerts: success rate drops, webhooks stop arriving, pending payments older than a threshold, reconciliation mismatches.
  • Support tools: look up an order's full event history; never let support edit payment state by hand.
  • Multiple gateways: routing or failover between gateways improves success rates, at the cost of more reconciliation.

Levels: what to expect

1 Foundation

  • Explain authorisation, capture, settlement, refunds and chargebacks
  • Explain the order → checkout → verify → webhook flow
  • Know why card data must never touch your servers

2 Practitioner

  • Integrate a gateway with server-side verification and signed webhooks
  • Make payment calls and webhook handling idempotent
  • Model payments as a state machine; test with test-mode fixtures

3 Senior

  • Design subscriptions, dunning and entitlements
  • Build a double-entry ledger and daily reconciliation
  • Own payment security, PCI scope and regulatory rules (RBI)

4 Expert

  • Design multi-gateway routing and payment platforms
  • Lead payments compliance and audits
  • Set money-handling standards across the organisation

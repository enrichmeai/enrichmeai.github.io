Specifications: the documents everything is built on

Every protocol, file format and language in this guide is defined by a specification somewhere. Libraries and tutorials are other people’s readings of it. When two systems disagree, or a library behaves oddly, the specification is where the argument ends. This page gathers the ones engineers meet most often, says who publishes each, and shows how to read them.

How to read a specification

  • Learn the key words. RFC 2119 defines them: MUST (or REQUIRED, SHALL) is an absolute requirement; SHOULD (or RECOMMENDED) means there may be valid reasons to do otherwise, but the full implications must be understood and weighed first; MAY (or OPTIONAL) is truly optional.
  • Capitals matter. RFC 8174 clarifies that the words carry that meaning only when they appear in capitals. A lower-case “should” is ordinary English.
  • Normative and informative. Requirements are normative; examples, notes and appendices marked informative explain but do not bind.
  • Check the status and what replaced it. An RFC’s header lists what it obsoletes and updates: RFC 9110 (HTTP Semantics) obsoletes RFCs 7231, 7232, 7233, 7235 and several others, and portions of RFC 7230. Quote the current one.
  • Read the table of contents first, then only the sections your question needs. Few people read a spec front to back the first time.

Why it is worth the effort

Our view: reading the specification for the two or three formats you use every day pays back many times. You stop arguing from blog posts, you can tell a library bug from your own, and you can write a precise bug report: quoting the section of RFC 9110 on 404 Not Found settles a review in one line.

The other view: specifications are long, formal and written for implementers. For most daily work a good library and its documentation are enough, and time spent on the spec is time not spent shipping. Go to the spec when the library and your expectation disagree.

The catalogue: languages

  • ECMA-262, the ECMAScript Language Specification, edited in public by TC39; proposals are tracked in its proposals repository (see JavaScript).

Describing an interface: choose by requirement

If this is true for youIt leans towards
Clients call you with HTTP requests and wait for a responseOpenAPI
Services publish and consume messages on a brokerAsyncAPI, with CloudEvents for the envelope
Clients need to choose the fields they get, across related dataGraphQL’s schema
Typed calls between your own services, with streaming and generated clientsProtocol Buffers with gRPC
You only need to validate a JSON document, such as a config file or a message bodyJSON Schema
An AI agent must discover and call your toolsMCP

Our view: write the description first and generate code from it, so the document is the contract. The other view: generating the description from code keeps it from drifting from what runs, and suits teams that change the API often.

Levels: what to expect

1 Foundation

  • Read MUST, SHOULD and MAY as RFC 2119 and RFC 8174 define them
  • Find the specification behind a format or protocol you use every day
  • Tell an RFC that is a standard from one that is informational

2 Practitioner

  • Settle a disagreement by quoting the section of a spec
  • Describe an API in OpenAPI, AsyncAPI, GraphQL or Protobuf
  • Check which RFCs a document obsoletes before you cite it

3 Senior

  • Choose an interface description by requirement
  • Write a specification other teams can build from
  • Track proposals that will change your stack (JEPs, PEPs, TC39 stages)

4 Expert

  • Represent your organisation in a standards body or working group
  • Set the interface and versioning standards across an organisation
  • Contribute to a specification or its conformance tests

Each level includes the ones before it. See Start here for what the levels mean.

From a task to a live agent: train, validate, go live

The path for one agent doing one job: defining the task, building the simplest version, writing the evals before improving it, when “training” means prompting and when it means fine-tuning, validating it, and releasing it through a canary with a gate that can say no. With a release gate you can run.

The short answer

Pick one task and say how you will measure success. Build the simplest agent that could do it. Before improving it, write an eval set from real examples, so every change can be measured. Improve it mostly through instructions, context and tools; fine-tune only when evals show prompting has run out. Then release it like any risky change: an offline gate, a canary on a small share of traffic, and a rollback ready. In production, every failure becomes a new eval task.

For the wider system (guardrails, inference, observability, where people step in) see Building an Agentic System.

1. One task, one measure

Anthropic’s documentation starts here: “Building a successful LLM-based application starts with clearly defining your success criteria”. Good criteria are specific (“accurate sentiment classification”, not “good performance”) and measurable; even safety can be a number, such as less than 0.1% of outputs out of 10,000 trials flagged for toxicity by a content filter.

Our view: a task like “answer order questions and offer a refund within policy” is a good size; “handle customer service” is not.

Source: Claude docs: Define success criteria and build evaluations.

2. Build the simplest thing

“We recommend finding the simplest solution possible, and only increasing complexity when needed,” writes Anthropic. For many applications, it adds, “optimizing single LLM calls with retrieval and in-context examples is usually enough”, rather than a team of agents. The agent should get “ground truth” from its environment at each step, such as tool results, rather than guessing.

Source: Anthropic: Building effective agents, 19 Dec 2024.

3. Write the evals before improving it

OpenAI says you might consider “writing evals before you start writing prompts”, much like behaviour-driven development; Anthropic says “20-50 simple tasks drawn from real failures is a great start”. Keep two suites:

  • Capability evals ask what the agent can do well. They “should start at a low pass rate”, giving a hill to climb.
  • Regression evals make sure changes do not break what worked. Capability tasks the agent now passes “graduate” into this suite, which then runs continuously “to catch any drift”.

Run each task several times: a model can pass once by luck. For regression, require every trial to pass (pass^k); for capability, one pass in k shows the agent can do it (pass@k). Both are explained on Building an Agentic System.

Sources: OpenAI: Model optimization; Anthropic: Demystifying evals for AI agents, 9 Jan 2026.

4. “Training”: prompting, context or fine-tuning

Analysis: for many agents, “training” means shaping them with instructions, examples, retrieved context and tools, measured by the evals, rather than changing the model’s weights. Fine-tuning is the real alternative when that runs out. OpenAI describes the work as a flywheel of “evals, prompt engineering, and fine-tuning”, and says fine-tuning “can be a time-consuming process” but can make a model “consistently format responses in a certain way or handle novel inputs”.

If this is true for youLeans towards
The agent lacks your facts (policies, products, records)Retrieval and tools: give it the data at run time. See RAG
It misunderstands the job or the formatBetter instructions and examples, measured by evals
It needs a strict output format, a classification or a house style that prompting cannot holdSupervised fine-tuning: Google Cloud lists “hundreds to thousands of labeled examples” for this
It should prefer one kind of answer over another (tone, helpfulness)Preference tuning, on chosen and rejected pairs
Multi-step reasoning on tasks a program can check (code, SQL)Reinforcement fine-tuning with reward functions, where offered
Your data changes dailyRetrieval, not tuning: a tuned model only knows what it was trained on

Analysis: the leanings are our view; the tuning methods and dataset sizes are from Google Cloud: Tune Gemini models. Also OpenAI: Model optimization.

5. Validate: an offline gate

Our advice: before any user sees a new version, compare it with the live one on the same evals. A candidate must not lose any regression task, must stay within its cost and latency budget, and should do better on capability. Add adversarial tests: inputs that try to make it leak data or misuse a tool (see Agentic AI Security).

Anthropic notes that evals give “baselines and regression tests for free: latency, token usage, cost per task, and error rates”.

Source: Anthropic: Demystifying evals for AI agents, 9 Jan 2026.

6. Go live: canary, then widen

Google’s SRE workbook defines canarying as “a partial and time-limited deployment of a change in a service and its evaluation”, effectively an A/B test that risks “only a small fragment of our error budget”. Our advice: for an agent, compare the canary with the control on errors and on how often it hands a case to a person (and watch cost); widen only when they stay within a margin you set in advance, and only once there are enough events for the comparison to mean anything.

Our advice: keep the previous version deployable, and version the prompt, tools and model together, so a rollback is one switch.

Source: Google SRE Workbook: Canarying releases.

A release gate you can run

A short Python script, in the site’s repository at examples/agentprod with its data and the commands to re-run it, that decides whether a candidate may replace the live version. Stage 1 compares eval results; stage 2 compares canary metrics with the control. These are its rules:

RULES = {
    "regression_min": 0.95,     # the regression suite must stay this high (pass^k: every trial passes)
    "cost_growth_max": 0.20,    # cost per task may grow at most 20%
    "p95_latency_max_s": 8.0,
    "canary_min_events": 30,    # wait until the control's rate predicts this many events in the canary
    "canary_error_ratio_max": 1.10,       # canary error rate at most 10% above control
    "canary_escalation_ratio_max": 1.25,  # hand-offs to people at most 25% above control
}


class GateError(Exception):
    """The gate cannot decide. That is a refusal, never a pass."""


SUITES = {"regression", "capability"}


def number(x, what):
    if isinstance(x, bool) or not isinstance(x, (int, float)) or not math.isfinite(x) or x < 0:
        raise GateError(f"{what} must be a finite number >= 0, got {x!r}")
    return x


def by_task(results):
    """Validate every result before any arithmetic: bad input is a refusal, not a number."""
    if not isinstance(results, list):
        raise GateError("results must be a list")
    out = {}
    for r in results:
        if not isinstance(r, dict):
            raise GateError(f"each result must be an object, got {r!r}")
        t = r.get("task")
        if not isinstance(t, str) or not t:
            raise GateError(f"each result needs a task id, got {t!r}")
        if t in out:
            raise GateError(f"duplicate task id {t!r}")
        if r.get("suite") not in SUITES:
            raise GateError(f"task {t!r} has unknown suite {r.get('suite')!r}")
        if not isinstance(r.get("trials"), list) or not all(isinstance(x, bool) for x in r["trials"]):
            raise GateError(f"task {t!r} trials must be a list of true/false")
        number(r.get("cost_usd"), f"task {t!r} cost_usd")
        number(r.get("latency_s"), f"task {t!r} latency_s")
        out[t] = r
    return out


def passed(r, all_trials):
    if not r["trials"]:
        return False                      # no results is a failure, not a pass
    return all(r["trials"]) if all_trials else any(r["trials"])

Run on synthetic results (a stand-in agent on 30 regression and 10 capability tasks, 3 trials each; no model was called), it holds a candidate that is better on new tasks but breaks two old ones, rolls back a canary that hands too many cases to people, and refuses to decide on a canary too small to judge. A gate that cannot decide says so and counts as a hold, never a pass:

Analysis: the thresholds are examples; set yours from your success criteria. The minimum-events rule is a simple guard against noise, not a significance test. The folder also holds 26 unit tests: the 4 decided paths, and 22 ways to fool the gate that must each end in a refusal. Beyond those checks, the gate trusts the counts it is given.

7. Live: watch, learn, feed back

Our advice:

  • Trace every run: the steps, tools, tokens and cost (see Observability).
  • Sample real conversations for human review, and turn each failure into an eval task.
  • Re-run the evals when the model provider updates a model, even if you changed nothing.
  • When a capability eval reaches 100%, Anthropic warns it “tracks regressions but provides no signal for improvement”: add harder tasks.

Source: Anthropic: Demystifying evals for AI agents, 9 Jan 2026.

Our view, and the other view

Our view: the eval set deserves at least as much care as the prompt. It lets you change models, prompts and tools without guessing, and it is what a release gate stands on.

The other view: evals cost time to build and keep honest, and a small internal tool with a person checking every output may not need a formal gate. Match the process to what a wrong answer costs.

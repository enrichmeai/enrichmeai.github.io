AI for engineers

How language models behave, how to build features on them that you can test and operate, and how to work with AI assistants without lowering the bar.

Use AI like a bulldozer, not a shovel

A shovel moves one scoop at a time while you hold the handle: ask for a line, paste it, ask again. A bulldozer moves the whole job while you choose where it goes, set the boundaries and check the result. The second gets far more done, but only if you prepare the site. And only if you know enough to manage the site: see Fundamentals first on Start here.

Shovel habitBulldozer habit
"Write a function that…" with no contextHand over a whole task: the issue, the files, the conventions and what done means
Copy and paste answers from a chat windowLet an agent work in the repo: edit files, run the build and tests, read the errors, fix them
Re-explain the project in every sessionWrite the context down once (a CLAUDE.md or AGENTS.md, skills, runbooks) so every session starts informed
Check its work by reading every line as it typesDefine checks up front (tests, lint, type checks, CI) and review the finished change against them
One task at a time, waiting on eachRun independent tasks in parallel: separate branches or worktrees, subagents for research and review
Fix the same mistake by hand again next weekTurn each correction into a rule, test or hook in the repo so it cannot recur
Trust it because it sounds sureTrust it because the tests passed and the docs agree

Preparing the site

  • Context file in the repo: what the system is, how to build and test it, the rules that are not negotiable, the traps that cost time before.
  • Fast, exact gates: the commands that prove a change is done, written down so the agent runs them itself.
  • Guardrails: permission settings and hooks that stop destructive commands (force pushes, prod deploys, deletes) unless a human approves.
  • Small, clear tasks: one concern per task, with acceptance criteria. A vague brief gets a confident guess.
  • Pinned docs: links to the official docs for the versions you use, so it checks instead of recalling.
  • A reviewer that is not the author: a second agent or a person reviews the diff against the spec and the docs.

A brief that moves earth

(An illustrative brief: the problem and the paths are examples.)
Goal:     Reject dates that do not parse, instead of storing NULL.
Why:      One source sends dd-mm-yyyy; the parser turns those into NULL
          without saying so, and the rows look like "no date".
Where:    models/intermediate/int_cases_normalised.sql and its unit tests.
Rules:    Follow CLAUDE.md. Do not change the other sources. No new dependencies.
Done when:
  - a unit test with "05-05-1959" and "bad" fails before the fix, passes after
  - dbt build -s int_cases_normalised+ is green
  - the reject table counts unparseable rows
Out of scope: backfilling old rows (separate issue).
Report:   what changed, the test output, anything you could not verify.

Goal, reason, location, rules, a checkable definition of done, scope, and what to report. The same brief works for a colleague.

Where you still drive by hand

  • Irreversible actions: production deploys, data deletion, schema changes on live data, anything sent outside the company.
  • Unclear requirements: decide what to build first; an agent will fill gaps with plausible guesses.
  • Security and money: auth, permissions, payments, secrets. Review line by line.
  • Claims about state: "prod has X" needs someone to look at prod, not a model's inference from config.
  • Judgement calls that belong to a person: priorities, trade-offs, wording that speaks for the company.

The bulldozer is only as safe as its operator. Speed comes from preparation and checks, not from skipping them.

Why everyone's experience of AI is different

Ask ten people what AI is like at writing code and you will hear ten different answers, often strongly held, including from people who have never written code. Most of them are honest. They are describing different experiences, not the same one.

  • What you bring decides what you get. If you cannot read the code, you cannot tell good output from output that only looks good. An experienced engineer spots the bug, writes a precise brief, and knows when to stop and do it by hand. Same tool, very different results.
  • The task is different. A small demo built from nothing is not a ten-year-old system with real users, real data and real security needs. AI can shine at the first and still struggle with the second.
  • When and how much you used it. An afternoon is not years of daily use, and the tools change month to month. A view formed once, early or late, ages quickly.
  • Where you stand. A manager sees speed. A reviewer sees more code to check. The engineer on call sees the incident. A newcomer sees a patient teacher. Each is real.
  • Talking about AI and code without ever having coded is a little like describing a marathon without ever having walked: you can see the photos at the finish line, but not the miles. People who do not code still see things engineers miss, as users, designers and leaders, and their views on those things count. Judging how well AI writes and maintains code takes the experience of writing and maintaining code.
  • Trust works the same way, in both directions. Adaptive cruise control is a real help to someone who has driven for years, in manual and automatic cars: they know when to lean on it, and when to take the wheel back. For someone who has never driven at all, trusting it blindly and refusing it outright are both guesses. Trust in AI-written code grows from the same place: solid foundations, so you know what good looks like and when to take over.
  • And even good drivers need guard rails. Roads have speed limits, crash barriers and lane markings because skilled people still make mistakes. AI-written code needs its own: tests and type checks that run on every change (Testing), CI gates that block a red build, code review by someone who did not write it, hooks that check each edit as it happens and least-privilege permissions so an agent cannot touch production on its own (Claude Code & Cowork, Agent Harness), secrets kept out of prompts (Security), and a person who approves the merge.

So everyone is right about what they experienced, and none of it is the whole truth for everyone else. When you hear a strong view, ask: what did you try it on, for how long, and how did you check the result? Share specifics, not verdicts. And before forming your own view, try it yourself on real work, then check the result properly (see Behaviours: learn by doing, not by opinion). We still need solid foundations and guard rails: learn to drive first (see Start here: fundamentals first), then drive on a road with barriers.

Blueprints and frameworks, not generated boilerplate

AI makes boilerplate cost almost nothing to write. It does not make it cheap to own. Every generated copy has to be reviewed, secured, tested, upgraded and debugged, and fifty copies that are each slightly different are fifty places to fix the same bug. A blueprint (a framework, shared library, template, Terraform module or dbt package) makes each decision once, tests it once, and fixes it once for everyone.

Generated boilerplateBlueprint or framework
ConsistencyEach copy drifts: retries, logging, auth and error handling differ per serviceOne behaviour everywhere, so people and tools know what to expect
Fixing a bug or CVEFind and patch every copy, and miss somePatch once, bump the version, done
ReviewHundreds of generated lines to read in every PRReview only the part that is new; the rest is already proven
SecurityEach copy can reintroduce a hole the model learned from public codeSecure defaults built in and tested
UpgradesEvery service upgrades on its own, or neverUpgrade the blueprint; services follow
KnowledgeDecisions live in whichever prompt produced the codeDecisions are written down, versioned and reviewable
AI qualityThe model guesses your conventions from its training dataThe model follows your blueprint, so its output is smaller and fits
  • Rule of thumb: if you would ask AI to generate the same thing twice, it belongs in a blueprint.
  • Use AI to build and improve the blueprint, then to fill in only the part that is specific: the business logic, the one new query, the tests for it.
  • Point the AI at the blueprint in your context file ("new jobs use modules/pipeline-job; new services start from the service template"), so it extends instead of reinventing.
  • Generation is fine for one-off scripts, prototypes you will throw away, and filling in a blueprint's slots.

Examples in this guide: Spring Boot starters and Quarkus extensions; a Terraform module for every Cloud Run job; dbt macros, generic tests and packages; a shared library such as Culvert for storage and warehouse access; a service template in Backstage or Cookiecutter; and a written build-loop blueprint that is ported between repos instead of re-prompted in each. How models behave

  • Tokens: models read and write tokens (pieces of words). Cost, limits and latency are all counted in tokens.
  • Context window: everything the model can see in one call: instructions, history, retrieved documents, tool results. It remembers nothing between calls unless you send it again.
  • Non-deterministic: the same input can give different outputs. Test with sets of examples and scores, not one run.
  • Confidently wrong: a model can produce fluent, specific, false text (hallucination). Ground answers in retrieved sources and ask for citations you can check.
  • Knowledge cutoff: the model knows nothing after its training data. Current facts must come from your data or tools.
  • Instructions in data: the model cannot reliably tell your instructions from instructions hidden in a document it reads.

Calling a model (Anthropic Python SDK)

# pip install anthropic   — credentials from ANTHROPIC_API_KEY
import anthropic
client = anthropic.Anthropic()

resp = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=16000,
    system="You summarise Indian court judgments for lawyers. Cite paragraph numbers.",
    messages=[{"role": "user", "content": judgment_text}],
)
if resp.stop_reason == "refusal":
    handle_refusal(resp)                   # check before reading content
for block in resp.content:
    if block.type == "text":
        print(block.text)
print(resp.usage.input_tokens, resp.usage.output_tokens)   # log every call's cost

Other current IDs: claude-sonnet-5-5 (faster, cheaper) and claude-haiku-5-5 (cheapest, for bulk work). Long outputs should stream. On Vertex AI use AnthropicVertex(project_id=…, region=…) with the same calls.

Structured output, not string parsing

from pydantic import BaseModel

class Citation(BaseModel):
    case_name: str
    year: int | None
    court: str | None
    paragraph: str | None

class Extraction(BaseModel):
    citations: list[Citation]

resp = client.messages.parse(
    model="claude-opus-5-5",
    max_tokens=16000,
    messages=[{"role": "user", "content": f"Extract every case cited:\n\n{text}"}],
    output_format=Extraction,
)
result: Extraction = resp.parsed_output     # validated against the schema

The schema guarantees shape, not truth. Still check values against your data: does that case exist in the corpus?

Tools: let the model call your code

from anthropic import beta_tool

@beta_tool
def search_corpus(query: str, court: str | None = None) -> str:
    """Search the judgment corpus. Returns up to 10 results as JSON.

    Args:
        query: Full-text search terms.
        court: Optional court code, e.g. "2_5".
    """
    return json.dumps(corpus.search(query, court=court, limit=10))

runner = client.beta.messages.tool_runner(
    model="claude-opus-5-5",
    max_tokens=16000,
    tools=[search_corpus],
    messages=[{"role": "user", "content": "Find recent Himachal judgments on land acquisition."}],
)
for message in runner:          # the SDK runs the call → tool → call loop
    print(message)

Give tools the least privilege that works: read-only by default, writes behind human approval. MCP is the open protocol for exposing tools and data to any compatible client.

RAG: retrieval-augmented generation

StepWhat you buildWhere it goes wrong
1 IngestPipeline that loads documents with IDs, dates and sourceStale or duplicate documents; no way to tell which version was used
2 ChunkSplit into passages (by section or ~500–1,000 tokens with overlap)Chunks cut through the sentence that answers the question
3 EmbedVector per chunk; store with metadataQuery and documents embedded with different models
4 RetrieveVector search plus keyword search (hybrid), filtered by metadataExact names and citations missed by vectors alone
5 RerankScore the top 50 and keep the best 5–10Irrelevant passages crowd out the right one
6 GeneratePrompt with the passages, ask for citations to their IDsModel answers from memory when retrieval found nothing; say "not found" instead
7 EvaluateMeasure retrieval (did the right chunk come back?) and answers separatelyOnly judging the final answer hides which step failed

Vector search: Postgres & BigQuery

-- pgvector
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE chunks (id bigserial PRIMARY KEY, doc_id text, body text,
                     embedding vector(768));
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
SELECT id, doc_id, 1 - (embedding <=> $1) AS similarity
FROM chunks WHERE doc_id LIKE 'HP%'          -- HNSW filters after the index scan: can return fewer rows (pgvector 0.8+ iterative scans help)
ORDER BY embedding <=> $1 LIMIT 10;        -- <=> cosine distance
-- BigQuery: embed with a remote model, then search
CREATE OR REPLACE TABLE `p.ai.chunk_emb` AS
SELECT * FROM ML.GENERATE_EMBEDDING(
  MODEL `p.ai.embedding_model`,
  (SELECT id, body AS content FROM `p.ai.chunks`));

SELECT base.id, distance
FROM VECTOR_SEARCH(
  TABLE `p.ai.chunk_emb`, 'ml_generate_embedding_result',
  (SELECT ml_generate_embedding_result FROM ML.GENERATE_EMBEDDING(
     MODEL `p.ai.embedding_model`, (SELECT 'land acquisition compensation' AS content))),
  top_k => 10, distance_type => 'COSINE');

Evals: how you know it works

  • Build a test set of 50–200 real inputs with expected outputs or grading notes. Include the hard and adversarial cases.
  • Grade with code first: exact match, schema valid, cited ID exists, number within tolerance.
  • Model-as-judge for open-ended answers, with a written rubric, checked against human grades on a sample.
  • Run it in CI on every prompt, model or retrieval change, and track the score over time.
  • Hold out a test split you never tune against, so improvements are real.
  • Measure cost and latency beside quality; a 2% gain at 3× the cost may not be worth it.

Security

  • Prompt injection: a web page, PDF or email the model reads can say "ignore your instructions". Treat everything retrieved as untrusted data.
  • Limit the blast radius: tools get least privilege; destructive actions need human confirmation; the model never holds credentials directly.
  • Output is untrusted input: escape it before rendering, validate it before running it as SQL or shell.
  • Data leakage: do not send secrets or personal data you are not allowed to process. Check the provider's retention terms.
  • Log and audit prompts, tool calls and outputs (minus sensitive fields) so you can investigate.

Cost & latency

  • Estimate first: (input + output tokens) × price × calls per day. Log usage on every call.
  • Prompt caching: put the stable part (instructions, tool definitions, long reference text) first so repeated calls reuse it at a fraction of the price.
  • Batch API for work that can wait (bulk extraction overnight), at a lower price.
  • Right-size the model: measure whether a smaller model or lower effort holds quality on your eval before paying for the largest.
  • Trim context: retrieve 5 good passages, not 50 mediocre ones.
  • Stream long responses so users see progress, and set timeouts and retries with backoff.

Working with AI coding assistants

  • Give context: the repo's conventions, the failing test, the exact error. Vague asks get vague code.
  • Tests first: a test that fails before the change is the best spec and the best check.
  • Verify against docs: an assistant can invent a flag, method or version. Check the official docs for anything external.
  • Review every line as you would a colleague's PR: error paths, edge cases, security.
  • Keep secrets out of prompts and pasted logs.
  • Small steps: one concern per change, so a wrong turn is cheap to undo.
  • You own the result. "The AI wrote it" is not a review comment.

Agents: when and when not

  • Start with one call. Classification, extraction and summaries rarely need more.
  • Then a workflow: fixed steps in your code, a model call at each. Predictable and testable.
  • An agent (the model chooses tools in a loop) only when the steps cannot be known in advance, the value justifies the cost, and mistakes can be caught and undone.
  • Bound it: step and token budgets, timeouts, an approval gate on writes, and a full log of each tool call.

AI on Google Cloud

  • Vertex AI: hosted models (Gemini, Claude and others through Model Garden), endpoints, evaluation and pipelines in your GCP project and region.
  • BigQuery ML: call remote models from SQL (ML.GENERATE_TEXT, ML.GENERATE_EMBEDDING) and search with VECTOR_SEARCH, without moving data out.
  • Data residency: pick the region deliberately; some models run only in global or specific regions.
  • IAM as usual: service accounts with Vertex AI User, no API keys in code.

Levels: what to expect

1 Foundation

  • Call a model API and get structured output
  • Explain tokens, context, hallucination and prompt injection
  • Use an AI assistant with tests and review

2 Practitioner

  • Build a RAG feature with retrieval, citations and an eval set
  • Use tools and handle refusals, errors and cost
  • Brief an AI agent with context, rules and a definition of done

3 Senior

  • Design AI features with evals, guardrails, observability and fallbacks
  • Tune cost and latency (caching, batch, model choice)
  • Set up repos so AI agents work safely (context files, hooks, gates)

4 Expert

  • Set AI strategy, governance and security across the organisation
  • Design agentic systems and their safety boundaries
  • Build shared AI platforms, blueprints and evaluation infrastructure

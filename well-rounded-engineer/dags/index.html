Airflow DAGs

Airflow 3 syntax (Task SDK), with 2.x differences noted. Cloud Composer runs either; check its image version first.

TaskFlow DAG (Airflow 3)

from datetime import datetime, timedelta
from airflow.sdk import dag, task

@dag(
    schedule="15 6 * * *",          # cron, "@daily", timedelta, Asset, None
    start_date=datetime(2025, 1, 1),
    catchup=False,                  # default False in 3.x (True in 2.x)
    max_active_runs=1,
    default_args={"retries": 2, "retry_delay": timedelta(minutes=5)},
    tags=["orders"],
)
def orders_daily():

    @task
    def list_new(ds=None) -> list[str]:
        return find_objects(since=ds)

    @task(retries=3)
    def load(uri: str) -> int:
        return load_to_bq(uri)

    @task
    def report(counts: list[int]):
        print(sum(counts))

    report(load.expand(uri=list_new()))   # dynamic task mapping

orders_daily()

BigQuery & GCS operators

from airflow.providers.google.cloud.operators.bigquery import (
    BigQueryInsertJobOperator, BigQueryCheckOperator)
from airflow.providers.google.cloud.transfers.gcs_to_bigquery import (
    GCSToBigQueryOperator)
from airflow.providers.google.cloud.sensors.gcs import GCSObjectExistenceSensor

wait = GCSObjectExistenceSensor(
    task_id="wait_manifest", bucket="landing",
    object="manifests/{{ ds }}.json",
    deferrable=True, timeout=6 * 3600)

load = GCSToBigQueryOperator(
    task_id="load_parquet", bucket="landing",
    source_objects=["data/year={{ logical_date.year }}/*.parquet"],
    destination_project_dataset_table="proj.raw.orders",
    source_format="PARQUET", write_disposition="WRITE_APPEND")

build = BigQueryInsertJobOperator(
    task_id="build_fdp", location="asia-south1", deferrable=True,
    configuration={"query": {
        "query": "{% include 'sql/orders.sql' %}",
        "useLegacySql": False}})

check = BigQueryCheckOperator(
    task_id="rows_today", use_legacy_sql=False,
    sql="SELECT COUNT(*) > 0 FROM `proj.analytics.orders` WHERE _run_date = '{{ ds }}'")

wait >> load >> build >> check

Templates & context

{{ ds }}                     2025-01-31     (logical date, YYYY-MM-DD)
{{ ds_nodash }}              20250131
{{ logical_date }}           pendulum DateTime
{{ data_interval_start }}    start of the period this run covers (see below)
{{ data_interval_end }}      end (exclusive)
{{ macros.ds_add(ds, -1) }}  2025-01-30
{{ params.window }}          from dag(params={...})
{{ var.value.my_var }}       Airflow Variable
{{ conn.my_conn.host }}      Connection field
{{ run_id }}  {{ dag.dag_id }}  {{ task_instance.try_number }}

# in TaskFlow, ask for context by name
@task
def t(data_interval_start=None, ti=None):
    ti.xcom_push(key="n", value=1)
# or: from airflow.sdk import get_current_context

In Airflow 3 a cron string such as "15 6 * * *" or "@daily" uses CronTriggerTimetable: the run for 2025-01-31 starts at 06:15 that day, its logical date is that time, and data_interval_start equals data_interval_end. For a real window, schedule with CronDataIntervalTimetable (each run starts after its interval ends, as cron schedules did in 2.x) or pass interval= to CronTriggerTimetable. Decide which you use before writing "which data" logic, and never use now(). execution_date is removed in Airflow 3: use logical_date.

Branching, trigger rules, task groups

from airflow.sdk import task, task_group

@task.branch
def choose(**ctx):
    return "full_load" if ctx["logical_date"].day == 1 else "delta_load"

@task(trigger_rule="none_failed_min_one_success")
def join(): ...

@task(trigger_rule="all_done")   # always runs: cleanup, alerts
def cleanup(): ...

@task.short_circuit
def has_work(n: int) -> bool:
    return n > 0       # False skips everything downstream

@task_group
def per_store(store: str): ...

Data-aware scheduling (Assets)

from airflow.sdk import Asset, dag, task
raw = Asset("bigquery://proj/raw/orders")

@dag(schedule="@daily", start_date=datetime(2025,1,1))
def producer():
    @task(outlets=[raw])
    def load(): ...
    load()

@dag(schedule=[raw], start_date=datetime(2025,1,1))   # runs when raw updates
def consumer():
    @task
    def build(): ...
    build()

producer(); consumer()

Airflow 2.4–2.10 call these Dataset (from airflow.datasets import Dataset).

Reliability checklist

  • Idempotent tasks: a rerun of the same interval gives the same result. Use WRITE_TRUNCATE on a partition (table$20250131) or a MERGE, never a blind append.
  • No heavy work at parse time: top-level code runs on every scheduler parse. No API calls or DB queries outside tasks.
  • Small XComs: pass URIs and counts, not dataframes.
  • Deferrable operators and sensors (deferrable=True) free worker slots while waiting.
  • Pools cap concurrency against a shared resource: pool="bq_slots".
  • Alert on failure: on_failure_callback in default_args.
  • Pin provider versions in your Composer/requirements; operator args change between majors.

CLI & local testing

airflow dags list
airflow dags list-import-errors
airflow dags test orders_daily 2025-01-31          # full run, no scheduler

  --from-date 2025-01-01 --to-date 2025-01-07                    # 3.x
airflow dags trigger orders_daily -c '{"window": 3}'

def test_dags_load():
    bag = DagBag(dag_folder="dags", include_examples=False)
    assert not bag.import_errors

Airflow 2 → 3 gotchas

  • Authoring imports move to airflow.sdk (dag, task, Asset, Variable).
  • schedule_interval and timetable args are removed: use schedule.
  • catchup now defaults to False.
  • Context keys execution_date, next_ds, prev_ds, tomorrow_ds are removed.
  • Bash, Python and Empty operators live in the apache-airflow-providers-standard package.
  • Tasks no longer get direct metadata-DB access; use the REST API or the SDK.
  • SubDagOperator and SLAs are gone; use task groups and deadline alerts.
  • Run ruff check --select AIR3 dags/ to find most of these.

Levels: what to expect

1 Foundation

  • Read a DAG; find and read a failed task's log
  • Rerun a task or a date
  • Understand logical dates and data intervals

2 Practitioner

  • Write idempotent TaskFlow DAGs with retries and templates
  • Use provider operators and deferrable sensors
  • Test DAGs locally and in CI

3 Senior

  • Design orchestration across many pipelines (assets, pools, SLAs)
  • Run Composer or Airflow reliably; plan upgrades
  • Decide what belongs in Airflow vs inside the job

4 Expert

  • Choose the orchestration platform for the organisation
  • Run large Airflow estates: scaling, multi-tenancy, security
  • Set standards for scheduling and data-aware workflows

Each level includes the ones before it. See Start here for what the levels mean.

Data engineering on Google Cloud

Which Google Cloud service does each job in the data lifecycle, how they fit together in common architectures, and how to choose between similar ones. Concepts are on Data Engineering; the warehouse itself is on BigQuery.

Choosing between similar services

  • SQL in BigQuery vs Dataflow: if it can be expressed in SQL over data already in BigQuery, use SQL (dbt). Use Dataflow for streaming, non-SQL parsing, or work before data reaches BigQuery.
  • Dataflow vs Dataproc: Dataflow for new pipelines (serverless, Beam, streaming). Dataproc for existing Spark code or Spark libraries.
  • Cloud Run job vs Dataflow: a job for simple, bounded work (copy files, call an API). Dataflow when data volume needs many workers and autoscaling.
  • Composer vs Workflows: Composer for many pipelines with dependencies, backfills and sensors. Workflows plus Scheduler for a handful of steps; much cheaper to run.
  • dbt vs Dataform: both do SQL ELT with tests. Dataform is built into BigQuery; dbt has the larger ecosystem and runs on any warehouse.
  • Pub/Sub vs Kafka: Pub/Sub is serverless and global with nothing to size. Kafka gives log semantics, replay by offset, compaction and the Kafka ecosystem.
  • Cloud SQL vs AlloyDB vs Spanner: Cloud SQL for most Postgres needs; AlloyDB for heavier Postgres workloads and analytics; Spanner for global scale with strong consistency.

Handy commands

# Pub/Sub straight into BigQuery
gcloud pubsub topics create judgment-events
gcloud pubsub subscriptions create judgment-to-bq \
  --topic=judgment-events \
  --bigquery-table=my-proj:dp_odp.judgment_events \
  --use-table-schema

# Storage Transfer: one-off copy between buckets
gcloud transfer jobs create gs://source-bucket gs://my-landing

# Serverless for Apache Spark (Dataproc batches): run a PySpark job
gcloud dataproc batches submit pyspark job.py \
  --region=asia-south1 --deps-bucket=gs://my-deps

# Dataflow: list and inspect jobs
gcloud dataflow jobs list --region=asia-south1 --status=active
gcloud dataflow jobs describe JOB_ID --region=asia-south1

# Datastream streams
gcloud datastream streams list --location=asia-south1

IAM for data, in practice

  • One service account per pipeline component (landing, load, transform, serve), each with only its roles.
  • Dataset-level grants rather than project-wide: bigquery.dataEditor on the datasets it writes, dataViewer on those it reads.
  • bigquery.jobUser on the project that pays for queries; this is separate from data access.
  • Bucket-level roles with uniform bucket-level access; objectViewer for readers, objectAdmin only for the writer.
  • Policy tags for sensitive columns; authorised views to share a subset.
  • Serving databases get a read-only user for the API.

Cost controls

  • Partition and cluster; require partition filters on large tables.
  • Set per-user and per-project custom query quotas, and maximum_bytes_billed on jobs.
  • Export billing to BigQuery and build a cost dashboard by label.
  • Label every resource with team, component and environment.
  • GCS lifecycle rules to move old raw data to Nearline/Coldline/Archive.
  • Stop or scale down non-production Cloud SQL, Dataproc and Composer when unused.
  • Dataflow: right-size workers, use streaming engine, and set max workers.
  • Keep development windows small: a few partitions, not the full history.

Data quality and governance on GCP

  • dbt tests in the transformation layer for keys, relationships and accepted values.
  • Dataplex data quality scans for rules on tables, scheduled, with results in BigQuery.
  • Dataplex data profiling to see distributions, nulls and distinct counts.
  • Lineage from BigQuery jobs and Dataflow appears automatically in Dataplex.
  • Run records of your own: every pipeline run writes what it read, wrote and rejected.
  • Sensitive Data Protection scans to find personal data you did not know you had.

Certification path

  • Cloud Digital Leader: broad, non-technical overview.
  • Associate Cloud Engineer: hands-on GCP basics: IAM, compute, networking, gcloud.
  • Professional Data Engineer: design, build and operate data systems on GCP. The exam tests choosing services for a scenario, which is exactly this tab.
  • Professional Cloud Architect next, if you design whole platforms.

Certifications test breadth and judgement. Pair each with a real project built end to end.

Levels: what to expect

1 Foundation

  • Name the GCP service for each lifecycle stage
  • Load files from GCS into BigQuery and query them
  • Navigate IAM roles for data access

2 Practitioner

  • Build a batch ELT pipeline: landing, BigQuery layers, dbt, scheduling
  • Set up Pub/Sub to BigQuery, or Datastream CDC
  • Apply dataset-level IAM and cost controls

3 Senior

  • Choose between Dataflow, Dataproc, SQL and Cloud Run for a workload
  • Design a platform with governance (Dataplex), lineage and quality
  • Plan cost, regions and data residency

4 Expert

  • Own the organisation's GCP data architecture
  • Lead migrations from other clouds or on-premises
  • Hold the Professional Data Engineer or Architect level of judgement, and teach it

Each level includes the ones before it. See Start here for what the levels mean.

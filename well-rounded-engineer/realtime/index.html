Guide / Building services / Real-time to the Browser

Real time, near real time, and getting events to the browser

A customer adds an item to the cart on their phone, and the badge on their laptop should change too. Between those two screens sit an API, a database, a Kafka topic, a service that holds browser connections, and a choice of transport: polling, server-sent events, WebSockets or GraphQL subscriptions. This page defines the terms, follows the cart event end to end, and compares every option by requirement. Kafka itself is on Kafka, and GraphQL on GraphQL.

Real time and near real time are different promises

TermWhat it meansExamples (analysis)
Hard real timeMissing a deadline is a total system failureAirbag control, industrial safety systems
Firm real timeInfrequent misses are tolerable, but a late result is worth nothingA video frame or a market price that arrives too late to use
Soft real timeA late result is still useful, but worth less the later it isLive dashboards, multiplayer game state
Near real timeThe delay that processing and network transmission add between an event and its use, such as for displayA cart badge, an order status, a stock count, a notification

Our view: on the web, “real time” almost always means near real time, and the honest way to say it is a number: “the badge updates within two seconds for 99% of changes”. The other view: product teams use “real time” as shorthand for “no refresh button”, and insisting on the strict term can derail a useful conversation; agree the number, whatever word you use.

The journey of one cart event

  1. Change: the phone sends “add item” (a REST call or a GraphQL mutation) to the cart service.
  2. Record: the cart service saves the cart and an outbox row in one transaction, so the change and its event cannot disagree (see the transactional outbox on Architecture).
  3. Publish: a relay publishes CartItemAdded to the cart-events topic, keyed by cart id: the key decides the partition, so every event for one cart stays in order (see Kafka).
  4. Bridge: a push gateway (often the backend-for-frontend) consumes the topic and holds the open browser connections. Browsers cannot read Kafka directly (analysis: Kafka clients speak Kafka’s own protocol over TCP, which browser APIs do not offer).
  5. Deliver: the gateway sends the event to that customer’s open connections, over SSE, a WebSocket or a GraphQL subscription.
  6. Show and catch up: the laptop updates the badge. If it was offline, it catches up when it reconnects.

Analysis: the device that made the change already knows from its own response. Push is for everyone else: other tabs and devices, and changes made elsewhere, such as a price change or an item going out of stock.

From Kafka to browsers: the gateway’s three problems

  • Fan-out. In a Kafka consumer group, each partition is read by one consumer. If every gateway instance joins one group, an instance sees only some partitions, but the customer’s connection may be on a different instance. Three ways out (analysis):
    1. Each gateway instance uses its own consumer group, reads every event and forwards only those for customers connected to it: simple, but every instance reads the whole topic.
    2. Route each connection to the instance that owns the partition of the cart it watches (events are keyed by cart id): efficient, and hard to keep right as instances and partitions move.
    3. The gateway republishes to a fan-out layer built for connections, such as a pub/sub service or a managed one (below).
  • Missed events. A connection drops, and events arrive while it is down. With SSE the browser reconnects by itself after a dropped connection and sends the last event id it saw in a Last-Event-ID header, so the gateway can resume. The GraphQL specification defines a subscription’s result as a stream of events, but not replay, so a common pattern is to re-run the cart query on reconnect, then follow the stream (analysis).
  • Who may listen. Authenticate the connection, and let each customer subscribe only to their own carts. A long-lived connection outlives a short-lived token, so decide what happens when it expires.

Analysis: send the whole change (“item X added, new total Y”) or only a signal (“cart changed, fetch it”)? A signal keeps one source of truth and makes missed events harmless, at the cost of an extra request; the whole change saves the request and needs ordering and replay to be right.

Every option, side by side

OptionHow it worksDirectionFrom the sources
Short pollingThe browser asks every few secondsClient asksThe delay is up to one interval, and most requests return nothing (analysis)
Long pollingThe server holds each request open until it has something, then the client asks againClient asks, server waitsNot a true push, but it emulates one where a real push is not possible; RFC 6202 lists its known issues
Server-sent events (SSE)One long HTTP response carrying a stream of events, read with EventSourceServer to browser onlyReconnects by itself after a dropped connection and resends Last-Event-ID; without HTTP/2, browsers allow only 6 SSE connections per domain, across all tabs
WebSocketAn HTTP handshake upgrades to a framed, two-way connection over TCPBoth waysRFC 6455; the browser API has no backpressure, so a fast sender can overwhelm a slow page; reconnect and replay are yours to build (analysis)
GraphQL subscriptionA subscription operation returns a stream of results; the transport is separateServer to browser (over a two-way or one-way transport)Common transports: graphql-ws (WebSocket subprotocol graphql-transport-ws) and graphql-sse (over SSE, with single-connection and distinct-connections modes)
WebTransportStreams and datagrams over HTTP/3Both waysMultiple and unidirectional streams, out-of-order delivery, and unreliable datagrams
Web PushA message to the browser’s push service, handled by a service workerServer to deviceNeeds an active service worker; reaches the user when the page is closed, so it is for notifications rather than keeping a page in sync
Managed servicesA cloud service holds the connections; your backend publishes to itVariesAWS AppSync subscriptions; API Gateway WebSocket APIs (routes to Lambda, HTTP or AWS services); Azure Web PubSub; ASP.NET Core SignalR, which falls back from WebSockets to SSE to long polling

Choose by requirement

If this is true for youIt leans towards
Updates only flow from server to browser (a cart badge, an order status)SSE
The browser also sends a steady stream of messages (chat, collaborative editing, a game)WebSocket
Your front end already talks GraphQL and you want one schema for queries, mutations and updatesGraphQL subscriptions, over graphql-sse or graphql-ws
A delay of tens of seconds is acceptable, or traffic is smallShort polling: little to build or run (analysis)
Proxies or firewalls in front of your users break long-lived connectionsLong polling, or a library that falls back to it
You must reach the user when the page is closedWeb Push
You need many independent streams, unreliable datagrams, or backpressure in the browserWebTransport; check browser support first
You do not want to run servers that hold many open connectionsA managed service on your cloud
Your users still reach you over HTTP/1.1 and open many tabsAvoid one SSE connection per tab: share one connection between tabs, or use a WebSocket

SSE in the browser, and on the wire

// Browser: listen for cart events
const events = new EventSource('/carts/me/events');
events.addEventListener('cart', (e) => {
  const change = JSON.parse(e.data);
  updateBadge(change.itemCount);
});

// What the gateway writes on the response.
// Each event ends with a blank line.
id: 7f3a-42
event: cart
data: {"cartId":"c-9","itemCount":3}

A blank line ends each event, and the browser dispatches it then. After a dropped connection the browser reconnects and sends Last-Event-ID: 7f3a-42, and the gateway resumes after that event.

The same with GraphQL

type Subscription {
  cartChanged(cartId: ID!): CartEvent!
}

subscription {
  cartChanged(cartId: "c-9") { itemCount total }
}

The server resolves the subscription from the gateway’s Kafka consumer. Choose the transport separately: graphql-ws or graphql-sse. See GraphQL.

Our view, and the other view

Our view: for a cart, a second or two is near real time enough. SSE from a backend-for-frontend that consumes Kafka, sending a “cart changed” signal and re-fetching on reconnect, is little to build and run, and recovers from dropped connections on its own. Reach for WebSockets when the browser must send a stream too, and for GraphQL subscriptions when GraphQL is already your API.

The other view: a team that already runs GraphQL gains more from one schema and one client than SSE saves; a team with a managed WebSocket service on its cloud may find that cheaper to run than its own gateway; and at small scale, polling every few seconds is often the honest, boring answer that nobody has to be on call for.

Levels: what to expect

1 Foundation

  • Tell hard, firm and soft real time from near real time
  • Open an EventSource or a WebSocket and handle its messages
  • Explain why a browser cannot read a Kafka topic directly

2 Practitioner

  • Build a gateway that consumes Kafka and pushes to browsers
  • Resume after a reconnect with Last-Event-ID or a refetch
  • Authenticate and scope long-lived connections

3 Senior

  • Choose polling, SSE, WebSockets, GraphQL subscriptions or a managed service by requirement
  • Design fan-out across gateway instances
  • Set and measure a delivery target, such as p99 within two seconds

4 Expert

  • Set real-time standards across an organisation's products
  • Run connection-holding services at scale
  • Decide build or buy for real-time infrastructure

Each level includes the ones before it. See Start here for what the levels mean.

Guide / Architecture & design / Microservices

Microservices

Building a system as small, independently deployable services that each own their data. When it pays off, how to split, how services talk and fail, and the traps that turn microservices into a distributed monolith. Patterns referenced here are on Architecture.

Monolith, modular monolith, microservices

MonolithModular monolithMicroservices
DeployablesOneOne, with enforced internal modulesMany, deployed independently
DataOne shared databaseOne database, schema per moduleEach service owns its data
Calls between partsIn-processIn-process through module APIsOver the network
ScalingWhole appWhole appPer service
Team fitOne small teamOne to a few teamsMany teams owning services end to end
Main costTangling as it growsDiscipline to keep boundariesDistributed-systems complexity and operations

Most systems should start as a modular monolith and extract a service only when a boundary has proved stable and there is a concrete reason: independent scaling, a different release cadence, a separate team, or different technology or security needs.

What microservices buy, and cost

Gains

  • Teams deploy their service without coordinating a big release.
  • Scale and tune each service for its own load.
  • A failure can be contained to one service.
  • Different services can use different technologies where it helps.

Costs

  • Network calls fail, time out and add latency.
  • No cross-service transactions: sagas and eventual consistency instead.
  • Debugging needs distributed tracing; testing needs contracts.
  • Many pipelines, deployments, dashboards and on-call rotations.

How to split services

  • By business capability or bounded context (domain-driven design): search, carts, billing, identity. Not by technical layer (a "database service" is an anti-pattern).
  • Each service owns its data and is the only one that writes it. Others ask through its API or react to its events.
  • High cohesion inside, loose coupling between: a typical change should touch one service.
  • Align with teams (Conway's law): one team owns a service end to end.
  • Size by responsibility, not lines of code. Too many tiny services ("nano-services") multiply network calls and operations for no gain.
  • Test the split: if two services must always deploy together, they are one service.

Monorepo or one repo per service?

A monorepo is not a monolith. A monorepo stores the code of many projects in one repository; each service can still build, deploy and scale on its own. A monolith is one application. You can run microservices from a monorepo, or a monolith from many repositories. The repository decides how people change code together; the deployment decides how the system runs.

MonorepoOne repo per service (polyrepo)
Change across servicesOne atomic commit and one review for the API, its clients and their testsOne pull request per repo, merged and released in the right order
Shared codeA shared library is just a folder, used from sourceA published package with versions, which each service must upgrade
Large refactorsYou can see and fix every caller in one changeCallers in other repositories you cannot see may stay on the old version
Access controlBy default everyone can read everythingGrant access per repository
VersionsSome teams use one version for everything and lose per-service versionsEach service has its own version and release history
Tooling neededA build that only builds and tests what changed; CI that scales with the repoSimple per repo; harder across repos (dependency updates, shared standards)
Clone sizeEverything by default; partial or sparse clones fix itOnly the service you work on

Who runs very large monorepos: Wikipedia names Google, Meta, Microsoft, Uber, Airbnb and Twitter. Several had to change their tools to do it: Google built its own version control system (Piper), Facebook (now Meta) contributed to Mercurial, Microsoft contributed to the Git client and built the Virtual File System for Git when it moved its Windows engineers to one Git repository, and Twitter wrote the Pants build system.

Where a monorepo fits with microservices

Choose by your requirements, not by preference. Read down the left column, tick the rows that are true for you, and see which way they lean.

If this is true for youIt leans towardsWhy
Services often change together (shared API contracts, schemas, clients)MonorepoOne atomic commit and one review instead of ordered releases across repos
You need large refactors across many servicesMonorepoEvery caller is visible and fixed in the same change
Code must be hidden from some contributors (partners, vendors, regulated code)Separate reposA monorepo gives read access to everything by default
Each service is versioned and released to outside users on its ownSeparate reposPer-project versions are simpler; some monorepos lose them
Nobody owns build tooling and CI capacitySeparate reposA monorepo needs a build that only builds what changed, or CI slows with every service added
Teams are separate organisations with little shared codeSeparate reposLittle gain from atomic changes; more cost in shared tooling
A few teams, mostly one domain, shared librariesEither; one repo per team or domain is a common middleKeeps atomic changes where they matter, and access lines where they matter
  • Conway's law (Melvin Conway, 1967): systems mirror the communication structure of the organisation that builds them. The repository layout should match how your teams actually work together.
  • Other views: companies have moved in both directions as they grew. Uber engineers gave a talk titled “Monorepo to Multirepo and Back Again” (2017). Neither layout is a maturity level: the right one can change when your teams, access rules or tooling change.

Making it work

  • Build only what changed. A build tool that knows the dependency graph (Bazel, Buck, Pants, Please, or Nx) builds and tests only the affected services. CI that rebuilds everything on every commit does not scale.
  • Deploy each service on its own. One repository, many pipelines: each service keeps its own image, version tag and rollout. A monorepo must not turn into a release-everything-together monolith.
  • Ownership per folder: a CODEOWNERS file names the team responsible for each path; owners are requested for review automatically, and branch protection can require their approval.
  • Keep clones fast: git clone --filter=blob:none (partial clone) downloads file contents only when needed, and git sparse-checkout set services/orders libs/common keeps only the folders you work on in your working tree.
  • The required-check trap: on GitHub, a workflow skipped by a paths filter leaves its required checks stuck as "Pending", so the pull request cannot merge. A job skipped by an if: condition reports success instead. GitHub’s advice is to avoid requiring workflows that can be skipped. So run the workflow always, decide what changed in a first job, and skip the expensive jobs with if:. Make that first job a required check too: a job whose needs failed is skipped and may not block the merge.
  • Enforce the boundaries in code: a service may import shared libraries but never another service's internals. Check this in the build, or the monorepo quietly becomes a distributed monolith.
# .github/workflows/ci.yml : always runs, so required checks always report
on: [pull_request]
jobs:
  changes:
    runs-on: ubuntu-latest
    outputs:
      orders: ${{ steps.f.outputs.orders }}
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - id: f
        run: |
          changed=$(git diff --name-only origin/${{ github.base_ref }}...HEAD)
          if printf '%s\n' "$changed" | grep -E '^(services/orders|libs/common)/' > /dev/null
          then echo "orders=true" >> "$GITHUB_OUTPUT"; else echo "orders=false" >> "$GITHUB_OUTPUT"; fi
  orders:
    needs: changes
    if: needs.changes.outputs.orders == 'true'   # skipped by if: reports success
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: ./gradlew :services:orders:build
# .github/CODEOWNERS : who reviews which folder
/services/orders/   @acme/orders-team
/libs/common/       @acme/platform-team

Communication

StyleUse forWatch out for
Synchronous REST / gRPCQueries that need an answer nowChains of calls: latency adds up and availability multiplies down
Asynchronous events (Kafka, Pub/Sub)Telling others something happenedEventual consistency, duplicates, ordering
Asynchronous commands (queues)Work another service should doRetries, dead letters, idempotency
  • Prefer events between domains; keep synchronous calls shallow (ideally one hop).
  • Cache or replicate the data you need from other services (from their events) rather than calling them on every request.
  • See APIs & Integration, Kafka and GraphQL.

Infrastructure around services

  • Service discovery: Kubernetes DNS names, Cloud Run URLs, or a registry. Never hard-code instance IPs.
  • API gateway at the edge for authentication, rate limits and routing (Apigee); a backend for frontend per client type when needs differ.
  • Service mesh (Istio / Cloud Service Mesh) for mTLS, retries and traffic splitting between services, without code in each one.
  • Configuration and secrets injected at runtime per environment.
  • Platform blueprint: a service template with logging, tracing, health checks, security and CI already wired, so each new service starts correct.

Resilience in code (Spring + Resilience4j)

@Service
class SupplierClient {
  private final RestClient http;
  SupplierClient(RestClient http) { this.http = http; }

  @CircuitBreaker(name = "supplier", fallbackMethod = "unavailable")
  @Retry(name = "supplier")
  public Listing list(String prefix) {
    return http.get().uri("/objects?prefix={p}", prefix).retrieve().body(Listing.class);
  }

  // honest degradation: "cannot see", never "nothing there"
  Listing unavailable(String prefix, Throwable t) {
    return Listing.unknown("supplier unavailable: " + t.getMessage());
  }
}
resilience4j:
  circuitbreaker:
    instances:
      supplier:
        slidingWindowSize: 20
        failureRateThreshold: 50
        waitDurationInOpenState: 30s
  retry:
    instances:
      supplier:
        maxAttempts: 3
        waitDuration: 200ms
        enableExponentialBackoff: true

Quarkus offers the same through MicroProfile Fault Tolerance (@Retry, @CircuitBreaker, @Timeout, @Fallback). Always set a client timeout too.

How a circuit breaker works

Martin Fowler’s description: wrap a protected call in a circuit breaker object that monitors for failures. Once failures reach a threshold, the breaker trips, and further calls return an error at once, without the protected call being made.

  1. Closed: calls go through, and failures are counted.
  2. Open: calls fail fast for a set time, giving the dependency room to recover.
  3. Half-open: trial calls go through (Fowler describes one; libraries allow a configured number); success closes the breaker, failure opens it again.

Alert when a breaker opens: it is a symptom someone needs to see.

The states, drawn

From Hystrix to Resilience4j

  • Hystrix, Netflix’s library, is in maintenance mode and no longer in active development. Netflix says it keeps using it for its existing applications, uses open, active projects such as Resilience4j for new ones, and is beginning to recommend others do the same.
  • Resilience4j is a lightweight fault-tolerance library designed for functional programming. It provides a circuit breaker, retry, rate limiter, time limiter (timeouts) and bulkhead, in semaphore and thread-pool forms, which wrap any function or lambda.
  • On Quarkus and other MicroProfile runtimes, MicroProfile Fault Tolerance gives the same ideas as annotations (see Resilience in code, above).

Analysis: if you still run Hystrix, expect to rewrite each command as a decorator or annotation. The concepts, closed, open and half-open, carry over.

Circuit breaking in code, or in the mesh?

Istio’s “circuit breaking” is configured on a DestinationRule and enforced by its Envoy sidecars. It is not the same mechanism as a library’s breaker. Envoy enforces connection and request limits at the network level, without code in each application, and each proxy decides on its own (Envoy calls its limits “fully distributed (not coordinated)”). Its outlier detection is passive health checking: it removes hosts that behave unlike the others, for example after consecutive errors, from the load-balancing set for a while.

In code (Resilience4j, MicroProfile Fault Tolerance)In the mesh (Istio, Envoy)
What trips itFailure rate or slow calls over a window, per named dependencyConnection and pending-request limits; outlier detection on errors per host
What it isolates (analysis)The whole dependency, as your code calls itIndividual pods (ejection), or the connections to a service
When it tripsYour fallback runs: a cached answer, a default, or an honest “unavailable”The caller gets an error (in Istio’s own example, HTTP 503) and must handle it
Languages (analysis)One library per language, and the same settings repeated per serviceAny language, no code change, configured in one place
Who changes it (analysis)The service team, in code and configurationOften a platform team, in Kubernetes resources

Choose by requirement

If this is true for youIt leans towards (analysis)
The caller needs a fallback that makes business sense (cached prices, “delivery date unknown”)Our view: a breaker in code, because only the application knows what a sensible fallback is
Services in many languages, and you want one consistent policy without changing codeThe mesh
Usually one bad pod among healthy onesMesh outlier detection, which takes that pod out of rotation
A whole dependency is down, or it is an external API outside the meshA breaker in code, around the client: the mesh guards only traffic that passes through its sidecars
You do not run a service meshOur view: a breaker in code. Adopting a mesh only for this has a cost (see Service Mesh & Istio)
You need both protectionsBoth: the mesh for connection limits and pod ejection, code for timeouts and fallbacks

Analysis: set retries in one layer only. If the application retries three times and the mesh retries twice per attempt, one failing call can become up to nine requests, when the dependency is least able to take them. Istio applies a default retry policy (two retries on connection failures and similar) even if you configure none.

Our view, and the other view

Our view: keep timeouts and fallbacks in code, where the business meaning is, and let a mesh, if you have one, add connection limits and eject bad pods. Do not adopt a mesh only to get circuit breaking.

The other view: platform teams that already run a mesh often prefer one place for every network policy. Keeping resilience out of application code means fewer libraries to upgrade in every service and the same behaviour in every language, and teams accept handling a 503 in exchange.

Data across services

  • Database per service: separate schemas or instances; no other service reads its tables.
  • Cross-service transactions become sagas with compensating steps.
  • Reliable events with the transactional outbox, so a state change and its event never disagree.
  • Queries across services: API composition (call and combine) for small cases; a read model built from events (CQRS) for heavy ones.
  • Reporting goes to the warehouse via events or CDC, not by joining services' databases.
  • Details on Architecture and Event Sourcing.

Observability is not optional

  • Distributed tracing (OpenTelemetry): one trace ID follows a request through every service, queue and database call.
  • Structured logs with trace ID, service, version and request ID on every line.
  • Metrics per service: rate, errors, duration (RED) and saturation; SLOs on user-facing ones.
  • Health endpoints: liveness (restart me) separate from readiness (send me traffic).
  • Dependency maps from traces show who calls whom, and where latency comes from.

Testing microservices

  • Unit and component tests inside each service, with its own database in a container.
  • Contract tests (Pact, Spring Cloud Contract) between consumers and providers, run in both pipelines, so a provider cannot break a consumer unnoticed.
  • A few end-to-end tests of critical journeys in a shared environment.
  • Event schema checks with a schema registry and compatibility rules.
  • Resilience tests: kill or slow a dependency and check the caller degrades as designed.

Security between services

  • Zero trust: authenticate every call, even inside the network.
  • Service identity: mTLS from a mesh, or Google-signed ID tokens between Cloud Run services.
  • User context: propagate the user's token or a signed internal token; each service still checks its own permissions.
  • Least privilege per service: its own service account, database user and secrets.

Anti-patterns

  • Distributed monolith: services that must be deployed together or share a database.
  • Shared database written by several services.
  • Chatty synchronous chains: A calls B calls C calls D for one request.
  • Nano-services too small to justify their operational cost.
  • Shared libraries with business logic that force lock-step upgrades (shared infrastructure blueprints are fine).
  • No ownership: services nobody is on call for.
  • Splitting before understanding the domain: boundaries drawn too early are expensive to move.

Migrating from a monolith

  1. Make the monolith modular first: enforce module boundaries and separate each module's data.
  2. Pick one capability with a clear boundary and a real reason to move.
  3. Put a routing layer (gateway or proxy) in front, and route that capability's traffic to the new service (strangler fig).
  4. Move its data, with a period of syncing or dual reads, and make the new service the only writer.
  5. Remove the old code. Repeat only if the first extraction paid off.

Readiness checklist

  • Can you deploy a service with one automated pipeline, in minutes?
  • Do you have centralised logs, metrics and tracing?
  • Can you create a new service from a template in under an hour?
  • Do teams own services end to end, including on-call?
  • Are the domain boundaries understood and stable?

If several answers are no, a modular monolith will serve you better for now.

Levels: what to expect

1 Foundation

  • Explain monolith vs modular monolith vs microservices
  • Work in one service: build, test, deploy, read its logs and traces
  • Know why services own their data

2 Practitioner

  • Build a service with timeouts, retries, circuit breakers and health checks
  • Use events and the outbox to integrate with other services
  • Write contract tests with consumers

3 Senior

  • Draw service boundaries from the domain; decide when not to split
  • Design sagas, read models and observability across services
  • Lead a strangler-fig extraction from a monolith

4 Expert

  • Set the organisation's service architecture and platform blueprint
  • Align team structure with service ownership
  • Decide when to consolidate services as well as split them

Each level includes the ones before it. See Start here for what the levels mean.

Microservices

Building a system as small, independently deployable services that each own their data. When it pays off, how to split, how services talk and fail, and the traps that turn microservices into a distributed monolith. Patterns referenced here are on Architecture.

Monolith, modular monolith, microservices

MonolithModular monolithMicroservices
DeployablesOneOne, with enforced internal modulesMany, deployed independently
DataOne shared databaseOne database, schema per moduleEach service owns its data
Calls between partsIn-processIn-process through module APIsOver the network
ScalingWhole appWhole appPer service
Team fitOne small teamOne to a few teamsMany teams owning services end to end
Main costTangling as it growsDiscipline to keep boundariesDistributed-systems complexity and operations

Most systems should start as a modular monolith and extract a service only when a boundary has proved stable and there is a concrete reason: independent scaling, a different release cadence, a separate team, or different technology or security needs.

What microservices buy, and cost

Gains

  • Teams deploy their service without coordinating a big release.
  • Scale and tune each service for its own load.
  • A failure can be contained to one service.
  • Different services can use different technologies where it helps.

Costs

  • Network calls fail, time out and add latency.
  • No cross-service transactions: sagas and eventual consistency instead.
  • Debugging needs distributed tracing; testing needs contracts.
  • Many pipelines, deployments, dashboards and on-call rotations.

How to split services

  • By business capability or bounded context (domain-driven design): search, case files, billing, identity. Not by technical layer (a "database service" is an anti-pattern).
  • Each service owns its data and is the only one that writes it. Others ask through its API or react to its events.
  • High cohesion inside, loose coupling between: a typical change should touch one service.
  • Align with teams (Conway's law): one team owns a service end to end.
  • Size by responsibility, not lines of code. Too many tiny services ("nano-services") multiply network calls and operations for no gain.
  • Test the split: if two services must always deploy together, they are one service.

Communication

StyleUse forWatch out for
Synchronous REST / gRPCQueries that need an answer nowChains of calls: latency adds up and availability multiplies down
Asynchronous events (Kafka, Pub/Sub)Telling others something happenedEventual consistency, duplicates, ordering
Asynchronous commands (queues)Work another service should doRetries, dead letters, idempotency
  • Prefer events between domains; keep synchronous calls shallow (ideally one hop).
  • Cache or replicate the data you need from other services (from their events) rather than calling them on every request.
  • See APIs & Integration, Kafka and GraphQL.

Infrastructure around services

  • Service discovery: Kubernetes DNS names, Cloud Run URLs, or a registry. Never hard-code instance IPs.
  • API gateway at the edge for authentication, rate limits and routing (Apigee); a backend for frontend per client type when needs differ.
  • Service mesh (Istio / Cloud Service Mesh) for mTLS, retries and traffic splitting between services, without code in each one.
  • Configuration and secrets injected at runtime per environment.
  • Platform blueprint: a service template with logging, tracing, health checks, security and CI already wired, so each new service starts correct.

Resilience in code (Spring + Resilience4j)

@Service
class MirrorClient {
  private final RestClient http;
  MirrorClient(RestClient http) { this.http = http; }

  @CircuitBreaker(name = "mirror", fallbackMethod = "unavailable")
  @Retry(name = "mirror")
  Listing list(String prefix) {
    return http.get().uri("/objects?prefix={p}", prefix).retrieve().body(Listing.class);
  }

  // honest degradation: "cannot see", never "nothing there"
  Listing unavailable(String prefix, Throwable t) {
    return Listing.unknown("mirror unavailable: " + t.getMessage());
  }
}
resilience4j:
  circuitbreaker:
    instances:
      mirror:
        slidingWindowSize: 20
        failureRateThreshold: 50
        waitDurationInOpenState: 30s
  retry:
    instances:
      mirror:
        maxAttempts: 3
        waitDuration: 200ms
        enableExponentialBackoff: true

Quarkus offers the same through MicroProfile Fault Tolerance (@Retry, @CircuitBreaker, @Timeout, @Fallback). Always set a client timeout too.

Data across services

  • Database per service: separate schemas or instances; no other service reads its tables.
  • Cross-service transactions become sagas with compensating steps.
  • Reliable events with the transactional outbox, so a state change and its event never disagree.
  • Queries across services: API composition (call and combine) for small cases; a read model built from events (CQRS) for heavy ones.
  • Reporting goes to the warehouse via events or CDC, not by joining services' databases.
  • Details on Architecture and Event Sourcing.

Observability is not optional

  • Distributed tracing (OpenTelemetry): one trace ID follows a request through every service, queue and database call.
  • Structured logs with trace ID, service, version and request ID on every line.
  • Metrics per service: rate, errors, duration (RED) and saturation; SLOs on user-facing ones.
  • Health endpoints: liveness (restart me) separate from readiness (send me traffic).
  • Dependency maps from traces show who calls whom, and where latency comes from.

Testing microservices

  • Unit and component tests inside each service, with its own database in a container.
  • Contract tests (Pact, Spring Cloud Contract) between consumers and providers, run in both pipelines, so a provider cannot break a consumer unnoticed.
  • A few end-to-end tests of critical journeys in a shared environment.
  • Event schema checks with a schema registry and compatibility rules.
  • Resilience tests: kill or slow a dependency and check the caller degrades as designed.

Security between services

  • Zero trust: authenticate every call, even inside the network.
  • Service identity: mTLS from a mesh, or Google-signed ID tokens between Cloud Run services.
  • User context: propagate the user's token or a signed internal token; each service still checks its own permissions.
  • Least privilege per service: its own service account, database user and secrets.

Anti-patterns

  • Distributed monolith: services that must be deployed together or share a database.
  • Shared database written by several services.
  • Chatty synchronous chains: A calls B calls C calls D for one request.
  • Nano-services too small to justify their operational cost.
  • Shared libraries with business logic that force lock-step upgrades (shared infrastructure blueprints are fine).
  • No ownership: services nobody is on call for.
  • Splitting before understanding the domain: boundaries drawn too early are expensive to move.

Migrating from a monolith

  1. Make the monolith modular first: enforce module boundaries and separate each module's data.
  2. Pick one capability with a clear boundary and a real reason to move.
  3. Put a routing layer (gateway or proxy) in front, and route that capability's traffic to the new service (strangler fig).
  4. Move its data, with a period of syncing or dual reads, and make the new service the only writer.
  5. Remove the old code. Repeat only if the first extraction paid off.

Readiness checklist

  • Can you deploy a service with one automated pipeline, in minutes?
  • Do you have centralised logs, metrics and tracing?
  • Can you create a new service from a template in under an hour?
  • Do teams own services end to end, including on-call?
  • Are the domain boundaries understood and stable?

If several answers are no, a modular monolith will serve you better for now.

Levels: what to expect

1 Foundation

  • Explain monolith vs modular monolith vs microservices
  • Work in one service: build, test, deploy, read its logs and traces
  • Know why services own their data

2 Practitioner

  • Build a service with timeouts, retries, circuit breakers and health checks
  • Use events and the outbox to integrate with other services
  • Write contract tests with consumers

3 Senior

  • Draw service boundaries from the domain; decide when not to split
  • Design sagas, read models and observability across services
  • Lead a strangler-fig extraction from a monolith

4 Expert

  • Set the organisation's service architecture and platform blueprint
  • Align team structure with service ownership
  • Decide when to consolidate services as well as split them

Each level includes the ones before it. See Start here for what the levels mean.

Build tools: Maven, Gradle, npm, Yarn and pnpm

A build tool turns source code into something you can run or ship: it fetches dependencies, compiles, runs the tests, packages the result and publishes it. A good build gives the same result on every laptop and every CI runner. This page covers the Java tools (Maven and Gradle) and the Node.js tools (npm, Yarn, pnpm and the bundlers), with each claim checked against the tool's own documentation.

What every build tool does

  • Resolves dependencies: downloads the libraries you name, and the libraries they need (transitive dependencies), from a registry such as Maven Central or the npm registry.
  • Runs the steps in order: compile, test, package, publish. You ask for the last step and the tool runs the ones before it.
  • Pins versions: a lockfile, a wrapper script or a version catalog, so a build next year uses the same versions as today.
  • Avoids repeated work: skips steps whose inputs have not changed.
  • Is the same in CI as on your machine. If it only builds on one person's laptop, it does not build.

Maven: convention over configuration

A Maven project is described by its pom.xml (Project Object Model). If you follow the standard layout (src/main/java, src/test/java), you configure almost nothing.

  • Three built-in lifecycles: default (build and deploy), clean and site.
  • Main phases of the default lifecycle, in order: validate, compile, test, package, verify, install (into your local repository), deploy (to a remote repository). mvn verify runs every phase before verify too, so you only name the last one.
  • Plugins do the work: each phase runs plugin goals bound to it, and the bindings depend on the packaging (jar, war, pom).
  • Transitive dependencies are included automatically. When two versions of one library meet, Maven picks the nearest definition in the dependency tree, not the newest. That surprises people: check with mvn dependency:tree.
  • <dependencyManagement> pins versions for the whole tree, and the import scope pulls in a published bill of materials (BOM), as Spring Boot and many cloud SDKs provide.
  • Scopes: compile (the default), provided (the JDK or the container supplies it at runtime), runtime, test (only for compiling and running tests, and not passed on).
  • The Maven Wrapper (mvnw) downloads the Maven version the project declares, so nobody needs the right one installed.
<project>
  <modelVersion>4.0.0</modelVersion>
  <groupId>com.example</groupId>
  <artifactId>orders</artifactId>
  <version>1.0.0-SNAPSHOT</version>

  <dependencyManagement>           <!-- one place for versions -->
    <dependencies>
      <dependency>
        <groupId>org.junit</groupId>
        <artifactId>junit-bom</artifactId>
        <version>5.11.0</version>
        <type>pom</type>
        <scope>import</scope>
      </dependency>
    </dependencies>
  </dependencyManagement>

  <dependencies>
    <dependency>
      <groupId>org.junit.jupiter</groupId>
      <artifactId>junit-jupiter</artifactId>   <!-- no version: the BOM sets it -->
      <scope>test</scope>
    </dependency>
  </dependencies>
</project>

./mvnw verify                  # compile, test, package, verify
./mvnw dependency:tree         # which version won, and why

Gradle: a task graph you can program

A Gradle build is written in Kotlin (build.gradle.kts) or Groovy (build.gradle). Instead of a fixed lifecycle, it builds a graph of tasks and runs the ones your request needs.

  • Three phases every build goes through: initialization (which projects are in the build), configuration (run the build scripts and work out the task graph), execution (run the selected tasks).
  • The Gradle Wrapper (gradlew) is the recommended way to run any Gradle build: it runs the declared Gradle version and downloads it if needed. Commit it.
  • The Daemon is a long-lived background process that hosts Gradle's engine, so later builds skip the start-up cost.
  • Incremental builds: a task whose inputs and outputs have not changed is skipped as up to date.
  • The build cache goes further: it reuses task outputs from earlier builds, on this machine or from a shared remote cache, when the inputs match.
  • The configuration cache saves the result of the configuration phase and reuses it on the next build.
  • Version catalogs keep every dependency version in one file, gradle/libs.versions.toml, referenced as libs.… in the build scripts.
  • Android apps are built with Gradle, through the Android Gradle plugin.
# gradle/libs.versions.toml
[versions]
junit = "5.11.0"
[libraries]
junit-bom = { module = "org.junit:junit-bom", version.ref = "junit" }

// build.gradle.kts
plugins { java }
dependencies {
    testImplementation(platform(libs.junit.bom))
    testImplementation("org.junit.jupiter:junit-jupiter")
}
tasks.test { useJUnitPlatform() }

./gradlew build                # compile, test, assemble
./gradlew build --build-cache  # reuse outputs from earlier builds

Choose by requirement

If this is true for youIt leans towards
You build an Android appGradle: Android builds use it, through the Android Gradle plugin
A large multi-module build where build time hurtsGradle: up-to-date checks, the Daemon and the build and configuration caches skip work
You want every project to look the same, with little custom logicMaven: a fixed lifecycle and conventions, configured rather than programmed
The build needs real custom logicGradle: the build is code; in Maven the logic goes into a plugin
Your team, CI templates and company plugins already use oneStay with it unless a row above is a real, measured problem: switching has a cost

Other views: some engineers find Gradle builds harder to read because the scripts are code; others find Maven’s XML verbose. Both are preferences. The rows above are requirements.

npm: the default for Node.js

  • package.json names your dependencies with version ranges and holds your scripts; npm run build runs one. A script named prebuild or postbuild runs before or after it.
  • package-lock.json is generated whenever npm changes node_modules. It records the exact tree, so the next install builds the same one. Commit it.
  • npm ci is for CI: it needs an existing lockfile, fails if package.json and the lock disagree, and never writes to either. Use npm install to change dependencies, and npm ci to reproduce them.
  • npx runs a package's command without installing it into your project.
  • Ranges: a caret allows any change that keeps the left-most non-zero number; a tilde allows only patch-level changes when the minor is given. The lockfile is what stops a range from drifting between installs.
"dependencies": {
  "express": "^5.1.0",     // 5.x.x, never 6
  "lodash": "~4.17.21"     // 4.17.x only
}

npm 12: install scripts are off by default

Install scripts (preinstall, install, postinstall) run code from a dependency on your machine the moment you install it, so a compromised package can act before you have run a line of your own code. npm 12, released in July 2026, changed the defaults:

  • Dependency lifecycle scripts are blocked unless the root package's allowScripts policy allows them. Run npm install-scripts approve to record approvals, then npm rebuild to run the newly approved scripts.
  • Git and tarball-URL dependencies are refused unless you opt in (allow-git and allow-remote now default to none).
  • npm-shrinkwrap.json is no longer read: rename it to package-lock.json.
  • On an older npm, --ignore-scripts turns install scripts off, though npm test and npm run still run the script you asked for.

Yarn, pnpm and Corepack

  • Yarn started at Facebook in 2016. Its modern version can install with Plug'n'Play: no node_modules folder at all, but a single .pnp.cjs loader that tells Node where each package is. It can also use a normal node_modules install.
  • pnpm keeps one content-addressable store on disk. Each project's files are hard-linked or copy-on-write cloned from it, so a hundred projects using one library do not keep a hundred copies, and a new version adds only the files that changed.
  • pnpm's node_modules is not flat: only your direct dependencies sit at the top, as symlinks. Code cannot quietly import a package it never declared. Tools that dislike symlinks can use nodeLinker: hoisted.
  • Corepack lets a project use the Yarn or pnpm version named in the packageManager field of package.json, without installing it globally. It shipped with Node.js until version 25. From 25 on, install Corepack separately.

Bundlers: the other half of a JavaScript build

  • A package manager (npm, Yarn, pnpm) fetches dependencies. A bundler turns your modules into the few files a browser downloads. A front-end build needs both.
  • webpack (2014) builds a dependency graph of your modules and supports code splitting with dynamic import().
  • Vite has two parts: a dev server that serves native ES modules with very fast hot module replacement, and a build command that bundles for production with Rolldown.
  • TypeScript adds a type-check step: tsc --noEmit in CI catches type errors even when the bundler only strips the types.

Levels: what to expect

1 Foundation

  • Run a Maven, Gradle and npm build from the wrapper or lockfile
  • Name the lifecycle phases or tasks a build runs
  • Add a dependency and read the dependency tree

2 Practitioner

  • Pin versions with a BOM, a version catalog or a lockfile
  • Explain why a transitive version won and override it
  • Make CI builds reproducible and cached

3 Senior

  • Design a multi-module or monorepo build
  • Use the Gradle build and configuration caches
  • Set an install-script and dependency-source policy

4 Expert

  • Set build standards across an organisation
  • Lead migrations between build tools
  • Secure the build supply chain end to end

Each level includes the ones before it. See Start here for what the levels mean.

Kubernetes: disaster recovery and best practices

How to keep Kubernetes workloads running through ordinary failures, and how to get them back after a bad one. Read Kubernetes first; this page is about what happens when things break.

Know what you are protecting

Two numbers decide everything else. RPO (recovery point objective): how much data you can afford to lose, measured in time. RTO (recovery time objective): how long you can afford to be down. Agree them with the business before choosing a design, because a shorter RTO or RPO always costs more.

Best practices that prevent most outages

  • Never run naked Pods: use a Deployment or StatefulSet, so a failed Pod is replaced.
  • Run more than one replica of anything that matters.
  • Spread across zones: topology spread constraints (with a topologyKey such as the zone label) keep replicas apart, so one zone failing does not take them all.
  • PodDisruptionBudgets: say how many replicas must stay up during voluntary disruptions such as node drains and upgrades. Tools should evict through the Eviction API, which respects them.
  • Probes: readiness keeps traffic away until a Pod is ready; liveness restarts a stuck container; a startup probe holds the other two off until a slow starter is up.
  • Requests and limits on every container, so the scheduler can place work and one noisy Pod cannot starve the rest.
  • Version-control all configuration and keep it simple, with consistent labels.

Back up: three layers

  • etcd (self-managed clusters): take regular snapshots with etcdctl snapshot save, store them off the cluster, and encrypt them: they hold every Secret.
  • Workloads and volumes: Velero backs up cluster objects and persistent volumes to object storage, on a schedule, with a retention period (--ttl). The VolumeSnapshot API takes snapshots of volumes through the storage system's driver.
  • Managed clusters: the provider runs the control plane and etcd; you protect your workloads and data. Each has a backup service: Backup for GKE, AKS backup, and AWS Backup for EKS.
  • Databases: prefer a managed database, or a database operator with its own backups and point-in-time recovery, over raw volume snapshots of a running database.

Restore: the commands

From the Kubernetes and Velero documentation. Names in angle brackets are yours.

# etcd (self-managed): snapshot, and restore into a new data directory
ETCDCTL_API=3 etcdctl --endpoints $ENDPOINT snapshot save snapshot.db
etcdutl --data-dir <data-dir-location> snapshot restore snapshot.db

# Velero: back up on a schedule
velero schedule create <schedule-name> --schedule "0 7 * * *" --ttl 720h0m0s

# Velero disaster recovery: make the backup location read-only, restore, then set it back
kubectl patch backupstoragelocation <location> --namespace velero \
  --type merge --patch '{"spec":{"accessMode":"ReadOnly"}}'
velero restore create --from-backup <schedule-name>-<timestamp>
kubectl patch backupstoragelocation <location> --namespace velero \
  --type merge --patch '{"spec":{"accessMode":"ReadWrite"}}'

Making the backup location read-only first stops a scheduled backup from overwriting good backups while you restore.

Four DR strategies, from cheap to fast

  1. Backup and restore: rebuild the cluster and restore data when disaster strikes. Cheapest; slowest to recover.
  2. Pilot light: a minimal copy of the core (data replicated, little else running) in another region, scaled up on the day.
  3. Warm standby: a smaller but working copy runs all the time, ready to take traffic and scale.
  4. Multi-site active/active: two or more regions serve traffic at once. Fastest recovery; most expensive and hardest to keep consistent.

These four are the categories in AWS's disaster recovery whitepaper; the same ideas apply on any cloud.

A backup you have not restored is a hope

  • Restore regularly into a scratch cluster, and time it. That time is your real RTO.
  • Write the runbook a person can follow without the automation, and keep it outside the cluster. See SRE.
  • Run game days: drain a zone, delete a namespace in a test cluster, lose the etcd leader, and watch what happens.
  • Watch the backups: alert when a scheduled backup fails or is late. See Observability.

Levels: what to expect

1 Foundation

  • Run workloads as Deployments with several replicas
  • Add readiness and liveness probes
  • Explain RPO and RTO

2 Practitioner

  • Add PodDisruptionBudgets and zone spreading
  • Schedule Velero or managed backups and restore one
  • Keep all manifests in Git so a cluster is replaceable

3 Senior

  • Choose a DR strategy against agreed RPO and RTO
  • Design multi-zone and multi-region clusters
  • Run restore drills and game days

4 Expert

  • Own platform resilience across clusters and regions
  • Set backup, restore and DR standards
  • Lead recovery during a major incident

Each level includes the ones before it. See Start here for what the levels mean.

A brief history of software systems

How we got here, in plain words: each era solved the last one's pain and rediscovered the same hard problems. Knowing the story makes today's tools easier to understand, and easier to judge.

The thread through it all

Every era wrestled with the same four questions: how do two programs agree on a contract, where does state live, what happens when something fails, and how do we see what went wrong? The answers moved from heavy and agreed in advance, to light and flexible, and back again whenever the light way hurt. The questions never went away.

Distributed objects: everything agreed in advance

  • CORBA, from the Object Management Group, let programs in different languages call each other's objects across a network. You wrote the contract in an interface definition language and generated client stubs and server skeletons before anything could talk.
  • Java RMI did the same between Java programs, more simply, and Java could load the classes it needed over the network.
  • Application servers such as WebLogic wrapped this with transactions, security and pooling. Powerful, and heavy.
  • What it taught us: a remote call is not a local call. It can be slow, fail halfway, or never answer.

Enterprise JavaBeans: the beans we lived with

  • Session beans held business logic. Stateless ones served any caller and were pooled, so they suited reads and simple operations. Stateful ones kept a conversation with one client across calls.
  • Stateful session beans and database locks were how some booking and ticketing systems held a seat while a customer finished: the bean kept the conversation, the database kept the lock.
  • Entity beans represented rows in the database, with the container managing how they were loaded and saved. They were heavy and slow to work with, and plain Java objects mapped by tools such as Hibernate, and later JPA, replaced them.
  • Message-driven beans consumed messages from a JMS queue or topic, bringing event-driven work inside the application server.
  • What it taught us: the ideas (stateless services, conversations, transactions, messaging) were right; the weight was not. Spring, and later EJB itself, kept the ideas and dropped the ceremony.

Models, UML and generated screens

  • UML, which appeared in 1997, gave teams one language for drawing systems: class diagrams, sequence diagrams, use cases. Grady Booch, James Rumbaugh and Ivar Jacobson brought their methods together into it.
  • Model-driven architecture, from the Object Management Group, went further: draw the model, then generate the code from it. It worked well for some layers and poorly for the rest.
  • XSLT transformed XML into HTML, so screens could be generated from data and templates rather than written by hand.
  • What it taught us: generating code from a model is powerful when the model is the truth, and painful when people edit the generated code. The same lesson applies to AI-generated code today.

The early web: stateless by design

  • HTTP forgets you between requests. To remember who you were, pages carried state in hidden form fields, in the URL (URL rewriting) and, increasingly, in cookies.
  • HTML was standardised in the mid-1990s, but browsers still differed: code checked whether it ran in Internet Explorer or Netscape, and what we now call Ajax worked first through Microsoft's XMLHTTP object.
  • Caching mattered because bandwidth was precious on dial-up: browsers and proxies kept copies, and pages said how long a copy stayed fresh.
  • What it taught us: statelessness scales, and every bit of state has to live somewhere on purpose.

Pages made on the server

  • CGI scripts started a new process for every request.
  • PHP began in 1994 as Rasmus Lerdorf's "Personal Home Page" tools and grew into a language for building web pages on the server.
  • Java servlets and JSP ran inside a long-lived server, handling many requests without starting a process each time.
  • Struts, an Apache project founded in May 2000, brought the model-view-controller pattern to Java web applications.

Runtimes get fast, and get company

  • Java began by interpreting bytecode, which was slow. Just-in-time (JIT) compilers, which compile the busiest code to machine code while the program runs, made it fast, and the JVM's HotSpot became the standard approach.
  • Microsoft's C# and .NET arrived in the early 2000s with many of the same ideas: a managed runtime, garbage collection and code compiled just in time.
  • What it taught us: a good runtime lets you write simpler code and still go fast, and ideas spread quickly once they work.

Integration: buses, services and lighter ways

  • SOAP web services brought back contracts agreed in advance, written in WSDL, with generated clients, much as CORBA had done.
  • Enterprise service buses put routing, transformation and orchestration into one large central product.
  • Lighter tools followed. Apache Camel implemented the patterns from Hohpe and Woolf's Enterprise Integration Patterns as a library. Spring came into being in 2003, by its own account, as a response to the complexity of the early J2EE specifications.
  • What it taught us: one big central hub becomes the bottleneck and the single point of failure.

REST, long journeys, and sagas

  • REST, which Roy Fielding described in his doctoral dissertation, used the web's own design (resources, URLs, standard methods, caching) instead of a custom remote-call layer.
  • Without distributed transactions, a long piece of work becomes a journey of steps. If it fails halfway, you undo the completed steps in reverse order, which only works if you recorded every step you took.
  • This idea is old. It was described as the "saga" in a 1987 database paper by Hector Garcia-Molina and Kenneth Salem, long before microservices made the word popular again. See Architecture.

Microservices, cloud, and seeing what happens

  • Microservices split systems into small services that each own their data. They brought back every distributed-systems problem at once, now spread across many teams.
  • For years, failures were hard to follow from one service to the next. Observability caught up: logs, metrics and traces, and a shared trace context passed with every call (the W3C traceparent header). See Observability.
  • The cloud turned servers into something you rent by the minute and declare in code.

The people behind the ideas

We remember the famous product launches and forget many of the people whose ideas we use every day. A few worth knowing, and reading:

  • The "Gang of Four", Erich Gamma, Richard Helm, Ralph Johnson and John Vlissides, wrote Design Patterns: Elements of Reusable Object-Oriented Software, which gave us a shared vocabulary: factory, observer, strategy, adapter.
  • Martin Fowler wrote Refactoring (its second edition with Kent Beck) and Patterns of Enterprise Application Architecture, and has explained ideas such as continuous integration and microservices to a generation of engineers. He calls the Gang of Four's book "the best book ever written on object-oriented design".
  • Kent Beck developed Extreme Programming, and test-driven development within it, in the late 1990s.
  • Grady Booch, James Rumbaugh and Ivar Jacobson created UML. Gregor Hohpe and Bobby Woolf wrote Enterprise Integration Patterns. Roy Fielding described REST. Hector Garcia-Molina and Kenneth Salem described sagas.
  • And thousands of open-source maintainers whose names most of us never learn, whose work runs in almost everything we build.

Before you ask an AI to explain a pattern, read the person who named it. The original is usually clearer, and it tells you why. Start with Fowler on the Gang of Four, Extreme Programming and test-driven development.

And now, AI

AI can generate the code that each of these eras made us write by hand: the stubs, the boilerplate, the glue. But the four questions have not changed: contracts, state, failure, and seeing what went wrong. People who know this history recognise an old problem in a new form, and do not mistake generated code for understanding. See AI for Engineers.

Database design

Relational modelling, indexes, partitioning, sharding, transactions and migrations. Examples in PostgreSQL; the ideas carry to other engines. Warehouse design is on the BigQuery tab.

Modelling rules

  • Start normalised (third normal form): each fact stored once, in the table it describes. Denormalise later, on purpose, for a measured read need.
  • Every table has a primary key. Surrogate (bigint identity or UUID) for internal identity; natural keys (CNR, email) get a UNIQUE constraint.
  • Never reuse or renumber a key that others store: URLs, foreign systems, legal records.
  • Constraints are free correctness: NOT NULL, UNIQUE, CHECK, FOREIGN KEY. The database enforces them for every writer, including the one you forgot.
  • Right types: date / timestamptz not strings; numeric for money, never float; text over arbitrary varchar(n); jsonb for truly variable attributes, not as a substitute for columns.
  • Name things plainly and consistently: snake_case, singular or plural but one choice, _at for timestamps, _id for keys.

A schema example

CREATE TABLE court (
  court_code text PRIMARY KEY,
  name       text NOT NULL
);

CREATE TABLE judgment (
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  judgment_key  text NOT NULL UNIQUE,             -- stable natural key
  cnr           text NOT NULL,
  court_code    text NOT NULL REFERENCES court,
  decision_date date,
  status        text NOT NULL CHECK (status IN ('DISPOSED','PENDING')),
  full_text     text,
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now()
);

-- many-to-many through a join table
CREATE TABLE judgment_citation (
  citing_id bigint NOT NULL REFERENCES judgment ON DELETE CASCADE,
  cited_id  bigint NOT NULL REFERENCES judgment,
  PRIMARY KEY (citing_id, cited_id)
);

Index rules of thumb

  • Index for your queries, not your columns. Start from the slow query's WHERE, JOIN and ORDER BY.
  • Composite order: equality columns first, then the range or sort column. (court_code, decision_date) serves court_code = ? AND decision_date > ?; the reverse order serves it poorly.
  • Leftmost prefix: an index on (a, b, c) helps queries on a, a,b, a,b,c, not on b alone.
  • Foreign keys usually need an index on the referencing column, or deletes and joins scan.
  • Every index slows writes and uses disk. Drop unused ones (pg_stat_user_indexes.idx_scan = 0).
  • Low-selectivity columns (a boolean, a status with 3 values) rarely help alone; use a partial index instead.
  • Functions on columns (WHERE date(created_at) = …) skip a plain index; write a range or index the expression.
  • Build on live tables with CREATE INDEX CONCURRENTLY, then confirm it is valid: an interrupted build leaves an INVALID index.

Reading a query plan

EXPLAIN (ANALYZE, BUFFERS)
SELECT cnr, decision_date FROM judgment
WHERE court_code = '2_5' AND decision_date >= '2024-01-01'
ORDER BY decision_date DESC LIMIT 20;

-- look for:
--   Seq Scan on a big table          → missing or unusable index
--   rows=10 (estimated) vs actual rows=500000 → stale stats: ANALYZE
--   Sort … external merge Disk       → work_mem too low, or index the sort
--   Nested Loop with huge inner loops → join order or missing index
--   Index Only Scan, Heap Fetches: 0 → ideal

-- check index validity after a concurrent build
SELECT indexrelid::regclass, indisvalid FROM pg_index WHERE NOT indisvalid;
-- slowest queries (pg_stat_statements extension)
SELECT query, calls, mean_exec_time FROM pg_stat_statements
ORDER BY total_exec_time DESC LIMIT 10;

Partitioning (one database)

CREATE TABLE event (
  id         bigserial,                -- identity columns on partitioned tables need PostgreSQL 17+
  event_date date NOT NULL,
  payload    jsonb,
  PRIMARY KEY (id, event_date)          -- must include the partition key
) PARTITION BY RANGE (event_date);

CREATE TABLE event_2025 PARTITION OF event
  FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');
CREATE TABLE event_2026 PARTITION OF event
  FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');
CREATE TABLE event_default PARTITION OF event DEFAULT;

-- retire old data instantly instead of a slow DELETE
ALTER TABLE event DETACH PARTITION event_2025;
DROP TABLE event_2025;

-- other kinds:  PARTITION BY LIST (region)   PARTITION BY HASH (customer_id)
  • Why: queries that filter on the key skip other partitions (pruning); old data drops in one statement; maintenance runs per partition.
  • When: very large tables (tens of millions of rows and up) with a natural time or category filter. Small tables only get slower.
  • Cost: unique constraints must include the partition key; queries without it scan every partition.

Sharding (many databases)

  • What: split rows across separate database servers by a shard key, so each holds part of the data and load.
  • Shard key choice is the whole design: high cardinality, evenly spread, present in almost every query (tenant ID, user ID).
  • Hash sharding spreads load evenly but makes range queries hit every shard. Range sharding keeps ranges together but creates hot shards (all of today's writes on one).
  • Directory / lookup sharding maps keys to shards in a table: flexible, but the directory becomes critical.
  • Costs: cross-shard joins and transactions become application problems; resharding is a migration project; operations multiply.
  • Try first: better indexes, read replicas, caching, partitioning, a bigger instance, archiving cold data. Shard when one primary truly cannot take the writes.
  • Managed options do it for you: Spanner, AlloyDB with read pools, Citus, Vitess, CockroachDB.

Replication & scaling reads

  • Read replicas copy the primary asynchronously. Scale reads; accept replica lag (a user may not see their own write).
  • Synchronous replicas confirm writes before commit: no data loss on failover, at the cost of write latency.
  • High availability (Cloud SQL HA, Patroni) promotes a standby when the primary fails.
  • Connection pooling (PgBouncer, HikariCP, R2DBC pool): Postgres connections are expensive. Size pools so instances × pool size stays under max_connections.
  • Caching (Redis) for hot, read-heavy data, with a deliberate invalidation rule.

Transactions, isolation, locking

IsolationPrevents
Read committed (Postgres default)Dirty reads. Each statement sees data committed before it began.
Repeatable readNon-repeatable reads: the transaction sees one snapshot throughout.
SerializableAll anomalies; transactions behave as if run one by one. Retry on serialization failure.
-- pessimistic: lock the row you will change
SELECT * FROM account WHERE id = 7 FOR UPDATE;

-- job queue: each worker claims different rows
SELECT id FROM job WHERE state = 'READY'
ORDER BY created_at LIMIT 10 FOR UPDATE SKIP LOCKED;

-- optimistic: version column, fail if someone else changed it
UPDATE doc SET body = $1, version = version + 1
WHERE id = $2 AND version = $3;     -- 0 rows → conflict, reload and retry

Keep transactions short. A long one holds locks and stops vacuum cleaning up dead rows.

Safe schema changes on live data

  • Additive first: add a nullable column, a new table, a new index (concurrently). Safe and reversible.
  • Expand / contract for renames and type changes: add the new column, write to both, backfill in batches, switch reads, stop writing the old, drop it in a later release.
  • Avoid long locks: some ALTER TABLE forms rewrite the whole table. Set lock_timeout so a migration fails fast instead of blocking traffic.
  • Backfill in batches (by ID range), committing as you go, not one giant UPDATE.
  • Version every change with a migration tool (Liquibase, Flyway, Alembic), and never edit a migration that has already run in production.
  • Test on a production-sized copy; a change that takes 30 s on 10k rows can take hours on 20M.

Anti-patterns

  • Entity-attribute-value tables (key, value rows for everything): no types, no constraints, painful queries.
  • Comma-separated lists in a column: use a join table or an array with a GIN index.
  • Floats for money and strings for dates.
  • No foreign keys "for speed": orphans and silent corruption cost more.
  • N+1 queries from an ORM loop: one query per row instead of one join.
  • SELECT * in application code: breaks when columns change, fetches what you do not need.
  • OFFSET pagination on deep pages: use keyset pagination (WHERE (date, id) < ($1, $2) ORDER BY date DESC, id DESC LIMIT 20).
  • Unbounded growth with no retention or archiving plan.

Levels: what to expect

1 Foundation

  • Design a normalised table with a primary key and constraints
  • Add an index for a slow lookup
  • Understand what a transaction guarantees

2 Practitioner

  • Read EXPLAIN ANALYZE and fix the plan
  • Choose composite, partial and covering indexes
  • Write safe, additive migrations

3 Senior

  • Partition large tables; plan retention and archiving
  • Choose isolation levels and locking strategies
  • Plan replicas, pooling and capacity

4 Expert

  • Decide between scaling up, partitioning, sharding or a distributed database
  • Run zero-downtime migrations on very large tables
  • Set database standards and review all schema changes

Each level includes the ones before it. See Start here for what the levels mean.

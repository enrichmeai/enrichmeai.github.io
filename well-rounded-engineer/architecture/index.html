Architecture patterns

Event-driven systems, choreography vs orchestration, sagas, the outbox, and a full catalogue of architectural, data, cloud and integration patterns, each with when to use it and what it costs. Ends with how to choose a style and record the decision.

Event-driven systems

Services communicate by publishing events (facts about something that happened: JudgmentLanded, OrderPaid) to a broker. Other services subscribe and react. The producer does not know or wait for its consumers.

TermMeaning
EventSomething that happened, past tense, immutable. Many consumers.
CommandA request to do something (LoadPartition). One handler, may be refused.
BrokerPub/Sub, Kafka, Eventarc: stores and delivers messages.
Topic / subscriptionWhere events are published / one consumer group's view of them.
At-least-onceThe usual guarantee: a message may arrive twice. Consumers must be idempotent.
OrderingUsually not global. Use an ordering key (per order, per entity) when sequence matters.
Dead-letter queueWhere messages go after repeated failures, so one bad message does not block the rest.

Gains: loose coupling, independent scaling, new consumers added without touching producers. Costs: eventual consistency, harder debugging (no single call stack), duplicates and reordering to handle, schema changes that ripple to unknown consumers.

Choreography vs orchestration

ChoreographyOrchestration
HowEach service reacts to events and emits its own. No one is in charge.A central orchestrator tells each service what to do next and tracks state.
AnalogyDancers who each know their cueA conductor with the score
Good forFew steps, independent teams, fan-out reactions ("on landing, also index and notify")Many steps, strict order, retries, compensation, a need to answer "where is this run?"
RiskThe overall flow exists only in people's heads; cycles and lost steps are hard to seeThe orchestrator is a central dependency and can grow into a god service
ToolsPub/Sub, Kafka, EventarcAirflow, Cloud Workflows, Temporal, Step Functions, a custom orchestrator with a ledger

Many systems mix them: orchestration inside a bounded process (a data pipeline's stages), choreography between domains (the pipeline publishes "ready"; the search team reacts).

Saga: transactions across services

A distributed transaction across several databases cannot use one ACID commit. A saga splits it into local transactions, each with a compensating action that undoes it if a later step fails.

Book a paid subscription:
  1. Billing:  create pending invoice        ↺ compensate: void invoice
  2. Payments: charge card                   ↺ compensate: refund charge
  3. Accounts: activate plan                 ↺ compensate: deactivate plan
  4. Email:    send welcome                  (no compensation needed; last, pivot-free)

Step 3 fails → run compensations in reverse: refund (2), void invoice (1).
  • Orchestrated saga: a coordinator runs the steps and the compensations, and stores the saga's state. Easier to follow and test.
  • Choreographed saga: each service listens for the previous step's event and emits its own, including failure events that trigger compensation.
  • Compensation is a new action, not a rollback: a refund is not "un-charging". Some steps (an email sent) cannot be undone, so put them last.
  • Every step and compensation must be idempotent, because messages repeat.
  • Expose intermediate states (PENDING, ACTIVE, CANCELLED): other readers will see them.

Transactional outbox

Problem: you update your database and publish an event. If one succeeds and the other fails, they disagree.

BEGIN;
  UPDATE orders SET status = 'PAID' WHERE id = 42;
  INSERT INTO outbox (id, topic, payload, created_at)
  VALUES (gen_random_uuid(), 'order.paid', '{"order_id":42}', now());
COMMIT;

-- relay process (or CDC on the outbox table)
SELECT * FROM outbox WHERE published_at IS NULL
ORDER BY created_at LIMIT 100 FOR UPDATE SKIP LOCKED;
-- publish each, then
UPDATE outbox SET published_at = now() WHERE id = ANY($1);

One local transaction makes the state change and the intent to publish atomic. The relay may publish twice; consumers dedupe by event ID.

Idempotent consumers

-- remember what you processed, in the same transaction as the effect
CREATE TABLE processed_events (event_id uuid PRIMARY KEY, processed_at timestamptz);

BEGIN;
  INSERT INTO processed_events VALUES ($event_id, now())
  ON CONFLICT DO NOTHING;
  -- if 0 rows inserted: duplicate, skip the effect
  UPDATE accounts SET plan = 'pro' WHERE id = $account;
COMMIT;
  • Prefer naturally idempotent operations: SET status = 'PAID' rather than balance = balance + 10.
  • APIs take an idempotency key header so a retried POST does not charge twice.
  • Batch jobs overwrite a partition or MERGE on a key.

CQRS & event sourcing

  • CQRS (command query responsibility segregation): writes go to a model shaped for updates; reads come from separate models shaped for queries (a search index, a denormalised table). Reads are eventually consistent.
  • Event sourcing: store the sequence of events as the source of truth; current state is derived by replaying them. Full audit history and time travel, at the cost of complexity, schema versioning of old events, and snapshots for speed.
  • Append-only ledger is the lightweight version many data platforms use: one row per state change, current state from a "latest event" view. Never UPDATE, never DELETE.
  • Use them where history and audit are the product. Most CRUD services do not need either.

Common architectural patterns

Hexagonal (ports & adapters)Domain logic in the centre; databases, APIs and queues are adapters behind interfacesLogic you want to test without infrastructure, or swap providers.
Modular monolithOne deployable with enforced module boundariesMost teams' best starting point. Split later along boundaries that proved real.

Backend for frontend (BFF)A thin API per client type (web, mobile)Clients with very different data needs.

Circuit breakerStop calling a failing dependency for a while; fail fastPrevents one slow service taking down its callers.
Retry with backoff + jitterRetry transient failures with growing, randomised waitsOnly for idempotent calls. Cap attempts; never retry 4xx validation errors.
BulkheadSeparate pools for separate dependenciesOne slow dependency cannot exhaust all threads or connections.

Consistency & trade-offs

  • CAP: during a network partition a distributed store chooses consistency (refuse some requests) or availability (answer, possibly stale).
  • PACELC: and when there is no partition, it trades latency against consistency.
  • Strong consistency: every read sees the latest write. Eventual: replicas converge, reads may lag. Read-your-writes: a user always sees their own changes.
  • Exactly-once delivery is rarely real end to end; build at-least-once delivery plus idempotent processing.
  • Fallacies of distributed computing: the network is not reliable, latency is not zero, bandwidth is not infinite, and the topology changes.

Design review checklist

  • Who owns each piece of data, and who may write it?
  • What happens when each dependency is slow, down, or returns garbage?
  • Which operations must be atomic, and how is that achieved across boundaries?
  • What is retried, and is it idempotent?
  • How do we see a request or run end to end (IDs, traces, ledger)?
  • What is the expected load, and what breaks first at 10×?
  • How do we deploy, migrate and roll back without downtime?
  • What is the simplest design that meets today's need?

Choosing a style

  1. List the quality attributes that matter most, in order: e.g. correctness and auditability, then cost, then latency.
  2. Note the constraints: team size and skills, budget, regulations, existing systems.
  3. Pick the simplest style that satisfies the top attributes; resist adding patterns "for later".
  4. Identify the riskiest assumption and test it with a spike or prototype.
  5. Record the decision and its trade-offs in an ADR.

Architecture decision record

# ADR 0042: Serve corpus search from Postgres, not a search engine
Status:   Accepted (2026-11-12)
Context:  20 M judgments, ~60 searches/s peak, p95 < 500 ms;
          team already runs Postgres; no search-engine skills.
Decision: Postgres full-text (GIN) + B-tree filters on a read replica;
          revisit if p95 > 500 ms or relevance complaints exceed X/month.
Alternatives: Elasticsearch (more ops, better relevance);
              BigQuery (latency too high for interactive search).
Consequences: + one database to run  − relevance tuning limited
Links:    load test results, issue #…

One decision per record, numbered, never edited after acceptance; supersede it with a new one. Keep them in the repo.

Levels: what to expect

1 Foundation

  • Explain layered and hexagonal architecture
  • Tell events from commands; choreography from orchestration
  • Recognise retries that need idempotency

2 Practitioner

  • Implement outbox, idempotent consumers and retries with backoff
  • Design a saga with compensations
  • Apply circuit breakers, bulkheads and timeouts

3 Senior

  • Choose monolith, modular monolith or services for a context
  • Design event-driven systems with contracts and evolution
  • Run design reviews and write decision records

4 Expert

  • Set architecture direction across many teams
  • Balance consistency, availability, cost and team structure
  • Lead large migrations (strangler fig) safely

Each level includes the ones before it. See Start here for what the levels mean.

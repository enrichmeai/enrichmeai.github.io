OAuth 2.0 and OpenID Connect

How delegated authorisation and login work, which flow to use for which client, how to validate tokens, and the mistakes that cause breaches. Broader security is on Security.

The roles and the two standards

RoleIsExample
Resource ownerThe user who owns the dataA customer
ClientThe app that wants accessThe web app, a mobile app, a partner's server
Authorisation serverAuthenticates the user and issues tokensGoogle Identity, Okta, Auth0, Keycloak, Entra ID
Resource serverThe API that accepts tokensThe search API, or Apigee in front of it
  • OAuth 2.0 is about authorisation: giving a client an access token to call an API on someone's behalf, limited by scopes.
  • OpenID Connect (OIDC) adds authentication on top: an ID token (a JWT) that says who the user is. "Sign in with Google" is OIDC.
  • Access token goes to APIs. ID token is for the client to learn who logged in; never send it to APIs as an access token. Refresh token gets new access tokens without a new login.

Which flow for which client

ClientFlowNotes

Mobile / desktop appAuthorisation code + PKCE via the system browserPublic client: no secret can be kept safe in the app
Service to serviceClient credentialsNo user; the service authenticates as itself
TV, CLI, device without a browserDevice authorisation grantUser approves on another device with a code
Workloads on GCPService account identity (Google-signed tokens)No secrets at all; Workload Identity Federation from outside GCP

Authorisation code + PKCE, step by step

1. Client makes a random code_verifier and its hash:
   code_challenge = BASE64URL(SHA256(code_verifier))

2. Browser is sent to the authorisation server:
   GET /authorize?response_type=code
       &client_id=shop-web
       &redirect_uri=https://shop.example.com/callback
       &scope=openid%20profile%20email%20search.read
       &state=RANDOM            (CSRF protection)
       &nonce=RANDOM            (ID-token replay protection)
       &code_challenge=…&code_challenge_method=S256

3. User logs in and consents; server redirects back:
   https://shop.example.com/callback?code=AUTH_CODE&state=RANDOM
   (client checks state matches)

4. Client exchanges the code at the token endpoint
   (from the server for a web app or BFF; from the device for a mobile or desktop app):
   POST /token
   grant_type=authorization_code&code=AUTH_CODE
   &redirect_uri=…&client_id=shop-web&code_verifier=ORIGINAL

5. Response: access_token, id_token, refresh_token, expires_in

6. Client calls the API:
   Authorization: Bearer ACCESS_TOKEN

PKCE proves the party redeeming the code is the one that started the flow, so a stolen code is useless.

Client credentials (machine to machine)

curl -s https://auth.example.com/oauth2/token \
  -u "$CLIENT_ID:$CLIENT_SECRET" \
  -d grant_type=client_credentials \
  -d scope=orders.read

# → {"access_token":"…","token_type":"Bearer","expires_in":3600}
curl -H "Authorization: Bearer $TOKEN" https://api.example.com/v1/orders/123
  • Cache the token until shortly before it expires; do not fetch one per call.
  • Prefer private-key JWT or mTLS client authentication over shared secrets where supported.
  • On GCP, prefer service account identity over client secrets.

Validating an access token (JWT)

  1. Fetch the issuer's keys from its JWKS URL (from /.well-known/openid-configuration); cache them.
  2. Verify the signature with the key matching the token's kid; accept only the expected algorithm (e.g. RS256 or ES256). Never none.
  3. Check iss equals your issuer exactly.
  4. Check aud contains your API's identifier.
  5. Check exp (and nbf) with small clock skew.
  6. Check required scopes for the operation.
  7. Then check object-level permission in your own code.
# Python (PyJWT)
jwks = jwt.PyJWKClient("https://auth.example.com/.well-known/jwks.json")
key = jwks.get_signing_key_from_jwt(token)
claims = jwt.decode(token, key.key, algorithms=["RS256"],
                    audience="https://api.example.com", issuer="https://auth.example.com/")
# Spring Boot resource server
spring.security.oauth2.resourceserver.jwt.issuer-uri: https://auth.example.com/
spring.security.oauth2.resourceserver.jwt.audiences: https://api.example.com

# Quarkus
quarkus.oidc.auth-server-url=https://auth.example.com/
quarkus.oidc.token.audience=https://api.example.com

Opaque (non-JWT) tokens are validated by calling the server's introspection endpoint (RFC 7662).

Scopes, claims and roles

  • Scopes limit what a client may do on the user's behalf (orders.read). They are about the app, not the user's own rights.
  • Claims are facts in the token: sub (stable user ID), email, groups, custom claims.
  • Roles and permissions are your application's rules. Load them from your source of truth; do not trust a role the client could have influenced.
  • Key users by sub plus issuer, not by email, which can change or be reused.
  • Keep tokens small; large claim sets slow every request.

Tokens in browsers and apps

  • Best for SPAs: a backend-for-frontend does the OAuth flow and keeps tokens; the browser gets an HttpOnly; Secure; SameSite session cookie.
  • Avoid localStorage for tokens: any XSS can read it.
  • Short access tokens (minutes) and rotating refresh tokens that are revoked if reused.
  • Mobile: store refresh tokens in the platform keychain / keystore; use the system browser, not an embedded web view, for login.
  • Logout revokes refresh tokens and ends the provider session if needed.

Common mistakes

  • Accepting a token without checking audience: a token for another API works on yours.
  • Using the ID token to call APIs.
  • Loose redirect URIs (wildcards, prefix matching): codes get sent to an attacker.
  • Missing or unchecked state: login CSRF.
  • Implicit flow or tokens in URLs, where they leak through logs and referrers.
  • Long-lived access tokens with no revocation.
  • Trusting scopes alone and skipping object-level checks.
  • Rolling your own authorisation server instead of using a maintained one.

Beyond the basics

  • Sender-constrained tokens (DPoP or mutual TLS) make a stolen token useless to anyone else.
  • Pushed authorisation requests (PAR) send the request parameters server to server first.
  • Token exchange (RFC 8693) for a service calling another on the user's behalf.
  • OAuth 2.1 (draft) consolidates current best practice: PKCE everywhere, no implicit or password grants.
  • OAuth for AI agents and MCP servers: agents act with delegated, scoped, revocable tokens, never the user's password.

Levels: what to expect

1 Foundation

  • Explain access, ID and refresh tokens and scopes
  • Protect an API with a JWT resource server configuration
  • Use the authorisation code flow with PKCE through a library

2 Practitioner

  • Validate tokens fully: signature, issuer, audience, expiry, scopes
  • Choose the right flow per client type
  • Store tokens safely in web and mobile apps

3 Senior

  • Design identity for a product: providers, BFF, service-to-service, token lifetimes
  • Review OAuth implementations for the common mistakes
  • Integrate gateways (Apigee) and workload identity

4 Expert

  • Own identity architecture across the organisation
  • Apply advanced specs (DPoP, PAR, token exchange)
  • Lead identity incidents and provider migrations

Each level includes the ones before it. See Start here for what the levels mean.

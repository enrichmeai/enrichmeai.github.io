Frameworks and blueprints vs AI-generated boilerplate

AI can generate a new service, pipeline or Terraform stack in minutes. That makes it tempting to generate every time. This tab explains why a well-built framework usually wins, when generation is the right call, and how to use AI to build and maintain the framework instead.

The core argument

Writing code was never the main cost; owning it is. Every copy of generated boilerplate must be reviewed, secured, tested, upgraded, debugged and understood by the next person. Generation makes the cheap part cheaper and multiplies the expensive part. A framework makes each decision once, tests it once, fixes it once, and upgrades everyone together.

Generate per projectFramework / blueprint
Time to first versionMinutesMinutes, once the framework exists
ConsistencyEach copy differs subtly (retries, logging, auth, errors)Same behaviour everywhere
Fixing a bug or CVEFind and patch N copies; some get missedPatch once, release, bump versions
Review burdenHundreds of generated lines per PROnly the business-specific part
SecurityEach copy may reintroduce a known holeSecure defaults, tested once
Upgrades (Java, Spring, providers)N separate migrationsOne migration in the framework, then a version bump
OnboardingEvery repo is a new dialectLearn the framework once
KnowledgeDecisions live in prompts nobody keptDecisions in versioned, reviewed code and docs
AI output qualityModel guesses your conventions from public codeModel extends your framework; smaller, consistent output
Total cost over 2 yearsGrows with every copyMostly fixed, shared

A cost model in one line

generated:  N copies × (review + security fix + upgrade + drift) per year
framework:  build once + maintain once + N × (small version bump)

With N = 15 services, 3 framework-level fixes a year, ~1 day each:
  generated:  15 × 3 = 45 fix-days, plus drift
  framework:   1 × 3 =  3 fix-days + 15 version bumps (automatable)

The numbers are illustrative; the shape is the point. The gap grows with every new copy and every year.

When generation is the right call

  • One-off scripts and investigations you will delete.
  • Prototypes and spikes to learn whether an idea works.
  • Filling a framework's slots: the business logic, the new query, its tests.
  • Codemods: AI-written scripts that apply the same change across many repos (an upgrade, a rename), reviewed once.
  • Tests and documentation for code that follows the framework.
  • Before the third repetition: the first two times, write or generate it directly; you do not yet know what to abstract.

When not to build a framework

  • Rule of three: abstract after three real uses, not one imagined future.
  • Inner-platform effect: a framework so configurable it becomes a worse version of the language or tool it wraps.
  • Business logic in shared libraries: forces lock-step releases between teams. Share infrastructure concerns, not domain rules.
  • No owner: a framework without a maintaining team decays faster than copies.
  • Escape hatches missing: teams need a supported way to do the unusual thing without forking.

Using AI to build the framework

  1. Collect the 3+ existing implementations; ask AI to list what they share and where they differ.
  2. Decide the framework's API and its escape hatches yourself; that is the design work.
  3. Let AI draft the framework code, tests and documentation against that design.
  4. Review it like any critical library; add contract tests.
  5. Let AI write codemods that migrate each existing project onto it, one PR per repo.
  6. Point every repo's AI context file at the framework, so future work extends it instead of reinventing it.

Keeping a framework healthy

  • An owning team with a roadmap, changelog and support channel.
  • Semantic versioning; breaking changes rare, announced, with migration guides and codemods.
  • Automated upgrades (Renovate or Dependabot) open version bumps in every consumer.
  • Golden path, not a cage: the easy way is the right way, and the unusual way is possible.
  • Scorecards (e.g. in a Backstage catalogue) show which services are on current versions.
  • Measure adoption and time to first deploy for new services.

Decision guide

  • Will this exist in more than one place for more than a few months? → blueprint.
  • Does it carry security, compliance or reliability rules? → blueprint, even for two uses.
  • Is it unique business logic? → write it (with AI help) inside the blueprint's slots.
  • Is it throwaway or exploratory? → generate, and delete it afterwards.
  • Is it the same change across many repos? → AI-written codemod, reviewed once.

AI is the bulldozer; the framework is the road. Build the road once and drive on it, rather than bulldozing a new track for every trip.

Levels: what to expect

1 Foundation

  • Explain why owning generated code costs more than writing it
  • Use the team's templates and libraries instead of generating new boilerplate
  • Fill a blueprint's slots with AI help

2 Practitioner

  • Spot repeated code and propose a blueprint after the third use
  • Write codemods with AI to apply a change across repos
  • Point AI context files at the blueprints

3 Senior

  • Design framework APIs with escape hatches
  • Own a blueprint: versioning, docs, migration guides
  • Decide build vs generate with a cost model

4 Expert

  • Run a platform team with golden paths and scorecards
  • Set the organisation's policy on AI generation vs shared frameworks
  • Measure developer productivity and adoption

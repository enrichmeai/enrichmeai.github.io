Guide / Foundations / Graph Databases

Graph databases

Some data is mostly about connections: who knows whom, which account paid which, which part goes into which product, which service calls which. A graph database stores those connections as first-class data, so following them is a basic operation rather than a chain of joins. This page covers the two main graph models, how to query them, how they compare with relational databases, and when a graph is worth it. (GraphQL, despite the name, is an API style, not a database: see GraphQL.)

The idea: nodes and edges

  • Nodes are things: people, accounts, products, services. They are roughly the equivalent of a row in a relational database or a document in a document store.
  • Edges are the relationships between them, and can be directed (A follows B) or undirected.
  • Properties are key–value details on both, such as a person’s name or the date a payment was made.

The mathematics is old: Leonhard Euler’s 1736 proof that no walk crosses each of Königsberg’s seven bridges exactly once is regarded as the first paper in the history of graph theory.

Two models

  • Labelled property graph: nodes and relationships both carry key–value properties; nodes have labels that group them; relationships are named, directed and have a start and an end node. Neo4j (where Cypher began) and Amazon Neptune (through openCypher) support this model.
  • RDF (Resource Description Framework): a W3C standard where everything is a triple, subject–predicate–object, such as “Ana – worksFor – Acme”. Databases built for it are called triplestores, and it underlies many knowledge graphs and linked data.

Some products, Amazon Neptune among them, support both models.

Query languages

  • Cypher: created at Neo4j in 2011, largely by Andrés Taylor, and opened up through the openCypher project in 2015. It draws patterns like (a)-[:KNOWS]->(b).
  • GQL: the ISO standard graph query language for property graphs, ISO/IEC 39075, published in April 2024.
  • SQL/PGQ: Part 16 of SQL:2023 adds property graph queries to SQL itself, narrowing the gap between relational and graph databases.
  • Gremlin: Apache TinkerPop’s graph traversal language, described as playing the role for graph databases that JDBC and SQL play for relational ones.
  • SPARQL: the W3C query language for RDF; SPARQL 1.0 became a W3C Recommendation in January 2008.

What a query looks like

// GQL / Cypher style: people and the city they live in
MATCH (p:Person)-[:LIVES_IN]->(c:City)
RETURN p.first_name, p.last_name, c.name

// friends of friends: two hops along the same relationship
MATCH (me:Person {name: 'Ana'})-[:KNOWS]->(friend)-[:KNOWS]->(fof)
RETURN DISTINCT fof.name

Analysis: the second query adds one pattern per hop. In SQL, each hop is typically another join on a link table, which is where graph databases are said to read more naturally.

Graph or relational?

Graph databaseRelational database
Following relationshipsGraph databases typically use index-free adjacency: each node holds direct references to its neighbours, so reaching an adjacent node is typically constant time, and query time depends on how much of the graph is queried rather than the size of the graphRelationships are joins through indexes; queries with many joins across many tables get complex, and joins can be expensive
Operating on many rows at onceTypically slower at the same operation over large numbers of rowsTypically faster at the same operation over large numbers of rows
SchemaFlexible: new kinds of node and relationship can be added without redesigningA strict schema and normalisation, which preserve data consistency and support ACID transactions
Standard languageGQL since 2024; Cypher, Gremlin and SPARQL are all in useSQL, the standard for relational databases, which have been the industry standard since Codd’s 1970 relational model

Wikipedia’s summary adds a caution worth keeping: the graph model alone should not be the reason to replace an existing relational database.

Where graphs are used

  • Shortest paths between two nodes, and measures such as a graph’s diameter.
  • Community detection: clusters of closely connected nodes.
  • Knowledge graphs: Google introduced its Knowledge Graph in 2012, to answer searches with “things, not strings”.
  • Graphs for AI retrieval: Microsoft’s GraphRAG research project used language models to extract a knowledge graph from text and used it as context for answering questions. Microsoft now describes it as a research project largely in maintenance mode, and warns that indexing can be expensive (see RAG).

Choose by requirement

If this is true for youIt leans towards (analysis)
Your key queries follow chains of relationships of unknown length (paths, networks, “how is A connected to B”)A graph database
Your queries are mostly filters, totals and reports over many rowsA relational database or a warehouse
You already run PostgreSQL or another SQL database and need some graph queriesTry graph queries in SQL first (recursive queries, or SQL/PGQ where supported): a second database has a cost
You need to link data from many sources with shared, published vocabulariesRDF and SPARQL
Your data has many kinds of entity and relationship that keep changingA graph model of either kind: new data can be added without planning every future use in advance
You need to be able to move between graph productsA standard language, GQL (ISO/IEC 39075) or openCypher, rather than one vendor’s extensions

Our view, and the other view

Our view: learn to think in graphs even if you never run a graph database: many problems (dependencies, permissions, fraud rings, service maps) are graphs, and drawing them that way clarifies them. Reach for a graph database when relationship queries are the core of the product.

The other view: one well-run relational database covers most needs, including many graph-shaped queries through recursive SQL and now SQL/PGQ. Adding a specialised database brings another system to operate, back up and secure, and another query language for the team to learn.

Levels: what to expect

1 Foundation

  • Explain nodes, edges and properties
  • Tell a labelled property graph from RDF triples
  • Say why GraphQL is not a graph database

2 Practitioner

  • Write MATCH queries for one and two hops
  • Model a small domain as a graph
  • Compare a graph query with the same query in SQL

3 Senior

  • Choose between a graph database, SQL/PGQ and recursive SQL for a case
  • Explain index-free adjacency and its trade-offs
  • Design a graph for fraud, permissions or dependencies

4 Expert

  • Decide whether a graph database earns its place in the estate
  • Plan a knowledge graph across sources
  • Set standards: GQL, openCypher or vendor extensions

Each level includes the ones before it. See Start here for what the levels mean.

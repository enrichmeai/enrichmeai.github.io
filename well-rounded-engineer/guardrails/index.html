Guide / AI / Standards as Guardrails

Standards as guardrails in a human–AI ecosystem

A model does not know what your team agreed unless something tells it, and checks it. How to make agents build on your frameworks, templates and deployment standards instead: which layers to put in place, how much to specify (and where to stop), what to automate completely, and a Spring Boot example where the rules catch an agent going off the road.

The short answer

Put the team’s standards where an agent cannot miss them and where a check can say pass or fail: in a framework the code builds on, in templates that create and deploy services, in tests that check the architecture, and in hooks and policies that refuse what breaks the rules. Then the agent spends its effort on what is different about this service, and the shared parts stay the same because they are shared, not because someone remembered.

This is an ecosystem, not a production line. People own the standards and change them as they learn; agents work inside them; the gates show where the two disagree. And the services are not copies of each other: standards fix only what should be the same everywhere, such as errors, security, logging and deployment.

An ecosystem, not a factory

In a domain with, say, half a dozen services that talk over messaging, each service does something different. What they share is the plumbing: how errors look, how they log, how they deploy, how they are secured, how they publish events. That shared part is what the standards cover. The domain logic, the part that makes each service worth having, is where people and agents should spend their thinking.

Our view: a standard earns its place when getting it wrong in one service would hurt the others, or when the same fix would otherwise be made many times. Anything else is a choice the service team can make.

More on why a framework beats generated copies: Frameworks vs AI Boilerplate.

Why a model needs guiding

Our view: a model fills gaps with what is common. Ask for “an endpoint to list stock” and a likely answer is a controller that queries the database, prints to the console and handles its own errors: fine in a tutorial, wrong in a codebase that put data access in services and has one error format. Böckeler saw agents ignore instructions they had been given, and follow others too eagerly.

The other view: a clear rules file and a good brief steer a model well most of the time, and for a small codebase may be all you need.

Our view: so instructions alone are not enough. Write the standard down for the agent to read, and also give it something to run that fails when the standard is broken.

Source: Birgitta Böckeler, “Understanding Spec-Driven-Development”.

How much to spec: striking the balance

Specifying every service in detail before building any of them turns into planning that outlasts the work. Böckeler doubts that “lots of up-front spec design” helps and prefers small, iterative steps; Martin Fowler’s Yagni warns against building a “presumptive feature” that nobody uses yet. The balance is to specify the seams between services carefully, and the inside of each service only as much as its risk needs.

If this is true for the workHow much spec
It is a message or API other services depend onA written contract (for events, an AsyncAPI document) agreed by producer and consumers, with contract tests
It handles money, personal data, security, or cannot be undoneA spec with numbered acceptance criteria, reviewed before code
It is logic inside one service, behind a stable contractA few acceptance criteria; let the code and tests carry the detail
It is a bug, a refactor or a renameNo spec: a failing test, then the fix
It is a dependency or framework upgradeNo spec and, for minor versions, no person: automate it (below)
Nobody yet knows what users needA spike or prototype first; spec what you learn

Analysis: the table is our view, built on: Robinson’s consumer-driven contracts, where a provider learns its obligations from what consumers actually use and receivers do “just enough” validation (Ian Robinson, “Consumer-Driven Contracts: A Service Evolution Pattern”, 12 June 2006); Martin Fowler, “Yagni”, 26 May 2015; Birgitta Böckeler, “Understanding Spec-Driven-Development”. BMad Method sizes its process the same way: “Small changes go straight to build” (BMad Method (README)).

The seam: a contract for events

When services talk over messaging, the event is what they share. This contract, in AsyncAPI 3.1.0, is the part of the stock service’s design the order and warehouse teams would need to agree on. It is a design document: the example service does not publish the event yet. We checked only that it is valid AsyncAPI, with the AsyncAPI parser (0 errors); a copy with action: publish was rejected, because the specification allows only send and receive.

asyncapi: 3.1.0
info:
  title: Stock events
  version: 1.0.0
  description: The seam between the stock service and the order and warehouse services. Agreed by the teams; the only part of their designs they share.
channels:
  stockReserved:
    address: stock.reserved
    messages:
      stockReserved:
        $ref: '#/components/messages/stockReserved'
operations:
  sendStockReserved:
    action: send
    summary: Sent once a reservation commits, never for a replayed retry.
    channel:
      $ref: '#/channels/stockReserved'
components:
  messages:
    stockReserved:
      payload:
        type: object
        required: [reservationId, sku, quantity]
        properties:
          reservationId: { type: string, format: uuid }
          sku: { type: string }
          quantity: { type: integer, minimum: 1, maximum: 100 }

Once the event exists, contract tests can hold both sides to it. Spring Cloud Contract offers consumer-driven contracts, and its reference has a section on messaging; the example does not include them.

Sources: AsyncAPI specification 3.1.0; Spring Cloud Contract reference.

Automate the mechanical: upgrades

Version upgrades need no spec and little judgement, so they suit full automation. Dependabot opens “automated pull requests that keep your dependencies updated” from a dependabot.yml, and can group updates “into fewer, targeted pull requests”. A workflow can switch on auto-merge for patch updates, and auto-merge “merges a pull request automatically after all required reviews and status checks pass”. For code changes an upgrade needs, OpenRewrite’s rewrite-spring has recipes to “automatically apply best practices in Java Spring Boot applications”.

version: 2
updates:
  - package-ecosystem: "maven"
    directory: "/"
    schedule:
      interval: "weekly"
name: Dependabot auto-merge
on: pull_request
permissions:
  contents: write
  pull-requests: write
jobs:
  dependabot:
    runs-on: ubuntu-latest
    if: github.event.pull_request.user.login == 'dependabot[bot]'
    steps:
      - name: Dependabot metadata
        id: metadata
        uses: dependabot/fetch-metadata@v3
        with:
          github-token: "${{ secrets.GITHUB_TOKEN }}"
      - name: Enable auto-merge for patch updates
        if: steps.metadata.outputs.update-type == 'version-update:semver-patch'
        run: gh pr merge --auto --merge "$PR_URL"
        env:
          PR_URL: ${{ github.event.pull_request.html_url }}
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}

Two settings make this safe, and both are needed: auto-merge must be enabled for the repository, and the build and the platform rules test must be required status checks. Without required checks, auto-merge has nothing to wait for. GitHub’s own example pins the third-party fetch-metadata action to a commit SHA; a tag is shown here for readability. Our view: with those in place, people look only at major versions and at anything the gates reject.

Sources: GitHub: Dependabot version updates; GitHub: dependabot.yml options; GitHub: Automating Dependabot with GitHub Actions; GitHub: Automatically merging a pull request; OpenRewrite: rewrite-spring (README).

Example: a platform starter and its rules

The stock reservation service from spec-driven development, moved onto a shared platform starter. The starter is a Spring Boot auto-configuration that every service depends on. It brings one error format, and it ships the team’s architecture rules as ArchUnit tests. An exception that never reaches a client can opt out with @NotClientFacing. Built on Spring Boot 4.2.0 and ArchUnit 1.5.1, compiled and tested on 24 November 2026 (H2, one JVM).

One error format, defined once in the starter:

/** One error format for every service: RFC 9457 problem details with a stable code. */
@RestControllerAdvice
public class PlatformErrors {
    @ExceptionHandler(DomainException.class)
    ProblemDetail domain(DomainException e) {
        var p = ProblemDetail.forStatusAndDetail(e.status(), e.getMessage());
        p.setProperty("code", e.code());
        return p;
    }
}

A service’s errors then carry only their status and code, and the service has no error handler of its own:

    public static class InsufficientStock extends DomainException {
        InsufficientStock() { super(HttpStatus.CONFLICT, "INSUFFICIENT_STOCK", "Not enough stock for this sku"); }
    }

The rules, owned by the platform team and checked in every service’s build:

/** The standards every service shares, as tests. Owned by the platform team; agents and people meet the same rules. */
public final class PlatformRules {

    public static final ArchRule CONTROLLERS_DO_NOT_TOUCH_THE_DATABASE =
            noClasses().that().areAnnotatedWith(org.springframework.web.bind.annotation.RestController.class)
                    .or().areAnnotatedWith(org.springframework.stereotype.Controller.class)
                    .should().dependOnClassesThat().resideInAnyPackage("org.springframework.jdbc..", "jakarta.persistence..")
                    .because("data access belongs in a service, where transactions are");

    public static final ArchRule SERVICE_EXCEPTIONS_GO_THROUGH_THE_PLATFORM =
            classes().that().areAssignableTo(RuntimeException.class).and().resideOutsideOfPackage("com.example.platform..")
                    .and().areNotAnnotatedWith(NotClientFacing.class)
                    .should().beAssignableTo(DomainException.class)
                    .because("one error format for every service; mark internal-only exceptions @NotClientFacing");

    public static final ArchRule NO_OWN_ERROR_HANDLERS =
            noClasses().that().resideOutsideOfPackage("com.example.platform..")
                    .should().beAnnotatedWith(org.springframework.web.bind.annotation.RestControllerAdvice.class)
                    .orShould().beAnnotatedWith(org.springframework.web.bind.annotation.ControllerAdvice.class)
                    .because("the platform already maps errors; a second handler drifts");

    public static final ArchRule NO_LOCAL_EXCEPTION_HANDLERS =
            noMethods().that().areDeclaredInClassesThat().resideOutsideOfPackage("com.example.platform..")
                    .should().beAnnotatedWith(org.springframework.web.bind.annotation.ExceptionHandler.class)
                    .because("the platform already maps errors; a second handler drifts");

    public static final List<ArchRule> ALL = List.of(
            CONTROLLERS_DO_NOT_TOUCH_THE_DATABASE,
            SERVICE_EXCEPTIONS_GO_THROUGH_THE_PLATFORM,
            NO_OWN_ERROR_HANDLERS,
            NO_LOCAL_EXCEPTION_HANDLERS,
            GeneralCodingRules.NO_CLASSES_SHOULD_ACCESS_STANDARD_STREAMS);

    /** Checks every rule and reports every violation at once, so a reviewer (person or agent) sees them all. */
    public static void check(JavaClasses service) {
        CompositeArchRule.of(ALL).check(service);
    }

    private PlatformRules() {}
}
/** The platform's standards, checked on this service's own classes in every build. */
class PlatformRulesTest {
    @Test
    void thisServiceFollowsThePlatformRules() {
        PlatformRules.check(new ClassFileImporter()
                .withImportOption(ImportOption.Predefined.DO_NOT_INCLUDE_TESTS)
                .importPackages("com.example.stock"));
    }
}

The example: an agent goes off the road

Asked for “a quick endpoint to list stock”, a model might write this. It compiles, and it works:

/** What a model might write when asked for "a quick endpoint to list stock". */
@RestController
@RestControllerAdvice
class ShortcutController {
    private final JdbcClient db;
    ShortcutController(JdbcClient db) { this.db = db; }

    static class NotFound extends RuntimeException {}

    @GetMapping("/stock/{sku}")
    Integer available(@PathVariable String sku) {
        System.out.println("looking up " + sku);
        return db.sql("SELECT available FROM stock WHERE sku = :sku").param("sku", sku).query(Integer.class).single();
    }

    @ExceptionHandler(NotFound.class)
    ProblemDetail notFound() { return ProblemDetail.forStatus(HttpStatus.NOT_FOUND); }
}

So might this quieter version, which uses JdbcTemplate and a handler inside the controller:

/** The quieter shortcuts: JdbcTemplate instead of JdbcClient, and a controller-local handler. */
@RestController
class BypassController {
    private final JdbcTemplate jdbc;
    BypassController(JdbcTemplate jdbc) { this.jdbc = jdbc; }

    @GetMapping("/stock-count")
    Integer count() { return jdbc.queryForObject("SELECT COUNT(*) FROM stock", Integer.class); }

    @ExceptionHandler(IllegalStateException.class)
    String oops() { return "oops"; }
}

The build refuses both. All five rules fire in one report, so the agent (or a person) sees everything to fix at once:

A rule only catches what it was written to catch: the first draft of these rules missed JdbcTemplate and controller-local handlers until a review pointed it out. On the service as built, the same check passes: 10 tests, 0 failures (the 9 spec tests, unchanged after the move to the starter, plus the platform rules). The violations tell the agent what to do instead: move the query into a service, throw a DomainException, drop the handler and the System.out.

The example: the agent is told, not just blocked

A Claude Code PreToolUse hook refuses edits, through the Edit and Write tools, to the files the templates own and to the hook’s own settings. Exit code 2 blocks the edit, and the message goes back to the agent so it can choose the right path:

#!/bin/bash
# PreToolUse hook for Edit|Write: deployment files come from the platform's templates.
# The agent may change service.yaml (the values); it may not write its own Dockerfile,
# Kubernetes manifests or deploy workflow, nor the hook settings. Exit 2 blocks the edit and tells the agent why.
# It catches honest mistakes; it is not a security boundary (a shell command can still write a file).
path=$(python3 -c 'import json,sys; print(json.load(sys.stdin).get("tool_input",{}).get("file_path",""))')
case "$path" in
  Dockerfile|*/Dockerfile|k8s/*|*/k8s/*|helm/*|*/helm/*|.github/workflows/*|*/.github/workflows/*|.claude/*|*/.claude/*)
    echo "Blocked: $path is generated from the platform templates (or guards them). Change service.yaml instead, or ask the platform team to change the template." >&2
    exit 2 ;;
esac
exit 0
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/paved-road.sh" }
        ]
      }
    ]
  }
}

Tested by feeding it the JSON a Write call sends:

/repo/svc/Dockerfile                  -> exit 2  Blocked: ... generated from the platform templates
.github/workflows/deploy.yml          -> exit 2  (relative paths too)
/repo/svc/k8s/deployment.yaml         -> exit 2
/repo/svc/.claude/settings.json       -> exit 2  (the guard guards itself)
/repo/svc/docs/Dockerfile-notes.md    -> exit 0
/repo/svc/.github/dependabot.yml      -> exit 0
/repo/svc/src/.../ReservationService.java -> exit 0
/repo/svc/service.yaml                -> exit 0

Analysis: the hook catches an honest mistake and explains it; it is not a security boundary. A shell command can still write a file. The real stops are the build and the cluster policy below.

Source: Claude Code: Hooks reference (“Exit with code 2 to block the action”).

The example: the last line, in the cluster

If something non-compliant still reaches Kubernetes, a ValidatingAdmissionPolicy (stable since Kubernetes 1.30) can reject it. This one requires a CPU request on every container (a CPU-based HorizontalPodAutoscaler measures use against the request) and an owning team label:

apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: "require-cpu-request.platform.example.com"
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
    - apiGroups: ["apps"]
      apiVersions: ["v1"]
      operations: ["CREATE", "UPDATE"]
      resources: ["deployments"]
  validations:
  - expression: "object.spec.template.spec.containers.all(c, has(c.resources.requests) && 'cpu' in c.resources.requests)"
    message: "every container needs a CPU request, or the autoscaler has nothing to measure"
  - expression: "has(object.metadata.labels) && 'team' in object.metadata.labels"
    message: "every Deployment names its owning team"
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: "require-cpu-request-binding.platform.example.com"
spec:
  policyName: "require-cpu-request.platform.example.com"
  validationActions: [Deny]

Not run against a cluster; YAML checked to parse, CEL written after the examples in Kubernetes: Validating Admission Policy. On CPU requests: Kubernetes: Horizontal Pod Autoscaling.

What goes wrong

  • A cage instead of a road. Analysis: if a rule cannot be changed, people and agents route around it. Every rule needs an owner and a way to propose a change.
  • Rules narrower than their names. A rule called “controllers do not touch the database” that only looks for one class is a false comfort. Test each rule against the shortcuts it is meant to stop.
  • Too many rules. A wall of violations teaches nobody. Keep the rules to what would hurt other services or repeat a fix.
  • Templates that go stale. A template nobody updates becomes the old way, copied everywhere. Version it, and let automated upgrades carry changes to every service.
  • Planning instead of building. Detailed specs for every service before any runs is the trap above: spec the seams, build, learn.
  • Business rules in the shared library. They tie teams’ releases together. Share infrastructure, not domain logic (see Frameworks vs AI Boilerplate).

Our view, and the other view

Our view: standards that run as code are a practical way to keep agents aligned with a team, because they say pass or fail where a document only asks. Put them in the framework, the templates and the build, keep them few, and let people change them.

The other view: a heavy platform costs a team to build and own, and can slow the small number of services that need to be different. For a handful of services, a rules file and a good review may be enough; build the platform when the same fix starts being made in many places.

Guide / Cloud providers / Retail & Hybrid Cloud

Retail integration, hybrid and multi-cloud

A retailer joins tills in hundreds of stores, a website, warehouses, suppliers and a finance system, and each of them has to agree about stock and money. This page shows how those pieces are usually connected, the same building blocks on AWS, Azure and Google Cloud, and when keeping some work on premises or using more than one cloud pays for itself. The general comparison of the three providers is on GCP vs AWS vs Azure.

What a retailer has to connect

  • Stores and tills: the point of sale, where a retail transaction is completed. A till that stops when the network does stops the shop, so stores need to keep selling on their own (see below).
  • Online: the website, the apps, search and recommendations.
  • Orders and stock: order management, and one view of stock across stores, warehouses and goods on the way.
  • Warehouses and delivery: picking, packing, carriers and returns.
  • Payments: cards and wallets in store and online (see Payment Gateways).
  • Finance and planning: the ERP, the general ledger, buying and replenishment.
  • Suppliers: often through EDI, the computer-to-computer exchange of structured business documents such as purchase orders, invoices and shipping notices, in standards such as UN/EDIFACT, ANSI ASC X12, GS1 EDI and TRADACOMS.
  • Customers: loyalty, marketing and service, which all want the same customer record.

Analysis: the hardest part is rarely one system. It is keeping stock and orders consistent between them, for example when a customer buys online and collects in a store that is also selling the same item at its tills.

Integration patterns that hold up in retail

Analysis, built on the pages linked.

  • Events for things that changed: “order placed”, “stock moved”, “item sold”, published once and read by every system that cares (see Kafka and Event Sourcing).
  • APIs for questions that need an answer now: the price of this item, or reserving stock for this order (see APIs & Integration).
  • Store and forward at the till: record each sale locally with its own unique id, and send it when the network returns. The receiving side must accept the same sale twice without counting it twice.
  • The outbox: write the change and the event in one local transaction, then publish, so the two cannot disagree.
  • Batch where batch is fine: supplier EDI files and nightly finance loads do not need to be real time.
  • Reconcile: compare till totals, orders, stock and payments every day, and treat a gap as an incident.

A worked example: click and collect

  1. The customer orders online. The order service, in the cloud, reserves stock at the chosen store through an API.
  2. An “order placed” event reaches the store system, which adds a pick task and takes the item out of sellable stock.
  3. The store picks the item and sends “ready”; the customer gets a message.
  4. At collection the till records the hand-over. If the store is offline, it records it locally and sends it later.
  5. The stock change flows to replenishment, which may send a purchase order to the supplier by EDI.

Analysis: every arrow above can fail or arrive twice. Give each message a unique id, make each receiver idempotent, and decide in advance what the store does when it cannot reach the cloud.

The same building blocks on AWS, Azure and Google Cloud

You needAWSAzureGoogle Cloud
Messaging and events between systemsAmazon EventBridge: a serverless service that uses events to connect application componentsAzure Service Bus: a managed message broker with queues and publish-subscribe topicsPub/Sub: an asynchronous messaging service that decouples services producing messages from services processing them
A private network link from your data centreDirect Connect: your network to a Direct Connect location over a fibre-optic cableExpressRoute: a private connection to Microsoft cloud services through a connectivity providerCloud Interconnect: low-latency, high-availability connections between your networks
The provider’s cloud on your own premisesAWS Outposts: AWS infrastructure and APIs at your site, operated by AWS as part of a RegionAzure Local: Azure capabilities on customer-owned machines, connected or disconnected, managed through Azure ArcGoogle Distributed Cloud connected: for a very stable network connection, the lowest attainable latency, data too large to transfer for performance or cost reasons, or laws that require data to stay on premises

Some useful pieces do not line up one to one. Each of these is described in its provider’s own documentation:

  • Azure Arc lets you manage servers, Kubernetes clusters and databases that run outside Azure, on premises or on other clouds, as if they ran in Azure.
  • GKE Multi-Cloud creates Google Kubernetes Engine clusters in AWS and Azure.
  • Cross-Cloud Interconnect is a dedicated physical connection between Google’s network and another cloud provider’s.
  • A gateway you run yourself: Azure API Management’s self-hosted gateway is a container version of its managed gateway (Developer and Premium tiers); Apigee hybrid keeps the management plane in Google’s cloud and runs the runtime plane on your own Kubernetes.
  • On devices, for example in a store: AWS IoT Greengrass is an open-source edge runtime that lets devices act on their own data locally and send it to AWS.
  • For retail search and recommendations: Amazon Personalize generates item recommendations from your data; Google’s AI Commerce Search serves search and recommendations from catalogue and user-event data.

This list is what we checked in each provider’s documentation. It does not prove a provider has no equivalent; check the current documentation before you decide.

Hybrid: what stays on premises, and why. Choose by requirement

Hybrid cloud is a public cloud and a private environment, such as a private cloud or on-premises machines, that stay separate but are bound together.

If this is true for youIt leans towardsWhat it costs you
Stores must keep selling when the network dropsCompute in every store, holding the sales and prices it needsA fleet of small sites to update, secure and monitor
Law or contract says data must stay in a place you controlOn premises, or the provider’s on-premises offeringHardware and capacity you plan for yourself; Google lists limited processing capacity as a limit of its connected deployments
Devices in the store make large data, such as camera videoProcess it locally and send only the resultsLocal capacity, and models to update at every site
The work cannot tolerate network delay or jitterRun it next to the devicesSame as above
A mainframe or ERP in your data centre runs the business and worksKeep it, and connect it with a private link, events and APIsTwo ways of operating, and the skills for both
Seasonal peaks go beyond what you ownCloud bursting: use public cloud capacity for the temporary peakData and networks designed so work can move
None of the abovePublic cloud onlyThe least to run

Multi-cloud: when it pays, and when it costs. Choose by requirement

ISO/IEC 22123-1 defines multi-cloud as a deployment model in which a customer uses public cloud services from two or more providers.

If this is true for youIt leans towardsWhat it costs you
You need a service only one provider offers, and the rest runs elsewhereUse that service on its own cloud for that jobData transfer between clouds, a second identity and security setup
A customer, regulator or contract requires a named provider, or a tested exit planMulti-cloud, or one cloud with a rehearsed exitKeeping the exit working, not just written down
You bought a company that runs on another cloudConnect the two with APIs and events first; decide on moving laterTwo platforms until you consolidate, if ever
Your contract renewal depends on having a credible alternativeThe ability to move a workload, shown in practiceOnly credible if you have actually kept it portable
You must survive a whole provider failingThe same system running on two cloudsThe highest cost here: two of everything, and the data kept in step
A small team builds one productOne providerSome lock-in, accepted on purpose (see Staying portable)

Wikipedia’s summary of the sources: multi-cloud can improve resilience, reduce dependence on one vendor and help in negotiating price, and it brings more operational complexity, security risk, cost and integration work.

The costs that usually decide it

  • Data leaving a cloud: on Google Cloud, inbound data transfer has no charge (though services that process it, such as load balancers and Cloud NAT, may), while data leaving Google Cloud is priced by network tier and destination. Check each provider’s network pricing for your traffic before you split a system across clouds.
  • Switching in the EU: under the EU Data Act, from 11 January 2024 to 12 January 2027 providers may charge only the costs directly linked to switching; from 12 January 2027 they may charge nothing for switching, data egress included.
  • Skills and tools: two clouds means two sets of identity, networking, monitoring and on-call knowledge.
  • The lowest common denominator: code written to run anywhere cannot use what makes one provider better at a job.

Our view, and the other view

Our view: start on one cloud. Make every store able to work alone, connect the data centre you already have rather than rushing to empty it, and add a second provider only for a reason you can name from the tables above.

The other view: some teams start multi-cloud on purpose, so that portability is built in from day one rather than retrofitted at great cost, and so that no single provider’s prices or outages can hold them hostage. Lower switching charges under the EU Data Act cut the cost of moving later, which weakens the first argument for some and strengthens the case for keeping a real exit open for others.

Levels: what to expect

1 Foundation

  • Name the systems a retailer connects and what each one owns
  • Explain why a till must keep selling offline
  • Explain the difference between an event and an API call

2 Practitioner

  • Build store-and-forward with idempotent receivers
  • Map a retail flow onto AWS, Azure or Google Cloud services
  • Connect a data centre to a cloud over a private link

3 Senior

  • Decide what runs in the store, the data centre and the cloud, by requirement
  • Design one view of stock across channels
  • Price data transfer before splitting a system across clouds

4 Expert

  • Set a hybrid and multi-cloud strategy with named reasons
  • Lead the integration of an acquired company on another cloud
  • Keep an exit plan from a provider tested, not just written

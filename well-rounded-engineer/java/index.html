Threads in Java, release by release

ReleaseWhat arrivedWhat it meant
1.0Thread, Runnable, synchronized, wait/notifyThreads built into the language from the start. Early JVMs used "green threads", scheduled by the JVM itself rather than the operating system; they were abandoned for native threads in later releases.
5java.util.concurrent (JSR 166): ExecutorService, thread pools, Future, locks, atomics, concurrent collectionsStop creating threads by hand; submit tasks to a pool.
7Fork/join (ForkJoinPool)Split a big job into small ones and use every core; work-stealing keeps them busy.
8CompletableFuture, parallel streamsCompose asynchronous steps instead of blocking on each Future.
9Flow (reactive streams interfaces)A standard contract for streams with back-pressure, used by reactive libraries.
19, 21Virtual threads: preview in 19 (JEP 425), final in 21 (JEP 444)Cheap threads managed by the JVM: one per blocking task, without a reactive rewrite.
21 onwardsStructured concurrency, previewing since 21 (JEP 453; fifth preview in 25, JEP 505; seventh preview in 27, JEP 533)Treat a group of related tasks as one unit: they finish, fail and cancel together.
24Virtual threads no longer pin on synchronized (JEP 491)Old synchronized code stops blocking the carrier thread.
25Scoped values, final (JEP 506)Share immutable data with child tasks; a safer replacement for many uses of ThreadLocal.

The full circle: the first JVMs scheduled threads themselves, Java then handed them to the operating system for twenty-five years, and virtual threads bring JVM scheduling back, this time on top of native threads. Release numbers come from each class's "Since" in the Java API documentation and from the JEPs.

Who steers Java: Sun, the JCP, Apache, Oracle and OpenJDK

Java is not only a language; it is a set of specifications, an open-source implementation, a test suite and a trademark, owned and steered by different groups. Knowing who decides what explains why the package names changed, why there are several JDKs, and why version numbers jumped.

WhenWhat happened
1991James Gosling, Mike Sheridan and Patrick Naughton start the language project at Sun Microsystems. It is first called Oak, after a tree outside Gosling’s office, then Green, then Java.
1995–96Java is released in May 1995; Java 1.0, the first public implementation, follows in 1996 with the promise of “write once, run anywhere”.
1998The Java Community Process (JCP) is set up: the formal way companies and individuals propose and agree changes to the platform through Java Specification Requests (JSRs).
2006–07Sun releases its virtual machine and compiler as free software under the GPL (November 2006) and nearly all of the class library in May 2007: the start of OpenJDK.
2007The Apache Software Foundation, building its own free Java (Apache Harmony), writes an open letter to Sun because it cannot get an acceptable licence for the Technology Compatibility Kit (TCK), the test suite an implementation must pass to call itself Java.
2010Oracle completes its acquisition of Sun on 27 January 2010. In April, Gosling leaves Oracle. In December, Apache resigns its seat on the JCP Executive Committee because Oracle will not license the TCK for Apache’s Java.
2011Apache Harmony is retired. Parts of it had been used for the core class library of Android, which later moved to OpenJDK (Android 7.0).
2017Oracle hands Java EE, the enterprise specifications, to the Eclipse Foundation. Because Oracle owns the Java trademark, it becomes Jakarta EE; Jakarta EE 9 (2020) moves the API packages from javax to jakarta.
2018 onwardsJava moves to a feature release every six months, with long-term-support releases (11, 17, 21, 25) between them. Since JDK 10, the OpenJDK JDK Project produces every feature release; changes are proposed as JDK Enhancement Proposals (JEPs).
2021In Google v. Oracle, over Android’s use of the Java APIs, the US Supreme Court rules 6–2 that Google’s use was fair use, without deciding whether APIs can be copyrighted.
NameWhat it is today
JSRA Java Specification Request: a formal proposal for a specification, reviewed in public and voted on by the JCP Executive Committee; a final JSR comes with a reference implementation and a TCK. The JCP itself is described by a JSR.
JEPA JDK Enhancement Proposal: how changes to the JDK itself are proposed, reviewed and tracked on openjdk.org; the list of JEPs serves as the roadmap for future releases.
OpenJDKThe free, open-source implementation of Java SE, where every JDK feature release is now produced; builds, commercial support and free updates are available from several organisations.
TCKThe compatibility test kit an implementation must pass before it can be called compatible.
Jakarta EEThe enterprise specifications (servlets, persistence and more), now run by the Eclipse Foundation; Spring Boot 3 and Apache Tomcat follow the jakarta package names (see Spring Boot).
ApacheThe Apache Software Foundation hosts many of the Java tools you use daily: Tomcat, Maven and Ant among them (see Build Tools).

Our view: the history is worth knowing because it still shows up in your code: javax versus jakarta imports, the choice of which JDK build to install, and how a feature you want reaches the language (a JEP, not a vote of users). The other view: for day-to-day work you need only the current LTS release, a supported OpenJDK build and the jakarta names; the politics behind them changes little about how you write Java.

The plethora of JDKs: which one to install

Java SE is a specification. OpenJDK is the open-source code that implements it. The JDK you download is somebody’s build of that code, usually with the builder’s own patches and backports, and usually tested against the compatibility kit (the TCK in the card above). Wikipedia gives the reason there are so many: because Oracle no longer releases updates for long-term-support releases under a permissive licence, other organisations publish their own builds. Most Linux distributions and package managers ship one too.

Our view: for most teams the build matters far less than staying on a supported LTS release and taking its quarterly updates; pick one free, TCK-tested build and use it everywhere, from laptops to containers. The other view: licensing and support terms do differ, and they change (Oracle’s have changed several times), so an organisation with a legal or compliance team may prefer a paid contract that makes one company answerable.

What happened to JNI, java.awt.Robot and MIDlets

Three pieces of Java that many engineers met early on, and what each became.

ThenWhat happenedToday
JNIThe Java Native Interface is how Java calls C, C++ and other native code. JEP 454 lists its “tedious artifacts”: native methods in Java, a C header file derived from them, and a C implementation that calls the library you want. And, as JEP 472 puts it, calling native code “can lead to arbitrary undefined behavior, including JVM crashes”. Project Panama’s Foreign Function & Memory (FFM) API was previewed in JDK 19, 20 and 21 (JEPs 424, 434, 442) and became final in JDK 22 (JEP 454), to call native libraries “without the brittleness and danger of JNI”. The jextract tool generates the Java bindings from a library’s C header files.Still there, but discouraged. Since JDK 24 (JEP 472), loading native code through JNI prints a warning unless native access is enabled, and FFM’s native calls are restricted in the same way. JEP 472 states that it is not a goal to deprecate or remove JNI, and many JDK classes, such as those for file I/O and audio, still use it inside. New code should use FFM.
Robotjava.awt.Robot, added in Java 1.3, generates real mouse and keyboard events in the operating system’s input queue, “for the purposes of test automation, self-running demos, and other applications where control of the mouse and keyboard is needed”. Robot.mouseMove really moves the pointer. Its documentation warns that platforms may restrict that access: on X Window systems without the XTEST extension, for example, creating a Robot fails.Still in the JDK (it is in the Java SE 25 API), and still used to test desktop apps. For web apps, browser-automation tools such as Playwright and Selenium do this job (see Testing). If you meant robots: leJOS replaced the firmware on LEGO Mindstorms bricks so that they could run Java, with versions for the RCX (2000), NXT (2007) and EV3 (2014); Robotics covers today’s tools.
MIDletsJava apps and games on feature phones. A MIDlet is an application for MIDP, the Mobile Information Device Profile of Java ME, which ran on the Connected Limited Device Configuration (CLDC). The first MIDP phones launched in April 2001. Apps came as a .jad description and a .jar, often downloaded over the air. By 2013 there were more than three billion Java ME phones, but the platform was already in decline as smartphones overtook feature phones. Android runs apps written in Java, but its runtime is very different from Java ME.Largely gone from phones; emulators keep the old games playable. Java’s smallest platform lives on as Java Card, in SIM and eSIM cards, bank cards, identity cards and passports. The browser applet, another early Java promise, was deprecated in JDK 9 (JEP 289), marked for removal in JDK 17 (JEP 398) and removed in JDK 26 (JEP 504).

What FFM looks like. One Java method handle replaces the native method, header file and C wrapper:

// calling C's strlen from Java with the FFM API (the example in JEP 454)
Linker linker = Linker.nativeLinker();
MethodHandle strlen = linker.downcallHandle(
    linker.defaultLookup().find("strlen").get(),
    FunctionDescriptor.of(JAVA_LONG, ADDRESS)
);
try (Arena arena = Arena.ofConfined()) {
    MemorySegment str = arena.allocateFrom("Hello");
    long len          = (long)strlen.invoke(str);    // 5
}

The JNI warning since JDK 24, as JEP 472 shows it. Adding --enable-native-access=<module> (or ALL-UNNAMED for code on the class path) at launch removes it:

WARNING: A restricted method in java.lang.System has been called
WARNING: System::load has been called by com.foo.Server in module com.foo (file:/path/to/com.foo.jar)
WARNING: Use --enable-native-access=com.foo to avoid a warning for callers in this module
WARNING: Restricted methods will be blocked in a future release unless native access is enabled

Our view: the pattern across all three is the same. Java keeps an old API working for years, adds a safer replacement, and then warns, deprecates and removes in public steps, each in a JEP you can read. The other view: some still see that pace as too slow. JNI took over twenty years to get a supported alternative, and the slow fading of applets and Java ME let other platforms take the browser and the phone.

Levels: what to expect

1 Foundation

  • Write classes, records, collections and streams
  • Use Optional and java.time correctly
  • Run and write JUnit tests

2 Practitioner

  • Use modern features (records, sealed types, pattern switch, virtual threads)
  • Handle concurrency safely with executors and CompletableFuture
  • Build with Gradle or Maven and manage dependencies

3 Senior

  • Tune the JVM for containers (memory, GC, startup)
  • Design APIs and module boundaries
  • Profile and fix performance problems

4 Expert

  • Lead platform upgrades across LTS releases
  • Understand JVM internals (JIT, GC, class loading)
  • Set the organisation's Java standards and libraries

Each level includes the ones before it. See Start here for what the levels mean.

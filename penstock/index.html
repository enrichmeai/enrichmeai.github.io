Runs your agents on your data, with receipts: headless, self-hosted, and the reference client for governed access. Every model call and tool invocation is written to an audit log the owner reads back.

Penstock runs your agents on your data, with receipts. A self-hosted agent runtime for the work that happens where no editor is open (CI hooks, chat commands, scheduled triage, webhooks) against your own internal systems, on models you choose: Copilot, Claude, OpenAI, or a local one. Three things define it. Where it runs: headless, not at a developer's keyboard. Whose hardware: yours; the transcript, the audit log and the credentials never leave the deployment. Whose data, provably: through the pod tool it reads a person's own data in a Cistern pod under rules that person wrote, and every access is receipted on their side, not ours. And it keeps the record its work deserves: every model call and every tool invocation is written to an audit log the owner reads back, in the app as well as on disk.

The idea01

The first thing to ask Cistern for something

It earns its place here by being the first thing to ask Cistern for something. An agent that wants a file has to present an identity of its own, receive only what was granted, be refused the rest, and leave a receipt behind. The shape of that exchange is the same whether the agent is writing code, reading a case file, or doing something nobody has built yet. Proving it on an agent we run ourselves is how the pattern gets settled before anyone else has to depend on it.

So there are two things in one repository, on purpose. An agent worth running, and the reference implementation of how a client should ask for someone else's data. Neither would prove much alone.

Two records, one job
On the agent's side The audit log

Every model call and every tool invocation, attributed to the authenticated user. What the agent did, in its own words, on the record.

On the owner's side The receipt

What it was allowed to read, under which rule, recorded by Cistern rather than by the agent. The half an agent cannot write for itself, and the half that stays true if the agent is wrong about what happened.

Next to JetBrains Air

JetBrains announced Air on 22 September 2026: agents inside the IDE, governed for which agent and model a developer may spend against. Penstock answers a different question: whose data an agent may touch while it works, and proof afterwards that it stayed inside the rules. The two fit together rather than compete.

Run it02

On your own machine, for now

The release carries a signed jar, a bill of materials and a multi-architecture image. Until it clears the stranger test, treat it as something to run locally rather than expose.

shellJava · Spring Boot
# the signed jar and its bill of materials are release assets
java -jar penstock-0.3.0.jar
# or as the agent inside JetBrains Air or Zed, over stdio
java -jar penstock-0.3.0.jar --acp
# or the multi-architecture image, bound to loopback
docker run --rm -p 127.0.0.1:8080:8080 \
  ghcr.io/enrichmeai/penstock:0.3.0

Since v0.2.0 the published image requires a login by default: set AGENT_AUTH_PASSWORD, read the generated one from the container logs, or opt out deliberately with AGENT_AUTH_ENABLED=false. Exact coordinates, configuration and the model options are in the release notes and the shipped docs: v0.3.0 →.

Status04

Where it stands

This project has a rule: nothing is announced before it has run on real infrastructure. So here is the honest state, not the roadmap in disguise.

Today
Open source: three surfaces (web, REST, streaming), pluggable models including a local one, and an audit log of every model and tool call, attributed to the authenticated user and readable from the app itself. live
Release
v0.3.0: a signed jar, a bill of materials, a multi-architecture image, and the Agent Client Protocol mode. live
Governed access
The pod tool has shipped. Penstock asks a Cistern pod for a file over plain HTTPS as its own principal, is refused outside its grant, and what it read is receipted on the owner's side. That is application-level consent: the receipt names the application, not the person who asked it. Per-user credentials are available by configuration for deployments that want attribution per person. live
In your IDE
Penstock speaks the Agent Client Protocol. Launched with --acp it runs as a selectable agent inside JetBrains Air or Zed, over stdio. The read-only tools and pod reads run unprompted; write_file, edit_file, shell, git and pod writes each go through the editor's own permission prompt first. Registration steps for both editors are in the shipped docs. v0.3.0
Later
The stranger test: deploy and use it from the published artifacts alone, following only the shipped docs. Cistern is held to it; Penstock has not cleared it yet, which is why this page says to run it locally. later

FAQ06

Can I put this on a network?

Not yet. It has not cleared the stranger test that Cistern is held to, so it is a thing to run on your own machine for now.

How is this different from JetBrains Air?

Air puts agents inside the IDE and governs which agent and model a developer may spend against. Penstock runs headless, on your hardware, and governs whose data an agent may touch, with a receipt afterwards. They fit together: Penstock speaks the Agent Client Protocol, so it can be one of the agents Air runs.

Can I run it inside my editor?

On main, yes: --acp speaks the Agent Client Protocol over stdio to JetBrains Air or Zed, with the read-only tools and the pod tool first. It is not in a release yet, so build from source or wait for the next tag.

Do I have to send anything to a model provider?

Models are pluggable and one of them is local. Whichever serves the call, the call is written to the audit log.

Do I need Cistern to use it?

No. It is an agent in its own right. The pod tool is what makes what the agent read receipted on the owner's side, and it is what turns the audit log into two records that can be checked against each other. See Cistern →

Why publish a critical finding rather than close it quietly?

Because there is no fix to apply. It waits on an upstream release that does not exist yet, and saying so is more useful than a clean dashboard.

Is any of it held back for a paid tier?

No. Apache 2.0, free for commercial use. Support, integration and hosting are how the company earns. COMMERCIAL.md →

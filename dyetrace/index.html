Find the journeys that started and never finished.

A Java library that gives each journey (a payment, a checkout, an account opening) one ID that survives every HTTP call, database row and Kafka message it passes through, and reports the journeys that stopped.

A journey starts in one service and ends in another. Tracing follows one request, and a trace ends wherever context is not carried: at a queue, a scheduled job, an outbox table. Dyetrace carries a journey ID across all of them, records the marks each journey reaches, and folds the events from every service together. A message lost in the middle produces no error and no failed span. Dyetrace notices that the journey never reached its end.

The idea01

One ID, all the way

The name comes from dye tracing in hydrology: put dye in the water at one point, and you learn where the water goes and where it stops.

The path of one journey
Where it enters Start
the journey

Give it an ID from a business key you already have, such as a payment reference, so support can find it later.

→↓
Every hop Carry
the ID

In a W3C baggage header on HTTP and Kafka, and in the database row when a message waits in an outbox.

→↓
Each service Mark
the way

Emit an event at each point that matters: order.created, payment.authorised, then complete or fail.

→↓
The tracker Notice
the silence

A journey still open after its target time is stuck. You see the last mark it reached, the service, and the traces it passed through.

Vendor-neutral by design: the core needs only the JDK, and the ID travels in an open header format. OpenTelemetry is one adapter behind a small extension interface; a different standard would be another adapter, and code that calls Dyetrace would not change.

When it helps02

Dyetrace, or tracing on its own?

Our view, by requirement. For many systems, distributed tracing (for example OpenTelemetry alone) is enough, and adding another library has a cost.

If this is true for youIt leans towardsWhy
Every step is a synchronous call inside one requestTracing aloneOne trace already covers the whole journey.
The journey crosses a queue, an outbox, a scheduled job or a retry laterDyetraceThe trace ends at that hop; the journey ID is carried on.
You must be told when something did not happen, such as a payment that never settledDyetraceTracing records what happened. The tracker reports journeys that are open past their target.
Your services already use OpenTelemetryEither; Dyetrace sits on topThe dyetrace-otel adapter puts the journey into OpenTelemetry baggage and onto spans, so nothing is replaced.
You need a journey tracker that survives restarts at production volume todayNot Dyetrace yetThe tracker keeps its state in memory, in one process (see Status).
Use it03

Three calls, in any Java application

Plain Java, Spring, Quarkus, Jakarta EE, MicroProfile: the API is the same, because the core depends on nothing beyond the JDK.

javaJava 17 or newer
// where the journey enters the system
try (JourneyScope journey = Dyetrace.start("payment", JourneyId.of("pay-" + paymentRef))) {
  Dyetrace.inject(request, JdkHttp.REQUEST_SETTER);
}
// in another service, perhaps after a queue
try (JourneyScope journey = Dyetrace.continueFrom(record.headers(), KafkaHeaders.GETTER)) {
  Dyetrace.mark("payment.authorised");
}
// where it ends
Dyetrace.complete();   // or Dyetrace.fail("declined")
dyetrace-core
The API, W3C baggage propagation, helpers for the JDK's own HTTP client and server, event JSON, and the journey tracker with Prometheus output. Depends on the JDK only.
dyetrace-otel
The journey in OpenTelemetry baggage, the journey ID on the current span, events as span events, and the trace ID on every journey event. Depends on opentelemetry-api; works with the OpenTelemetry Java agent.
dyetrace-slf4j
journey_id and journey_type in the logging MDC, so every log line can be found by journey.
dyetrace-servlet
A filter for any Jakarta Servlet 6 container: Tomcat, Jetty, Undertow, Spring MVC, Open Liberty.
dyetrace-kafka
Kafka header propagation, a producer interceptor that adds the journey to every record, and a sink that publishes journey events to a topic.

Adapters install themselves when their jar is on the classpath. A failing adapter is logged and skipped: observing a journey never breaks it.

The demo04

A payment journey you can break on purpose

Six services on a local kind cluster, in the same repository: three plain Java services with no framework, one Spring Boot service with Postgres and an outbox, a journey monitor and a load generator. Traced by the OpenTelemetry agent, with Jaeger, Prometheus and Grafana.

You need
A JDK 17 or newer, Maven 3.9 or newer, Docker, kind and kubectl, and about 4 GB of memory for Docker. No Kubernetes? The same demo runs with Docker Compose.
The proof
make verify runs five acceptance checks against the running demo: one journey followed across all four services and two linked traces; a lost message reported stuck where it stopped; a flaky dependency that still completes; a decline recorded as a failure; a slow step that is stuck while over target and clears once it completes.
Where to look
The journey monitor lists stuck journeys and links each to its traces in Jaeger. Grafana shows the journey view above the component view, so the difference is on one screen.
Status05

Where it stands today

What exists, its limits, and what is planned.

Released
Nothing yet. The library and the demo are on main; build them with Maven. There is no hosted CI: make check runs every gate on your own machine.
Its limits
The journey tracker keeps its state in memory, in one process: right for the demo, not yet for production. With the OpenTelemetry agent, the Kafka event sink's own sends show up as extra spans in application traces. The demo's Docker Compose and kind paths are both in the repository: run make verify for kind, or make verify MODE=compose for Docker Compose.
Planned
A first release on Maven Central, and a tracker store that survives restarts. planned
